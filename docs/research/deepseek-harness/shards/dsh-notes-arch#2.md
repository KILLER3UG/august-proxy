# deepseek-harness / dsh-notes-arch#2

## Shard shape

This shard is the archived **architecture** notebook of the deepseek-harness (DSH) repository for the window 2026-08-06 → 2026-09-17: 88 note slugs, 260 tracked files, every file under `.agents/notes/archived/architecture/`. Each note exists as a triad — an English decision record (`.md`), a Chinese translation (`.zh.md`) and a bilingual-pairing consistency record (`.i18n.yaml` that pins the git blob hash of both sides) — so the shard is 86 English notes, 87 Chinese notes and 87 pairing records, plus one note present only in Chinese and one present only as a pairing record. The English notes follow one house shape: front-matter `Status:`/`Archived:` (and sometimes `Superseded:`), then `## Problem`, `## Decision`, `## Consequences`, `## Alternatives considered`, sometimes with `## Verification`/`## Testing` and tables of behaviour. They are **decision records, not documentation**: each one states a mechanism, the reason the mechanism was chosen, and the alternatives that were rejected — which is why this shard is unusually good source material for a harness-design review, because every line was written to defend a choice against a named counter-example.

Thematically the shard is the DSH **client/host event spine and its persistence**, not the model loop: session log format and write batching, per-session projection caches, packed chunk-row transport, conversation-node assembly for the Trajectory view, live assistant stream frames versus durable settlements, remote event delivery with an allowlist, the skill registry's scope layering, sub-agent provider ownership, subprocess containment, the inspector and the Web/Desktop shells, plugin extension slots, and the release/install machinery. What it contributes to an agent-harness review is therefore mostly *infrastructure that surrounds the model*: how a durable event log is shaped, how a UI is fed incrementally without polluting the log, how a tool registry is layered by scope, how a deployment's capabilities are separated from a session's tool surface, and how a note format keeps two languages and a hash manifest in step. The lenses the brief asks about (prompt construction, compaction, memory, model adaptation) appear here only at the edges — as the *system-prompt section order allocation*, the *pi-ai route's per-model reasoning/modality declarations*, and the *session log's embedded assistant stream* — because DSH's own compaction, memory and model-adaptation notes live in other shards.

### .agents/notes/archived/architecture/2026-08-06-web-shell-dist-chunk-layout.md
- Purpose: Status: implemented. Splits the apps/web shell bundle into an `index` chunk and a cache-stable `vendor` chunk and sorts `dist/assets/` into `langs/` and `fonts/`.
- Key abstractions: `VENDOR_PACKAGES` (exact npm names, no regexes), `BOOT_GRAMMAR_FILES`, `FONT_EXTENSIONS`, `manualChunks`, `chunkFileNames`/`assetFileNames`.
- Data flow: Vite splits on membership; the bundler emits index via `<script>` and vendor via `<link rel="modulepreload">` so both fetch in parallel; fonts load only when a formula renders.
- Non-obvious design decisions: The list is of packages workspace code *imports directly* — transitive deps follow automatically by rollup colouring; every vendor member must be react-free because rollup folds a module shared with the entry into the manual chunk and would drag the single react copy into vendor.
- Edge cases / failure handling: Grammar chunks are detected by `moduleIds` membership, not `facadeModuleId`, because embedded grammars (php/ruby/mdx) have facade-less shared chunks; a stale `BOOT_GRAMMAR_FILES` silently lands a grammar in index, visible only to the dist audit.
- Surprising: The audit tool `scripts/attribute-chunk-bytes.mjs` does sourcemap VLQ byte attribution to prove vendor holds no workspace bytes and react sits entirely in index.

### .agents/notes/archived/architecture/2026-08-07-shared-feedback-telemetry-user-id.md
- Purpose: Status: implemented. Extracts the anonymous UUID into `@deepseek-ai/dsh-anonymous-user-id` so telemetry, `/feedback` and direct DeepSeek requests share one identity.
- Key abstractions: `getOrCreateAnonymousUserId()`, the `$DSH_HOME/.anonymous-user-id` storage contract.
- Data flow: OTel uses it as Resource `user.id`; the feedback acknowledgement prints it on a second line; the DeepSeek adapter sends `x-deepseek-harness-user-id`.
- Non-obvious design decisions: The helper was deliberately kept inside the OTel backend until a *second real consumer* existed; importing it from `session-telemetry-otel` would create a dependency cycle when telemetry mounts feedback export.
- Edge cases / failure handling: Invalid feedback is rejected before the id is resolved, and the DeepSeek adapter resolves it only after credentials succeed, so neither an empty command nor a credential failure creates the file.
- Surprising: Three unrelated surfaces (exported traces, an acknowledgement line, an outbound HTTP header) are bound by one file; a missing package would silently make three reports uncorrelatable.

### .agents/notes/archived/architecture/2026-08-08-bounded-session-persistence-write-batching.md
- Purpose: Status: implemented. Coalesces durable session-event appends into a fixed 200 ms window so a burst of events becomes one JSONL append.
- Key abstractions: `LIVE_WRITE_BATCH_MAX_DELAY_MS` (200), per-handle pending array, single-flight drain, the handle's mutation chain, `session/flush` quiescence barrier.
- Data flow: An event is copied on admission into the handle's pending array; the first event of an idle buffer arms one fixed timer that later events join *without* resetting; the deadline drains the pending prefix through the handle's serialising mutation chain.
- Non-obvious design decisions: Bounded coalescing, not debounce — a fixed window from the *first* pending event gives a real upper bound, whereas debouncing from the latest event lets a streaming response postpone its first write indefinitely.
- Edge cases / failure handling: A failed background drain keeps its whole batch in order ahead of newer events, reports once, and *pauses* the automatic timer; the next explicit drain retries and surfaces the repeat to its caller, which avoids a timer-driven failure loop.
- Surprising: The batching lives on the *provider's handle*, not in a shared provider-neutral controller — a first iteration shipped the shared controller and it was reverted because the handle's mutation chain already serialised writes.

### .agents/notes/archived/architecture/2026-08-08-client-tool-presentation-ownership.md
- Purpose: Status: implemented. Moves tool-call presentation out of the conversation view into a dedicated `dsh-client-ui-tool` package, splitting data assembly from rendering.
- Key abstractions: `ToolCallBlock` with recursive `subCalls`, the `tool.call.toolview` keyed child slot, `GenericToolCard` fallback, `ChatNodeSeat`, the `tool-call` conversation node.
- Data flow: Session events → Tool Definition (call/result pairing + Code Dispatch topology) → one `tool-call` Chat Node → `ChatView` places a generic seat → `ToolCallTree` recurses root/subCalls → per-level keyed dispatch by wire tool name → atomic renderer or generic fallback.
- Non-obvious design decisions: A business tool plugin receives a `ToolCallBlock` and must not read Session, Context or the assembler; an atomic renderer understands *one* call and does not know whether it is root or child, so recursion lives once in `ToolCallTree`.
- Edge cases / failure handling: If `ui-tool` is absent, conversation data assembly stays valid and the generic fallback renders — presentation is optional, data is not; a plugin that throws cannot be the reason the conversation fails.
- Surprising: The row model keeps only `bodyRaw`; argument pretty-printing happens only while an expanded generic input section is visible, so a collapsed row retains no second copy of the arguments.

### .agents/notes/archived/architecture/2026-08-08-per-preset-standing-mounts.md
- Purpose: Status: implemented. Makes a preset one composition per *process* mounted under a synthetic standing scope, instead of one per session.
- Key abstractions: `bindScopeParent(agentKey, standingKey)`, the `dsh-scope` parent chain (`agent → preset → global`), scoped upward-only dispatch, `ScopeParentBinding`.
- Data flow: The roster mounts a preset once under a standing scope; each agent joins by binding its scope key to the mount's; registration views walk the parent chain with nearest shadowing farthest; listeners tagged with an ancestor of the carrier key are admitted.
- Non-obvious design decisions: Sibling presets' listeners stay deaf because scoped dispatch admits *upward only*; a shared realm *label* was not an option because `provide()` throws on a second registration under the same realm symbol — labels pool the realm, never the instance.
- Edge cases / failure handling: The standing mount hangs off the service's untraced `selfCtx`; a traceable proxy rebinds `this.ctx` to the caller with a shadow, so reflect resolution minted from it fails to find a service the entry's own `inject` declares.
- Surprising: Per-session mounts caused *silent* degradation elsewhere — cold `session.history` found no presenters (every card degraded to the generic renderer, indistinguishable from "tool has no presenter") and the projections block dropped preset-registered keys, which clients read as capability absence and *clear* the row.

### .agents/notes/archived/architecture/2026-08-09-cordis-event-walk-backstop.md
- Purpose: Status: implemented. Extends the independent AST backstop from cordis *services* to cordis *events*, and deepens both scans to the full package source tree.
- Key abstractions: `scripts/cordis-walk.ts`, `eventNameList`, `EVENT_WALK_EXEMPTIONS` (keyed by full event name), `walkPartitionProblems(input, maps)`.
- Data flow: An independent `ts.createSourceFile` walk enumerates every `declare module 'cordis'` block and every `interface Events` member; the generator renders host events; the partition check demands every declared event either renders or names itself in the exemption map.
- Non-obvious design decisions: The backstop must fail *independently* of the Typert projection, so the scan deliberately shares no machinery with it — a Typert reachability bug is exactly what the backstop exists to catch.
- Edge cases / failure handling: Fail-closed in both directions — an unexempted invisible event, an exemption for an event that renders, and an exemption no merge declares are all hard errors; exemptions are keyed by event name, not scope, because client and host events share scopes.
- Surprising: 12 declared events (`slash/input-*`, `theme/change`, `locale/change`, `*/changed`) and 13 client-face Context keys were documented nowhere generated and nothing would ever have noticed a thirteenth.

### .agents/notes/archived/architecture/2026-08-09-headless-direct-core-entry-point.md
- Purpose: Status: implemented. Defines the `headless` profile as a direct core entry point: one local task, assistant text on stdout, success-sensitive exit code, no listening port.
- Key abstractions: `headless-runner`, `ctx.agentDefaultModel.currentSelection()`, `ctx.agents.create`, `ctx.sessions.flush`, `AgentDefaultModelConfig`, the `dsh-headless` bundle.
- Data flow: After Loader settlement the runner reads the default model selection, creates a persisted Agent, installs the `ModelSelection` in the Agent scope, waits for quiescence, anchors the Session sequence, submits one user message, waits again, flushes sessions, folds its durable event interval for the last non-empty assistant text and the final `turn/end` reason.
- Non-obvious design decisions: The same transport-independent default model service is shared with the Web path so one deployment has one answer; a separate provider/model config for headless would give two.
- Edge cases / failure handling: Exit 0 exactly when the reason is `completed`; a terminal `error` reason writes its durable code and message to stderr and exits 1; flush-before-exit ordering is pinned because completion must not observe incomplete state.
- Surprising: The shipped `headless` tree contains no browser Connection, HTTP server or Web runtime — a one-shot local task deliberately depends on no transport tree at all.

### .agents/notes/archived/architecture/2026-08-09-layered-skill-registry.md
- Purpose: Status: implemented. Makes the skill registry a host-held singleton layered per scope, mirroring the tools registry, instead of a per-preset realm.
- Key abstractions: `SkillRegistry` holding `ScopedLayers<SkillLayer>`, `registerProvider()`, `SkillViewOptions` (the viewing scope), discovery caches keyed by scope chain + revision counter.
- Data flow: A provider registers into the layer of the *calling* context's scope; reads merge the global layer with the scope's chain.
- Non-obvious design decisions: The nearest layer wins a duplicate name *outright* and rank only decides duplicates **within one layer** — rank-pooling across layers was rejected because a later-installed repository plugin could silently displace a preset's same-named skill on a registration-order tiebreak.
- Edge cases / failure handling: Cross-layer shadowing is silent (logged nowhere), matching the tools registry's convention; the registry exposes no API to inspect shadowed definitions.
- Surprising: The original per-preset realm registry made the gateway's skill listing depend on a live agent — a cold session's `/` popup had *no registry to read at all* — and a repository plugin's `inject: ['skills']` wrapper waited forever, hanging the e2e.

### .agents/notes/archived/architecture/2026-08-10-message-feedback-sidecar.md
- Purpose: Status: implemented. Stores editable per-message feedback in a storage-domain sidecar row per session, outside the canonical session log and outside telemetry.
- Key abstractions: `ctx.messageFeedback`, the sidecar row, the session header identity `{createdAt, cwd}`, per-item opaque version + `ifVersion`, per-session mutation queue, `maxNoteBytes` (8192 in the web bundle).
- Data flow: `put` inspects the observed log (live owner in memory, else a persistence read handle) for a non-empty append-origin `assistant/message`, flushes the target log past a durability barrier, re-reads it physically from sequence zero, re-checks identity and target, then writes the sidecar row.
- Non-obvious design decisions: A row is bound to the session *header identity*, not just the id, so a recreated id cannot inherit stale feedback; the version comparison is strict even when the desired value already matches, so a stale request cannot cross an ABA value cycle.
- Edge cases / failure handling: The storage-domain API has no cross-process conditional write, so the implementation claims no cross-process linearizability; a cold `stat()` preflight classifies definite absence while a read failure for a catalogued session stays an infrastructure failure.
- Surprising: There is no fake deletion cascade — `session/disposed` means detach, not durable deletion, so orphan sidecar rows can remain and are neutralised only by the differing header identity.

### .agents/notes/archived/architecture/2026-08-10-product-subagent-providers-in-shared-host.md
- Purpose: Status: implemented. Places product sub-agent providers (Codex, Claude Code) in the shared profile host rather than inside agent presets.
- Key abstractions: `ctx.subagents` (process registry), provider Bundle patches, named provider instances (`providerName`), the preset's ordinary `dsh-tool-subagent` rows.
- Data flow: A profile that opts in installs the provider Bundle; the patch mounts the default instance on the host plane; agent presets independently contribute ordinary subagent tool rows naming exactly the instances one agent needs.
- Non-obvious design decisions: Two independent facts are kept apart — *availability* (deployment) and *exposure* (model-visible tool) — so loading a provider never starts or authenticates a product, while the tool grant stays per preset.
- Edge cases / failure handling: Provider names are unique within the host, so mounting inside every preset would collide; a profile that omits a provider carries no package or module-loading footprint, and loading a provider starts no product process, login, model call or product home.
- Surprising: The product process starts on the *first actual delegation call*, not at load — registration is dormant, which is what lets a preset be edited without restarting anything.

### .agents/notes/archived/architecture/2026-08-10-remote-event-delivery.md
- Purpose: Status: implemented. Gives the client one event-subscription verb, `ctx.remote.$on(event, listener)`, with allowlist-driven verbatim forwarding of host cordis events.
- Key abstractions: `API_REMOTE_FORWARDED_EVENTS` (the single allowlist, in `packages/api/remotes/src/remote-events.ts`), `TypertForwardableEvent`/`TypertForwardableEventEntry` type projections, the `$events` gateway stream, `emit` vs `waterfall` modes, `$events/result`.
- Data flow: The host source installs every allowlist listener synchronously when a client opens `$events`; the gateway yields a `ready` item before iterating the source; `ConnectionController` publishes `connected` only after that item, so baseline reads cannot race ahead of incremental listeners.
- Non-obvious design decisions: There is no second event-signature table — owner packages put their cordis `Events` declarations in client-safe `./types` exports so both faces read *one* declaration, and verbatim correspondence holds by construction rather than by a proof; the allowlist is `satisfies readonly TypertForwardableEventEntry[]`, so the name, the mode and the signature shape are checked at compile time.
- Edge cases / failure handling: A physical mux disconnect ends the logical stream with `RemoteStreamCarrierError` and the connection reopens after backoff; ordinary events are **not replayed**, so any state needing recovery must provide a query, cursor or opening baseline; every argument is checked with `isJsonValue` before queueing and a bad one fails loudly at emit.
- Surprising: The consumer contract exposes only the subscription verb — `TypertClientRemote` has no producer operation, so a business plugin can subscribe to a host event but can never synthesise one; and `apps/web` browser e2e files typecheck in the *host* program, because driving a browser does not place a file in the client TypeScript program.

### .agents/notes/archived/architecture/2026-08-10-unary-apiproxy-remote-migration.md
- Purpose: Status: implemented. Moves simple unary browser operations off the host API Proxy onto their owning business Remote services and deletes the API Proxy service.
- Key abstractions: the shared agent/session resolver, `TypertRemoteService`/`@Remote`, `session-log-export`'s exact Fetch route, `dsh-native-command`.
- Data flow: A table maps every former API Proxy operation to its new owner (`sessionTitle/rename`, `commands/list`, `llm/listProviders`, `session/modelCatalog`, `credentials/*`, `settings/*`, `agentPresets/*`, `subagents/interruptByParent`, `workspace/*`, `skills/list`, `fileReferences/list`, `session/openWorkspacePath`).
- Non-obvious design decisions: The shared resolver remains the authority for anything that accepts an agent or session — it reuses live agents, resumes cold sessions, deduplicates concurrent resumes and rejects subagent-owned identities; the skill listing path must *not* activate an agent, so it uses a live agent only when one already exists.
- Edge cases / failure handling: A lookup refusal raises a `RemoteError` carrying its own code (`session/not-found`, `session/agent-busy`) which the gateway encodes unchanged, so a refusal stays distinguishable from `gateway/internal`; session export is a registered Fetch route because the browser download manager consumes a streamed response, not a JSON result.
- Surprising: `host.describe` was deleted rather than kept: the generation-ready frame now carries only the stable host home, and each capability-owning page queries its own domain when shown — one bootstrap call no longer couples connection readiness to unrelated business facts.

### .agents/notes/archived/architecture/2026-08-11-cmdline-seam-trim.md
- Purpose: Status: implemented. Deletes three command-line seams that were wider than their consumers needed: a vendored row-activation state machine, a vendored config-resolver protocol symbol and launcher app-knowledge.
- Key abstractions: `Entry.enableRuntime`/`enableRow` (deleted), `EntryConfigResolver` (deleted), `EntryGroup.key` (the existing tree-carrier marker), `ctx.appExit`.
- Data flow: The reload chain becomes unconditional — `dsh-web-app` mounts `client-hmr` always and `--dev`, the web `mode` config, the mode-forked prompt contract and `DSH_WEB_MODE` are all deleted; the launcher recognises no app row.
- Non-obvious design decisions: Without a rebuild watcher rewriting client bundles, the chain polls unchanged files and stays idle, so the always-on row costs one stat-poll interval — cheaper than the conditional machinery it replaced.
- Edge cases / failure handling: SIGTERM now exits 0 on every surface (SIGINT stays 130) because the launcher cannot know whether the app considered its work complete; one-shot surfaces still mount the config-watch rows they previously skipped.
- Surprising: The old SIGTERM 143 depended on the launcher *naming* the headless row; removing app knowledge from the launcher also removed a hard-coded exit-code contract that a supervisor could have read as failure.

### .agents/notes/archived/architecture/2026-08-11-loader-entry-disabled-interpolation.md
- Purpose: Status: implemented. Makes the loader interpolate the entry `disabled` field, so a row can gate itself on platform or environment.
- Key abstractions: `!!js` interpolation in `vendor/loader/src/config/entry.ts`, the `disabled`-only interpolation rule, `verify-cordis-config`.
- Data flow: At every mount decision a `!!js` expression evaluates against the loader context; the raw node stays in the options so write-back keeps the `!!js` form; the base bundle's `cordis.patch.yml` gates `bash-sandbox`/`tool-bash` and their pwsh twins on `process.platform === 'win32'`.
- Non-obvious design decisions: The condition lives on the row it governs, which is why the launcher's separate `windows.cordis.patch.yml` platform layer could be deleted entirely; `id`, `name`, `group` and `inject` stay literal.
- Edge cases / failure handling: Postmortem 0002's hazard is closed by *evaluation* rather than prohibition — `disabled: !!js ...` used to stay a truthy expression object and disable the row everywhere; `verify-cordis-config` now allows expressions only in `disabled`.
- Surprising: The bug was a silent duplication: the platform layer disabled `tool-bash` on win32 while the presets (composed last) re-enabled the same-id row, so the session silently had both `tool-bash` and `tool-pwsh` at once.

### .agents/notes/archived/architecture/2026-08-11-trajectory-conversation-context-assembly.md
- Purpose: Status: implemented. Rebuilds the Trajectory view on the shared Conversation assembler with target-owned definitions, instead of a second independent session-history fold.
- Key abstractions: `ConversationNodeAssembler`, `Conversation Definitions`, the `trajectory` View Builder, `Session.views`, context identities (`turn:step`, root call id, compaction id, event seq), `Location`, `Reader` dependencies.
- Data flow: Session owns one contiguous event window and publishes both chat and trajectory snapshots; the assembler matches events to definitions by exact business id, folds state in forward event order, and the builder converts materialised nodes into the ledger's `eventNodes`, requests, tool schemas, running calls and location map.
- Non-obvious design decisions: The two views share only the assembler's exact-id matching, ordered matches, location facts, reader dependencies, publication scheduling and replace/prepend/append lifecycle — *not* the final node payloads, because sharing them would couple each view to the union of both views' requirements.
- Edge cases / failure handling: A reader miss while older history remains records a window-gap dependency, and a later prepend replays the affected chain in forward event order, so historical page direction cannot permanently misclassify a message; legacy events lacking a required correlation id are ignored by that definition rather than merged into an `undefined` context.
- Surprising: The complexity table is explicit: an older-page prepend costs `O(P × D + M)` instead of restarting over the loaded window, and the note refuses to claim end-to-end `O(1)` publication — it claims `O(C log C)` and nothing more.

### .agents/notes/archived/architecture/2026-08-15-packed-session-history-transport.md
- Purpose: Status: implemented. Carries packed chunk rows through session history so a long delta run costs one wire record instead of one per token.
- Key abstractions: `SessionHistoryRecord` (`{type:'event'|'chunks'}`), `ChunkRowEvent` (`chunkrow/text-chunks|reasoning-chunks|tool-call-chunks`), the shared lossless codec, `SessionEventLike`, the `RemoteJournalStream` inclusive sequence ranges.
- Data flow: The host selects the page from *logical* events, then packs; the generated remote decoder validates the response; the journal checks page continuity, pagination joins, reconnect repair, duplicates, partial overlaps and live-event dedup before publishing; the client narrows the records to entries without allocating replacements, and the assemblers reject a packed `start()`.
- Non-obvious design decisions: The outer discriminator selects the record class *without* interpreting the detailed chunk kind, and the shared `.event` field avoids a second payload name; the page is cut from logical events so message-aligned pagination stays independent of the physical persistence layout.
- Edge cases / failure handling: A row covers `[seq, seq + memberCount - 1]` so packed records create neither false gaps nor hidden overlaps; cold persisted history is still decoded into the full logical event array before the host repacks, so this decision improves transport and browser work, not the host's cold-read decode memory.
- Surprising: Measured on a production-sized private sample: 416,756 logical events became 696 top-level records, 90.8% less uncompressed JSON and 73.2% less Brotli, with client parse/validate/fold dropping from 4,682 ms to 276 ms — and the note says the figures describe that sample, not a protocol guarantee.

### .agents/notes/archived/architecture/2026-08-19-projection-cache-per-session-files.md
- Purpose: Status: implemented. Replaces the single global `session_projcache.json` with one version-stamped document per session under a `per-record` storage domain.
- Key abstractions: the `session_projcache` domain, `per-record` layout, `cachedSnapshot(meta)`, `compatibleVersions` (3–6 with current 7), the `{createdAt, cwd, isSeeded, inheritedEventCount}` record identity.
- Data flow: Reads are synchronous in-memory lookups (zero I/O); writes queue on the domain's per-unit write chain and mutate memory only after durability; the json backend creates its tree owner-only (`0o700`).
- Non-obvious design decisions: The cache never consults the persistence layer — no `locate`, no dependency on which backend is mounted — because the directory *is* the state in the `per-record` model, unlike `single`'s memory-authoritative whole-file publish.
- Edge cases / failure handling: A malformed or stale-version document reads as an absent record at open, so one bad file never bricks the cache and a schema bump discards stale sessions per record; the legacy whole-unit bootstrap is suppressed for the whole unit if any new-layout path exists, even an unreadable one.
- Surprising: The cache runs **no cold-refold ladder** — a consumer needing a guaranteed cold snapshot refolds from the log itself, because reading the log belongs to the persistence layer, not the cache.

### .agents/notes/archived/architecture/2026-08-19-session-projection-state-and-client-views.md
- Purpose: Status: implemented. Splits projection *host state* from *client-visible values* into two independently typed, separately validated tables.
- Key abstractions: `SessionProjectionStateMap` (merge-extensible, every definition supplies a `stateSchema`), `SessionProjectionMap` (client values), `wire.viewSchema`/`wire.view`, `stateOf(session, key)`.
- Data flow: Cached rows are validated against the state schema before they seed a fold; every unit's state is checkpointed; snapshot APIs enumerate only definitions that have a `wire`, so internal state cannot reach a client payload by omission.
- Non-obvious design decisions: The `persist` opt-in was removed — a unit must not be able to silently skip the durable cache, because the savings (one small row per session) never justify the asymmetry or the `stateVersion` confusion it invites.
- Edge cases / failure handling: Malformed cached state cannot seed a view checkpoint; restore rejects it and the cache's full-read fallback rebuilds from the log; `stateOf` returns a *borrowed* readonly reference, and cloning every host read was rejected as work without a boundary.
- Surprising: One type table had been describing two different values (the internal fold state and the client `view`); a unit may now expose a compact compatibility-preserving client value while keeping richer host state.

### .agents/notes/archived/architecture/2026-08-21-session-log-read-intent.md
- Purpose: Status: implemented. Replaces the all-purpose `Session.events` accessor with three cost-specific read operations.
- Key abstractions: `seq` (constant-time length), `eventAt(seq)` (constant-time single event), `snapshotEvents(fromSeq?, toSeqExclusive?)` (explicit materialisation), session projections.
- Data flow: The complete snapshot is cached until an append invalidates it; a range snapshot copies only the selected references and is *not* cached, because arbitrary range caching would retain unbounded arrays and need an eviction policy.
- Non-obvious design decisions: Sequence parameters are log positions, not `Array.prototype.slice` offsets from the end — the array-like API was the trap that made a cheap-looking read expensive.
- Edge cases / failure handling: Previously returned snapshots stay stable because accepted events are immutable and a snapshot array never grows after append; recurring domain state (e.g. the selected preset) is read from a projection instead of rescanning live history.
- Surprising: The problem was not the copy but the *cache*: a full snapshot can be cached, but streaming invalidates that cache on every event, so a caller needing only the log length repeatedly copied millions of references.

### .agents/notes/archived/architecture/2026-08-25-sparse-first-party-prompt-section-orders.md
- Purpose: Status: implemented. Centralises the ordering of first-party system-prompt sections in one live service instead of letting every package declare its own numeric literal.
- Key abstractions: `ctx.systemPrompt.getSectionOrder(name)` / `getContextOrder(name)`, `SystemPrompt.assemble()`, the named allocation table, `TypertRemoteEventSelection`-style type-level constraint.
- Data flow: Every repository contributor asks the live service for its typed placement; `assemble()` sorts by `order` and breaks equal orders by code-unit section name; dynamic prompt contexts use a separate context allocation and tool schemas a separate `toolOrder` sequence.
- Non-obvious design decisions: Adjacent allocated section values differ by at least ten, so a future insertion has room; equal orders are broken by *name* because plugin activation order is not a prompt-order decision and varies across valid compositions.
- Edge cases / failure handling: Scoped `deployment:persona` shadows the global section *by name* before sorting, so a scoped persona keeps the same placement; the note is explicit that an external plugin may pick any finite number and equal external ranks remain supported and deterministic.
- Surprising: Renumbering alone does not change model text, but moving Bash/PowerShell ahead of filesystem guidance does — and the note flags that this "may invalidate provider prefix reuse from the first moved paragraph", the one place in the shard where provider prompt caching is discussed at all.

### .agents/notes/archived/architecture/2026-08-26-preset-health-resolves-rows.md
- Purpose: Status: implemented. Makes preset health prove that each row *can resolve*, so a healthy roster row means "will compose".
- Key abstractions: `discoverPresets(roots, harnessBase)`, `scanRoot(root, harnessBase)`, `src/specifier.ts` (the one classifier), `resolveMountable`, `presetOptions`, `mountDetail`, `CompositionStamp`.

- Edge cases / failure handling: Hits replay their missing-family observations because an initialisation request can recur after document font collection starts; worker termination releases both the cache and the engine memory; installing or replacing fonts requires a provider reload, and a file changed since indexing can fail a later conversion.
- Surprising: The image-resolution cap is explicitly *not* an engine memory cap — LibreOffice can still decode full-resolution source images, load large font collections or exhaust its build-time WASM memory maximum.

### .agents/notes/archived/architecture/2026-09-11-windows-directory-installation.md
- Purpose: Status: implemented. Replaces the copy-based Windows installation with a staged, two-rename directory transaction.
- Key abstractions: the NSIS adapter retaining electron-builder's installer, signed uninstaller, registration, shortcuts and updater cache; `installer-directories.nsh` staging beside the destination; the pinned embedded 7-Zip command-line tool.
- Data flow: The complete new application is staged beside the destination *before* the old application stops; the transaction renames the old directory to a unique backup, renames the new one to the destination, and removes the backup before launch; both renames stay on the destination volume.
- Non-obvious design decisions: The staging tool is chosen for its *exit status*: `Nsis7z::Extract` can retain an old file without setting the NSIS error flag, so a mixed installation would look like success; deleting the old version before extraction was rejected because a corrupt archive would remove the only usable version first.
- Edge cases / failure handling: A nonzero extraction exit leaves the old application intact; a failed promotion restores the renamed old directory, and if another process prevents restoration the complete backup remains available; the installer explicitly does not claim crash-atomic replacement across two renames.
- Surprising: The measured motivation is plain: a 616,701,792-byte, 11,735-file payload took 101.2 / 79.2 / 114.4 seconds through extract, copy and delete, with the copy alone accounting for 70.3 / 56.7 / 85.3 seconds — so the fix removes the copy phase entirely rather than optimising it.

## Ideas worth stealing

- **One live service owns the ORDER of every first-party prompt section — no numeric literals in packages** - `.agents/notes/archived/architecture/2026-08-25-sparse-first-party-prompt-section-orders.md:18` - `@deepseek-ai/dsh-system-prompt` keeps private named allocations; every contributor asks `ctx.systemPrompt.getSectionOrder(name)` for its typed placement, values are unique integers **at least ten apart**, and equal orders break by code-unit *name* rather than by plugin activation order. August's system prompt is assembled from many places, so a collision there is silent and produces a non-deterministic prompt; a single allocator with a spacing rule plus a name tie-break makes the order deterministic *and* gives future insertions room, and the note proves the point: an earlier local fix did not stop the next package from reusing the value.
- **An identity field may only NARROW — a stream delta can never erase what the first delta established** - `.agents/notes/archived/architecture/2026-09-01-streamed-tool-call-identity.md:16` - `acceptIdentity` accepts only a non-empty string for a tool call's `id`/`name`; `undefined`, `null`, `''` and non-strings leave the established value in place, and the wire type is *widened* to admit `null` so the guard is load-bearing rather than speculative. August's tool-call accumulator has exactly this shape, and the blast radius here is the reason it matters: an empty identity was written verbatim into the durable log, so a session was writable and no longer loadable.
- **Make an over-budget response a durable, only-forwarding SURFACE REDUCTION instead of a per-request projection** - `.agents/notes/archived/architecture/2026-09-02-durable-image-offload.md:18` and `:22` - the offload of an image occurrence is recorded as a `surfaceOp: replace` node in the same log that compaction uses, a replacement **never reverts**, and the adapter *projects* the budget rather than deciding it (it fails the attempt with `IMAGE_OFFLOAD_REQUIRED` and a count). This is the direct fix for August's "model-visible input must be reconstructable from the session log" invariant: the old arithmetic was recomputed per request, so an inline fallback or a route switch silently moved the prefix and invalidated the provider cache — here the prefix only advances and the log alone determines what was sent.
- **Lossless packing on the wire: one record per delta run, with the page cut from LOGICAL events** - `.agents/notes/archived/architecture/2026-08-15-packed-session-history-transport.md:16` and `:28` - a history page carries `SessionHistoryRecord[]` where consecutive same-block assistant deltas become one `{type:'chunks'}` row; the explicit outer discriminator selects the record class without interpreting the chunk kind, the page is selected from logical events *before* packing, and the journal validates inclusive logical ranges so packed records create neither false gaps nor hidden overlaps. Measured: 416,756 logical events → 696 top-level records, 90.8% less JSON, and client parse/validate/fold from 4,682 ms to 276 ms. August's transcript replay and its SSE history feed are the same shape of problem.
- **Live stream frames are NOT durable events: one settlement owns the durable stream, frames are branded and revisioned** - `.agents/notes/archived/architecture/2026-08-31-live-assistant-stream-frames.md:14` - `agent/assistant-stream` frames carry a branded `LlmAttemptId` and a per-lifecycle revision; a settlement arriving after an active opening is owned by that attempt only when its seq follows `startedAfterSeq` and its turn/step match, and it stays staged until the matching end index/type/seq arrive. August needs exactly this separation: its "one run of tool calls is ONE line in the transcript" rule and its live spinner both want frame granularity, while "model-visible ⟺ logged" forbids durable token-level events.
- **Nearest layer wins a duplicate name OUTRIGHT; rank only orders duplicates WITHIN one layer** - `.agents/notes/archived/architecture/2026-08-09-layered-skill-registry.md:18` - a rank pool across layers was rejected because a later-installed deployment plugin could silently displace a preset's own same-named skill on a registration-order tiebreak, changing a composition's behaviour remotely. August layers exactly this way (bundled skills, workspace `.aug/skills`, data-dir skills, per-agent skills) and the same rule gives each composition's author the final word.
- **A capability definition's AUTHORITY and its TOOL EXPOSURE are two owners, not one switch** - `.agents/notes/archived/architecture/2026-08-10-product-subagent-providers-in-shared-host.md:16` - providers stay process-scoped host-plane registrations (availability), presets contribute ordinary tool rows (exposure), and loading a provider registers a *dormant* backend — the product process starts on the first real delegation. August's own sub-agent hierarchy keeps the same split (the stable Subagent service owns child identity and teardown; an experimental Team service consumes it), which is how a stable layer avoids naming an experimental one.
- **One process-table SNAPSHOT answers every question of a poll — and signals deliberately do NOT share it** - `.agents/notes/archived/architecture/2026-08-27-process-table-snapshots.md:30` and `:12` - `ProcessInspector.snapshot()` returns one observation answering `tree`/`session`/`alive`, so a readiness poll costs one table read regardless of descendant count (measured: 18 ms at 0 descendants, 178 ms at 10 — the old N+1 reads saturated a 50 ms poll). The review explicitly *refused* to let the signal path reuse the snapshot, because an observation carries the original PID-to-start-time pairing forward and would defeat the PID-reuse fence; "what the table showed" and "what is true now" are different questions and only the second may decide a signal.
- **A child process has NO PID and NO public startup state** - `.agents/notes/archived/architecture/2026-08-28-subprocess-native-containment.md:18` - a Linux user-systemd scope or a Windows kill-on-close Job owns the *managed range*, `waitForExit()` succeeds only after that range is proven empty, and a failed native launch is never replayed because an ambiguous failure may be post-execution. August's `run_command` has exactly the "did it stop?" question, and the note's discipline — a range proof rather than a pid check, and no replay after an ambiguous failure — is directly transferable.
- **One reader, many derivations — and a pinned budget of TWO reads** - `.agents/notes/archived/architecture/2026-08-17-settings-describe-mirror.md:14` and `:20` - one mirror holds the whole `settings.describe` answer; fifteen independent readers became two reads, and a new preference-owning plugin now adds zero. The in-flight slot owns its run *before* its loading publication can re-enter `load()` and clears the rerun flag inside the same synchronous segment, because a `.finally()` on the returned promise runs a microtask later and lets a refresh in that gap mark a rerun nobody reads. The pinned second read closes the window where a commit lands between the eager read and the SSE subscription.
- **Make a capability KEYED by the thing it serves, so ABSENCE is the signal** - `.agents/notes/archived/architecture/2026-08-12-plugin-owned-settings-surface.md:24` and `:26` - a `list` slot becomes a `keyed` slot whose key is the settings namespace the card edits, and what renders is the *intersection* of two ledgers (namespaces a live host plugin registered, and cards registered under those keys). A namespace another surface owns has no card under its key and therefore renders nothing without declaring anything anywhere — and the old "count the registered cards" empty state disappears with it.
- **A type's identity and its KIND are different things, so an extension can replace a built-in in place** - `.agents/notes/archived/architecture/2026-09-05-sidebar-tab-types-and-navigation.md` (`register(definition)` block) - `kind` is what `openTab` names and what tab identity is built from; `id` is one *implementation*'s identity, unique across registrations. The registry refuses a second `id`, a second registration in the same band of a kind, and any registration meeting a `fallback` of the same kind — while accepting the extension-over-builtin pair, with the built-in resuming on unregister. Priority is a *literal* band string, because a dynamically loaded plugin may not import a runtime constant.
- **Two ledgers, one intersection — and the *subject* is a projection, not the store** - `.agents/notes/archived/architecture/2026-09-17-plugin-detail-page-extension-slots.md` - three region-keyed list slots (`actions`/`badge`/`section`) beat nine per-object slots, and each entry receives a subject carrying only the facts it decides on, so the page's store stays private; the host's read-only reasons, errors and fiber phases are deliberately excluded, because exposing them would make store internals a public contract.
- **Make the tool-call IDENTITY an event-local fact and let the *assembler* own the topology** - `.agents/notes/archived/architecture/2026-08-11-trajectory-conversation-context-assembly.md:20` and `:59` - two views (chat and trajectory) share only exact-id matching, ordered matches, location facts, reader dependencies, publication scheduling and the replace/prepend/append lifecycle, while each keeps its own state and final node payloads. The complexity table is the transferable part: an older-page prepend costs `O(P × D + M)` instead of restarting the fold over the whole window, and a reader miss records a *window-gap dependency* so a later prepend replays only the affected chain in forward order.
- **A sidecar row is bound to the session's LIFECYCLE IDENTITY, not to its id** - `.agents/notes/archived/architecture/2026-08-10-message-feedback-sidecar.md:18` and `:24` - a row is bound to `{createdAt, cwd}`, so a recreated session id cannot inherit stale feedback and a fork gets its own identity with no copy; per-item opaque versions make the compare-and-swap *strict even when the desired value already matches*, which is what stops a stale request from crossing an ABA value cycle. August's Brain rows have the same "id can be reused" hazard.
- **There is no `end` call — settlement is the only close** - `.agents/notes/archived/architecture/2026-09-01-jobs-absorb-activity-record.md:21` - the dual-settlement pairing (`end` first-wins against teardown force-ends) was deleted rather than reimplemented, because two closers for one record is the thing that produces a frozen wrong terminal state. The same note pins the pump's constant-resource rule (subscribe to `done` once and keep one pending timer — racing the same pending promise every poll round retained a reaction per round, over a million closures on a day-long job) and the roster rule (a row *flags* a record, it does not count bytes).
- **Split session POSITIONS into identity and offset with validating constructors** - `.agents/notes/archived/architecture/2026-08-31-session-sequence-and-log-offset-brands.md:16` and `:26` - `SessionSeq` names one existing event, `SessionLogOffset` names a gap, prefix length or read offset; the compiler then refuses an offset where an event identity is required. The note also states the limit honestly: a compile-time brand cannot discover unknown numeric fields in an external event, so a format migration still needs an exhaustive owner disposition.
- **The ROLE WORD is a contract, and a rename ledger makes it enforceable** - `.agents/notes/archived/architecture/2026-08-11-repository-naming-contract-and-rename-ledger.md:46` - a seventeen-row table says when to use `Controller`, `Store`, `Directory`, `Registry`, `Runtime`, `Resolver`, `Binder`, `Engine`, `Policy`, `Executor`, `Gateway`, `Provider`, `Backend`, `Handle`, `Config` and when *not* to, with the operational test: "if callers mainly call `register()` and receive a disposer, use `Registry`". August's `app/services/` and `app/tools/` vocabulary is exactly this surface, and the note's "explicit non-renames" list is the part that makes the contract safe to apply.
- **Exhaustive INDEPENDENT backstops, fail-closed in three directions** - `.agents/notes/archived/architecture/2026-08-09-cordis-event-walk-backstop.md` - a separate `ts.createSourceFile` walk enumerates every declared event and every context key; the partition check fails when an event is invisible and unexempted, when an exemption names something that renders, when an exemption names nothing, and when the scan itself cannot see something the generator rendered. The scan deliberately shares no machinery with the projection, because a reachability bug in the projection is exactly what the backstop exists to catch.
- **A bilingual-pairing record pins the BLOB HASH of each side, so a translation cannot silently drift** - `.agents/notes/archived/architecture/2026-08-19-projection-cache-per-session-files.i18n.yaml:5` - every note in this shard ships an `.i18n.yaml` holding the git blob hash of the English and the Chinese file plus the `pnpm run verify-translation-pairing --write` command. August's AGENTS.md and docs are far more valuable than a machine translation, but the *mechanism* — a per-document pair record that a gate can check — is cheap and directly reusable for any doc set that has a translated twin.

## Uncertainties

- **The shard's own scope does not cover the lenses the brief emphasises most.** This shard is the *archived architecture* notebook of the client/host spine, the desktop/web shells, the plugin and inspector surfaces and the packaging machinery. DSH's own compaction, memory/learning, agent-loop and model-adaptation notes live in other shards (`dsh-llm-compaction#1/#2`, `dsh-core`, `packages-compaction-*`, `packages-memory-*` etc., none of which are in this manifest). I therefore could not confirm from *this* shard how DSH compacts a context, what its memory store looks like, or how it prices and adapts per model — the few touchpoints here are the prompt-section order allocation, the pi-ai route's per-model modality declaration, the embedded assistant stream, the durable image offload and the `run_code`/PTC tool-presentation transport.
- **I did not verify DSH's actual source code.** Every claim here comes from the archived Agent Notes themselves. Where a note describes behaviour (a measured number, an invariant, a rejected alternative), I reported the note's claim and attributed the measurement to the note; I did not check the implementation, and a note can be wrong or superseded.
- **One Chinese translation diverges from its English source in a literal.** `2026-08-07-shared-feedback-telemetry-user-id.zh.md` prints the `/feedback` acknowledgement's second line as `User: {userId}` where the English says `Anonymous user: {userId}` (verified at line 16 of each file). Every other Chinese note's `Status:` and `Archived:` front-matter matches its English counterpart exactly — I compared all 87 pairs mechanically and found no other divergence. The `.i18n.yaml` pairing record pins *both* blob hashes, so a divergence of this kind is possible in the tree: the pairing mechanism proves the two files were consistent at a recorded moment, not that the translation is semantically identical today. I checked every Chinese file's front-matter and section headings while reading; I did not diff every sentence.
- **The Chinese notes are not line-aligned with the English ones.** They use translated section headings (`## 问题` / `## 决策` / `## 后果` / `## 备选方案` / `## 验证`), sometimes a condensed structure (for example `2026-08-08-per-preset-standing-mounts.zh.md` merges Problem and Decision and drops the Alternatives table) and sometimes English headings inside a Chinese body (`2026-08-12-plugin-owned-settings-surface.zh.md` and `2026-08-23-cross-realm-cdp-inspector.zh.md` keep `## Problem` / `## Decision` / `## Consequences`). So the pairing record is a *blob-hash* pairing, not a line-for-line pairing, and my "mirrors the same decision" notes describe content equivalence, not layout equivalence.
- **The `.i18n.yaml` for `2026-09-17-session-row-menu-actions-slot` is the only file of that note in this shard** — its `.md` and `.zh.md` exist in the tree but are owned by another shard, so I could only read the hash record and not the note it pairs. The same applies in reverse to `2026-08-06-web-markdown-incremental-ast-renderer.zh.md`, the only note in this shard present in Chinese only.
- **Two notes reference siblings I did not read** (for example `2026-08-09-client-conversation-node-assembly.md`, `2026-09-01-v2-embedded-assistant-streams.md`, `2026-08-27-handle-based-session-persistence.md`, `2026-09-18-agent-teams-single-bundle.md`). I reported what the in-shard notes say about them, in their own words.

The consequence is that the per-file notes are my own reading rather than a worker's, and the earlier partial worker output (none of which was usable) is not represented in this report.
