# pi / coding-agent-tests#2

## Shard shape

This shard is four files, all of them fixtures under `packages/coding-agent/test/fixtures/`. There is no source code and no test file in it. Three of the four are tiny: a 25-line Node script that impersonates a user's `$EDITOR`, and two 0-byte `.gitkeep` markers whose *directories* are the actual payload. The fourth is a 2.37 MB captured session log (`before-compaction.jsonl`) — a real pi session recorded by the repo's author on 2025-12-08/09, in the **v1** session-file format, containing 1,003 JSONL entries, 990 messages, two real compaction records, five model changes and five thinking-level changes. The three small fixtures are all *inputs to other shards' tests*: `fake-external-editor.mjs` is spawned by `test/external-editor.test.ts`, and `empty-agent/` + `empty-cwd/` are handed to `loadSkills()` by `test/skills.test.ts`. The large fixture is, as far as I could establish, **referenced by nothing in the repo** — it is an orphan, and that fact is itself the most interesting thing about it.

The three lenses this shard actually speaks to are **session storage / branching / compaction** (the session-file format and its v1→v2→v3 migrations, the compaction-entry shape, the cut-point semantics), **config** (the empty-directory determinism device, and the fact that pi's session header carries fields the current schema no longer declares), and **testing approach** (a fake external program used as an assertion probe; a captured real-world artifact used as a golden fixture). The agent-loop, tool-execution, provider, UI and error-handling lenses are only touched indirectly, through the contents of the recorded session.

## Per-file notes

### packages/coding-agent/test/fixtures/before-compaction.jsonl
- **Purpose:** A real captured pi session, committed as a fixture. The session is the repo author's own 2025-12-08/09 refactor of `pi-mono`'s `coding-agent` (splitting `main.ts`/`tui-renderer.ts` into a shared `AgentSession` plus `print-mode.ts`/`rpc-mode.ts`/`InteractiveMode`), run against `anthropic` / `claude-opus-4-5` via the `anthropic-messages` API. Its name says it is the state *before* a compaction, and it does contain two compaction records (entries at 0-based indices 359 and 628) — so it is a golden input for anything that has to survive or produce a compaction.
- **Key abstractions:** The pi **session file** format: one JSON object per line, discriminated by `type`. Record census over all 1,003 lines: `message` × 990, `compaction` × 2, `model_change` × 5, `thinking_level_change` × 5, `session` × 1 (the header, line 1). Message roles inside: `assistant` × 484, `toolResult` × 448, `user` × 55, `bashExecution` × 3. Tool names used: `bash` × 204, `edit` × 124, `read` × 104, `write` × 16 — all 484 assistant turns went through `anthropic-messages`, all on `claude-opus-4-5`. Every assistant entry carries `usage` with `input`/`output`/`cacheRead`/`cacheWrite`/`totalTokens`/`cost`, plus `stopReason`.
- **Data flow:** Line 1 is the session header (`id`, `timestamp`, `cwd` = `/Users/badlogic/workspaces/pi-mono`, `provider`, `modelId`, `thinkingLevel`, `branchedFrom` = the absolute path of the session file it was branched from). Lines 2…990 are the turn log. Line 360 is a `compaction` entry with `summary` (4,291 chars of markdown), `tokensBefore: 175004`, `firstKeptEntryIndex: 293`; line 629 is a second with `summary` (3,649 chars), `tokensBefore: 185014`, `firstKeptEntryIndex: 551`. Both `firstKeptEntryIndex` values point at a **user** message ("i reviwed what we have, it's good. continue" and "can leave it") that sits *before* the compaction entry in the log — i.e. the index means "the first entry of the turn that survives the cut", and the cut is allowed to land mid-turn. Lines 711–715 are a burst of `model_change` records (the user cycling models: `claude-3-opus-20240229` → `claude-opus-4-5-20251101` → `claude-sonnet-4-5` → `claude-sonnet-4-5-20250929` → `claude-opus-4-5`), lines 9–12 and 1003 are `thinking_level_change` records stepping `minimal → low → medium → high` and back to `off`.
- **Non-obvious design decisions:**
  - **It is a v1 session file.** The header has *no* `version` field, and no entry carries `id`/`parentId`. `SessionHeader.version` is declared optional with the comment "v1 sessions don't have this" (`packages/coding-agent/src/core/session-manager.ts:45`), and `migrateToCurrentVersion` treats a missing version as 1 (`session-manager.ts:339`). So loading this fixture runs `migrateV1ToV2` (adds `id`/`parentId`, and **rewrites the compaction's positional `firstKeptEntryIndex` into a stable `firstKeptEntryId`**, `session-manager.ts:301-311`) and then `migrateV2ToV3` (renames the `hookMessage` role to `custom`, `session-manager.ts:316-331`). The fixture is the only place in the repo where the v1 shape survives, which makes it the natural regression input for the migration.
  - **The header carries fields the current schema no longer declares.** `provider`, `modelId`, `thinkingLevel`, `branchedFrom` are *not* in `SessionHeader` (`session-manager.ts:43-50` — only `type`/`version?`/`id`/`timestamp`/`cwd`/`parentSession?`). They are silently ignored on load. That is the shape of a format rotting quietly: an old key that nobody reads any more.
  - **The compaction summary is a fixed markdown skeleton, not prose.** Both summaries are headed `# Context Checkpoint: <task>` and carry the same sections: `## Branch`, `## Goal`, `## Key Decisions Made` (numbered), `## Completed Work` (a WP table with a ✅ column), `## Files Created/Modified`, `## Next Steps` (numbered, with the *next* WP marked "NEXT"), `## Key Files`, `## User Preferences`, `## Commands`. The first one also embeds a `## AgentSession Key API` TypeScript code block. `## User Preferences` and `## Commands` are the two sections that carry standing facts rather than narrative.
  - **Big tool output is truncated in the transcript and pointed at a file.** Entry 1002 is a `bashExecution` message for `find .` with `output` of 51,199 characters, `truncated: true`, `exitCode: 0`, and a `fullOutputPath` field. Entries 640 and 997 are the same `ls` command with `truncated: false` and no `fullOutputPath`. This is the "tool result too big for the transcript" mechanism, captured in the artifact.
- **Edge cases / failure handling:** The three `bashExecution` entries are the only non-conversational message role present; `BashExecutionMessage` (`packages/coding-agent/src/core/messages.ts:29-40`) carries `exitCode`/`cancelled`/`truncated`/`fullOutputPath`/`excludeFromContext`, and pi converts it to a plain user message for LLM context via `bashExecutionToText` (`messages.ts:82`). The fixture contains no error-shaped entries: no `isError: true` tool result, no failed exit code, no aborted turn. It is a clean run.
- **Surprising:**
  - **Nothing in the repo references it.** A repo-wide grep for `before-compaction` returns zero hits outside the file itself; the only fixture any test names is `fixtures/large-session.jsonl` (`packages/coding-agent/test/compaction.test.ts:35`). A 2.37 MB tracked fixture with no consumer is dead weight that still costs every clone.
  - **It is a self-hosting capture.** The tool results contain the *actual source of pi itself* at that revision — `main.ts`, `tui-renderer.ts`, `compaction.ts`, `session-manager.ts`, the newly written `core/agent-session.ts` — so the file is simultaneously a session log, a code archive and a golden compaction input. The `write` tool calls embed whole files as JSON string arguments (e.g. line 783 writes `src/cli/args.ts`).
  - **It contains no credentials.** The `apiKey` hits inside it are all *source code* (`getApiKeyForModel`, `ANTHROPIC_API_KEY` in an error string); there is no `sk-ant-` literal, no `Bearer <token>`, no `"apiKey":"<value>"`. That is why a raw capture was safe to commit — and it is a useful precedent for August, which has to decide the same thing about its own transcripts.
  - **The truncation boundary is visible.** The single 51 KB `find .` output is the only place the file crosses megabyte scale; `truncateTail` is what produced the `truncated: true` + `fullOutputPath` pair.

### packages/coding-agent/test/fixtures/empty-agent/.gitkeep
- **Purpose:** A 0-byte marker whose *directory* is the payload. `packages/coding-agent/test/skills.test.ts:349` resolves `fixtures/empty-agent` and passes it as the `agentDir` argument to `loadSkills({ agentDir, cwd, skillPaths, includeDefaults: true })`; `includeDefaults: true` makes the loader scan `<agentDir>/skills` (`packages/coding-agent/src/core/skills.ts:458`), so an empty agent dir guarantees **zero** default-layer (scope `"user"`) skills.
- **Key abstractions:** `LoadSkillsOptions` (`skills.ts:399-408`) — `cwd` = "Working directory for project-local skills", `agentDir` = "Agent config directory for global skills", `skillPaths` = explicit paths, `includeDefaults` = whether to include the two default directories.
- **Data flow:** The test at `skills.test.ts:352-362` asserts that with an empty agent dir, an empty cwd and one explicit `skillPaths` entry, exactly one skill loads and `skills[0].sourceInfo.scope === "temporary"`, with zero diagnostics. Sibling cases at `skills.test.ts:364` (nonexistent path → a diagnostic containing "does not exist") and `skills.test.ts:375` (tilde expansion in `skillPaths`) reuse the same two directories.
- **Non-obvious design decisions:** The directory is **empty on purpose and the file is empty on purpose**. `.gitkeep` exists only because git does not track empty directories; its content is irrelevant. The decision being encoded is *determinism*: the loader would otherwise read whatever the developer's own `~/.pi/agent/skills` or `<repo>/.pi/skills` contained, and the assertion "exactly one skill" would become machine-dependent.
- **Edge cases / failure handling:** Because the directory is empty, `loadSkills` cannot distinguish "no default layer exists" from "the default layer was unreadable" — there is no error path exercised by this fixture. The nearest diagnostic path (`does not exist`) is tested against a *nonexistent* `skillPaths` entry instead.
- **Surprising:** The same directory name appears twice in the manifest (`empty-agent` and `empty-cwd`) and both are `.gitkeep` — a reader skimming the manifest sees two identical 0-byte rows and might discard them as noise. The manifest's size column (0) is actively misleading: the *directory* is the fixture, the file is a placeholder. August's manifest tooling should carry a "directory fixture" marker, because a 0-byte row that is load-bearing is exactly the kind of thing a size-based triage drops.

### packages/coding-agent/test/fixtures/empty-cwd/.gitkeep
- **Purpose:** The twin of `empty-agent`, and the 0-byte marker of the directory used as the *project* root. `packages/coding-agent/test/skills.test.ts:350` resolves `fixtures/empty-cwd` and passes it as `cwd`; with `includeDefaults: true` the loader also scans `<cwd>/.pi/skills` (`packages/coding-agent/src/core/skills.ts:459`, `CONFIG_DIR_NAME` = `".pi"`, `packages/coding-agent/src/config.ts:581`).
- **Key abstractions:** `scope` — `loadSkillsFromDirInternal(dir, "user", true)` vs `(dir, "project", true)`; the empty cwd makes the project layer resolve to nothing, so a test can tell the two scopes apart.
- **Data flow:** Identical to its twin; the pair together guarantees that the only skills in the result are the ones the test passed explicitly, so `sourceInfo.scope` is the assertion that actually distinguishes "loaded from `skillPaths`" from "loaded from a default layer".
- **Non-obvious design decisions:** A *project* cwd of `fixtures/empty-cwd` also suppresses any accidental pickup of a repo-local `.pi/` directory (the repo does have a `.pi/` tree with extensions, prompts and skills at the root — `scripts-ci` shard). Without this fixture, running the test from inside the checkout would load the repo's own skills and the "exactly one skill" assertion would fail on a clean checkout. The fixture therefore does double duty: it isolates from the developer's *home* and from the *checkout*.
- **Edge cases / failure handling:** None of its own — it is an empty directory. It also silently disarms a failure mode that would otherwise be intermittent: `includeDefaults: true` scans the real cwd, so a test run from a different working directory would see a different project layer.
- **Surprising:** Two 0-byte files carry a real test-design decision, and the decision (isolate the loader from *both* ambient layers) is invisible from the manifest. August has the same shape of problem — its skill catalogue reads `<dataDir>/skills` and `<workspace>/.aug/skills` — and the transferable mechanism is: *every ambient layer a loader reads needs a designated empty fixture, and the test must pass all of them explicitly.*

### packages/coding-agent/test/fixtures/fake-external-editor.mjs
- **Purpose:** A stand-in for the user's `$EDITOR`, used by `packages/coding-agent/test/external-editor.test.ts:25` as `command: \`${process.execPath} ${editorFixturePath} ${capturePath}${flag ? " " + flag : ""}\``. It is spawned by `editInExternalEditor` (`packages/coding-agent/src/modes/interactive/external-editor.ts:26`) as `spawn(editor, [...editorArgs, filePath])`, so argv is `[node, script, capturePath, (flag), filePath]`. The script's job is to *report what the editor saw* and then simulate an edit.
- **Key abstractions:** `ExternalEditorResult` (`external-editor.ts:12`) — a discriminated union `{ status: "complete"; content: string } | { status: "failed" }`. The fixture is the probe that distinguishes the two, plus a third observable: the *environment* (directory mode, directory contents) the editor was handed.
- **Data flow:** argv[2] = capture path, argv.at(-1) = the file to edit. The script reads the file's content, lists the containing directory, stats the directory's mode, writes all of that as JSON to the capture path (lines 10–20). Then: if `--fail` is present it exits 1 (line 22-24); otherwise it writes `"edited\n"` back to the file, or `""` if `--empty` was passed (line 25). The caller reads the capture back, and the production code strips a BOM and a trailing newline from what the editor wrote (`external-editor.ts:38`).
- **Non-obvious design decisions:**
  - **The capture is written BEFORE the failure branch.** Line 11 writes the capture unconditionally; the `--fail` check is at line 22. That ordering is the whole point of the fixture: a failed editor round-trip is still *observable*, so the test can assert the editor was handed the right file with the right content even when the exit code was non-zero. The test at `external-editor.test.ts:52-57` uses exactly that — it asserts `status: "failed"` **and** that the temp directory was cleaned up, and the capture is still there to be read.
  - **The capture records the DIRECTORY MODE, not just the file.** Line 17: `directoryMode: statSync(directory).mode & 0o777`. The test asserts `capture.directoryMode & 0o077 === 0` on non-Windows (`external-editor.test.ts:46-48`) — i.e. the scratch directory holding the prompt is `0700`, and the directory listing (`entries`) must be exactly `["prompt.md"]` (line 44), so the editor's private directory holds nothing else.
  - **`process.argv.at(-1)` rather than a positional index.** The production code appends the file path as the last argument, so "last" is the contract, not "index 3" — the fixture tolerates the optional `--fail`/`--empty` flag sitting in between.
- **Edge cases / failure handling:** The fixture itself is defensive about its own contract — `if (!capturePath || !filePath) process.exit(1)` (lines 6-8), so a mis-wired test fails loudly instead of writing `"undefined"` into the capture. The production side treats a non-zero exit as `status: "failed"` and then deletes the temp directory in a `finally` block whose `rmSync` is wrapped in its own try/catch ("Cleanup is best effort", `external-editor.ts:39-45`); the test then asserts `existsSync(directory) === false` (`external-editor.test.ts:49`, `:56`). The `--empty` case pins the other edge: an editor that clears the file must yield `{ status: "complete", content: "" }`, not "failed".
- **Surprising:**
  - **A fake external program is a better assertion probe than a mock.** Nothing is mocked: a real process is spawned, a real file is written, a real exit code is produced, and the *observation* is made by the program under test's own environment. The test asserts on `dirname(capture.filePath)` — that the file really landed in a fresh `pi-editor-*` directory under the OS temp dir (`external-editor.test.ts:38-43`), which a mocked `fs` could not prove.
  - **The production code deliberately avoids `spawnSync`.** `external-editor.ts:22-24` explains why: on Windows a synchronous child process can keep libuv's console read active after the parent pauses stdin, racing vim/nvim for the console input buffer until Ctrl+C. A fixture-driven test would not have found that; it came from a real editor on real Windows.
  - **The editor's private directory is deleted even on failure.** The test asserts the temp dir is gone after a *failed* editor (`external-editor.test.ts:56`) — the prompt text, which may be sensitive, does not survive a crash.

## Ideas worth stealing

- **Capture what the subprocess SAW, and write the capture before the failure branch** — `packages/coding-agent/test/fixtures/fake-external-editor.mjs:11` — the fixture records `filePath`, `content`, `entries`, `directoryMode` to a capture file *before* it honours `--fail` (line 22), so a non-zero exit is still a fully observable round-trip. August runs approval surfaces, tool processes and MCP servers the same way; asserting only on the exit code throws away everything the callee knew. Port this shape: every external-process boundary in August should have a "what did it see" probe written before the failure branch.
- **Assert the mode of a scratch directory, not only the file it contains** — `packages/coding-agent/test/fixtures/fake-external-editor.mjs:17` — `statSync(directory).mode & 0o777` lets the test assert `mode & 0o077 === 0` on POSIX (`external-editor.test.ts:46-48`). August writes prompts, patch previews and terminal buffers into temp directories; a `0700` assertion is the cheapest possible check that a credential-bearing temp file is not world-readable, and it is a single line to add to any door that materialises sensitive text on disk.
- **The compaction summary is a fixed skeleton with `User Preferences` and `Commands` as first-class sections** — `packages/coding-agent/test/fixtures/before-compaction.jsonl:360` (first summary) and `:629` (second) — both are `# Context Checkpoint` → `## Branch` → `## Goal` → `## Key Decisions Made` → `## Completed Work` (a WP table) → `## Files Created/Modified` → `## Next Steps` → `## Key Files` → `## User Preferences` → `## Commands`. The lesson for August is *which* sections survive a compaction: the standing preferences ("E2E tests only", "keep old code working alongside new code") and the exact commands (`npm run check`) are the facts that must not be lost, while the narrative is what may be. August's `<<compressed_summary` note currently squeezes predecessors into 600 chars of prose; a section skeleton with dedicated `Preferences` and `Commands` slots would be strictly better than prose.
- **A compaction cut may land mid-turn, and the surviving pointer is a user message** — `packages/coding-agent/test/fixtures/before-compaction.jsonl:360` (`firstKeptEntryIndex: 293`) and `:629` (`firstKeptEntryIndex: 551`) — both indexes resolve to a **user** message, never to a tool result, and both sit *before* the compaction record in the log. The rule in the code is explicit: cut points may be user or assistant messages but "never tool results" (`packages/coding-agent/src/core/compaction/compaction.ts:436-437`). August's compaction rotates and replays a verbatim head; the transferable invariant is that **the replayed head must start at a turn boundary, never at an orphaned tool result** — a head that begins with a tool result is exactly the pairing bug August's `_compactionCall` has to avoid.
- **A positional pointer rewritten into a stable id by the migration, not by the writer** — `packages/coding-agent/src/core/session-manager.ts:301-311` (exercised by the fixture at `packages/coding-agent/test/fixtures/before-compaction.jsonl:360`) — `migrateV1ToV2` converts `firstKeptEntryIndex` → `firstKeptEntryId` by indexing the *already-migrated* array and deleting the old field. When August changes how its `messages`/`turn_outcomes` rows are addressed (and it will), the conversion has to happen in the migration, keyed on the new id, and the old positional form has to be deleted — a file that keeps both fields is a file with two truths about where the live context starts.
- **Truncate the tool result in the transcript and keep the full output in a file** — `packages/coding-agent/test/fixtures/before-compaction.jsonl:1002` — a `bashExecution` entry with a 51,199-character `output`, `truncated: true`, and a `fullOutputPath`; the sibling `ls` entries at `:640` and `:997` carry `truncated: false` and no path. The transcript stays small, the bytes stay reachable, and the *fact of truncation* is persisted rather than inferred from a length. August's tool-result truncation currently has to invent its own marker; pi's triple (`truncated` boolean + `fullOutputPath` + the message type that owns both) is a schema worth copying.
- **Give every ambient layer a designated empty fixture** — `packages/coding-agent/test/fixtures/empty-agent/.gitkeep` and `packages/coding-agent/test/fixtures/empty-cwd/.gitkeep`, consumed at `packages/coding-agent/test/skills.test.ts:349-350` — the loader reads `<agentDir>/skills` and `<cwd>/.pi/skills` (`packages/coding-agent/src/core/skills.ts:458-459`); passing two empty directories is what makes "exactly one skill" a fact instead of a hope about the developer's machine. August's skill catalogue reads `<dataDir>/skills`, `<dataDir>/bots/<id>/skills` and `<workspace>/.aug/skills` — that is at least three ambient layers, and each needs the same designated empty stand-in, plus an assertion that the layer's *scope* is what got loaded (`skills[0].sourceInfo.scope === "temporary"`).
- **A stored format keeps keys the reader no longer declares — and the fixture proves it** — `packages/coding-agent/test/fixtures/before-compaction.jsonl:1` (header carries `provider`, `modelId`, `thinkingLevel`, `branchedFrom`) vs `packages/coding-agent/src/core/session-manager.ts:43-50` (`SessionHeader` declares only `type`/`version?`/`id`/`timestamp`/`cwd`/`parentSession?`) — the extra keys are silently ignored on load. August's `providers.json`, `config.json` and `secrets.json` readers should be checked against the same rule: an unknown key in a stored file is a compatibility bug that nobody will notice until the format has already moved on.
- **Ship a captured real session as the golden artifact, not a synthetic one** — `packages/coding-agent/test/fixtures/before-compaction.jsonl` — the fixture is a genuine 1,003-entry pi run (real tool calls, real thinking blocks with signatures, real `usage`/`cost` on every assistant turn, real model and thinking-level switches, real compactions), and it contains **no credentials** despite containing real source code. The transferable decision is the *scrubbing policy*: a captured transcript is committable only because the credential-shaped content was checked; August, which stores transcripts in a database, should adopt the same check as a gate rather than as a habit.
- **A fixture census is a gate, not a lint** — `packages/coding-agent/test/fixtures/before-compaction.jsonl` is referenced by nothing (repo-wide grep for `before-compaction` → 0 hits outside the file), while its sibling `packages/coding-agent/test/fixtures/large-session.jsonl` is referenced at `packages/coding-agent/test/compaction.test.ts:35`. August already has the shape of this gate (`test_exactly_one_site_builds_a_compaction_request`, which also asserts its census is non-empty); the same census over the fixture directory would have caught 2.37 MB of dead weight in pi and would catch the same class of drift in August.
