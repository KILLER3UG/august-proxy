## 5. The concrete signal that triggers a probation restore

Worth stating precisely, because "it regressed" is not an implementation:

1. An auto-apply books an outcome row (`harness_outcome.record`, `source='proposal'`,
   `key='proposal:<id>'`) and the apply's snapshot id goes on the ledger row.
2. The scheduled `outcome` job runs `measure_pending()`, which only considers rows whose
   **after-window has fully elapsed** (`applied_at <= now − outcomeWindowDays`, default 14) and
   that have never been measured (`measured_at IS NULL`).
3. `_classify(before, after)` fires the restore on `verdict == 'regressed'`, which means exactly one
   of two things — and both are RATES over a sample, since the review round fixed a rule that
   could revert a change on three episodes:
   - **targeted** (the proposal carried a `fingerprint`): recurrence as a proportion of the window
     (`fingerprintRecurrence / episodes`) rose by at least `_IMPROVE_EPS` (**0.15**).
   - **untargeted**: the after window's resolved rate is at least 0.15 below the before window's.
   - **Both sides need `_MIN_EPISODES` (8) episodes**, or the verdict is `insufficient`.
4. `_file_revert_proposal` then asks `harness_rails.probation_revert(...)`, which returns a receipt
   only if the outcome's proposal has an `auto_apply` ledger row, autonomy is still on, a
   `version_ts` is recorded, **and that snapshot is still the newest version for the skill**. Any
   one missing → `None` → the human gets the revert proposal instead, unchanged from before.
5. The restore goes through `skill_service.restoreVersion`, so it lands in the same history a
   human's undo writes to.

The honest limit: `flat`, `improved` and `insufficient` all leave the change in place, and a skill
that is simply never loaded measures `insufficient`, not a verdict. The trigger is recurrence or a
measured resolved-rate drop — never silence.

## 14. Learned skills are now procedures, not rules (2026-10-08)

Asked for: "improve the skill creation in august — it's too short to be a skill and reads more like a
rule." Measured against the Hermes authoring standards (`%LOCALAPPDATA%/hermes/hermes-agent/agent/
learn_prompt.py`, `_AUTHORING_STANDARDS`) and the Anthropic skill spec. Four causes, all in the code:

1. **The evidence had no recovery in it.** `episode_miner._extractEvents` stores only failures and user
   prose — deliberately, because `events` is the fingerprint/dedupe substrate (`_episodeText` joins every
   excerpt into the token set). So the judge could see the error and the correction but never the call
   that fixed it. It could not write a procedure, because the procedure was not in the input.
2. **The contract asked for a blob.** `_JUDGE_SYSTEM` offered one optional `body_markdown` string with no
   shape and no standard.
3. **The normalizer padded.** `_ensure_canonical_body` + `_placeholder_for` filled every gap with
   boilerplate, so a one-sentence rule came out with all the right headings present — and nothing could
   tell a drafted pitfall from a template one.
4. **`body or description`** at `skill_distiller.py:716` made the rule literally the body.

**Landed.** `_actionTimeline(ep)` reads the window's `blocks_json` between `start_message_id` and
`end_message_id` at judge time and lists every tool call in order with its arguments and outcome (head +
tail, so the fix survives the cut) — mining, fingerprints and the rubric are untouched. `_JUDGE_SYSTEM`
now states the rule-vs-skill distinction and the standards (name, ≤60-char description, intro saying what
it does NOT do, verbatim commands only, pitfalls that happened here), and answers in **section fields**
(`intro`, `when_to_use`, `when_not_to_use`, `prerequisites`, `steps[{do,command}]`,
`pitfalls[{seen,instead}]`, `verification`, `keywords`) rather than one escaped markdown blob — markdown
inside JSON is where a small model breaks the envelope. `skill_service.renderSkillBody` renders those into
the canonical order, **omitting** what was not authored; `skill_service.bodySubstance` then measures what
was drafted *before* padding (one situation, ≥2 steps, one pitfall, one verification) and a draft below
the bar is filed to **memory as a lesson** instead of into the inbox as a skill. `_EXCERPT_CAP` 240→600
(a truncated command is worse than none — the judge fills the gap with the flag it expects), the dead
`_DRAFT_CAP` deleted, `_JUDGE_TIMEOUT_S` 60→120.

**Adjacent defects the same trace turned up, all fixed:**
- `amend_trigger` carries no body, so `body or description` normalized into `payload.body` and
  `_apply_skill_write` writes `payload.body` **over** the target — approving a trigger-only patch replaced
  a real skill's procedure with `_placeholder_for` boilerplate. It now ships the target's current body
  through, and refuses an unknown target (`rejected-unknown-skill`) instead of filing an unapprovable
  patch. Proven red first: against HEAD the payload body was
  `'# Run sims\n\nrun-sims\n\n## When to Use\n\n- run-sims\n\n## How to Run\n\n1. \`load_skill("run-sims")\`…'`.
- The bundled-skill supersession paths (`amend_trigger`/`amend_body` → `<name>-revised`) filed a
  `skill_create` whose entire body was placeholder text **superseding and disabling a human-written
  skill**. Both now carry the original text plus the amendment, and refuse when it cannot be read.
- A description over the 60-char cap was caught only at APPROVAL (`_apply_skill_write` re-validates), so
  those proposals were unapprovable by construction. `_fitDescription` cuts at a clause boundary at draft
  time; a marketing word is a claim, not a typo, so it is reported and the verdict downgrades rather than
  being silently rewritten.
- The §3.3 sensitive-topic denylist scanned only `description`/`body_markdown`/`trigger`/`patch_markdown`
  — a health detail in `pitfalls` walked straight past it. `_DRAFT_FIELDS` is now the single list the
  scan and the renderer share.
- Proposal evidence was built from `verdict['events']`, a key the judge never sends, so every real draft
  arrived with empty evidence. `_evidenceWindow` re-reads the episode row.
- `AnthropicClient.generate` hard-codes `max_tokens: 2048`; a batch of full skill drafts truncates the
  JSON, which fails the batch and burns the cooldown. It now honors `config['max_tokens']` (default
  unchanged) and the judge asks for 4096.
- `# What this skill is` was a literal H1 the normalizer wrapped *around* the author's own `# Title`, so
  every learned skill shipped two H1s. The author's H1 is the title now; the description is the intro.

**Deliberately not done:** no `platforms:` / `metadata.hermes.related_skills` frontmatter — nothing in
August's loader reads either, and `keywords` already carries tags into the BM25 index (Hermes needs
`platforms` because it filters by OS; we do not). No second "author" model call: the shape is code's job
now, so the judge only supplies content. The manual Settings → Skills editor keeps its placeholder
template — for a human starting from a blank page that is scaffolding, not a lie.
