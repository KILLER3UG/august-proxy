# deepseek-harness / dsh-apps-desktop#4

## Shard shape

This shard is the **desktop shell's build-and-trust corner**, not a slice of the agent runtime. It holds exactly 7 files under `apps/desktop/`: the three TypeScript project-reference files that split the Electron app into a *host* project and a *client* project (`tsconfig.json`, `tsconfig.host.json`, `tsconfig.client.json`), the `tsdown` bundler configuration that turns the compiled output into the shipped Electron artifact, and a three-file bilingual documentation unit describing **Windows EV-code-signing and the self-hosted packaging runner** (`windows-signing/README.md`, its Chinese counterpart `README.zh.md`, and the `README.i18n.yaml` section-hash record that mechanically proves the two languages still say the same thing). The two halves fit together as one story: *how the desktop app is compiled and bundled without shipping a broken artifact* (the tsconfigs + tsdown config, incl. a bundler plugin that fails the build when a bare import survives that the packaged app cannot resolve) and *how the resulting artifact is signed and published with an EV token on a shared runner* (the signing README, which is really an operations runbook with a security-threat model in prose). **None of the harness's agent machinery is in this shard** — no agent loop, no prompt construction, no reasoning/thinking streaming, no compaction, no memory, no subagents, no model-specific adaptation. The `lenses` most relevant here are *config* and *testing/ops*; the rest are covered by other `dsh-apps-desktop#N` shards or by `packages/*`.

## Per-file notes

### apps/desktop/tsconfig.json
- Purpose: The solution-style root project file for the desktop app — 11 lines, `files: []` and two project references (`./tsconfig.host.json`, `./tsconfig.client.json`). It exists so that a single `tsc -b` at this directory builds both sub-projects in dependency order.
- Key abstractions: TS "solution" tsconfig (`files: []` + `references`), nothing else. It carries no `compilerOptions` of its own.
- Data flow: `apps/desktop/package.json` `"build": "tsc -b && pnpm run bundle"` → `tsc -b` picks up this file → the two referenced projects compile into `lib/types/` → `tsdown --config-loader native` then bundles `lib/types/*.js` into the shipped `lib/*.js`.
- Non-obvious design decisions: `files: []` (line 2) is deliberate: without it, `tsc -b` would treat this file as a compilation unit and the references would be advisory rather than the build graph.
- Edge cases / failure handling: none of its own — a broken reference surfaces as a `tsc -b` project-graph error, not as a runtime failure.
- Surprising: this 11-line file is the *only* thing that makes `tsc -b` build both halves of the desktop app; a reader looking for "the desktop tsconfig" will land here and find nothing but pointers.

### apps/desktop/tsconfig.host.json
- Purpose: The **Electron main-process** compile project — `extends ../../tsconfig.base.json`, `rootDir: "src"`, `outDir: "lib/types"`, `include: ["src"]`, `exclude: ["src/client"]` (lines 2-38). It is the Node-side half: `main.ts`, `update-coordinator.ts`, `host-process.ts`, `tray.ts`, the `preload-*.ts` sources, etc.
- Key abstractions: (a) TS project references (lines 10-35) pinning the host's dependency closure to eight workspace packages — `packages/boot/app-boot`, `packages/util/home-paths`, `packages/credentials/deepseek-account`, `packages/api/gateway`, `packages/client/ui-sidebar-browser`, `packages/client/shortcuts`, `packages/util/atomic-write`, `packages/client/product-analytics`; (b) the `exclude: ["src/client"]` boundary that separates host from renderer.
- Data flow: `src/**` → `tsc -b` → `lib/types/*.js` (+ `.d.ts`, `.js.map`, `.tsbuildinfo`) → consumed by `tsdown.config.ts` (`entry: ['lib/types/main.js']`, `lib/types/command-manager-entry.js`, `lib/types/<preload>.js`) and directly by test fixtures (`apps/desktop/tests/fixtures/*.mjs` import `../../lib/types/locale.js` etc.).
- Non-obvious design decisions: the `include`/`exclude` split is a **directory** boundary (`src/client`) rather than a file list, so any new file under `src/` is host code by default and any new file under `src/client/` is renderer code by default — the boundary is positional, not declarative. The base (`tsconfig.base.json`) comments explain the repo-wide choice: "Project references, not declaration path aliases, keep each package/vendor source compiled under its own tsconfig boundary."
- Edge cases / failure handling: `composite: true` + `incremental: true` come from the base, so `tsc -b` is incremental; a stale `.tsbuildinfo` is the only stateful hazard. `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` (base) are the strictness knobs.
- Surprising: `include: ["src"]` with only `src/client` excluded means `src/locale.ts` and `src/welcome-api.ts` are compiled **twice** — once here and once by `tsconfig.client.json` — into the **same** `outDir: "lib/types"`. Both projects declare `outDir: "lib/types"` (host line 5, client line 5), so two composite projects write `lib/types/locale.js` and `lib/types/welcome-api.js`. It only works because both files are locale/IPC-constant modules whose emitted JS is identical under either compiler config; it is a two-writers-one-path hazard, not a partition.

### apps/desktop/tsconfig.client.json
- Purpose: The **renderer/welcome** compile project — `extends ../../tsconfig.base.client.json` (which adds `jsx: react-jsx`, `lib: [ES2024, DOM, DOM.Iterable, ESNext.Disposable]`, `types: ["client-build-environment"]` and *no* Node ambient types), `rootDir: "src"`, `outDir: "lib/types"`, `include: ["src/client", "src/welcome-api.ts", "src/locale.ts"]` (lines 2-11).
- Key abstractions: the browser/host type split. `tsconfig.base.client.json` states the rule: "browser library API, React JSX, no ambient node types (packages that need them override locally)". This is what stops renderer code from reaching for `process`, `fs`, or `child_process` at the type level.
- Data flow: `src/client/welcome.tsx` + `src/client/WelcomePage.tsx` + the two shared modules → `lib/types/client/*` → `tsdown.config.ts`'s Vite `onSuccess` build (lines 53-83) which bundles `src/client/welcome.tsx` directly into an IIFE at `lib/welcome/welcome.js`.
- Non-obvious design decisions: two *non-renderer* files are deliberately pulled into the client project (lines 9-10) because the isolated welcome renderer needs the localized strings and the IPC channel names, while the host also needs them. Naming them explicitly rather than widening `include` is what keeps the DOM/Node type boundary honest.
- Edge cases / failure handling: `types: ["client-build-environment"]` (from the base) means the client project gets only the ambient `process.env.DSH_CLIENT_*` declarations — a renderer file that reads an arbitrary env var fails to compile, which is the point.
- Surprising: as noted above, `src/welcome-api.ts` and `src/locale.ts` sit in **both** projects and both emit into `lib/types/`; a reader checking "is this file compiled twice?" has to notice that the host's `exclude` only excludes the `src/client` *directory*, not those two files.

### apps/desktop/tsdown.config.ts
- Purpose: The desktop app's **bundler configuration** — 107 lines defining four kinds of output artifact: a standalone privileged-worker bundle, the Electron main-process bundle, a separate Vite-built welcome window, and five CommonJS preload bundles.
- Key abstractions: (1) `defineConfig([...])` returning an *array* of tsdown configs; (2) the `packagedImportsPlugin` policy object `{ packages: Set<string>, nodeBuiltins: boolean }`; (3) `clientBuildEnvironment` resolution from `scripts/client-build-environment.ts` (lines 6, 26-30); (4) tsdown's `deps.alwaysBundle` / `deps.neverBundle`.
- Data flow: `lib/types/command-manager-entry.js` → bundle A (`lib/command-manager-entry.js`); `lib/types/main.js` → bundle B (`lib/main.js`), whose `onSuccess` (lines 53-83) runs a *second* bundler (Vite) over `src/client/welcome.tsx` → `lib/welcome/welcome.js` + `lib/welcome/welcome.css`, plus a custom `desktop-brand-font` plugin that copies `brand-font.css`, three Montserrat `.woff2` files and `Montserrat-OFL.txt` out of `packages/client/ui-theme/src/styles/` (lines 57-66); the five preload entries (line 93) → `lib/preload-*.cjs`.
- Non-obvious design decisions: (a) **the privileged worker gets its own bundle with an empty external-package allowlist** — `packagedImportsPlugin({ packages: new Set(), nodeBuiltins: true })` (line 38) means the command-manager worker may leave *zero* bare package imports, with `@deepseek-ai/dsh-atomic-write` force-inlined via `deps.alwaysBundle` (line 47). The worker is what escalates to install `/usr/local/bin/dsh` on macOS, so its dependency closure is closed at build time. (b) **the preloads get a different module universe than the main process**: `preloadImports` allows only `{electron, events, timers, url}` with `nodeBuiltins: false` (line 21), because a *sandboxed* Electron preload's `require` polyfill offers only that set — the comment cites Electron's own Process Sandboxing doc. (c) The whole file is ESM (`format: ['esm']`, lines 40, 85) while every preload is forced CJS (line 98), with the reason stated inline at line 94: "Sandboxed Electron preloads run as CommonJS even though the application package is ESM." (d) `clean: false` on every bundle (lines 45, 90) so one tsdown pass cannot delete another's output. (e) Only `DSH_CLIENT_VERSION` is inlined via `define` (lines 32-33); every other variable stays a runtime lookup, and the build fails outright if the version is missing (line 30).
- Edge cases / failure handling: the build deliberately runs *after* the workspace tsdown pass, with the reason at lines 9-11 — "the main bundle inlines workspace devDependencies from their `lib/` output, which the concurrent workspace pass does not order ahead of this package." The `packagedImportsPlugin` is the guard that turns a would-be `ERR_MODULE_NOT_FOUND` at application launch into a build failure.
- Surprising: the *only* thing that differs between the "no external packages" bundle and the rest is one policy object; and the whole config's central idea is **encode the runtime's resolution limit as a build-time allowlist** — main process may leave `electron` + manifest `dependencies` + Node builtins; a sandboxed preload may leave only four modules; the elevated worker may leave none.

### apps/desktop/windows-signing/README.md
- Purpose: The Windows signing and shared-runner **operations runbook** (103 lines) — how to configure the EV token, SignTool, key container and PIN; how to run the supervised signing preflight; how the timestamp step retries; how a hardware failure is recorded and recovered; and how the runtime signature cache works. It is a security document as much as a build document.
- Key abstractions: the **hardware-attempt interlock** (`%USERPROFILE%/.dsh-desktop-signing/attempt.json`, line 79), the **account-level signing-stage lock** (line 87), the **signature cache** with entries keyed by original bytes + public certificate + toolchain (line 85), and the **packaging run journal** (`.desktop-build/packaging-runs/<unique>/` with `run.json`, `events.jsonl`, `stdout.log`, `stderr.log`, `result.json`, `fatal.json`, line 77).
- Data flow: machine preset + `.env.windows` → `setup-windows-packaging.ps1` creates `packaging/{presets,secrets,certificates}` and `cache/windows-signatures` (line 35) → `start-windows-packaging-runner.ps1` starts the GitHub runner with a scrubbed inherited environment → a job runs packaging → the electron-builder hook hands each artifact to `scripts/windows-sign.cmd`, which invokes the configured SignTool **once** with `/f`, SafeNet `/kc "[{{PIN}}]=container"`, `/csp "eToken Base Cryptographic Provider"` and a SHA-256 digest and **no** timestamp (line 67) → the hook then completes a DigiCert SHA-256 RFC 3161 timestamp on isolated copies without signing credentials → the runtime stages consult the cache (hit ⇒ restore after digest + Windows trust + timestamp + certificate checks; miss ⇒ serial hardware signing).
- Non-obvious design decisions (with the stated reasoning): (a) **the PIN cannot contain `]`, a quote, or a newline** (line 55) because those delimit the SafeNet `/kc` value or its CMD argument, and the CMD disables delayed expansion so a PIN containing `!` survives unchanged. (b) **credential withholding is an allowlist**: every `DSH_DESKTOP_WINDOWS_*` field is withheld from build and runtime-preparation subprocesses; only the four configured inputs reach preflight, the runtime signing stages and electron-builder; the signing CMD gets only the validated fields in an otherwise scrubbed environment; the fields are cleared before SignTool starts; SignTool diagnostics are redacted (line 55). (c) **the updater's `publisherName` is derived from the certificate's `CN`, `O` and `C`** rather than a pinned leaf thumbprint, so the certificate can be renewed without invalidating update identity (line 57). (d) **the preflight signs a throwaway probe that is never executed** (line 65), under a 60-second deadline that *includes* timestamp attempts; success proves the signing path works but explicitly does not prove the PIN was independently authenticated ("SafeNet may reuse login state"). (e) **timestamp retries are restricted to a normally-exited command** that returned failure or warning — at most three tries with 1s and 2s delays, each starting from the same verified primary signature; launch errors, uncertain termination and verification failures stop immediately (line 69). (f) **`SignTool Error: No private key is available.` is terminal, not retryable** (line 75) because the device's PIN retry limit is unknown and probing it burns attempts. (g) **the interlock has no timed recovery** (line 79): only a successful sign *plus* verification releases it, and "logging into the token or replacing a PIN file does not clear it" — an administrator must inspect retained evidence first. (h) **cache age alone does not trigger re-signing**, and an invalid cache entry stops packaging *without* a hardware fallback (line 85). (i) **the runner is an interactive Task Scheduler task, not a service**: disabled by default, limited permission, no stored account password, starts after desktop login, stops on logout, "does not provide unattended boot or unlock a signing Token" (line 39). (j) the restart budget is **persisted and consumed by login**: initial launch plus `-RestartCount` (default 10) restarts between explicit starts, and "after the budget is exhausted, login alone cannot restart the runner" (line 41).
- Edge cases / failure handling: every stage failure is journaled and "failed stages cannot start subsequent stages or create a release completion record"; "a missing final record means completion was not established" (line 77). The cache-maintenance CLI (`pnpm --dir apps/desktop/run cache:windows-signatures`) supports `--usage`, `--from <old-cache>`, `--clear`, `--directory` and "never clear[s] hardware failure evidence" (line 93). `SIGNATURE_CACHE_SUMMARY` (line 91) is a structured per-stage summary on stdout and in the journal: directory, policy identity, hit/miss counts, published/retained entries, signing requests, avoided signing requests, validation failures, with timings separated into signing / trust verification of restored files / trust verification of newly signed files / restoration.
- Surprising: the doc's first section is a **threat model of its own build system** (line 27) — the shared runner assumes trusted internal code, so credential and device isolation are deferred and the residual risk is *accepted and tracked* (#5973); unsigned mode cannot stop branch code running as the same Windows account from reading the signing files; "Direct device calls can bypass the signing scripts and exhaust PIN retries; the persistent failure interlock only protects calls through those scripts." Few build docs are willing to write that down.

### apps/desktop/windows-signing/README.zh.md
- Purpose: The Simplified-Chinese counterpart of `README.md` — a line-for-line mirror (103 lines, same 12 headings in the same order, same `<a id="…">` anchors, same fenced blocks, same tables of contents). It is not a summary; it is the same document in the other language, which the repo's pairing contract treats as **equal authority** (neither file outranks the other; they must simply say the same thing).
- Key abstractions: identical to the English file. The one mechanical difference is the *locale* of intra-repo link targets: the English file points at `../packaging/README.md#windows-actions`, the Chinese file at `../packaging/README.zh.md#windows-actions` (lines 33, 51, 57, 63, 99) — required by the repo rule that "the English side uses its `.md` path and the Chinese side uses its `.zh.md` path".
- Data flow: not a runtime artifact; it is one of the three files of a "pair" (`foo.md`, `foo.zh.md`, `foo.i18n.yaml`) whose consistency is proven by the `verify-translation-pairing` gate.
- Non-obvious design decisions: the Chinese file keeps the **English backlink immediately after the H1** (`[English](README.md) | 中文`, line 7) and mirrors the English file's reciprocal switcher (`English | [中文](README.zh.md)`, line 7 of the English file). The table-of-contents anchors are the *English* slugs (`#trust-and-isolation`, `#machine-setup`, …) because the `<a id>` anchors are byte-identical across the pair.
- Edge cases / failure handling: the pairing gate compares the two sides' structural signatures (heading depth and order, list kinds and item counts, table row/column counts, verbatim code blocks, semantic link targets with exact query/fragment suffixes) *and* the per-section hashes; a structural mismatch or a stale hash goes red in CI.
- Surprising: the Chinese text carries operational content the English does not soften — e.g. line 55 renders "打包流程不会把任何 `DSH_DESKTOP_WINDOWS_*` 字段传给构建与运行时准备子进程" (packaging withholds every `DSH_DESKTOP_WINDOWS_*` field from build and runtime-preparation subprocesses) — i.e. the credential-scrubbing contract is stated identically in both languages, and the pairing hashes exist precisely so neither side can quietly drift on a security promise.

### apps/desktop/windows-signing/README.i18n.yaml
- Purpose: The **bilingual-pair consistency record** for `README.md` — 43 lines, 14 section entries, each a 16-hex hash of that section's English and Chinese blocks. Its header comment states the rule: "per heading section, a hash of its English and Chinese blocks outside code blocks and generated regions. After editing either side, bring the other along and re-record with: `pnpm run verify-translation-pairing --write apps/desktop/windows-signing/README.md`".
- Key abstractions: a **section-keyed hash manifest** keyed by the section's English heading-slug path (`/` for the text before the first heading, a repeated path getting `~2`, `~3`, …). Section *i* of one side corresponds to section *i* of the other; each side's hash covers every top-level block of the section except fenced code blocks and generated regions (the two kinds of content the gate already requires to be identical).
- Data flow: the gate `pnpm run verify-translation-pairing` (root `package.json` line 129, `scripts/verify-translation-pairing.ts`) recomputes the hashes from the current file contents and compares them with this file; `--write` regenerates it. The record is the **reviewable artifact** of a human confirming the two sides agree.
- Non-obvious design decisions: hashing **per section** rather than per file is deliberate — it means two branches editing *different* sections produce different YAML lines and Git's default text merge composes them, while a conflict only occurs when both branches changed hashed content in the *same* section. A whole-file hash would make every translation PR an unmergeable conflict. Excluding code blocks and generated regions from the hash is what lets a generator refresh both languages without a manual re-record.
- Edge cases / failure handling: a section with no remaining blocks has **no** entry (so the record is not a fixed-size table); an out-of-sync pair is repaired by patching the counterpart minimally against the edited side's diff, never by re-translating the whole file, and the gate names each changed section. The record is validated as malformed if an entry lacks the `en:`/`zh:` 16-hex pair (verifier line 233).
- Surprising: the file is the *only* place in the repo that states "the two languages are equal authority and the binding is that they say the same thing" in machine-checkable form — a doc-drift detector that is also a merge strategy.

## Ideas worth stealing

- **Turn "the runtime can only resolve N" into a build-time allowlist, so an unresolvable import fails the build instead of the launch** - `apps/desktop/tsdown.config.ts:38` - The command-manager bundle is built with `packagedImportsPlugin({ packages: new Set(), nodeBuiltins: true })`: zero bare package imports may survive, and Node builtins may. The main bundle gets `electron` + the manifest's `dependencies` (line 16); a sandboxed preload gets exactly `{electron, events, timers, url}` and **no** Node builtins (line 21). The plugin implementation (in `apps/desktop/scripts/desktop-bundle-imports.mjs`, read for context) enumerates every static import, dynamic `import()` and `require()` of every module in the bundle and fails the build with the importing module's name when one of them cannot be resolved at runtime. For August this is the missing counterpart to the "static gates cannot see whether the app starts" problem: a static gate that compares every bare import of every built artifact against what the installer actually ships converts a launch-time `ERR_MODULE_NOT_FOUND` into a build-time error. The policy object is a one-line adaptation per artifact class (main / preload / privileged helper).

- **Give the privileged/escalated helper its own bundle with a closed dependency set** - `apps/desktop/tsdown.config.ts:36-48` - `command-manager-entry.js` is the process that installs `/usr/local/bin/dsh` on macOS via `osascript` elevation, and it is bundled **separately from `main.js`**, with `packages: new Set()` and a single `deps.alwaysBundle: ['@deepseek-ai/dsh-atomic-write']`. The consequence is structural: nobody can add an import to the elevated worker and have it silently pull in a package, because the bundler refuses to leave a bare specifier. August has the same class of component (anything that runs outside the sandbox, or with the user's own credentials) and can copy the shape — a separate entry with an explicit closed-world bundle — rather than relying on review to notice that a privileged process grew a dependency.

- **Preload/main module universes differ, and the build encodes which one each artifact gets** - `apps/desktop/tsdown.config.ts:21` - `preloadImports = { packages: new Set(['electron', 'events', 'timers', 'url']), nodeBuiltins: false }` with the reason stated inline ("Electron: Process Sandboxing, 'Preload scripts'"). A sandboxed preload's `require` polyfill offers only that set, so anything else is a renderer crash; the bundler makes the runtime's resolution limit a build policy instead of a runtime surprise. The same trick transfers to any in-process bridge August builds (an embedded Python bridge, a tool-host IPC shim): give each trust class its own explicit module allowlist.

- **Credential handling as an allowlist that is *withheld*, not a denylist that is *stripped*** - `apps/desktop/windows-signing/README.md:55` - "Packaging withholds every `DSH_DESKTOP_WINDOWS_*` field from build and runtime-preparation subprocesses, gives signing preflight, the dedicated runtime signing stages and electron-builder only the four configured inputs, gives the signing CMD only the validated signing fields in an otherwise scrubbed environment, clears those fields before SignTool starts, and redacts SignTool diagnostics." Note the shape: subprocesses receive *exactly* what they need, not "everything except the secrets". This is the same discipline August already applies to tool permissions (a deny set on the executor, not a filtered offer list) — and it is worth copying at the *process boundary* rather than only at the tool boundary, because a build subprocess is exactly where a key pasted into a log or an env var leaks from.

- **A retry policy that distinguishes "the command ran and refused" from "we don't know what happened"** - `apps/desktop/windows-signing/README.md:69` - "Timestamp completion retries only a normally exited timestamp command returning failure or warning, at most three times with one- and two-second delays. Each attempt starts from the same verified primary signature. Launch errors, uncertain termination and verification failures stop immediately." Three transferable properties: (a) retry only the *observable* failure; (b) every attempt restarts from the same **verified** prior state, so a retry cannot compound a partially-applied change; (c) the retry count is tiny and the delays are explicit. August's tool-retry ladder needs exactly this discrimination — a timeout ("uncertain termination") is not the same as a refusal, and retrying an uncertain termination can double-apply a side effect.

- **A failure that the failure itself makes unrecoverable must never auto-retry** - `apps/desktop/windows-signing/README.md:75` - "`SignTool Error: No private key is available.`" is treated as terminal: "The device-specific PIN retry limit and remaining attempts are unverified; do not probe them with authentication attempts." The mechanism is a **persistent interlock file** (`%USERPROFILE%/.dsh-desktop-signing/attempt.json`) acquired atomically before the command interpreter runs and released only by a successful sign *plus* verification of the primary signature; "There is no timed recovery or automatic retry… logging into the token or replacing a PIN file does not clear it" (line 79). For August: any external resource whose failure burns a retry counter (a rate-limit budget, a hardware token, a provider key) needs a persistent, human-cleared interlock rather than a backoff, and the doc must say plainly which state the interlock does *not* observe.

- **A canary that exercises the exact credential path with a throwaway payload, under one deadline, never executed** - `apps/desktop/windows-signing/README.md:65` - "The local .NET Framework C# compiler creates a small private probe; the production signer signs it once, and verification requires the configured certificate and a timestamp before building continues. The probe is never executed. The overall 60-second preflight deadline includes timestamp attempts; deadline expiry, hardware signing errors and verification failures stop the run without another hardware attempt." The probe proves the *whole* path (sign → timestamp → verify) in seconds instead of discovering a dead token 30 minutes into a build, and the deadline covers the slow part. The doc also states its own limit: "Success proves the current signing path works, not that the PIN was independently authenticated." August's equivalent is a cheap end-to-end credential canary run *before* a long job (a one-token model call, a sandbox write to a temp dir), with the honest caveat about what it does not prove.

- **Run the cheap path concurrently; run the expensive path strictly serially, and never let a bad cache entry fall back to the expensive path** - `apps/desktop/windows-signing/README.md:89` and `:85` - "All restores and their post-verification finish before cache misses enter serial hardware signing." and "Every restoration checks the digest, Windows trust, timestamp and certificate before replacing the unsigned file; invalid entries stop packaging without hardware fallback. Cache age alone does not trigger signing." Three rules worth lifting wholesale: concurrency is spent on verification (cheap), the expensive resource is serialized, and **a corrupt cache is a stop, not a fallback** — falling back would burn the scarce resource exactly when the system is already untrustworthy. The same "cache hit must be verified as strongly as a fresh computation, and a failed verification must not silently become a re-computation" rule applies to any cached prompt prefix or compiled artifact August keeps.

- **A watchdog's own restart budget must be persisted and must not be refillable by the event it is watching** - `apps/desktop/windows-signing/README.md:41` - "The persisted budget permits the initial launch plus `-RestartCount` restarts (default `10`) between explicit starts. Every desktop login also consumes this budget; `status` shows the remaining launches. After the budget is exhausted, login alone cannot restart the runner. Starting an already running task does not reset the budget." The subtlety is that a human action (logging in) must **not** silently refill a crash-loop budget — otherwise the loop can run forever and the operator never sees it. Transferable to August's unattended/Bot path: any auto-restart of a stuck worker needs a persisted, non-refillable-by-ordinary-activity budget.

- **Every stage emits one structured summary line with hits, misses, avoidances and failure counts** - `apps/desktop/windows-signing/README.md:91` - "Each runtime stage writes `SIGNATURE_CACHE_SUMMARY` to stdout and its packaging journal, including the actual directory, policy identity, hit/miss counts, newly published and retained entries, signing requests, avoided signing requests and validation failures." Note "**avoided** signing requests" — the summary measures what the cache *saved*, not just what it did. August's Usage/turn-outcome surfaces should report avoided work (compaction skipped, cache hit, prompt prefix reused) with the same discipline, so an efficiency mechanism is visible rather than invisible.

- **A build artefact digest that binds the environment to the bytes** - `apps/desktop/tsdown.config.ts:32-33` - `const clientVersionDefine = { 'process.env.DSH_CLIENT_VERSION': JSON.stringify(clientVersion) }` with the comment "Inline the one public build value the Node entry reads; every other variable stays a runtime lookup." The companion machinery in `scripts/client-build-environment.ts` (read for context) writes `.dsh-build/client-build-environment.json` containing the exact public environment *and* a SHA-256 digest over every produced client artifact, and `readClientBuildRecord` refuses a record whose digest no longer matches the files on disk. Transfer: a "what exactly is running" file whose digest proves the bytes on disk are the bytes the metadata describes — exactly what August's `turn_outcomes` / session-log audit wants, but for the build itself.

- **A section-keyed hash record makes a translation gate mergeable** - `apps/desktop/windows-signing/README.i18n.yaml:1-43` - One 16-hex hash per heading section per language, keyed by the English heading-slug path, excluding fenced code blocks and generated regions. Because the record is section-keyed, two branches editing different sections touch different YAML lines and Git merges them; a conflict only happens when both changed the same section's hashed content. The same per-section hash record works for any August artifact that must stay in sync across two producers (e.g. a docs page and the config table that describes it) — and unlike a whole-file hash it degrades to "these two sections disagree", which is actionable.

- **An operator runbook that states its own isolation limits and what it does *not* authorise** - `apps/desktop/windows-signing/README.md:27` and `:99` - The first section is a threat model of the build system itself ("The shared packaging runner assumes trusted internal code… signed/master-only access is not enforced… Direct device calls can bypass the signing scripts and exhaust PIN retries"), and the last is a disclaimer of scope ("This document does not authorize PIN retries, automatic interlock deletion, device initialization or changes to the accepted isolation policy"). Few internal runbooks say what they do not permit. August's AGENTS.md-style notes would benefit from the same convention: each operational doc names the actions it does *not* authorise, so an agent reading it does not mistake it for permission.
