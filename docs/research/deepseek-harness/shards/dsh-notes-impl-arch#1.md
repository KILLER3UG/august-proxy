# deepseek-harness / dsh-notes-impl-arch#1

## Shard shape

This shard is the **architecture decision record set** of the `deepseek-harness` repository: 260 files under `.agents/notes/implemented/architecture/`, comprising **87 English "Agent Notes"** (ADR-shaped markdown, each with Problem → Decision → Alternatives → Consequences, plus a bilingual translation), **86 Chinese translations** (`*.zh.md`, one per English note except `2026-09-11-plugin-owned-message-projections`), and **87 bilingual-pairing consistency records** (`*.i18n.yaml`, a generated per-heading hash table proving the English and Chinese blocks match). The English notes are the only files carrying independent content; the `.zh.md` and `.i18n.yaml` files are mechanical derivatives of them, and I confirmed that by line-count parity (every `.zh.md` has exactly the same line count as its English sibling) and by the pairing records' heading-key counts.

The notes themselves fall into five interlocking families. **(a) The core session substrate** — event-sourced sessions, an ordered "surface" projection over the event log, immutable identified messages, canonical event envelopes, log versioning, and the streaming migration stages. **(b) The agent loop and its edges** — bounded LLM request recovery, provider-routed adapters, tool-call timeout policy, cooperative cancellation, tool-output spilling, and the web capability seam. **(c) The client** — a Cordis-microkernel plugin loader with hot reload, a slot/type system for plugin-composed UI, a conversation-node assembly engine, a resource model, session-observation/projection state, and the Electron desktop packaging. **(d) Configuration, packaging and trust** — one harness-home resolver, one configuration-source ordering, profile plugin bundles, an outbound proxy policy, browser trust and token authentication, credential records, and the single-file Python SDK runtime. **(e) Cross-cutting policy notes** — event-domain semantics, capability seams, and the "no verifier gate" style notes that record *why a mechanism was deliberately left out*. Together they read as a single argument: *the durable log is the only source of truth, every model-visible fact has exactly one owner, and every observable surface (UI, transport, filesystem) is derived from that log rather than maintaining a second copy.*

## Per-file notes

### .agents/notes/implemented/architecture/2026-06-11-dev-invariants-over-deep-readonly.md
- Purpose: Make the session log's immutability an always-on runtime boundary of `Session`, not an optional plugin or a TypeScript `readonly` type.
- Key abstractions: `Session.append()` boundary, recursive lossless JSON snapshot, deep-freeze, `snapshotEvents(fromSeq?, toSeqExclusive?)`, `eventAt(seq)`, `seq`, `deriveMessages()`.
- Data flow: caller event → one recursive snapshot pass (rejects unsupported values, detaches nested references) → deep-freeze → published to `session/event` observers and `eventAt`; derived messages are separate deep-frozen projections over the log.
- Non-obvious design decisions: TypeScript `DeepReadonly<T>` was rejected because types are erased and a cast bypasses them (lines 15, 35-37); a dev-only freezing plugin was rejected because "code could pass development tests and still corrupt history in production" (line 39-41); `deriveMessages()` detachment is an *additional* isolation boundary, not a substitute for the log protecting itself (line 43-45).
- Edge cases / failure handling: a stateful getter could otherwise let validation and storage observe different values; seed records go through the same validation/snapshot/freeze path before construction succeeds (line 25).
- Surprising: the note explicitly scopes out relationship rules ("immutability of individual values does not establish relationships among records", line 13) — a deliberate decision not to grow this note into a session-semantics note.

### .agents/notes/implemented/architecture/2026-06-11-event-sourced-sessions.md
- Purpose: Define the session as an append-only typed event log and make the LLM message history a *derivation* of it.
- Key abstractions: `Session`, `SessionEvent`, `deriveMessages()`, `session/event`, `session/flush`, replay/fork = seeding a new session with an existing log.
- Data flow: loop claims inbox → `agent/pre-step` → append returned `user/message` batch → derive request → assemble provider output → append `assistant/message` → dispatch tools; persistence plugins buffer write-behind and drain at the awaited `session/flush` at every turn end.
- Non-obvious design decisions: raw stream chunks are logged for token-level replay fidelity while the assembled `assistant/message` is authoritative for derivation (line 13); a mutable message array with events as notifications was rejected because "with event-sourcing the log IS the state, so divergence is structurally impossible" (line 21).
- Edge cases / failure handling: the ordering contract is pinned by regression tests — "the durable log records the exact message the tools follow" (line 17).
- Surprising: derivation cost grows with log length, and the stated mitigation is compaction, *not* log mutation (line 28) — an explicit trade of memory for a single source of truth.

### .agents/notes/implemented/architecture/2026-06-13-capability-seams.md
- Purpose: Name the three roles of a swappable capability (Service Definition / Service Provider / Consumer) and the package boundaries that follow.
- Key abstractions: `ctx.<key>` Cordis service, vocabulary types, consumer-side tool schemas, the "seam" term itself.
- Data flow: a Service Definition owns the contract; Providers register implementations; Consumers inject the service key and never import provider-specific types.
- Non-obvious design decisions: roles normally live in separate packages "when they evolve independently, but the split is not mandatory when the roles are genuinely one concern" — the LLM seam folds Definition and Consumer into `dsh-llm` (line 25); `@cordisjs/plugin-capability` is a *permission/security* service and explicitly NOT a mechanism for swapping implementations (line 34).
- Edge cases / failure handling: "Don't split preemptively — a capability with one conceivable provider and one Consumer stays one package until a second appears" (line 25).
- Surprising: the note defines what a "seam" is *not* (a single role), and flags the trap that "capability" means two different things in the ecosystem (line 29, line 34).

### .agents/notes/implemented/architecture/2026-06-13-twin-llm-adapters.md
- Purpose: Ship two real LLM adapters against one provider-neutral `StreamChunk` vocabulary so the "neutral" claim is continuously verified.
- Key abstractions: `StreamChunk` protocol (`block-start`, `text-delta`, `reasoning-delta`, `tool-call-delta`, `block-end`, `usage`, `finish`), content-block types, `dsh-llm-deepseek` (direct fetch), `dsh-llm-pi-ai` (SDK-backed).
- Data flow: adapter → provider-neutral chunk vocabulary → loop; the DeepSeek adapter delegates SSE framing to `eventsource-parser`, the pi-ai adapter has its own event vocabulary.
- Non-obvious design decisions: the rule is "anything the StreamChunk vocabulary cannot express for BOTH implementations is a core-vocabulary bug" (line 18); the twin identity is owning fetch/translate internals, not hand-rolling transport plumbing (line 15).
- Edge cases / failure handling: two sanctioned error paths (throw from `stream()` *or* end with `finish {kind:'error'|'aborted'}`) that a consumer must handle on both sides — a divergence the SDK adapter surfaced that a single direct-fetch adapter would have hidden (line 18).
- Surprising: the vocabulary conventions pinned by the twin include "usage emitted before finish, nothing after finish, tool-call `arguments` as raw JSON strings end-to-end" (line 18) — a concrete wire contract extracted from a design-verification exercise.

### .agents/notes/implemented/architecture/2026-06-18-session-surface.md
- Purpose: Add a *surface* — a derived, cached order of event sequences — so history manipulation (compaction, pruning) is durable and ordered rather than listener-order dependent.
- Key abstractions: `SurfaceManager`, `SessionSurface`, `SurfaceOp` (`'append'` | `{op:'replace', startSeq, endSeq}`), `sourceEventSeqs?: SessionSeq[]`, `surfaceOp` on the four surface event types.
- Data flow: `Session` owns one `SurfaceManager` holding an ordered `SessionSeq[]`; it validates each seed/append candidate before commit, then processes only committed events since the last sync (delta-based, O(new events)); `deriveMessages()` walks the surface as its sole derivation path.
- Non-obvious design decisions: replacement endpoints are **inclusive** and identified by surface event seqs (half-open was rejected, line 55); a linked node map was rejected because production never read predecessor links and one array has the same asymptotics (line 56); a dirty-flag full rebuild was rejected as O(N²) over a session's lifetime (line 57).
- Edge cases / failure handling: `sourceEventSeqs` must be non-empty, unique, earlier and known; `assistant/message` may not carry it; a surface-eligible event without `surfaceOp` is invalid, not an implicit append (line 36, 48); crash repair synthesises `tool/result` closers carrying `surfaceOp:'append'` and the orphaned call's seq (line 44).
- Surprising: the surface exists so *compaction* has a place to live — a compaction appends one `user/message` carrying the summary with a `replace` op, while its own trace events stay off-surface (line 66).

### .agents/notes/implemented/architecture/2026-06-21-bounded-llm-request-recovery.md
- Purpose: Give transient provider failures a bounded, observable recovery path without a second response lifecycle.
- Key abstractions: `LlmFailure` (JSON-serializable: `message`, `code`, `status?`, `providerRetryAfterMs?`, `requestId?`), `LlmError`, `agent/request-error` waterfall, `dsh-llm-retry` plugin, `llm/retry` session event, `assistant/attempt`, `streamIdleTimeoutMs`, `idleWatchdog`.
- Data flow: adapter throws or ends with a terminal finish → `LlmRuntime` normalises to one `LlmFailure` → loop passes it to `agent/request-error` → the retry plugin decides (transient code + budget) → it appends a durable non-surface `llm/retry` event, awaits the backoff, returns `{kind:'retry'}` → the next attempt reconstructs its request from the durable surface.
- Non-obvious design decisions: `LlmFailure` deliberately has **no** `retryable`/`failover`/`partialOutput` fields because "adapters report facts while deployment policy decides action" (line 41, line 102); the transient code set is intentionally small (RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT, EMPTY_RESPONSE) (line 49); adapter SDK retries are disabled so one `stream()` = one visible attempt (line 71); a provider-supplied delay *replaces* exponential backoff only when it does not exceed `maxDelayMs` — a longer provider delay causes delegation rather than an earlier retry that violates the provider instruction (line 59).
- Edge cases / failure handling: the plugin owns a lifetime `AbortController` and tracks every active recovery callback, so HMR disposal aborts and awaits them and a captured callback can neither retry nor enter the rest of its waterfall after disposal (line 61); defaults are 2 transient retries, 500 ms initial delay, 10 s cap, 10 % jitter, chosen to match the conservative edge of OpenCode / Pi / Codex (line 57); a partial-chunk failure still attributes the chunks to the failed step and commits no assistant message or tool side effect (line 118).
- Surprising: the Web countdown "anchors the scheduled delay to browser receipt rather than the Host event clock" and the retry chain is projected to ONE stable row (line 85); a retry can still duplicate provider billing even when no chunk arrived (line 125).

### .agents/notes/implemented/architecture/2026-06-24-web-capability-seam.md
- Purpose: Give the model stable `web_search` / `web_fetch` tools while multiple providers change underneath, without provider knobs leaking into the model contract.
- Key abstractions: `ctx.web` (registry + execution API), `WebSearchProvider` / `WebFetchProvider`, `WebSearchRequest`/`WebSearchResult`, `WebFetchRequest`/`WebFetchResult`, `WebFetchBody` closed union, `WebError` code space.
- Data flow: provider packages register capabilities with `ctx.web`; `dsh-tool-web` owns the model-facing schemas and calls `ctx.web.search()`/`fetch()`; the provider is resolved **at execution time**, so schema registration never depends on provider availability.
- Non-obvious design decisions: the model schema is deliberately thin — `max_results` is a `dsh-tool-web` config knob, not a model argument (line 165); the seam *truncates* `sources[]` to `maxResults` itself so the bound is a single cross-provider guarantee (line 172); selection never depends on registration order — multiple usable providers with no configured id is `WEB_PROVIDER_AMBIGUOUS`, not "first wins" (line 116-126); the fetch provider validates the whole DNS answer set and pins it in the Undici lookup callback, closing the DNS-rebinding interval (line 242, line 318).
- Edge cases / failure handling: a missing/unconfigured/ambiguous provider yields a structured `WebError` at execution time, never `UNKNOWN_TOOL`; cross-origin redirects fail with `WEB_REDIRECT_BLOCKED` and require a fresh call (line 245); the provider rejects an entire DNS answer set if any address is non-public, fail-closed (line 248).
- Surprising: HTTP status is *not* a tool failure — a `404` returns a normal `WebFetchResult` with the status and a bounded body; `WebError` is only for failures to safely retrieve the resource (line 213).

### .agents/notes/implemented/architecture/2026-06-30-event-domain-semantics.md
- Purpose: Draw one line between the three Cordis event domains so a plugin author knows where to subscribe.
- Key abstractions: `session/*` (durable `SessionEventMap` fact log), `agent/*` (live runtime signals carrying the live `Agent`), `tools/*` (registry and execution pipeline).
- Data flow: `Session.append` emits one `session/event` per append plus a `session/flush` durability checkpoint; live rendering and replay projections read the same `session/event` feed.
- Non-obvious design decisions: all four boundary mirrors (`agent/turn-start/end`, `agent/step-start/end`) were **removed** because no consumer needs the live `Agent` at a boundary — the ACP bridge correlates its in-flight prompt with the exact `session/event` pair (line 29); the boundary rule is one sentence: "a durable, replayable fact is a `SessionEvent`; a live interception or a transient/live-object signal is an `agent`/`tools` Cordis event" (line 27).
- Edge cases / failure handling: `Session.append` owns post-commit observer containment, so a throwing boundary observer cannot change the turn outcome or starve later consumers; an acceptance failure still escapes before the boundary enters the log (line 33).
- Surprising: this is a *pre-format* note (the marker at line 39 says alternatives were not recorded) and it is the canonical authority for the later "remove agent boundary mirror events" simplification.

### .agents/notes/implemented/architecture/2026-07-02-tool-render-intent-union.md
- Purpose: Replace the bag of optional `presentCall`/`presentResult` fields with a closed, tagged render-intent union.
- Key abstractions: `ToolCallView = GenericCallView | TerminalCallView | DiffCallView`, `ToolResultView = GenericResultView | TerminalResultView`, required `card` discriminant, `FileDiff {path, oldText, newText}`.
- Data flow: a tool declares one intent per call/result; the bridge `switch (view.card)` and `assertNever` on the default arm; a `diff` intent is a first-class affordance (`oldText: null` ⇒ new file).
- Non-obvious design decisions: `card` is **required** on every variant, not an optional default (line 39); the union is *closed* — "a plugin-added variant that the bridge silently drops would be worse than a compile error" (line 39); the fenced-console fallback for a UI without terminal capability moved to the **bridge**, not the tool (line 55).
- Edge cases / failure handling: `presentCall`/`presentResult` remain *pure functions of args* so they can run on live streaming and on session-log replay — "they must be replay-deterministic" (line 61); a `terminal` call that also sets `content` (description above the card) is the one meaningful combination.
- Surprising: the terminal intent is display-only — "a UI projects the completed call and never becomes a second execution backend" (line 57).

### .agents/notes/implemented/architecture/2026-07-05-prompt-variables-and-tool-guidance-ownership.md
- Purpose: Establish "every prompt fact has exactly one owner" and remove hand-written tool guidance from persona strings.
- Key abstractions: `SystemPrompt.assemble(context)`, `AssembleContext` (merge-extensible, with `scope` and a typed `agent` field), `ctx.systemPrompt.variable(name, provider)`, `{{name}}` interpolation, `harness:identity` section at order `-1000`, `deployment:persona-prefix` at order 0, `renderPrompt(assembly)`.
- Data flow: the loop registers `provider` and `model` as pure projections of the context agent → persona references `{{model}}` → one `renderPrompt(assembly)` path produces the exact prompt later replayed by `ctx.tokenMeter` and recorded in the routed request header.
- Non-obvious design decisions: the loop string-joined the persona *after* the assembled sections, so the model read "Use the read tool…" before "You are a coding agent" — identity-first was the convention (line 15); per-tool semantics live in the tool description and cross-call habits in the tool package's prompt section, so "loading or dropping a tool plugin no longer means editing any deployment's persona" (line 67); lenient interpolation was rejected because a typo ships `{{modle}}` and nobody notices (line 50).
- Edge cases / failure handling: rendering rejects unknown own-property references, providers returning `undefined`, malformed complete references and unbalanced references that still contain a closing `}}`; a lone unmatched `{{` stays prose; substituted values are not rescanned (line 29); `tools:sdk` sets `interpolate: false` because tool schemas document their own `{{…}}` syntax.
- Surprising: the note accepts a known staleness window — a plugin that switches models in the `agent/request` waterfall makes the prompt's claim stale for that step, and the remedy is the ownership rule itself (the plugin states it early on the `system-prompt/assemble` waterfall) (line 68).

### .agents/notes/implemented/architecture/2026-07-05-reconstructable-requests.md
- Purpose: Make every LLM request reconstructable from the session log, so provider prefix caching and byte-exact replay are consequences rather than goals.
- Key abstractions: "Model-visible ⟺ durably referenced", `deriveEventMessage(event)` (public per-event projection), `EpochHeader {config, adapterDefaults?, tools?}`, `request/header` with reasons `initial | resume | change | series`, `request/context`, `markAgentLoopRequest()`.
- Data flow: each step claims its inbox batch → assembles prompt and tools → projects the rendered prompt against the surviving `system/message` node → `agent/pre-step` → `step/start` → commit prompt + `user/message` events → `agent/request` may replace only the frozen call-config seed → record the owed header snapshot → build `GenerateOptions` from derived messages + header → freeze (leaving `AbortSignal` live).
- Non-obvious design decisions: prefix-cache stability is "corollary #1, not the headline: an append-only log projected by a per-node pure function yields requests that are append-extensions of their predecessors whenever the header is unchanged — stability is emergent, not managed" (line 19); per-call request scalars were rejected because a listener could flip the model per call "with zero accounting, silently abandoning the provider cache this design exists to protect" (line 41); event-driven assembly was rejected as a missed-signal bug class (line 43); a header-delta codec was rejected in favour of full snapshots to retain one replay representation (line 44).
- Edge cases / failure handling: writers omit `tools: []` and `adapterDefaults: {}` and current acceptance *rejects* those fields rather than repairing them; a `change` snapshot carries `startsSeries: true` when the changed request also starts a series; a web model selection restored from the log omits an adapter-owned effort so a false change is not detected (line 25).
- Surprising: the production cache signal is *per-step usage* — "a header change or compaction appears as a cache-read drop on the next step" (line 31).

### .agents/notes/implemented/architecture/2026-07-06-timeout-deadline-library.md
- Purpose: Extract the shared timing/classification half of timeout into one library, leaving the hard kill to each capability.
- Key abstractions: `TimeoutReason`, `clampTimeout(requested, def, max, name?)`, `deadline(upstream, timeoutMs, code)` (fused signal + `Symbol.dispose`), `IdleWatchdog {signal, next(), pulse(), dispose}`, `timeoutOf(x, code?)`.
- Data flow: a capability calls `deadline()`/`idleWatchdog()`, passes the returned signal to its transport, and on abort calls `timeoutOf(signal, code)` to classify the first abort reason as timeout vs cancellation.
- Non-obvious design decisions: the package is a **library of pure functions**, not a Cordis service — "there is deliberately no central 'timeout service' that would have to know how to stop every capability's work" (line 19); `withTimeout(promise, ms)` was rejected because it "resolves the *tool-call* promise on deadline without stopping the underlying work" (line 114); `timeoutOf(signal, code)` scopes the match to this deadline's own timer, so a nested deadline does not steal the outer one's classification (line 71); file read/write/edit take **no** `timeoutMs` at all because a local syscall cannot be forced to stop (line 90).
- Edge cases / failure handling: `timeoutMs <= 0` is an internal no-timeout sentinel for background jobs; a pulse outside an outstanding demand or after disposal is a no-op; concurrent demand fails; the idle watchdog settles the one demand it drives when a transport abandons it (line 75, 104).
- Surprising: the division-of-labor table (lines 79-88) is the note's real payload: `dsh-timeout` owns clamp/arm/clear/classify; the capability owns *actually terminate the work*; the capability owns the default/max values and the timeout `code` string.

### .agents/notes/implemented/architecture/2026-07-07-tool-call-timeout-policy.md
- Purpose: Make tool-call timeout a deployment *policy* (a plugin) rather than a per-tool implementation detail, for model-facing tools only.
- Key abstractions: `tools/execute` around-dispatch waterfall (between `tools/pre-execute` and `tools/post-execute`), `ToolDefinition.timeoutMs`, `@deepseek-ai/dsh-tool-call-timeout-policy`, `TOOL_TIMEOUT` result code.
- Data flow: `ctx.tools.execute(exec)` → `tools/pre-execute` → `tools/execute` (base `next()` = dispatch-with-normalization) → `tool.execute(args, exec)` → `tools/post-execute`; the enforcer derives a deadline, assigns it to `exec.signal`, and converts its own expiry into a `TOOL_TIMEOUT` result.
- Non-obvious design decisions: the base `next()` being *dispatch-with-normalization* is load-bearing — the registry converts a thrown upstream-abort into a normal error result first, and only then can the policy replace it with `TOOL_TIMEOUT` (line 39); the signal is supplied by **in-place mutation of `exec.signal`** because Cordis's waterfall `next()` ignores arguments and re-invokes downstream listeners with the shared payload array (line 57); the budget is declared on the tool, not in the plugin, so a misspelled unused policy is impossible (line 43).
- Edge cases / failure handling: a tool declaring no `timeoutMs` gets no deadline (conservative default, line 33); the plugin restores the caller's original signal in a `finally` so `tools/post-execute` never sees the deadline (line 57); a timeout-policy signal reaching the fetch provider first is provider-scoped as `WEB_ABORTED`, and the outer wrapper then replaces the final result with `TOOL_TIMEOUT` (line 82).
- Surprising: declaring `timeoutMs` **means** "this tool is cooperative with `exec.signal`" — a misconfiguration risk the plugin README states as its contract (line 74); a `tools/execute` wrapper that returned a new `exec` object would silently do nothing.

### .agents/notes/implemented/architecture/2026-07-08-tool-output-spill-files.md
- Purpose: Keep oversized tool results out of the next model request while leaving the full result readable later with existing file tools.
- Key abstractions: `ctx.spillStore` seam (`saveText` → `{locator, bytes, retrievalHint}`), `SpillSource` (`tool` | `session-reference`), branded `SpillLocator`, `dsh-spill-local`, `dsh-spill-policy` (`maxInlineTokens`), `dsh-output-retention` (`TextRetainer`/`ItemRetainer`).
- Data flow: final tool result → `tools/post-execute` → policy retains ordered text/image ends under `maxInlineTokens` → oversized results are replaced by a preview plus a spill locator; the model follows the backend-supplied retrieval hint and reads the file with `read`/`grep`.
- Non-obvious design decisions: the seam is deliberately minimal — "save text and return a locator plus retrieval hint" — because a broad `tool-results` package would invite retention policy, replacement, preview wording, search and early spill into one seam (line 166); the local backend writes with `open(path, 'wx', 0o600)` — exclusive and owner-only — "so a planted symlink cannot redirect it" (line 65); spill files are runtime artifacts, not model-authored workspace edits, so they are NOT written through `ctx.fs.writeText` (line 168).
- Edge cases / failure handling: an omitted budget installs no listeners; recovery failures keep the original result; model-facing `read` results skip retention "to avoid a read/spill loop" (line 69); a provider that already returned `truncated: true` means the spill file holds the *formatted result*, not the original page — the policy does not claim otherwise (line 106).
- Surprising: through a proxy `web_fetch` stops resolving and pinning entirely, because the proxy performs the origin's DNS — the one outward-facing security promise this shard's proxy note later alters (see `2026-08-27-outbound-proxy-policy.md`).

### .agents/notes/implemented/architecture/2026-07-10-single-file-executable-sdk-runtime-distribution.md
- Purpose: Ship the Python SDK's runtime as a single-file executable with no system Node, where the booted plugin set is decided entirely by an external `cordis.yml`.
- Key abstractions: `@yao-pkg/pkg --sea` (enhanced SEA with a `/snapshot` VFS), `dsh-python-runtime-closure` (a zero-code pure dependency manifest that IS the deploy root), `HarnessSdkJsonRpcServer`, `runtime-bootstrap.mjs`, `DSH_RUNTIME_MODE=node` dev carrier.
- Data flow: `verify-runtime-closure` → build → `pnpm --filter dsh-python-runtime-closure deploy` into the wheel's `runtime/node/` → symlinks replaced with target bytes → `pkg --sea` per target → executable + `-rg` sidecar + Office skill assets copied into the runtime directory.
- Non-obvious design decisions: a repo-owned patch removes pkg's `patchChildProcess` call, because unpatched pkg rewrites a spawned `node` (including the string after `-c`) to the executable itself, so a model-issued `node --version` silently booted the dsh CLI (line 24); the same patch makes native-addon extraction atomic via a same-directory temp file + `renameSync`, because upstream's `writeFileSync` could truncate a file another process had already mapped — measured 39/80 concurrent first starts died with SIGBUS before the change and 0/80 after (line 26); the deploy root is a *manifest package*, not the app bin, so the "packaging manifest masquerading as real dependency relationships" objection is avoided (line 87).
- Edge cases / failure handling: bare specifiers inside the VFS resolve upward along `node_modules` and fail loudly for a name outside the set; a config inside another Node project cannot shadow the packaged plugin set (line 41); pkg standard mode was killed by a PoC, not a trade-off — every `import()` throws `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` (line 83).
- Surprising: `stdin` EOF is treated as "the client is gone" and disposes immediately, so a short-lived pipe aborts an in-flight turn (line 75).

### .agents/notes/implemented/architecture/2026-07-14-provider-routed-llm-adapters.md
- Purpose: Make the *provider* the adapter registration key so one deployment can serve an open-ended model catalog.
- Key abstractions: `GenerateOptions.provider` + `.model`, `LlmRuntime.registerAdapter(providers, adapter)`, explicit pi-ai provider profiles, `ReplayEnvelope` (response-level + per-block), `BlockAssembler` keep/drop alignment.
- Data flow: a request names `{provider, model}` → `LlmRuntime` resolves the provider's single adapter owner → the adapter serialises → the terminal `finish` chunk may carry replay state → the loop attaches it to the assembled assistant message → later turns hand it back to the *same* adapter instance.
- Non-obvious design decisions: model ids are **not** registration keys (line 23); a provider has exactly one adapter owner per Cordis context — loading two is a configuration error, not an ordering rule or fallback (line 25); pi-ai's `maxRetries` is forced to zero so one `stream()` is one visible attempt (line 31); an explicitly empty API key is invalid configuration rather than an environment fallback (line 31); replay state is portable only within the adapter instance that owns *both* the historical and target providers — a different adapter receives provider-neutral content only (line 82).
- Edge cases / failure handling: `registerAdapter` validates the whole provider list before mutating the registry, rejects duplicates with `DUPLICATE_ADAPTER`, and disposes the whole registration as one effect (line 23); replay state that an adapter cannot use degrades that message to provider-neutral conversion with a diagnostic rather than failing (line 82); `dsh-llm-pi-ai` rejects a defined `stop` option with `UNSUPPORTED_OPTION` rather than silently ignoring it (line 37).
- Surprising: the note records that this was a repo-wide breaking API change with no compatibility aliases, and that a pi-ai dependency update can change the accepted provider/model catalog, so the lockfile and adapter e2e matrix *define* the tested set (line 93).

### .agents/notes/implemented/architecture/2026-07-15-agent-initiator-scope.md
- Purpose: Carry the initiating Agent below explicit parameters for deep process-local infrastructure, without turning it into a model-visible or globally-mutable fact.
- Key abstractions: `ctx.agents` service over Node `AsyncLocalStorage`, `currentInitiator()`, `requireInitiator()`, `withInitiator(agent, op)`, `withoutInitiator(op)`, a private run-token lineage.
- Data flow: `AgentLoop` wraps each concrete driver's whole `runLoop` lifetime in `agents.withInitiator(agent, …)`; package-private loop/turn/step/tool entries recover the exact Agent from `ctx.agents` and derive `agent.session` once.
- Non-obvious design decisions: ALS stores the exact `Agent` directly rather than a one-field frame, because Agent/Session/inbox/cancellation already have authoritative owners and a copied field would go stale (line 15, 47); "ambient identity does not replace explicit contracts" — `ToolExecution.agent`, `AssembleContext.agent`, `GenerateOptions.sessionId`, job ownership, approval subjects all stay explicit (line 23); a process-global mutable slot is incorrect across `await` (line 51).
- Edge cases / failure handling: teardown first rejects new boundaries, then drains injected dependents, then waits for active returned-Promise boundaries before `AsyncLocalStorage.disable()`; a nested boundary that unloads its own owning fiber releases its lineage from the drain so teardown does not wait on itself (line 25); the scope deliberately does not own detached work — the owner must stop it (line 27).
- Surprising: the design explicitly accepts Node's Stability-1 `AsyncLocalStorage.disable()` dependency because Node requires `disable()` before an ALS instance can be garbage-collected, which matters under HMR (line 63).

- Data flow: the workspace root is the *base* for relative input paths, not a read boundary; absolute paths and relative paths that leave the workspace are readable when the backend allows them; the service still requires regular files, refuses symlinks, and applies its text and byte caps.
- Non-obvious design decisions: `list` and `changes` remain workspace-scoped "because they expose workspace navigation and observation rather than a named file read" (line 15); the HTML preview's exposure of `..` paths for local JS/CSS is an *intentional* security trade, recorded as such (line 17).
- Edge cases / failure handling: outside files do not produce `changes` frames, so their previews require an explicit refresh to observe updates (line 29); a stricter CSP that blocked all iframe networking was rejected because it would also reject external assets and network behaviour intentionally retained for the static-HTML preview (line 25).
- Surprising: the note states the consequence bluntly — "Any caller holding a valid Session file address can receive bytes from every regular file that the Session filesystem backend permits it to read, including files outside the workspace" (line 29); the opaque sandbox protects the parent application but "does not promise network isolation" (line 25).

### .agents/notes/implemented/architecture/2026-09-10-component-factories-and-local-slots.md
- Purpose: Support a reusable UI assembly whose consumers each choose the internal component.
- Key abstractions: `registerFactory()`, `renderFactorySlot()`, `useFactorySlot(name, fallback)`, `SlotFactoryMap` (declaration merging), `SlotFactoryDef {scope, props?, children?, store?, inject?, locale?, slots?}`, `FactoryComponentPropsOf<F>`, `FactoryLocalComponentPropsOf<F, N>`.
- Data flow: the definition owner declares the Factory (its scope, children, store, inject, locale and local slot names); a parent calls `renderFactorySlot()` per occurrence, selecting one Component per local slot name; the renderer supplies the Factory's store, injection, locale, child renderers and the local slot's own standard scope props.
- Non-obvious design decisions: the Factory inverts the ordinary Slot's ownership direction — the definition owner declares, and *parents render occurrences* — so a definition is globally unique while occurrences are per-caller (lines 21-32); local slots have **no** list/keyed/chain routing and no independent registration lifetime, because a local slot represents one caller choice for one occurrence (line 63); `renderFactorySlot()` accepts no Session id or scope target — the occurrence inherits its render-position scope, because "a second identity argument would create two authorities that can disagree" (line 97).
- Edge cases / failure handling: an exclusive store factory creates one handle per occurrence and **rejects** that handle if it declares `spec.persist`, because independently live occurrences cannot share one persistence key safely (line 57); definition replacement remounts occurrences; a disposed definition collapses its ordinary child declarations and invalidates retained child-render authority (line 51).
- Surprising: the first shipped use is `conversation.content`, whose strict-Session `views` local position defaults to an adapter rendering the existing `conversation.session` Slot — so an embedded occurrence can select a different view Component *without mounting the main Conversation Header* (line 71); the Factory deliberately does not own the Conversation store, because the Header and Session body share one strict-Session handle (line 73).

### .agents/notes/implemented/architecture/2026-09-10-desktop-web-wrapper.md
- Purpose: Run the desktop app through the shared Web application instead of maintaining a second backend.

### .agents/notes/implemented/architecture/2026-09-10-image-offload-events.md
- Purpose: Make image omission a *durable decision*, so the model-visible image set does not depend on unlogged request preparation.
- Key abstractions: the `image/offload` session event (`{targets: [{seq, imageIndexes}]}`), `IMAGE_OFFLOAD_REQUIRED` in the `LlmFailure`, `dsh-compaction-image-offload` on the `agent/request-error` waterfall, `contentGeneration` vs `replaceGeneration`, `offloadedImageText`.
- Data flow: the provider reports an image budget breach → the plugin selects that many oldest retained input-image occurrences in current surface order → it appends one `image/offload` event → it returns `retry` → the backend re-derives input and pricing, including the shrink baseline; reconstruction derives immutable message copies with `ImageBlock.offloaded: true` at the recorded positions.
- Non-obvious design decisions: the event has **no** `surfaceOp` — it neither creates nor replaces a message node — so message identity is preserved and image omission cannot masquerade as successful text compaction (line 19, 23); each target lists *strictly increasing, zero-based indexes* over every image in depth-first content order, because an attachment id or a raw-log prefix cannot identify the selected set (line 17); offload does not consume the provider retry budget and emits no `llm/retry` (line 13).
- Edge cases / failure handling: validation rejects missing or shadowed nodes, output images, duplicate targets, invalid indexes and already-omitted occurrences — atomically, before the Session commits the event (line 19); if no retained input image remains the plugin delegates rather than looping; each retry requires additional omitted occurrences, and exhaustion delegates the failure (line 15).
- Surprising: the choice of per-occurrence indexes over an attachment id or a single watermark exists because attachments can occur repeatedly and surface order can differ from event-sequence order (line 37); the event is required on read, so a reader without it refuses the log rather than silently restoring omitted images — but adding it does **not** advance `SESSION_FORMAT_VERSION`, because the envelope and operation grammar are unchanged (line 29).

### .agents/notes/implemented/architecture/2026-09-10-public-package-manifest.md
- Purpose: Publish the package.json fields DSH actually uses, without exposing internal metadata.

- Surprising: peer dependencies were rejected as the sole host requirement, because they constrain *installed npm packages* and do not identify the currently running DSH process when plugins live in a separate profile project (line 27).

### .agents/notes/implemented/architecture/2026-09-11-plugin-owned-message-projections.md
- Purpose: Keep feature-specific message transformation out of core Session.
- Key abstractions: the pure `SessionMessageProjection` (one event type plus a synchronous interpreter of the preceding history), the `@messageProjection` tag on a `SessionEventMap` member, `ctx.sessions.registerMessageProjection()`.
- Data flow: the event-owning plugin supplies a pure interpreter; Session owns atomic acceptance, shared live and detached folding, and content-generation cache invalidation; detached readers pass definitions explicitly, and the current Session format catalog assembles the same browser-safe plugin exports for persistence validation and offline queries.
- Non-obvious design decisions: the `@messageProjection` tag *generates* the required-interpreter inventory — a missing definition rejects append, seeded creation, restore and pure folding (line 15); a projection event cannot also declare a surface operation (line 15); the ordinary session-projection registry was rejected because its folds expose domain state *after* commit and cannot veto an invalid append or supply canonical `deriveMessages()` content (line 27).
- Edge cases / failure handling: each event has one registered owner; removing a definition invalidates pending committed decisions and cached reads that used it, and a replacement definition requires restoring the session (line 17); rejected, uncommitted candidates retain no interpreter dependency (line 17).
- Surprising: transforming only the *outgoing request* was rejected because compaction, fork and offline replay also derive messages — "A send-time transformation does not cover these consumers" (line 29); the event envelope and stored image decisions remain unchanged, so no structural Session format version is added (line 33).

## Ideas worth stealing

- **Make the LLM message history a *projection* over an append-only event log, so replay, fork and compaction are structural rather than bolted on.** `2026-06-11-event-sourced-sessions.md:13` — "A `Session` is an append-only log of typed `SessionEvent`s — the single source of truth. The LLM message history is *derived* from the log (`deriveMessages()`)". Why it transfers to August: August already persists a session log, but its model history is a separately maintained list; making the list a fold over the log makes "what did the model see" a question with one answer, and makes fork a seed rather than a copy. The same note's rejection of "a mutable message array with events fired as notifications" (line 21) is the argument: with event sourcing, log/state divergence is structurally impossible.

- **State the cache goal as a corollary, not a feature: "Model-visible ⟺ durably referenced", with prefix stability emerging from an append-only log projected by a pure per-node function.** `2026-07-05-reconstructable-requests.md:17` and `:19` — "Prefix-cache stability is corollary #1, not the headline: an append-only log projected by a per-node pure function yields requests that are append-extensions of their predecessors whenever the header is unchanged — stability is emergent, not managed." Why it transfers: August's prompt caching is currently managed by hand (keeping tool schemas and the system prompt stable). The mechanism to copy is *not* a cache hack — it is (a) the system prompt becoming a log-owned surface node, (b) the request "header" (config + tool schemas) being snapshotted durably on every real change, and (c) per-call request scalars being **forbidden** (the note rejects them at line 41 because "a listener could flip the model per call with zero accounting, silently abandoning the provider cache this design exists to protect"). The bonus is the production cache signal it derives: per-step usage, where "a header change or compaction appears as a cache-read drop on the next step" (line 31).

- **Put the system prompt on the surface as node 0, so a prompt change is a surface *replacement* and the prompt can never be shadowed by compaction.** `2026-09-02-system-prompt-as-surface-node.md:17` ("The system prompt lives on the surface"), `:33` (`assertSystemHeadRewrite` rejects a replacement covering node 0 unless the replacing event is itself a `system/message` covering exactly that node), `:81` ("node 0 is never compacted" is enforced in the replace operation itself). Why it transfers: August currently carries the system prompt in a place that is neither the message list nor the event log, so every reader re-derives it, and a compaction that anchors at the head can swallow it. The "protected head" trick (`:31` — an *empty* rendered prompt still occupies node 0, projecting to `null`) is the part that is easy to miss and hard to reinvent.

- **Normalise every provider failure into ONE structured, JSON-serialisable payload at the runtime boundary, and log the retry as a durable event so a silent backoff is visible.** `2026-06-21-bounded-llm-request-recovery.md:32` (the `LlmFailure` shape: `message`, `code`, `status?`, `providerRetryAfterMs?`, `requestId?`) and `:102` ("adapters report facts while deployment policy decides action" — the payload deliberately has no `retryable` field; the same refusal is stated at `:41`). The durable-status mechanism is at `:63` and the UI consequence at `:85` ("the Web countdown anchors the scheduled delay to browser receipt rather than the Host event clock"). Why it transfers: August's `_retryWaitRefusalMs` and its eight-family error taxonomy are exactly this shape but currently live in prose; adopting a single serialisable failure fact plus a durable retry event would let August's UI show *why* it is waiting and for how long — the note's diagnosis is that "a long silent wait looks like a stalled loop" (`:19`).

- **Split timeout into "the library notifies" and "the capability kills", and never race a promise against a deadline.** `2026-07-06-timeout-deadline-library.md:19` ("there is deliberately no central 'timeout service' that would have to know how to stop every capability's work") and `:114` (a `withTimeout(promise, ms)` wrapper was rejected because it "resolves the *tool-call* promise on deadline without stopping the underlying work — the child process or fetch socket leaks on"). The classification rule at `:71` (`timeoutOf(signal, code)` — "`code` scopes the match to this deadline's timer", so a nested deadline does not steal the outer one's classification) is the transferable bit. Why it transfers: August's tool timeouts are per-implementation; this turns the common half into one library and forces every capability to state *how it actually stops* — and the division-of-labor table at `:79-88` is a ready-made checklist for finding August's missing timeouts.

- **Enforce the tool-call budget as a plugin on a new around-dispatch waterfall, and put the catch *inside* the base `next()`.** `2026-07-07-tool-call-timeout-policy.md:37` ("That the catch is the base `next` — not something outside the waterfall — is load-bearing: when a provider sees the timeout signal and throws its own upstream-abort error, registry dispatch first converts it to a normal error result, and only then can `timeout-policy` replace the final result with `TOOL_TIMEOUT`"). The mechanism detail at `:57` is that the deadline is installed by *in-place mutation of `exec.signal`*, because a Cordis waterfall's `next()` ignores arguments and re-invokes downstream listeners with the shared payload. Why it transfers: August's per-tool timeout fields are exactly the "budget declared on the tool" shape this note adopts (`:43`), and the `exec.signal`-mutation trick is the part that is non-obvious enough to be worth stealing outright.

- **Record whether a cancelled tool body ever ran: `ABORTED` vs `ABORTED_BEFORE_DISPATCH`.** `2026-07-19-cooperative-tool-cancellation.md:31` and `:33` — "It applies whenever cancellation prevents body invocation, including pre-aborted entry, cancellation during pre-policy or approval, an aborted wrapper signal, a wrapper success overtaken by caller cancellation before delegation, and agent-loop siblings skipped after turn cancellation." Why it transfers: August's receipts and its `is_error` classification both need to know whether side effects were possible; a single undifferentiated `ABORTED` cannot say it, and the note explains why that matters for durable consumers (`:13`).

- **Collapse the two representations of a provider failure (throw vs terminal `finish` chunk) into one, and delete the sidecar.** `2026-07-29-terminal-llm-stream-failures.md:17` — "`LlmRuntime` is the normalization boundary for one adapter attempt. It catches only final-adapter selection, synchronous dispatch, iterator construction, and `next()` failures, converts the thrown value to immutable `LlmFailure`, and emits one terminal `finish`." The scope rule at `:19` ("The adapter-owned catch ends before each yielded chunk") is what keeps middleware and assembly bugs from being misfiled as provider outages. Why it transfers: August's provider adapters speak at least three wire formats (OpenAI, Anthropic, responses) and its error handling has to work across all of them; one normalisation boundary plus one terminal protocol is the mechanism, and the note's stated benefit is deletion (`:37`).

- **Make a cancelled stream *finalise* the prefix the user already saw, as a durable `assistant/message` with `interrupted: true`.** `2026-08-10-cancelled-stream-prefix-finalize.md:15` — "It appends that prefix as the step's `assistant/message` with `interrupted: true`, `surfaceOp: 'append'`, and the exact embedded timed stream. The append precedes the committed `agent/assistant-stream` end frame, `step/end`, and the aborted `turn/end`." Why it transfers: August's cancel path currently loses text that the user read — the note's diagnosis is exact: "A follow-up such as 'expand on your second point' then lacks text the user read, and a fork at the cancelled turn inherits the same gap" (`:9`). The negative decision at `:27` (no synthetic aborted tool results, because those "would claim an execution outcome that did not occur") is the part that keeps the record honest.

- **Keep the provider-side cache alive across subagents: the child gets the *same* tool schema and the *same* system prompt, and the return instruction rides the child's initial user task.** `2026-08-27-adjacent-agent-steer-messaging.md:49` and `2026-08-10-fork-children-stay-one-shot.md:17` — "The globally registered model tool is registered globally for every Agent in a composition. A continuable forked child therefore receives the same tool name, description, schema, and ordering as its parent. Its initial task is appended after the inherited Session seed." The rule at `2026-08-27-adjacent-agent-steer-messaging.md:49` is that a child-only tool or prompt section "preceded every inherited fork turn … forcing the provider to prefill the entire copied transcript again" (`:13`). Why it transfers: August has a fork and a subagent path; this is the concrete rule for not defeating the prefix cache when a child needs to talk back to its parent.

- **Route by *provider*, keep model ids out of the registry, and make replay state portable only within the adapter that owns both providers.** `2026-07-14-provider-routed-llm-adapters.md:25` ("A provider has exactly one adapter owner in a Cordis context … loading both owners is a configuration error rather than an ordering rule or fallback") and `:82` (replay state is portable only within the adapter instance that owns *both* the historical and target providers; a different adapter receives provider-neutral content only). The "provider is the registration key" rule at `:23` is the fix for August's per-model `apiFormat` sprawl: August currently overrides the provider format per model, whereas this note makes the *provider* the unit of ownership and treats "one adapter per provider" as a configuration error.

- **Let the adapter own exact-route capacity; let the consumer own compaction policy; keep the token meter model-agnostic with one fold and no model profiles.** `2026-07-20-routed-model-context-and-compaction-policy.md:17` (`LlmAdapter.resolveModel(provider, model, signal?)` returns capacity metadata), `:23` ("`dsh-token-meter` has no configuration and no model profiles … prevents replay accounting from becoming another model registry") and `:27` (`modelPolicies` keyed by the exact `{provider, model}` pair, with `thresholdRatio` default 0.8 and `retainRatio` default 0.16). Why it transfers: August compacts per model with a configurable ratio; the transferable piece is the *ownership split* plus the two-cap trigger at `:29` (`floor(min(W × thresholdRatio, W − O − headroomTokens))`, default headroom 65,536) — the second cap is the one most implementations miss, and it exists to leave room for the compaction *output* after a full generation.

- **Version the session log with one integer, read *directionally*, and make an unknown event refuse by default unless it is explicitly marked ignorable.** `2026-08-10-session-log-version-mechanism.md:19` (direction-aware refusal: equal reads normally, newer refuses and names the direction, older runs the adjacent chain in memory and leaves the source bytes and inode untouched) and `:21` ("the default is *required*: forgetting the marker over-refuses a resumable session (an inconvenience), while a default of ignorable would make the same mistake silently resume a gutted one (a safety failure)"). Why it transfers: this is the forward-compatibility contract for a durable log, and the asymmetry — *refuse by default, opt in to ignorance* — is the rule August would want if it ever ships a format other readers must open. The follow-up pair (`2026-08-30-retain-ignorable-external-session-events.md:15` and `2026-08-31-alpha-historical-unknown-event-refusal.md:15`) shows the second half: *equal-version read* tolerates a marked event, *migration* refuses it anyway because an opaque payload may hold references a format edge cannot validate.
