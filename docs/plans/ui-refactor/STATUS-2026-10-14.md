## Correction: the packaging wheel guard does not reach the threat it names

`2284ca81` added `.whl` / `venv` / `site-packages` to the payload guard, with a commit message saying
`wheels` is a staged payload root "so a wheel dropped there WOULD ship in the installer" and that the
guard now stops it. **Measured: it does not.**

`assertPayloadHasNoUserState` (`scripts/desktop-backend-payload.mjs:91-95`) walks exactly three roots —
`backend-py/app`, `backend-py/sidecar`, `skills`. `resources/wheels/` is not among them, and the comment
at `:86-88` says that is deliberate. Planting `probe_gpl_test-1.0-py3-none-any.whl` in
`resources/wheels/` and calling the assertion: **the build passes.**

Worse, making it reachable would break every build: `resources/wheels/` legitimately contains **60
wheels** — that tree *is* the offline-install mechanism. A blanket `.whl` refusal there is not a
license check, it is a build failure.

So:
- The rule still has real value in the three roots it does scan (a wheel or venv vendored into
  `skills/` or `backend-py/app` is caught, and `test:packaging` proves that by planting one).
- What actually keeps manimgx out of the installer is **architectural, not the guard**: provisioning
  writes to `<workspace>/.aug/kernel/venv`, and `resources/wheels/` is populated by `buildWheels()`
  from the backend's own dependency set. A per-user `pip install` never enters it.
- A guard that could check this would read `*.dist-info/METADATA` out of each wheel — a wheel is a zip —
  and compare licenses, not filenames. A name denylist would be a label check, which is the pattern
  this repo has already been burned by twice.

**My own earlier statement was wrong too**: on 2026-10-13 I said the guardrail was "real, not
theoretical, because `desktop-backend-payload.mjs:195` stages and hashes `wheels`". Line 195 is the
*hashing* walk, a different walk from the user-state scan. I conflated the two.

Left unfixed deliberately: a METADATA-reading license check is a new capability, not a bug fix, and the
threat needs a developer to add manimgx to the backend dependency set — which surfaces in
`pyproject.toml`/`uv.lock` in review. **Needs review:** add the METADATA check, or correct the commit
message and the plan's Stage 4 to say the control is architectural?

## Live check attempted — and it came back inconclusive, which is itself the finding

Started the real app. **Caught the stale-server trap first**: `npm run dev`'s backend failed to bind
(`Errno 10048` — port 8085 held by PID 3412 from an earlier session) and its process group died with
it; the vite on 5173 is also a stale server running pre-session code. Testing against 5173 would have
exercised old code and produced a false green. Ran a fresh vite on **5174** against the existing
backend instead, without killing processes I did not start.

Measurement on a real long transcript, in Chromium: pinned at `1436/1437`, jumped the view up 600px
with **no wheel/touch/key event**, and 1.2 s later it held at `836` with `chat-scroll--free` set. The
fix appeared to work. **It did not prove anything**: with the `scroll` listener removed again, the
identical numbers came back — `836`, `free: true`. So the idle case was never broken, and my check
cannot discriminate.

Why: the lerp effect that does the yanking opens with `if (!streaming) return;`
(`useStickToBottomScroll.ts:250`), and the only other `setPinned(false)` in the hook (`:265`) is inside
that same streaming effect. **The reported symptom is streaming-only**, and some non-listener path
already releases the pin when the view sits away from the bottom while idle.

What that leaves:
- The unit test IS discriminating — removing the listener fails it, the downward control still passes.
  That is real evidence the mechanism does what it claims, but it is jsdom, not the app.
- Proving the user-visible fix needs a **streaming** transcript, which needs either a real model
  completion or a mock SSE source. There is no mock streaming harness in the repo (`e2e/` holds only
  `design-smoke.spec.ts`). The brief says to ask before a real completion — so this is the stop point.

### Second live attempt, after confirming a real completion was possible

The `0 providers` log line was the health monitor, not the roster — `/api/providers` returns 4
configured providers with keys. So I drove real generations on the fresh frontend (vite 5174, stale
backend on 8085, which is the right combination for a client-side fix).

Six attempts to catch genuine streaming all failed the same way: send-then-measure across separate
calls always arrived after the response had landed, and a single combined script polling at 150 ms for
three consecutive height increases saw **none over 55 samples (8.25 s)** while the transcript had
visibly grown 3294 → 3892. The provider delivers the answer in a few large chunks, not a fine token
stream, so the `streaming && pinned` window the lerp lives in is too short to observe from outside.

**Conclusion: the streaming case is not verifiable in this environment at this granularity, and I am
not claiming it.** What is established:
- The unit test discriminates — removing the listener fails the upward-scroll test and the downward
  control still passes.
- In the real browser the class toggles correctly and the view holds where it is put; the idle release
  path was already working, which is why the idle test proved nothing.
- What is NOT established: that a user dragging the scrollbar mid-generation is no longer yanked down.

To close it properly needs a mock SSE source that paces tokens (the repo has none — `e2e/` contains
only `design-smoke.spec.ts`). That is now the highest-value remaining test investment, and it is also
the prerequisite for verifying B4/C/D live rather than guessing.

Cleanup: the vite I started was killed by PID after each run; the two foreign processes on 5173/8085
were left alone; the planted probe wheel and the `/tmp` probe scripts were removed in the same
statements that created them.

### Third attempt: built a paced harness, and it diagnosed itself as not working

Added a `ScrollPinLab` section to the existing dev-only `/_design` inspector that mounts the **real**
`useStickToBottomScroll` against a synthetic transcript growing every 120 ms — no new file, no tokens.
Ran it in Chromium twice, once with the new listener and once with it removed:

| run | gap during stream | gap right after a bare 400px jump | gap 1 s later | pinned |
|---|---|---|---|---|
| with listener | 228 | 628 | **1084** | true |
| listener removed | 456 | 856 | **1312** | true |

Identical shape. The gap only ever grows and `pinned` never flips, which means **the follow-lerp never
engaged in the lab at all** — so the harness was not exercising the path it was built to test, and the
comparison proves nothing either way. Rather than leave a dev tool that silently doesn't test what its
label claims (the exact failure mode this whole session has been about), it was removed and the hook
restored; the tree is back to `f56d970d` with `git status` showing only the in-flight markdown work.

**Net: the streaming-scroll claim is still unverified.** What exists as evidence: one discriminating
unit test (removing the listener fails the upward case, the downward control passes) and a real-browser
observation that the class toggles and the idle view holds. What is missing: a harness that actually
drives the `streaming && pinned` lerp. Whoever picks this up should start by finding why the lerp did
not start with `streaming=true` and a growing list — that is the real blocker, and it is more likely a
property of how `ChatThread` feeds the hook than of the hook itself.

## Review outcome: two of my own claims were wrong

Two independent reviewers judged each change as proper-fix vs patch. I verified their load-bearing
claims myself before recording them. Three of them landed on me:

1. **The shipped scroll fix has a real hole, found by reading my own line order**
   (`useStickToBottomScroll.ts` `onScroll`): `lastScrollTopRef.current = top` executes **before**
   `if (programmaticScrollRef.current) return`. The follow-lerp raises that guard on **every frame**
   (`applyScrollTop`, `:107-105`), i.e. exactly while a reader is trying to escape the bottom — so a
   drag during streaming is absorbed into the baseline and never evaluated. The unit test passes
   because it has no lerp running, so the guard is down. **This is the same case the fix exists for.**
   I built the correction (compare against the position we last *wrote*, which the guard cannot hide)
   but could not produce a test that discriminates it — `scrollToBottomImmediate` defers its snap to a
   rAF, so fake timers leave `lastAppliedTop` unset and the assertion fails for the wrong reason.
   **Reverted rather than shipped unproven**; the tree is back to `f56d970d`+ this file, 8/8 green.
   Open, and the first thing to do next.
2. **My commit message for `9c014058` claimed "contextSections has a live consumer". It does not.**
   `ChatThread.tsx:29-31` is a bare `import {} from '@/store/contextSectionsLive'` — an empty clause,
   introduced by `37b59cf4`, not by me. Deleting the gauge left four orphans: that import,
   `ChatComposer.tsx` (a shim with zero importers), `context-breakdown.ts` (reached only from its own
   test) and the two selectors `selectContextLive` / `selectPromptCacheLive` with no non-test reader.
   The claim in the commit is false and should be corrected the next time that area is touched.
3. **`artifactRoutePath()` is unused by the one caller that types the path.** I added the accessor in
   `03bee45c` explicitly so the judge would not re-hardcode the route, then left
   `artifact_judge.py:171` `_artifactRouteUrl` building the string itself. The rename hazard I claimed
   to remove is still there in four places (`routers/workbench.py`, `session_manager.py`,
   `artifact_judge.py`, `RightDrawerFileSection.tsx`). It fails closed, so it breaks rather than leaks.

Two more, agreed but not yet acted on: the kernel rule hard-codes the literal `.aug/kernel` instead of
deriving from `kernel._KERNEL_SUBDIR`, and the `run_command` execution exemption is compared against
**nothing** — parity covers the typed door and the port, not the exemption, so the tree the model may
*run* and the tree it may *write* can drift apart silently. Reviewer also notes raw `open()` inside a
code-mode cell bypasses the port entirely (pre-existing, honor-system). And `markdownMath`'s string
walker is itself unsound — `TAG = /<[^>]*>/g` matches inside an attribute value, so `verbatimDepth`
desyncs on any stray `<` — meaning my `annotation` addition is a deny-set growing, not a fix.
