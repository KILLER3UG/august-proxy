# deepseek-harness / dsh-notes-arch-bugfix#3

## Shard shape

This shard is 26 files and not one line of code: it is nine archived **Agent Notes** in `.agents/notes/archived/bug-fix/`, each carried as an English original plus a Chinese translation, plus the per-pair `.i18n.yaml` bilingual consistency records (eight of the nine pairs — the V3 note's pair record belongs to shard `dsh-notes-arch-bugfix#2`, which the manifest confirms). Every note is a decision record in a fixed house shape — **Problem / Decision / Alternatives considered / Testing-or-Verification / Consequences** — that explains *why a defect was fixed the way it was*, usually with a measured before/after and always with the rejected alternatives named. The nine defects cluster into three groups: **process and file lifetime** (a profile write lock stranded by a crashed holder; a `pnpm` child that printed `Done in 2s` and never exited; a persistent-pwsh tool that overwrote the backend's controlled prompt), **the client representation of one user action** (an idle input that must appear once, as an echo and then as a durable message; a transcript that must be clipped without becoming a scroll container), and **data that must survive** (a V3 subagent child whose descriptor is missing, so its parent catalog is incomplete; a multimodal tool result that must be priced in tokens rather than bytes; a Windows update overlay that must not be a second native window). They interlock: the lock-takeover note explicitly *depends on* the bounded-pnpm note (a takeover proves only that the recorded process exited, not that the pnpm it started stopped writing), and the V3 note defers its JSONL rules to a neighbouring decision it names. The shard's value to August is not the fixes themselves but the **method** the notes record: prove the state, name the owner, bound the wait, and state the limit — repeatedly, in nine different subsystems.

## Per-file notes

### .agents/notes/archived/bug-fix/2026-09-24-exited-holder-lock-takeover.md
- Purpose: Lets a writer take over a `<file>.lock` whose recorded holder has exited, instead of waiting out `lockWaitMs` (two minutes) and failing with a message that never says the holder is gone.
- Key abstractions: The `<pid>\n` lock record (kept in the old format so pre-change locks interoperate); a **signal probe** (`process.kill(pid, 0)`) whose `ESRCH` proves the holder is gone and whose `EPERM` means it exists under another user; a **content-addressed claim file** `<file>.lock.takeover-<first 16 hex of SHA-256(record)>`; the Plugin Manager's `.plugin-manager/run.json` run record.
- Data flow: Contender sees `EEXIST` on the `wx` create -> reads the record -> probes the PID -> on `ESRCH` creates the claim with `wx` -> under the claim re-reads the lock and re-probes the PID -> removes the lock only if it still holds that record and the PID is still absent -> removes the claim -> retries acquisition at once. Eight contenders over one exited holder never overlap.
- Non-obvious design decisions: **Only `ESRCH` counts as "gone"** — an empty, incomplete, non-decimal, PID-0 or out-of-int32 record is *waited for*, because none of them proves the holder stopped (`:19`). A record naming the contender's *own* PID is also waited for, since the browser Worker's process shim reports its own PID as absent (`:17`). The claim file is named by the hash of the *record*, not of the path, so two contenders reading the same record serialise on the same claim and a different record gets a different claim (`:18`). The re-probe under the claim is what makes PID reuse safe: a new holder that reused the PID fails the second probe, so a claimant never removes a lock another contender acquired (`:18`).
- Edge cases / failure handling: Takeover proves only that the *recorded* process exited, not that the processes it started stopped writing — so an operation that finds a live `run.json` record waits up to five seconds and otherwise **refuses to run**, naming the process and the record (`:20`). A claim left by a crashed contender blocks later takeover of that lock (`:50`). A PID reused by a live process after a reboot keeps the lock until an operator removes it (`:48`). Cross-host shared filesystems are explicitly unsupported: the probe runs on the contender's host (`:21`).
- Surprising: The kernel-released-lock alternative (`flock` on POSIX, a named semaphore on Windows, already used by the Session write lease) is *stronger* but was refused because it would give the zero-dependency `dsh-atomic-write` two dependencies and a transition would have to hold both locks (`:27`). A rename-aside-and-restore scheme was refused because restoring races a third contender that acquires the empty path, leaving two holders (`:29`).

### .agents/notes/archived/bug-fix/2026-09-22-windows-open-through-shell-resolution.md
- Purpose: Fixes the Windows desktop settings gesture "Open configuration file" (issue #4428) that opened nothing and reported nothing, by handing the path to `explorer.exe` instead of resolving the association in-process.
- Key abstractions: `openWindowsPath` / `revealNativePath`; the shared `runExplorer` helper owning the one Explorer invocation rule; `explorerTarget` owning the one encoding step for both intents; the file-URI encoding that percent-encodes **only** commas and equals signs.
- Data flow: Path -> `pathToFileURL(windowsPath, { windows: true })` -> non-ASCII escapes decoded back to literal characters -> `,` -> `%2C` and `=` -> `%3D` -> the URI as **one** argv element to `explorer.exe` (or `/select,<uri>` for a reveal). Explorer performs the same default-application resolution a double-click performs.
- Non-obvious design decisions: **Only commas and equals are percent-encoded**, because Explorer splits its own command line at both — and nothing else is escaped, because Explorer *rejects* percent-encoded non-ASCII in a file URI and falls back to the Documents folder (`:16`). The old `powershell.exe -NoProfile -Command "Invoke-Item -LiteralPath '<path>'"` and its `powershellLiteral` single-quote doubling are deleted: a path crosses the process boundary as an argv element, which removes the *shell-layer* escaping while keeping the encoding Explorer's own parser requires (`:18`). Resolving the default inside the host process was refused because it reimplements an order Windows owns, including the `UserChoice` hash Windows validates (`:26`).
- Edge cases / failure handling: Explorer exits **1** after delegating to the already-running desktop process, and that exit code is accepted as a success (`:18`). Consequently the opener can no longer distinguish "the shell opened it" from "the shell declined" — both are 0 or 1 — and the Remote still answers `{ opened: true }`; nothing verifies a window appeared (`:36`). A non-interactive Windows session (a service, or a scheduled task without an interactive logon) invokes no association and still exits 1, so that case is indistinguishable from a delegated open; the caller's abort signal is the only bound and no fallback is implemented (`:38`).
- Surprising: The negative control in the verification is the most valuable line in the note: the same file with a *raw* comma in the file URI invoked no association, opened the user's Documents folder, **and still exited 1** (`:44`). Exit code 1 therefore records delegation, not outcome, so accepting it cannot turn a wrong target into a success — the encoding is what keeps the path whole. A later pass read the shell's own window and selection state instead of pixels: the encoded `/select,` target selected the file, an unencoded `=` opened Documents, and percent-encoded non-ASCII opened Documents where literal characters worked.

### .agents/notes/archived/bug-fix/2026-09-22-input-echo-admission-ownership.md
- Purpose: Makes one idle submission appear exactly once in the UI — as a local Chat echo, then as a durable user message — instead of flickering between Chat and the QueueDock as Inbox projection and conversation history arrive independently.
- Key abstractions: **Display ownership** (idle input stays in Chat, running steering stays at the process tail, explicitly queued input stays in QueueDock; Inbox acceptance never changes the placement); the `rpcId` as the durable identity of a submission; the **claim watermark** (an Inbox projection sequence number) as the ordering evidence that a stale row cannot reappear; one keyed React list holding both pending bubbles and durable seats.
- Data flow: Local submission -> optimistic echo keyed by `rpcId` -> `user/message` (durable admission) or an Inbox acceptance projection -> Chat hides the echo by matching the `rpcId` *in the same render* -> the Session keeps the suppression identity until the Inbox projection watermark reaches the claim sequence -> only then is the identity retired. The existing per-submission receipt carries both the claim tracking and the cancellation; **no new SessionSnapshot field, Host event, or persisted format is needed** (`:18`).
- Non-obvious design decisions: The *placement* is decided locally at send time and is never migrated — "the client does not migrate an idle-classified echo into Dock merely because the Host queued it behind another Turn" (`:54`). Deleting the suppression identity as soon as `user/message` arrives was refused, because a later Inbox acceptance projection can resurrect a Dock or pending-steering row; the watermark supplies the ordering evidence without assuming the two streams publish together (`:30`). A fixed delay was refused outright: CPU throttling, transport batching and projection ordering can exceed any interval, and *time does not establish admission* (`:26`).
- Edge cases / failure handling: An empty, input-free progress control at the end of Chat gets the *first* transcript echo before it; other echoes stay at the tail, and running steering stays *behind* the title, because steering belongs after existing process content (`:19`, `:32`). Pending bubbles and durable nodes share one keyed list so inserting a progress title preserves the pending bubble's mounted identity (`:20`). Documented limits: steering without a locally tracked submission follows the Inbox projection and can briefly duplicate its durable row; reconnect may discard receipt-confirmed optimistic echoes; three locally submitted messages A, B, C whose durable admission order differs change their visible order (`:51`–`:54`).
- Surprising: The multi-input replay **asserts durable order and the absence of duplicate or residual echoes, but explicitly does not assert that optimistic ordering predicts Host order** (`:47`) — the note is careful to claim less than the mechanism guarantees, and says so.

### .agents/notes/archived/bug-fix/2026-09-22-chat-scroll-follow-and-footer-geometry.md
- Purpose: Separates three things that were fighting over one scrollport: transcript *clipping*, floating-control *geometry*, and *follow intent* — so Markdown code banners and expanded compaction headers can stick to the real conversation scrollport, and a height-capped process group can keep its own reading position.
- Key abstractions: `overflow-y: clip` on the clipped transcript root inside an unclipped frame; floating controls as *siblings* of the clipped transcript; `useScrollFollow` as **one independent controller per scrollport**; `useProcessScroll` owning a capped group's own body/content observer, directional fades and one-shot opening position.
- Data flow: The clipped root owns no scroll offset. Shared Conversation scrolling, standalone Chat scrolling, capped process groups and terminal sections each keep their own scrollport. An unclosed group opens at its bottom, a closed group at its top — decided by the group's own `closed` value, not the whole Turn's status and not an all-node search (`:27`).
- Non-obvious design decisions: **`overflow-y: clip` instead of `hidden`**, because an `overflow-y: hidden` ancestor becomes the nearest scroll container even when the reader scrolls a different outer element; `clip` constrains vertical overflow without inserting a scroll container between sticky content and its real scrollport (`:20`). The horizontal axis stays `visible` because pairing vertical `clip` with horizontal `auto` or `hidden` computes the vertical overflow back to `hidden` (`:25`). Native smooth growth keeps an **outstanding target separate from the current position**, so animation progress retains follow intent, and input interrupts native motion *before* the browser applies reader movement — the resulting actual displacement then decides whether following stops or resumes (`:29`). One shared follow flag was refused (it pulls a group away from a reader merely because the outer transcript follows) and two complete controllers were refused (they duplicate animation attribution and threshold rules) (`:39`).
- Edge cases / failure handling: A later close does not reset an already-open reader; browser find keeps its own reveal position; display-mode changes preserve mounted members (`:27`). A stop off the issued target releases following so focus and find keep their landing; shrink clamping counts as arrival (`:29`). The back-to-bottom button depends only on *outer* follow intent and restores only that intent; inner scrolling affects the outer controller only when scroll chaining actually moves the outer scrollport (`:31`). The shared controller stores intent without scheduling React renders (`:53`).
- Surprising: The note's stated scope is deliberately negative — "These changes establish behavior and ownership, not a measured latency or memory improvement" (`:53`) — and it names the two neighbouring decisions it does **not** supersede (navigation performance, conversation build groups), so the ownership graph stays explicit (`:55`).

### .agents/notes/archived/bug-fix/2026-09-23-bounded-pnpm-runs.md
- Purpose: Bounds a `pnpm` run that stops progressing, so one profile operation cannot hold the profile write lock forever — a `dsh web` process held `~/.dsh/profiles/web/package.json.lock` for **22 minutes** after its child printed `Done in 2s`.
- Key abstractions: **Process exit as the completion signal** (not pipe EOF); the `idleTimeoutMs` **silence bound**; the fixed `DRAIN_AFTER_EXIT_MS = 2000` grace period; `killDescendants` on every kill path; the `run.json` run record.
- Data flow: The operation awaits the raw child's `exit` event raced against execa's promise; the pipes then drain under a 2000 ms grace, after which this operation closes them; a captured run whose output stays silent for `idleTimeoutMs` is terminated, reports `timedOut` beside its exit status, and its whole process tree is stopped and awaited before the caller restores the profile and releases the lock.
- Non-obvious design decisions: **Silence, not duration, is the bound** — pnpm reports its own progress and its scripts' output there, while a non-TTY pnpm prints a build script's output only when the script finishes, so a native build on a slow machine compiles silently for longer than any defensible fixed budget; silence separates a stalled run from a slow one without guessing a duration (`:26`). The 600000 ms default leaves an approved build ten times the slowest silent stretch maintainers expect (`:26`). Terminating only the pnpm process was refused because an approved `postinstall` keeps writing into the profile after the operation reports a timeout and releases the lock, so a later restoration races that script (`:34`).
- Edge cases / failure handling: Only the close *this drain causes* is ignored; a reading that failed before the cut still surfaces as the run's failure and the log records that the tail was cut short (`:18`). A terminated run is classified `timeout` whatever exit status the signal left behind, and installation and removal report *failure* instead of success, so a manifest pnpm had half written is restored rather than activated (`:20`). `dsh plugin` inherits the caller's terminal and captures nothing, so no silence bound applies and the operator can still interrupt (`:22`).
- Surprising: The root cause is a **third-party defect** (pnpm 11.13.0 consumes its one-shot worker-pool teardown once and re-creates the pool lazily, unreferencing a worker only during destruction — issue #4981, PR #4982), so the whole mechanism is a declared workaround that becomes unnecessary once pnpm tears down its pool before a command returns (`:60`). The real-process test cases cover POSIX only, because Windows cannot stage a descendant that keeps inherited pipes open past its parent (`:49`).

### .agents/notes/archived/bug-fix/2026-09-21-persistent-pwsh-keeps-controlled-prompt.md
- Purpose: Stops `dsh-tool-pwsh-persistent` from installing its own `prompt` function, which overwrote the one `dsh-terminal-bash` installs and killed the backend's prompt-readiness fast path — 8493 ms for the first call and 3722/3832/3759 ms for the next three, against 1340/255/251/241 ms with the controlled prompt intact.
- Key abstractions: The **controlled prompt** `dsh> ` as one provider's protocol constant, marked by the OSC `133;D` end marker whose printable tail must equal it exactly; the `stdin_read` settle reason as the seam's own signal; `stripPrompt` collapsing to `trimTrailingNewline`.
- Data flow: `dsh-terminal-bash` owns the pwsh `prompt` function, installs it during `spawn`, and returns the session only after that startup reached `stdin_read` readiness — so the tool's initialisation send has nothing left to establish and is deleted together with its `PWSH_PROMPT_SETUP` command (`:16`). A send that settles as `stdin_read` without the end marker in scrollback returns the captured partial output (`:18`).
- Non-obvious design decisions: **The tool does not import the prompt constant**, because the prompt is one provider's protocol constant; a consumer matching it would couple the tool to `dsh-terminal-bash` specifically and any other mounted pwsh-dialect backend would break it again (`:24`). Aligning the text was refused too — it keeps a second installation of one protocol constant and a second owner of it (`:22`). Lowering `handoffGraceMs`/`idleSilenceMs` was refused because *no silence value fixes a dead fast path*; it only rebalances how much every call overpays, and the silence tier is also what absorbs a genuinely broken prompt (`:26`).
- Edge cases / failure handling: The `stdin_read` fallback is behaviour, not cosmetics: an interactive child returns captured partial output instead of spinning to the command deadline, but the early return **keeps the session**, so a child still reading stdin can consume the next call's command until that call reaches `timeoutMs` and resets the shell — and distinguishing the shell's own prompt readiness from a child's stdin wait belongs to the seam, not to either tool (`:34`). A model command that redefines `prompt` still removes the readiness marker and degrades later sends to the silence tier, because the backend installs its prompt once at startup and cannot re-assert it (`:38`).
- Surprising: The regression test asserts the **settle reason, not the duration**: the loader-composition suite records every send's `waitReason` and requires at least six `stdin_read` settlements and no `inferred_idle`; reinstating the removed prompt override fails that assertion after 30 s with `expected 0 to be greater than or equal to 6` while the case's *output* assertions still pass (`:36`). The package's own tests had masked the defect by configuring `idleSilenceMs: 300` (`:10`).

### .agents/notes/archived/bug-fix/2026-09-19-v3-incomplete-child-catalog-evidence.md
- Purpose: Lets a V3 parent session migrate when a child log has **no** own descriptor, an unsupported descriptor version, or multiple descriptors — previously the parent refused to migrate, making otherwise readable history unavailable.
- Key abstractions: The child's *header* (identity and parent relationship) as a distinct kind of evidence from its *descriptor* (discovery fields: mode, label); the **exactly-one-supported-own-descriptor** rule; the `unknown` catalog mode.
- Data flow: The V3->V4 migration appends a complete missing parent catalog entry only when exactly one supported own child descriptor supplies the discovery fields. Other descriptor counts and unsupported versions retain unknown-mode membership through session-local catalog preparation. Existing parent entries and child events remain intact; the source bytes are unchanged.
- Non-obvious design decisions: **A missing discovery field never justifies making valid history unavailable** — refusing the whole parent was refused because discovery metadata is insufficient ground (`:20`). Fields are never *inferred*: an invented mode or label would become a durable catalog fact without evidence (`:24`). Choosing the first or last descriptor was refused because two consumer policies disagree — `foldSubagentDescriptor()` takes the *first* under an exactly-once rule, the identity projection takes the *last* to override inherited identities — so backfill requires *one* own record rather than picking a side (`:22`).
- Edge cases / failure handling: Known child creation times must still match existing parent entries; mode/label and descriptor fields are checked only in the exactly-one-supported-descriptor case; JSONL isolates invalid descriptor fields and corrupt child bodies while retaining known header identity, and unreadable or unsupported headers are excluded from discovery; changed source revisions still refuse publication (`:16`). A V4 successor does not rescan historical children on open, so automatic later mode backfill is out of scope (`:28`).
- Surprising: The note is explicit that the JSONL failure-propagation rules are *partially superseded* by the adjacent session-local-catalog-preparation decision — the two notes overlap deliberately, and each names which half it owns (`:16`). A historical child with a readable header but no usable descriptor still occupies a slot in its parent's direct-child catalog as an `unknown`-mode member, so the parent can see the child even though it cannot describe it (`:28`).

### .agents/notes/archived/bug-fix/2026-09-21-multimodal-tool-result-retention.md
- Purpose: Keeps images in a tool result that a text-retention policy would otherwise have removed, and prices the result budget in tokens rather than bytes.
- Key abstractions: `ToolDefinition.projectContent` (execution-prepared content installed **before** post-execute policy) versus `finalizeContent` (terminal and job limits, a separate role); the **spill policy** pricing ordered text/image blocks in estimated tokens; the per-route image calculator; the spill file as the durable recovery artifact.
- Data flow: MCP prepares durable images asynchronously while the pure renderer emits text placeholders; `projectContent` installs the prepared content before policy runs, so transformations inspect the actual images; the spill policy prices the ordered blocks, reserves the omission notices, divides the remaining tokens between the two *contiguous ends*, and omits the middle; the complete spill file holds the accepted text and readable attachment paths in order, and the attachments own the image bytes.
- Non-obvious design decisions: **Preparing content before policy** rather than restoring images after it — restoring can resurrect blocked images or discarded text (`:24`). Images **share the result budget** with text and are priced by the *existing route calculator*, because that calculator already prices projected dimensions and descriptor text, so it owns that cost (`:26`). Embedding image bytes in the spill text was refused: base64 inflates the artifact and duplicates attachment storage; a readable attachment path preserves retrieval and ordering without copying bytes (`:28`). ## Ideas worth stealing

- **A stale lock is recoverable when you can PROVE the holder is gone — and the proof is a signal probe, not a timestamp** — `.agents/notes/archived/bug-fix/2026-09-24-exited-holder-lock-takeover.md:17` (implementation: `packages/util/atomic-write/src/index.ts:112-127`, `packages/util/atomic-write/src/index.ts:150-178`) — The mechanism: the lock file records the holder's PID; a contender sends signal 0 to that PID; `ESRCH` means the process is gone (take over), `EPERM` means it exists under another user (keep waiting), and a record that is empty, non-numeric, PID 0, or out of int32 range proves nothing (keep waiting). Takeover is then serialised by a **claim file named after the SHA-256 of the lock record**, and under the claim the claimant re-reads the lock and re-probes the PID before removing — so a holder that reused the PID cannot be mistaken for the dead one. Why it transfers to August: August writes `providers.json`, `config.json`, the brain SQLite file and the encrypted secret store from the UI, the backend and the Bot path, often in separate processes, and a crashed holder there wedges every later writer until a human deletes a file. The three-part rule — *prove with an OS-level signal, serialise with a content-addressed claim, re-prove under the claim* — is language-agnostic and works on a plain `O_EXCL` lock file with no dependency.

- **Bound a child process by SILENCE, not by duration — and treat the process's own exit as completion, never the pipe EOF** — `.agents/notes/archived/bug-fix/2026-09-23-bounded-pnpm-runs.md:19` and `:26` (implementation: `packages/boot/plugin-manager/src/operations.ts:367`, `packages/boot/plugin-manager/src/operations.ts:377-385`, `packages/boot/plugin-manager/src/operations.ts:431-448`) — The mechanism: (a) a run completes when the process exits, so the completion signal is the raw child's `exit` event raced against the library's promise, because a descendant that inherited stdout holds the pipe open forever; (b) the pipes then drain under a fixed 2000 ms grace and are closed, with only *this* close ignored so a pre-cut read failure still surfaces; (c) a captured run that prints nothing for `idleTimeoutMs` is terminated, and it is classified `timeout` regardless of the exit status the signal left, so the caller rolls back instead of activating a half-written manifest; (d) the whole process *tree* is stopped and awaited before the rollback, because an approved `postinstall` outlives its parent. Why it transfers to August: August's `run_command`, its code-mode sandbox, its MCP server launches and its background jobs all spawn children that can wedge. A silence bound separates *stalled* from *slow* — a duration bound would kill a legitimate slow native build — and the "exit, then drain, then cut" ordering is the part that is easy to get wrong and expensive to debug.

- **Keep an optimistic local echo alive until a durable, ORDERED watermark proves the stale duplicate can no longer appear** — `.agents/notes/archived/bug-fix/2026-09-22-input-echo-admission-ownership.md:18` (implementation: `packages/api/session-controller/src/client/sessions/session.ts:817-838`, `packages/api/session-controller/src/client/sessions/session.ts:846-873`) — The mechanism: the optimistic bubble is keyed by the submission's `rpcId`; the durable `user/message` echoes that `rpcId`; the Inbox projection carries a monotonic sequence number; the client keeps the local suppression identity until the Inbox projection's watermark has passed the sequence at which this submission was claimed — and only then retires the echo. Crucially the watermark is re-read at retirement time, so an *older* accepted row cannot reappear after the identity retires. Why it transfers to August: August's chat shows the user's message immediately and the durable row later; any implementation that deletes the optimistic bubble on the first `user/message` will double-render whenever the projection is late, and any implementation that deletes it on a timer will flicker under CPU throttling. The watermark is the only evidence that does not depend on wall-clock timing, and it needs no new persisted field when the transport already carries a sequence.

- **Price tool output in TOKENS, and price images with the SAME estimator that prices the request** — `.agents/notes/archived/bug-fix/2026-09-21-multimodal-tool-result-retention.md:16` and `:31` (implementation: `packages/spill/spill-policy/src/retention.ts:48-104`, `packages/spill/spill-policy/src/index.ts:56-74`) — The mechanism: the result budget is a token count, not a byte count; the block pricer is a per-block callback that uses the text estimator for text and the *active route's* image calculator (`visualTokens` plus the descriptor text) for images; retention keeps the two **contiguous ends** and omits the middle; text may be split at a UTF-16 code-point boundary; images are indivisible and keep their original positions; the omission notices are reserved out of the budget before the split; and the *complete* spill file records a **readable attachment path** at each image position so an omitted image can be re-read rather than re-sent. Why it transfers to August: August's context is measured in tokens and it already has a per-model token estimator and a per-model cost table; a byte budget under-prices a screenshot by two orders of magnitude and over-prices a log tail. The specific transferable detail is the *indivisible-block* rule: an image either fits whole at a retained boundary or that boundary's space is left unused — never half-kept, never moved.

- **A protocol constant has exactly ONE owner, and a consumer that re-installs it breaks the fast path silently** — `.agents/notes/archived/bug-fix/2026-09-21-persistent-pwsh-keeps-controlled-prompt.md:16` and `:36` (implementation: `packages/terminal/terminal-bash/src/sanitize.ts:9`, `packages/shell/tool-pwsh-persistent/src/index.ts:395-401`) — The mechanism: the backend owns the prompt and installs it during `spawn`; the client tool must not install a second copy *and must not import the constant* (a consumer that matches a provider's protocol string couples itself to that provider). When the tool did re-install its own prompt, the readiness check silently failed and every call fell to the slow tier: 8493 ms -> 1340 ms. The regression test asserts the **settle reason** (`stdin_read` at least 6 times, `inferred_idle` zero) rather than a duration, so the report is by mechanism and survives machine-speed changes. Why it transfers to August: August's backend has its own prompt/readiness protocol and the terminal drawer, the code-mode runner and the shell tool all consume it. Two owners of one protocol constant is exactly the shape of bug that costs 6 seconds per call and shows up as "the model is slow".

- **Accept the OS's "I delegated this" exit code, but never read it as "it worked" — assert on the arguments the peer actually received** — `.agents/notes/archived/bug-fix/2026-09-22-windows-open-through-shell-resolution.md:44` (implementation: `packages/util/native-command/src/path-opener.ts:116-123`, `packages/util/native-command/src/path-opener.ts:136-145`) — The mechanism: the path is handed to `explorer.exe` as **one argv element** with commas and equals signs percent-encoded (the shell splits its own command line at both) and nothing else encoded (Explorer rejects percent-encoded non-ASCII and falls back to Documents); Explorer's exit code 1 means "handed off to the running desktop process" and is accepted, while every other failure rejects. The negative control is the lesson: with a raw comma the shell opened the *Documents folder* and **still exited 1**. The verification then reads the shell's own window and selection state rather than pixels. Why it transfers to August: August's desktop is a Tauri shell that shells out to Explorer, the browser and the OS opener for "open file / reveal in folder". Any opener that checks only the exit code will report success for the wrong target; the fix is to assert on the exact argv the peer received, and to treat the exit code as evidence of *delegation* only.

- **Give a privileged in-page action a PRIVATE capability channel, not the shared document's event surface** — `.agents/notes/archived/bug-fix/2026-09-20-windows-embedded-mandatory-update.md:16` and `:22` (implementation: `apps/desktop/src/preload-mandatory-overlay.ts:37-61`) — The mechanism: the isolated preload creates a `MessageChannel`, transfers one port to the shell frame with a transfer list, keeps the other, and **only messages arriving on that paired port may invoke the privileged IPC**; a synthetic `window` event in the shared product document cannot, because source/origin are constructible by product scripts. The overlay is a closed shadow root inside the main window, so there is no second native window to keep in sync with the parent. Why it transfers to August: any future August feature that must interrupt the user from inside the app (a mandatory update, a dangerous confirmation, an approval prompt) needs exactly this split — the *display* lives in the product document, the *authority* lives on a private port. The note is honest that the DOM overlay is not a tamper-proof surface, which is the right amount of claim to make.

- **A follow controller per scrollport, and "the user scrolled" is a claim that native animation can invalidate** — `.agents/notes/archived/bug-fix/2026-09-22-chat-scroll-follow-and-footer-geometry.md:22` and `:29` (implementation: `packages/client/ui-chat/src/client/chat/use-scroll-follow.ts:22-171`) — The mechanism: each scrollport owns an independent controller holding *intent* (not a React flag); the controller keeps an **outstanding animation target** separate from the current position, so the browser's own scroll events during a smooth animation are not counted as reader movement; a reader gesture interrupts the native motion *before* the browser applies it, and the actual displacement afterwards decides whether following stops or resumes; `scrollend` settles and an off-target stop releases following. Why it transfers to August: August's chat is a transcript scrollport plus per-process-group scrollports plus a terminal section; one shared "following" flag pulls a capped group away from the reader whenever the outer transcript follows, and treating every non-bottom scroll event as reader input breaks native smooth follow outright.

- **`overflow-y: clip` clips without creating a scroll container; `hidden` silently becomes one** — `.agents/notes/archived/bug-fix/2026-09-22-chat-scroll-follow-and-footer-geometry.md:20` and `:25` (implementation: `packages/client/ui-chat/src/client/chat/ChatView.module.css:18-19`) — The mechanism: an `overflow-y: hidden` ancestor becomes the *nearest scroll container* even when the reader is scrolling a different outer element, which breaks `position: sticky` for code banners and compaction headers and makes floating controls measure transcript geometry instead of viewport geometry; `overflow-y: clip` constrains the overflow without that side effect — but only while the horizontal axis stays `visible`, because pairing vertical `clip` with horizontal `auto`/`hidden` computes the vertical overflow back to `hidden`. Why it transfers to August: August's chat has the same sticky headers, the same floating controls and the same nested scrollports, and the failure is invisible in review (nothing overflows, the content is simply shorter than expected).

- **Degrade to `unknown` rather than refuse the record — and never let a missing discovery field make readable history unavailable** — `.agents/notes/archived/bug-fix/2026-09-19-v3-incomplete-child-catalog-evidence.md:14` and `:24` (implementation: `packages/session/session-format-v3-to-v4/src/facts.ts:46-64`) — The mechanism: a child's *header* establishes identity and parentage; its *descriptor* carries discovery fields (mode, label). A catalog entry is backfilled only when **exactly one** supported own descriptor exists; zero or several, or an unsupported version, yield an `unknown`-mode membership instead of an invented mode, and never a refusal of the whole parent. The exactly-once requirement exists because two consumers disagree on which descriptor wins (`foldSubagentDescriptor` takes the first, the identity projection takes the last), so a backfill must not pick a side. Why it transfers to August: August migrates and reads session JSONL with subagent children; a rule that "refuses to open a conversation because a discovery field is missing" turns a cosmetic gap into data loss, and inventing the field turns a gap into a durable lie.

- **Say what the mechanism does NOT prove, in the note itself** — `.agents/notes/archived/bug-fix/2026-09-24-exited-holder-lock-takeover.md:20` and `.agents/notes/archived/bug-fix/2026-09-22-input-echo-admission-ownership.md:47` — The mechanism: the lock note states that takeover proves only that the *recorded process* exited, not that the processes it started stopped writing, and immediately pairs the limitation with a second mechanism (the run record) that closes it. The echo note states that the multi-input replay "does not assert that optimistic ordering predicts Host order". Why it transfers to August: August's own notes (and the repo AGENTS.md) make a habit of stating the limit and then saying which sibling decision owns the rest; a fix whose note claims more than the mechanism delivers is how a second reader ships a false guarantee.
