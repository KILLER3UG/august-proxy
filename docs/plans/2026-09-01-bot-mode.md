## 1. What Bot Mode is, mechanically (self-contained spec)

Five primitives, each deliberately cheap:

1. **Bot = an agent profile record.** No new runtime entity: a Bot is the existing agent
   registry entry (name, role, description, pinned model/provider, toolsets) plus UI metadata
   (avatar, title, group memberships) stored on the profile. Everything a Bot is — its chats,
   memory, skills, routines — is reachable from the API/CLI too; the UI "never owns your data,
   it only renders it."
2. **Canonical Bot Chat.** Each Bot is born with exactly one pinned, persistent conversation
   (title `Bot Chat`). It is the Bot's identity surface: routine results land there, teammate
   DMs arrive there, and opening the Bot from the roster opens it. `/new` inside a Bot Chat is
   rerouted to `/compact` — the forever-chat never forks the relationship.
3. **Routines = namespaced scheduled jobs.** A routine is a normal cron/automation job named
   `[bot:<name>] <title>` with the Bot's agentId, delivering its output into the Bot's own
   chat history. No separate scheduler.
4. **Teammate DMs via one injected tool.** `message_agent(target, message)` is injected into
   **only** canonical Bot Chat sessions (title-gated at prompt-build *and* re-checked at
   execution — a forged call returns a structured error). It is fire-and-forget: validates the
   target against the live roster, prefixes server-side attribution (`Message from 🤖 <sender>
   (@<handle>):`), runs one headless turn in the recipient's Bot Chat, and returns an ack
   immediately; the reply arrives later as a background-completion notification that wakes the
   sender on its next turn. A system-prompt section ("Messaging other agents") teaches the
   protocol: compose your own words (never forward the user's verbatim), message one relevant
   teammate, never ping-pong acks, silence is valid.
5. **Group rooms = bounded deterministic round-robin, no LLM router.** A room is one ordered
   shared log owned by the client. A user send triggers ≤3 serial rounds over the member
   roster; who speaks is a deterministic @mention parse (mentioned members, else everyone);
   a member *chooses* to speak or passes (literal `(pass)` / empty / failure = silence); a
   fully-silent round settles the room. Caps: 10 messages per send, 3 rounds. Each member runs
   in its own persistent `Group: <room>` session and is fed only room messages new since it
   last read. Escalation to the human is an `@user` mention → the room row shows a **needs
   you** badge.

Supporting behaviors worth copying exactly:

- **Presence strip** — "Active now": any Bot that wrote within 90 s shows a chip above the
  roster; chips open that Bot's chat; strip disappears when idle; never reorders the roster.
- **Avatars** — deterministic blob face derived from the name hash (same name → same face,
  zero storage, zero network), plus randomize/lock/silhouette options, uploaded image, or
  AI-generated portrait through the existing image path.
- **Capability epoch** — the Bot Chat's system prompt is rebuilt at most once per
  skills/toolsets/persona change (fingerprint check), so provider prefix caches stay warm
  (this is the same rule August's 08-29 cache work established).
- **Typed failure reasons** — a failed DM/delivery turn carries a machine-readable code
  (`provider_auth_or_access`, `provider_rate_limit`, `context_overflow`, `runtime_offline`,
  `target_busy`, …) end-to-end; transient failures retry exactly once on the *same* session
  (context-overflow retry compacts first); auth/quota failures never auto-retry.
- **Hide/unhide** — display-only removal from roster + presence; @mentions still resolve;
  hidden Bots accumulate unread silently and the eye toggle badges a dot.

## 1b. Verified mechanics — the two features that matter most

(Read from source 2026-09-01; line refs in Appendix A.1. These two areas were re-verified
after an initial misreading, so the spec below is the corrected, authoritative version.)

### How Bots actually communicate via @ (it is NOT what it looks like)

There is **exactly one send path: the `message_agent` tool, owned by the agent.** The `@`
sign is addressing sugar, never a delivery mechanism:

1. User types `@researcher look at this` in ANY chat. A composer middleware resolves
   `@researcher` against the **live roster** (handles renamed Bots' display titles,
   no-space forms, `@everyone`; emails and unknown handles pass through untouched).
2. The middleware **does not send anything to the researcher.** It appends an
   *identification note* to the user's message: `[@mentions resolved from the Bot Mode
   roster — the user is referring to: @researcher = agent profile "research-buddy"
   ("Research Buddy"). If they want one of these agents contacted, compose your own
   message and send it with your message_agent tool; never forward the user's text
   verbatim. If this session has no message_agent tool, agent messaging is unavailable
   here — say so.]`
3. The **current chat's agent** decides whether to act. If it has `message_agent` (only
   canonical Bot Chats do), it composes its OWN message to the researcher and calls the
   tool. The user's words are never relayed verbatim — the requesting agent paraphrases
   intent, which is also what keeps private 1:1 context from leaking across Bots.
4. `message_agent(target, message)` validates the target against the live roster, prefixes
   server-side attribution (`Message from 🤖 <sender> (@<handle>):`), runs **one headless
   turn in the recipient's canonical Bot Chat**, and returns an ack immediately
   (fire-and-forget; 16 000-char body cap). The recipient's reply arrives to the sender as
   a background-completion notification that wakes the sender; the sender relays it to the
   user, attributed to the replying agent.
5. In **group rooms** the @ mechanism is different and simpler: the round driver parses
   mentions deterministically to pick which members take turns (no agent tool involved, no
   LLM router); members can @-pull each other mid-room the same way.

Why this design earns copying: one auditable send path (attribution + containment applied
server-side), the model must *decide* to message (no user-text pipe into another agent),
and non-Bot sessions degrade gracefully ("say so") instead of silently dropping mentions.

### How each Bot's memory and skills stay its own

Isolation is **home-based, not filter-based** — the cleanest part of the design:

- Every memory read/write resolves `get_hermes_home()/memories/{MEMORY.md,USER.md}`
  (`tools/memory_tool.py:66`), and every skill subsystem resolves
  `get_hermes_home()/skills/` — creation (`skills_tool.py:159`), manager
  (`skill_manager_tool.py:192`), usage counts (`skill_usage.py:81`), curator ledger
  (`skill_ledger.py:91`), prompt snapshot, curator state. `get_hermes_home()` resolves to
  the **agent's own profile home** (derived from the agent's session-DB path, not ambient
  env — a deliberate fix for thread-fallback bugs that once leaked the default profile's
  skills index).
- A Bot's turn runs under that Bot's home → its MEMORY.md, USER.md, skills index, SOUL.md,
  and cron are loaded automatically. **No per-request filtering exists; isolation is
  structural.** A learned skill from Bot A's work is physically invisible to Bot B.
- Credentials are the ONE shared-by-default resource (new Bot shares the main profile's
  OAuth/token pool so refreshes can't invalidate each other); memory/skills are never
  shared. "Clone from existing" copies skills/SOUL/memory at creation — a fork, not a link.
- Defense in depth against a model that *tries* to cross over: (a) prompt-side — the
  system prompt names the active profile and its home paths and instructs "Do not modify
  another profile's skills/plugins/cron/memories unless the user explicitly directs you to"
  (`agent/system_prompt.py:764-806`); (b) tool-side — `classify_cross_profile_target(path)`
  (`agent/file_safety.py:498-523`) returns `{active_profile, target_profile, area,
  target_path}` for any write landing in another profile's scoped area; the caller surfaces
  a warning / prompts / proceeds only on explicit consent.

## 3. Phases

Score tags: **[feat]** earns its place as a capability, **[num]** measured improvement,
**[rel]** reliability, **[bug]** verified defect.

### Phase A — Bots tab: roster + canonical Bot Chat [feat]

The core ask. Spec:

- **Bot metadata extension.** Add `uiMeta: {title, avatar, hidden, groups}` to the agent
  registry record (KV blob — no migration). `POST /api/agents` grows the fields; a Bot is
  created with three fields (Name, Title, Description) or via Advanced (clone-from-agent,
  model pin, per-toolset ticks, custom persona text).
- **Canonical chat on birth.** Creating a Bot creates a workbench session titled `Bot Chat`
  bound to `agentId`, stamped `metadata.canonicalBotChat=<agentId>`, pinned in the session
  store. `/new` in that session reroutes to compaction (one-line guard in the reset path).
- **Bots rail.** New sidebar tab **Bots** next to Sessions (vertical rail — no horizontal pill
  tabs): one row per Bot = avatar + latest-message preview + timestamp + unread dot; search
  filter; right-click → Hide/Unhide, Edit Profile, Duplicate (full clone of record + persona +
  skills refs), Delete (destructive confirm; default agent undeletable). "Active now" strip:
  Bots with a message write in the last 90 s (backend: `touch_activity` already tracks
  activity — expose per-session last-write via `/api/sessions?recent=90`).
- **Avatars.** Deterministic identicon-style blob from `hash(name)` (pure SVG, no deps);
  Randomize (salt), Lock, silhouette pick; uploaded image; AI portrait via the existing image
  generation path when a provider is configured.
- **First message.** A new Bot introduces itself in its Bot Chat (one headless turn with its
  role prompt) — the roster is alive from birth.

Tests: registry round-trip for uiMeta; canonical-chat creation idempotency; `/new` reroute;
avatar determinism golden SVG; vitest for roster row/hide/presence. Files: `agent_registry.py`,
`routers/agents.py`, `workbench/sessions.py` (pin + guard), new `sections/bots/` + sidebar tab.

### Phase B — Routines [feat: the daily-briefing dogfood]

- Routine = automation job with `agentId` + name `[bot:<name>] <title>` + `deliver:
  "bot-chat"`. On completion the result is appended to the Bot's canonical chat as an
  assistant turn (same path as Phase C delivery — build `deliverToBotChat()` once, reuse).
- **Routines pane** docked beside the Bot chat while the Bots tab is active: structured
  schedule picker (frequency → detail), Advanced raw-cron field, run-now, last-run status,
  enable/pause. Routines also appear in the existing Automations section (single SoT).
- The Bot's system context gains a one-line roster hint: "You have routines; manage them with
  the automation tools" — so the user can say "summarize my inbox every morning" in the Bot
  Chat and the agent creates the job via the existing automation tool surface (check:
  `integration_tools.py` / tool registrations expose automation CRUD to the model; if not,
  register `create_routine`/`list_routines`/`delete_routine` — thin wrappers over
  `automations_store`).

Tests: namespacing + delivery into Bot Chat; run-now lands a message; pane CRUD against mock
API. Files: `automations_store.py` (agentId/deliver fields), `scheduler.py` hook,
`sections/bots/RoutinesPane.tsx`.

### Phase C — Teammate DMs: `message_agent` [feat: the "team" magic]

- **Durable inbox.** New SQLite table `bot_dm` (via `memory_conn` pattern):
  `{id, from_agent, to_agent, body, status: pending|running|delivered|failed, reason_code,
  created_at, delivered_at}`. Delivery = run one headless turn in the recipient's Bot Chat
  using the **existing bridge pattern** (`session_bridge.invokeAgent` shape: resolve/create
  canonical session → `sendWorkbenchMessageStream` → append reply). Fire-and-forget: the tool
  call enqueues + spawns the delivery task and returns the ack immediately.
- **Sender wake.** When the recipient's turn finishes, the reply is appended to the *sender's*
  Bot Chat as a `Message from 🤖 <recipient> (@handle): …` user-role turn and the sender's
  desktop session gets the existing session-update notification (SSE `session_status` /
  memoryUpdated-style push — reuse the live-update channel, don't build a new one). The
  sender relays it to the user on its next turn.
- **Injection gate.** `message_agent` schema + the "Messaging other agents" protocol section
  are added **only** when `session.agentId` is a Bot AND the session is its canonical Bot Chat
  (title check at prompt build in the `renderAgentContext` path, `workbench.py:1157`; re-check
  inside the tool executor — forged calls get a structured error). Roster lines
  (`- @handle — title — description`) come from the live registry; cached per capability
  epoch so prompt bytes are stable within a session.
- **Containment rules in the protocol text** (copy the reference doctrine): compose your own
  message, never forward user words verbatim, never reveal private 1:1 content, message one
  relevant teammate, no ping-pong acks, silence is fine.
- **Typed failures + one safe retry** per §1; `reason_code` enum in `bot_dm`.
- **@mention identification (user-side) — annotation only, never delivery.** Composer
  middleware (frontend): typing `@<bot> …` in ANY chat resolves the handle against the live
  roster (names, display titles, no-space forms; emails/unknown handles pass through) and
  appends an identification note to the outgoing text:
  `[@mentions resolved from the Bots roster — the user is referring to: @handle = agent
  "<name>" ("<title>"). If they want this agent contacted, compose your own message and send
  it with the message_agent tool; never forward the user's text verbatim. If this session has
  no message_agent tool, agent messaging is unavailable here — say so.]`
  The current agent decides whether to DM; there is exactly one send path (`message_agent`),
  attribution is applied server-side, and user text is never piped into another agent.
  Unknown `@handles` pass through untouched.

Tests: gate matrix (canonical vs regular vs subagent sessions see/don't-see the tool);
delivery round-trip with scripted model; sender-wake ordering; retry-once semantics per reason
code; mention-parse unit tests. Files: new `app/services/bot_mode/` (`dm.py`, `inbox.py`,
`protocol.py`), `agent_registry.py` (roster lines), `workbench.py` (injection point),
`routers/agents.py` (`POST /api/agents/{id}/dm` for the UI), composer middleware.

### Phase D — Group rooms [feat: deliberation; highest-risk, ships last]

- **Room = client-owned ordered log** (SQLite `bot_room` + `bot_room_message`), 2–6 members,
  name + member avatars; right-click a Bot → Manage groups.
- **Round driver** (backend service, not LLM): user send → ≤3 serial rounds; deterministic
  mention parse (names, quoted titles, collapsed forms, `@everyone`); each member runs one
  turn in its persistent `Group: <room>` session fed only new room messages; `(pass)`/empty/
  failure = silence; all-pass round settles. Caps 10 msgs/send, 3 rounds — enforced
  server-side.
- **`@user` escalation** → room row **needs you** badge (registry flag + UI dot).
- Room rows live in the Bots rail (activity-ordered beside Bot DMs); opening one shows the
  shared log with member avatars + device-free single-machine scope.

Tests: mention-parse goldens; round driver with fake members (caps, pass, settle, escalation);
session-per-member isolation. Files: `app/services/bot_mode/rooms.py`, `routers/agents.py`
room endpoints, `sections/bots/RoomView.tsx`.

### Phase E — Per-Bot memory & skills [rel: specialists must not contaminate each other]

Copy-the-mechanism where the mechanism is cheap and right; copy-the-behavior where August's
medium is stronger (revised 2026-09-01 after ruling discussion — the reference's skills
directory model IS copyable because August's Part 17 skill roots already work the same way):

- **Skills: copy the mechanism — per-Bot skill directories.** August's `_skillRoots()`
  (`skill_service.py:35-54`) already returns `(scope, path)` pairs with directory shadowing
  (project `<workspace>/.aug/skills/` overrides agent/bundled roots). Add one root kind:
  `('bot', dataDir/bots/<agentId>/skills)` — prepended for sessions with `agentId` set,
  shadowing global/bundled exactly like project skills do. Learned skills distilled from a
  Bot's episodes (`skill_distiller.py` → agent-root writes) gain a `botRootFor(agentId)`
  target. Clone = copy the folder. Per-Bot curator/usage state = sibling files in the same
  folder. This is the reference's home model, adopted verbatim where our stores are already
  file-based.
- **Memory: copy the behavior, not the file mechanism.** The reference's per-home
  MEMORY.md/USER.md are small bounded text files (2 200 / 1 375 char caps in its config);
  August's memory store is a SQLite DB with FTS, confidence, expiry, rollback, and import —
  reverting Bot memory to per-Bot md files would discard machinery Part 15/17 built and the
  user's readability rulings serve through the DB. Instead: the existing `workspace_path`
  scope-column pattern (`memory_schema.py:78,395`) gains scope kind `bot:<agentId>` —
  writes from Bot sessions (chat, routines, group turns, DM turns) stamped server-side in
  `save_fact`; retrieval for a Bot = global ∪ this-Bot; one shared scope-resolution function
  for skills + memory so the rule can't drift. Enforcement at the single write door is
  stronger than the reference's advisory classifier (`file_safety.py:498-523`).
- **Sessions: one DB, scope column — do NOT copy per-profile state.db.** Per-Bot DB files
  buy nothing for a single-user, single-process desktop and cost N× migrations, N× file
  handles, and union queries for cross-Bot search.
- **User profile stays GLOBAL** (one user; per-profile USER.md is a multi-tenant artifact —
  OQ7).
- **Guard layer 1 (prompt)**: `renderAgentContext` gains one deterministic line — "You are
  Bot @<handle>; your skills live in your own folder; other Bots' scopes are not visible to
  you." Cache-safe (stable per session).
- **Why not homes wholesale**: the reference's env/ContextVar home resolution caused it real
  bugs — a build thread losing the ContextVar leaked the default profile's skills index
  (`system_prompt.py:772-775` comment), and the shell-transport DM path had quoting traps +
  temp-file races that forced a rewrite into a real tool (`bot_mode_dm.py:14-20`). August
  passes the Bot scope as an explicit argument through one process: same isolation, none of
  that failure surface.

Tests: bot skill root shadowing (project > bot > agent > bundled precedence), distiller
writes to bot root when agentId set, clone copies folder, cross-Bot memory isolation matrix,
prompt bytes stable. Files: `skill_service._skillRoots`, `skill_distiller.py`,
`memory_store/` scope resolution, `memory_schema.py`, `agent_registry.renderAgentContext`.
