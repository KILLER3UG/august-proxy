# deepseek-harness / dsh-client-agents-ui

## Shard shape

This shard is the **browser client surface layer** of `deepseek-harness` — nine Cordis
"surface plugin" packages under `packages/client/`, all published as
`@deepseek-ai/dsh-client-ui-*` at version `0.2.1-rc.2`, all `platform: "web"`, all
`"type": "module"`, all built by the same one-line `tsdown.config.ts` calling a shared
`clientBundle()` helper. The packages, with their share of the shard's 259 files, are:

| Package | Files | What it renders |
|---|---|---|
| `ui-agent-preset` | 33 | the agent-preset roster, the new-task default, the read-only composition viewer, and the entry into Creator mode |
| `ui-approval` | 16 | the composer takeover that answers a Host permission request |
| `ui-brand-official` | 12 | the official sidebar brand occupants, gated on a build profile |
| `ui-goal` | 27 | the goal strip above the composer plus the durable `/goal` command-input bubble |
| `ui-plan` | 27 | the plan-mode chip, the submitted-plan cards and the sidebar plan document |
| `ui-schedule` | 77 | the Automation-tasks page, the session reminder catalog and the ambient sidebar marks |
| `ui-subagent` | 21 | the subagent lineage tree, continuation routing and the `@` reference source |
| `ui-user-questions` | 29 | the `ask_user_question` composer takeover, its timed wait, the plan-review card and the late-reply bubble |
| `ui-workflow-run` | 17 | the durable workflow-run chat node with nested phase/member disclosure |

`ui-schedule` is the largest package at 77 files (30 % of the shard) and holds the only
*page* in the shard — the global Automation-tasks page with its own detail pane, its own
stylesheet (the shard's largest, 1,475 lines) and its own 4,368-line test suite. Every
other package is a set of surfaces hung off the conversation.

They fit together through one shared framework that lives outside this shard: the
**Cordis slot registry** (`ctx.slots.inject(name, mount)` / `ctx.slots.register(...)`),
a **standard kit** of framework-bound hooks (`useProjection`, `useSessions`,
`useSessionStatus`, `useChat`, `useResource`, `useStore`, `useTabInfo`, `renderSlot`),
and a **Conversation Definition** API (`kind` / `match` / `start` / `update` /
`buildViewNode`) that lets a package claim a durable session event and project it into
the chat transcript as its own node. Every package splits itself into a **node half**
(`src/index.ts` — an empty `apply()`, so the package appears as a row in the host
Loader without doing anything) and a **browser half** (`src/client/index.ts`, discovered
through the `dsh.client` block in `package.json`). Every package registers a locale
dictionary under its own namespace, ships an English/Chinese README pair, and carries a
`README.i18n.yaml` hash record proving the two READMEs stayed in sync.

The shard's real subject is **not the agent loop** — it is everything the loop's
*output* looks like to a human: cards, chips, disclosures, countdowns, trees, and the
rules for when a UI is allowed to claim that something happened.

### packages/client/ui-agent-preset/README.md
- Purpose: the package reference for choosing Agent presets and the new-task default in Web.
- Key abstractions: "preset roster", "new-task default", "read-only composition viewer", "Creator entry".
- Data flow: `agentPresets/list` supplies the roster and marks the default; `agentPresets/read` supplies one declaration's YAML for the viewer; default changes write the `agent-preset-registry` settings namespace.
- Non-obvious design decisions: the choice lives on the **new-session screen** and the session header carries only a **read-only label**, because the host refuses to swap a session's composition after its first turn; Coding Tools off hides PTC and Minimal and resets a saved hidden default to Standard, per browser, while Standard/Creator/custom defaults survive.
- Edge cases: a failed preset stays readable because its diagnostic points into the YAML; a late read does not reopen a viewer that was closed; if Standard is missing or broken the default is left unchanged and an error is shown.
- Surprising: the `Model Experience` section states that a preset's *plugins* own model-visible capabilities — the UI package itself changes nothing, and the KV-cache effect is "selection changes affect only later tasks; existing plugins and prompts remain unchanged."
- Line 28 is a single 1,900-character paragraph carrying the whole behavioural spec — this repo's README style is dense prose, not bullets.

### packages/client/ui-agent-preset/src/client/seat-store.ts
- Purpose: the hero-chip controller — which preset the *next* session gets.
- Key abstractions: `AgentPresetSeatState`, `AgentPresetStage` (a shared mutable `{id, introduce}`), `AgentPresetSeatController`.
- Data flow: `load()` reads the roster (guarded by a `loadGeneration` counter so "only the newest roster read may publish after overlapping refreshes"); `select(id)` stages; the stage is applied when a session that is `blank` and current appears.
- Non-obvious design decisions: the stage is **forgotten once applied**, so the next new session starts from the Host-effective default again; a `fallback` field holds the Host default so a consumed stage can fall back without re-reading the roster.
- Edge cases: a session that records no preset of its own is still eligible (reading "already runs it" would drop the pick on the floor); a selection refusal prefers `error.details.reason` over `error.message` because the Toast already names the rejected preset.
- Surprising: the `introduce` flag is a one-shot cue so a pick staged from *another* screen (the Creator entry) can be announced by the chip even though the user never touched it.

### packages/client/ui-agent-preset/src/client/section-store.ts
- Purpose: the Settings page controller — roster, default write, read-only viewer.
- Key abstractions: `AgentPresetSectionState`, `AgentPresetSectionController`.
- Data flow: `view(id)` bumps a `viewRequest` counter so a read superseded by a close or a newer read is ignored.
- Non-obvious design decisions: `reconcileCodingTools(shouldReset)` **re-checks the predicate after waiting** for a pending save, and only then writes; it uses the settings form's `revision` as an optimistic-concurrency fence and refuses if `standard` is missing or broken (surfacing `standardUnavailable` instead of silently pointing at a broken default).
- Edge cases: `load()` shares one in-flight read between simultaneous callers (`this.loading ??= …`).
- Surprising: `makeDefault` writes the default, reloads, and **then** syncs the blank session — so a failed write still leaves the roster authoritative.

### packages/client/ui-agent-preset/src/client/settings-store.ts
- Purpose: the shared roster store.
- Key abstractions: `AGENT_PRESET_SETTINGS_NS = 'agent-preset-registry'`, `writeDefaultPreset(ctx, id, expectedRevision?)`, `readRoster`, `beginRosterRead`, `presetOptions`, `requiresCodingTools`.
- Data flow: one `agentPresets.list` call feeds every surface.
- Non-obvious design decisions: `readRoster` treats `gateway/invocation-unavailable` as an **empty roster**, not an error, because "agent presets are optional: without that service every session uses the Host composition"; `presetOptions` filters broken presets at the picker but not at the source ("a broken preset cannot compose one — offering it would defer the discovery of that fact to a failed session start"), and the management section renders the full roster from its own store instead.
- Edge cases: `requiresCodingTools` is true only for the *built-in* PTC and Minimal ids, so a custom override named "ptc" keeps its own behaviour.
- Surprising: the `exactOptionalPropertyTypes` spread dance in `presetOptions` is centralised "so … absent and present-as-undefined [are] different shapes" rather than repeated per store.

### packages/client/ui-approval/README.md
- Purpose: the browser approval UI.
- Key abstractions: "the scoped Remote Event waterfall", "the composer takeover", "the optional correlated Tool detail".
- Data flow: the plugin publishes each pending request through `ctx.uiSession`, takes over the Conversation composer, optionally renders correlated Tool detail, and returns the user's decision to the waiting Host request.
- Non-obvious design decisions: the mounted plugin **reserves** Enter and Escape against editable shortcuts; Enter on a focused Reject button keeps its native reject action; input controls and IME candidates keep their own keys.
- Edge cases: "Keyboard and pointer actions share one pending-request lock; a withdrawn or replaced request cannot accept another answer, and an earlier failed answer cannot unlock its replacement."
- Surprising: `Model Experience: None, as this package presents approval requests in the browser and registers nothing model-facing` — the package asserts its own absence from the model's surface.

### packages/client/ui-approval/src/client/ApprovalPanel.tsx
- Purpose: render one pending approval and its optional Tool detail.
- Key abstractions: `ApprovalFlow`, keyed on `pending.key` so a new request remounts.
- Data flow: `approval.answerable` gates the actions; a failed `pending.answer(...)` resets the local `waiting`/`answered` state so the buttons re-arm.
- Non-obvious design decisions: the keyboard handler refuses to act when the event target is inside an input/textarea/contenteditable, refuses Enter when the target is a button/link, refuses any modifier, and refuses while an IME composition is active (`event.nativeEvent.isComposing || event.keyCode === 229`).
- Edge cases: `aria-busy` tracks the in-flight answer; the detail region is `tabIndex={0}` with a `role="group"` and an aria-label so it can be focused and answered with Enter.
- Surprising: the "escalation" headline — "Tool {toolName} requests privileged execution" — is only used when the requester supplied no reason.

### packages/client/ui-approval/src/client/contract/slots.ts
- Purpose: the approval composer and optional detail contracts.
- Key abstractions: `PendingApproval` (a class, not a plain object), `ApprovalPresentationRequest`, `ApprovalDecision = 'allowed-once' | 'rejected'`.
- Data flow: the class owns a `Promise.withResolvers` for the Host's answer, an abort listener, and a `#delegated` sentinel.
- Non-obvious design decisions: `delegate()` rejects with a private `Symbol` so the listener can recognise it and hand the request to the next waterfall listener; `finish()` throws "already settled" so a double answer is a loud bug rather than a silent one.
- Edge cases: an already-aborted signal aborts in the constructor; `settlePendingComposer` converts a non-`Error` throw into a wrapped `Error` with `cause`.
- Surprising: the file is wrapped in a `/* jscpd:ignore-start */` block with the note "Approval and Question intentionally own independent pending-settlement lifecycles" — duplication between the two packages is *declared*, not accidental.

### packages/client/ui-approval/src/client/index.ts

- Data flow: `ctx.remote.$on('approval/request', (request, next) => answerApproval(...))`; the composer seat is claimed with `select: ({pendingInteraction}) => pendingInteraction instanceof PendingApproval ? pendingInteraction : null`.
- Non-obvious design decisions: the shortcut registration uses `registerFixed` for `Enter` and `Escape` under a dedicated `approval` group, and the approval is *not* translated in the failure strings.
- Edge cases: an unscoped request (`ctx.sessions.scopeOf(owner)` is `undefined`) immediately delegates to `next()`.
- Surprising: `ctx.slots.register` declares a child seat `conversation.approval.detail` of kind `single`, scope `session` — the Tool package can fill it, and the approval package never renders Tool detail itself.

### packages/client/ui-schedule/src/client/catalog-source.ts
- Purpose: the authoritative Schedule queries and deletion shared by the Session and Host catalogs.

### packages/client/ui-schedule/src/client/schedule-format.ts
- Purpose: the browser-safe formatter shared by the Session catalog, the Host catalog, the tasks page, the detail and the sidebar hover card — every place that has to state *when* a reminder fires.
- Key abstractions: `FrequencyTranslator` / `ZoneLabelKey` / `RelativeTimeKey` (the dictionary key unions this file needs, all namespace-independent so the `schedule.catalog` and `schedule.manager` dictionaries can both supply them), `FrequencyZone`, `zoneLabel`, `zoneName`, `zoneChoices`, `formatScheduleFrequency`, `formatScheduleNextRun`, `formatScheduleAbsolute`, `formatScheduleRelative`, `nextRunParts`, `orderScheduleRecords`, `taskName`.
- Data flow: a stored `ScheduleRecord` is switched on its `kind`; `formatScheduleFrequency` renders the exact rule text, `formatScheduleAbsolute`/`formatScheduleRelative` render the next-run pair, and `orderScheduleRecords` sorts overdue records first.
- Non-obvious design decisions: the zone inventory is **the browser's own ICU/CLDR data**, not a product table — `Intl.supportedValuesOf('timeZone')` supplies the ids and `Intl.DateTimeFormat(..., { timeZoneName: 'longGeneric' })` the names, so "there is no crawler or generated zone-name resource to refresh"; `zoneChoices` sorts by *current* UTC offset and canonical id, and appends a stored alias the inventory omits so "an accepted alias never disappears from the menu"; `zoneOffset` is read once per zone and cached in a local map before the sort, because resolving it inside the comparator would build O(n log n) `Intl` formatters for several hundred zones.
- Edge cases: an engine without `Intl.supportedValuesOf` falls back to `['UTC']` and a stored zone rather than an empty menu; a zone ICU cannot name keeps its raw IANA id; a cron expression the *browser's* parser cannot read keeps the raw `Cron {expression}` form, so "the stored rule stays visible when the Host's dialect and this parser diverge"; `formatScheduleFrequency` ends in `assertNever(record)` because the record kind is a closed union.
- Surprising: the *stored* zone and the *displayed* zone are deliberately different things — a daily/weekly/cron record keeps its own IANA zone for its rule, but `formatScheduleAbsolute` always shows the next run in the **reader's** zone ("the instant is the same one, and the reader compares it with their own clock"), and the year is a per-language typographic choice (`YEAR_LANGUAGES = ['en']`, `NO_YEAR_LANGUAGES = ['zh']`) with every unlisted language defaulting to stating the year.

### packages/client/ui-workflow-run/src/client/workflow-definition.ts
- Purpose: fold the four durable `tool-workflow/*` events into one keyed chat node.
- Key abstractions: `WorkflowRunStatus`, `WorkflowRunMemberData`, `WorkflowRunPhaseData`, `WorkflowRunChatData`, `workflowPhaseKey(phase)`, `projectWorkflow(context, location)`.
- Data flow: `match` claims `run-start` as `role: 'start'` and the three update events
  as `role: 'update'`; `update` folds each into a `WorkflowState`.
- Non-obvious design decisions: `workflowPhaseKey` builds a collision-free key that
  preserves *absent* from *empty* — `phase === null ? 'missing' : \`value:${phase.length}:${phase}\`` —

  `turnAbandoned(location)` infers interruption only when the owning Turn ended with

  closure says nothing about liveness."
- Edge cases: a zero-member run is retained as its own completed node; a member with
  no outcome is `running` unless the turn was abandoned, in which case it is
  `interrupted`.
- Surprising: the `stopReason` and `outcome` mappings are exhaustive over closed unions
  with `satisfies never` guards, so a new variant is a compile error.

## Ideas worth stealing

- **Every browser package must declare its own model-visible effect and its
  KV-cache effect** — `packages/client/ui-plan/README.md:81-83` (and the same
  `## Model Experience` / `#### KV Cache effect` block in all nine packages) — the
  mechanism is a *mandatory section in the package README* that states whether the
  package reaches a model request and whether it invalidates a provider prefix cache.
  Why it transfers to August: the AGENTS.md file already argues at length about
  prefix stability and cache-hit optimisation; this turns "does this change the
  prompt?" into a checkable per-package fact rather than folklore. It also forces a
  distinction the shard proves is real: exactly one package in the shard
  (`ui-plan`) changes the request prefix (the `plan:policy` section), one is
  append-only (`ui-subagent`, and it says so with a token count of zero), one is
  conditional (`ui-goal`: "unless the queued goal context is admitted"), and the rest
  say "None". A package that cannot say which of the four it is has not understood
  its own blast radius.

- **Order reads with counters, never by comparing clocks** —
  `packages/client/ui-schedule/src/client/catalog-source.ts:24-43` — the mechanism is
  a `readRequest` counter (how many reads have been *asked for*) and a `readSettled`
  counter (which request's result the current records came from), so a consumer can
  ask "is this record definitely gone?" without ever comparing a browser timestamp to
  a Host timestamp. The consumer is
  `packages/client/ui-schedule/src/client/ScheduleTurnCard.tsx:62-78`, which records
  the ordinal at mount and only reads "deleted" when a read *requested after that
  point* has succeeded. Why it transfers: August has the same problem everywhere a
  browser and a server both hold a record (a deleted file, a closed task, a revoked
  credential), and every clock-based answer is wrong by exactly the amount the two
  machines disagree. The file's own comment is the transferable sentence:
  "Counters rather than timestamps, so the answer never compares the browser's clock
  with the Host's."

- **Epoch-guard a read so a late HTTP response cannot overwrite a live event** —
  `packages/client/ui-goal/src/client/activation-source.ts:57-75` — the mechanism is
  three independent counters (`readEpoch`, `eventEpoch`, `projectionEpoch`) captured
  before the await and re-checked after it, so a result is discarded if *anything*
  moved while it was in flight. Why it transfers: this is the exact class of bug
  August's `stuck-request` ladder exists to escape, on the client side of the wire —
  a projection frame arrives, then the older HTTP read lands and clobbers it. The
  equivalent DSH pattern is "a stale result must not overwrite a newer edge", and
  this is the shortest correct implementation of it I have seen.

- **A countdown must be owned by the request carrier, not by the component that
  displays it** — `packages/client/ui-user-questions/src/client/contract/slots.ts:360-373`
  — the mechanism is `#reschedule()` on the `PendingQuestion` object, with the
  reason written at `:359-363`: "the panel can be hidden and remounted while the
  request stands, and a timer that died with the component would leave the tool call
  waiting past its deadline." Why it transfers: any timeout August puts in front of a
  human (an approval, a question, a wait-for-input) has the same shape, and the
  usual implementation — a `useEffect` timer in the dialog — silently stops ticking
  the moment the dialog is closed or the tab is backgrounded. The same file also
  distinguishes `waitState` (`counting | focused | editing | waiting | continued`)
  from `channel` (`waterfall | rpc | none`), which is a good vocabulary for "what is
  the request waiting on right now".

- **Distinguish "sent" from "confirmed", and re-arm rather than claim success** —
  `packages/client/ui-user-questions/src/client/QuestionComposer.tsx:203-214` — the
  mechanism is: a waterfall submission is only *sent* ("the gateway drops an outcome
  that arrives after another Client settled the event, without telling anyone"), so
  the draft survives, the controls stay disabled, and when the card flips to
  `continued` the composer re-arms with an explicit message — "The answer did not
  arrive before work continued; submit it again." Why it transfers: this is
  precisely the family of "silent blindness" that August's AGENTS.md keeps
  rediscovering (the `[Blocked]` marker read as success; the 400 marker hiding the
  provider's reason; the `recovered` event emitted and vanishing). The general
  rule is: **a UI must not report a send as a success unless something confirmed
  it, and it must keep the user's work when it cannot.**

- **A specialised view may not narrow the answer space** —
  `packages/client/ui-user-questions/src/client/contract/slots.ts:81-101`
  (`planReviewOf`) — the mechanism is a narrowing predicate that claims a request
  only when the specialised card can represent *every* answer the generic flow
  could: one question, non-multi-select, at most two options, and a named approve
  option. Everything else — a third option, a multi-select, a missing intent — falls
  back to the generic flow. The stated reason (`:213-214` of the test file) is the
  transferable sentence: "Two buttons cannot send a third label or a combination,
  and the generic flow can: an intent never costs the user a reachable answer." Why it
  transfers: any "smart" specialised renderer August adds (a plan card, a diff card,
  a form card) can silently remove a legitimate answer; this predicate is the guard.

- **Fold the host's state; never guess it client-side** —
  `packages/client/ui-plan/src/client/PlanModeControl.tsx:32-34` — the mechanism is
  `const target = plan.pending ? !plan.active : plan.active`, with the comment "a
  folded host value, not client optimism, so an arriving frame corrects the chip
  either way." Why it transfers: the same fold is needed for every optimistic UI in
  August (a mode toggle, a "running" badge, a queued indicator). The rule is that
  the client computes nothing the host can contradict; it renders the host's fold.

- **Two independent fences: the server's compare-and-set for staleness, the client's
  synchronous ref for double-submit** —
  `packages/client/ui-goal/src/client/index.ts:89-95` (the CAS ref is read from the
  session's *current* projected value at call time — "no staleness fence: the RPC's
  compare-and-set is the guard") and
  `packages/client/ui-goal/src/client/GoalBar.tsx:59-71` ("React state disables the
  controls on the next render; the ref closes the same-render window so rapid clicks
  cannot submit the same CAS twice"). Why it transfers: this is the *correct* pairing
  for an optimistic UI, and it is exactly what August's `check:brain-config` gate
  and its CAS-fenced writes need mirrored on the client side.

- **Recover a durable artifact by replaying the log, not by storing it** —
  `packages/client/ui-plan/src/client/plan-resource.ts:37-81` — the mechanism is a
  resource provider that follows the Session history, breaks on the `snapshot` frame
  to fix the page API's log cut, and pages backwards with `beforeSeq` until it finds
  the exact invocation. The plan *text* is therefore never persisted in layout
  state, and "browser reload restores the document from Session history" is free.
  Why it transfers: August stores plans, patches, reports and diffs in exactly this
  kind of "artifact the user will want to reopen tomorrow" class; reading them back
  out of the durable log removes a whole class of persistence bugs (stale copies,
  half-saved drafts, two sources of truth) at the price of one paging loop.

- **A node that is a deterministic replay of durable events** —
  `packages/client/ui-workflow-run/src/client/workflow-definition.ts:154-198` with
  the property asserted at
  `packages/client/ui-workflow-run/tests/workflow-run.client.spec.tsx:161-176` — the
  mechanism is that prepend, complete replay and live append produce *the same*
  state, and an update-only history tail stays **pending** until an older page
  supplies the unique start event. Why it transfers: a chat node that can be
  reconstructed from a log is reload-safe, testable without a live host, and
  diffable against a replay — and the "pending until the start arrives" rule is the
  piece that stops a partial history window from rendering a half-built node.

- **Do not infer liveness from a step boundary** —
  `packages/client/ui-workflow-run/src/client/workflow-definition.ts:83-93`
  (`turnAbandoned`) — the mechanism: "A foreground run writes its run-end before its
  Tool Step ends, and a background run outlives that Step, so an ordinary Step or
  Turn closure says nothing about liveness. Only a Turn closed after a crash or at a
  fork boundary proves that a run without run-end stopped." Why it transfers: this is
  August's `turn_end { reason }` vocabulary in miniature — `interrupted` and `forked`
  are the only two closers that prove anything, and a client that treats "the step
  ended" as "the work ended" will show a dead run as running forever.

- **Defer an auto-collapse until the user is not reading inside it — and settle the
  deferral on three paths** — `packages/client/ui-workflow-run/src/client/WorkflowRunPanel.tsx:123-141`
  (`advanceDisclosureState` with `pendingCleanCollapse`), `:424-441` (the blur
  settle), `:372-373` and `:373-400` (the `useLayoutEffect` settle, "outer hiding
  unmounts Phase content without a dependable blur event"), `:310` and `:448-450`
  (the `onMouseDownCapture` focus guard) and
  `:163-168` (`preventPendingHeaderFocus`). Why it transfers: any panel that
  auto-collapses when its work completes (August's activity groups, a running-tool
  summary) will yank content out from under a keyboard user. The four-part fix
  (defer flag, blur settle, layout-effect settle, focus guard) is the complete recipe.

- **One shared query, N rows, and an equality predicate so the rows do not
  re-render** — `packages/client/ui-schedule/src/client/session-schedule-state.ts:73-111`
  (`selectSessionScheduleFacts` + `sameSessionScheduleFacts`) with the property
  asserted at
  `packages/client/ui-schedule/tests/session-schedule-shared.client.spec.tsx:54-77`
  (the row's render count stays at 1 when another Session's task changes). Why it
  transfers: this is the client-side twin of August's "N visible rows issue one query
  rather than one per row" rule, and the equality predicate is the piece that makes
  the shared query safe — without it, one busy session re-renders the whole sidebar.

- **A durable local binding for a UI whose container does not persist its own
  parameters** — `packages/client/ui-schedule/src/client/task-tab-bindings.ts:1-20`
  (the module header) and `:208-222` (the store) — the mechanism: the Sidebar
  persists a tab's layout record but *not* the opener's navigation parameters, so the
  page keeps a `localStorage` binding from the layout id to the task it last showed;
  the key is the layout id, not the `contentId`, because "every tab of one page kind
  records the same one"; a write prunes against the *committed* tab ids, and an empty
  committed list skips pruning entirely. Why it transfers: any August UI that opens a
  detail in a tab will hit exactly this — the tab survives, its parameters do not, and
  the user reloads into an empty panel.

- **A test that reads the CSS as text when there is no layout engine** —
  `packages/client/ui-goal/tests/goal-command-input-styles.client.spec.ts:16-30` and
  `packages/client/ui-workflow-run/tests/panel-styles.client.spec.ts:19-49` — the
  mechanism: parse the module stylesheet with a regex and assert the *declarations*
  (e.g. that the command bubble declares no `font` of its own and uses the shared
  `--dsh-content-font-size` axis; that the workflow panel's phase status column
  width scales with `--dsh-content-font-delta-secondary`). Why it transfers: August's
  `check:truncate` gate already reads the AST for a similar reason; the same trick
  extends to any design-system rule that a screenshot test cannot see.

- **Assert the architecture, not just the behaviour** —
  `packages/client/ui-user-questions/tests/node-plugin.client.spec.ts:24-25` — a
  27-line test that mounts the Host's `SystemPrompt`, `ToolRuntime` and
  `UserQuestionService` and asserts `ctx.tools.get('ask_user_question')` is
  `undefined`, with the comment "Host UI registration must leave each preset's
  model-facing tool list intact." Why it transfers: a UI package that registers a
  model-facing tool is a capability escalation; a two-line invariant test makes that
  impossible to do by accident, and the same shape would let August assert that no
  browser plugin can add a tool to the model's surface.

- **A "closing is not an answer" affordance contract** —
  `packages/client/ui-user-questions/src/client/contract/slots.ts:245-250` and
  `packages/client/ui-user-questions/src/client/QuestionComposer.tsx:294-314` — the
  mechanism: `dismissal: 'hide' | 'cancel'` distinguishes a card the Host named by
  tool call (closing withdraws the panel, the request stands, the tool row brings it
  back) from one it did not (closing ends the wait as `ASK_CANCELLED`); and when
  there is no channel to carry the cancellation, the surface says "Cannot submit
  right now; try again in a moment" rather than pretending the request was closed.
  Why it transfers: the X button in August's dialogs currently has to mean one thing
  everywhere; this is the vocabulary for letting it mean two honest things.

- **An auto-growing textarea measured by a hidden mirror, not by counting
  newlines** — `packages/client/ui-user-questions/src/client/QuestionComposer.tsx:90-123`
  — the mechanism: a hidden element renders the draft plus a trailing newline in
  normal flow and owns the row's height, because "counting rows by '\n' cannot see
  soft wraps"; the textarea shares that one cell and stretches to it, and "Mirror and
  textarea MUST share font, line-height, padding and wrapping rules or the two heights
  diverge." Why it transfers: a dependency-free auto-grow that handles soft wraps,
  and the comment names the exact failure mode to avoid.

- **One writer, one namespace, one revision fence** —
  `packages/client/ui-agent-preset/src/client/settings-store.ts:16-37` and
  `packages/client/ui-agent-preset/src/client/section-store.ts:85-99` — the mechanism:
  `writeDefaultPreset` is the single place that knows which settings namespace and
  field the Host resolves at session creation, it takes an optional
  `expectedRevision`, and the reconciliation path re-checks its predicate *after*
  waiting for a pending save and refuses if the target preset is broken. Why it
  transfers: August's `check:brain-config` gate exists because the Settings panel and
  the backend can disagree about a key; this is the writer-side discipline that makes
  such a disagreement impossible rather than merely detected.

- **Filter a broken option at the picker, not at the source** —
  `packages/client/ui-agent-preset/src/client/settings-store.ts:104-127` — the
  mechanism: `presetOptions` drops presets marked `broken` for the *pickers* (a
  broken preset cannot compose a session, and "offering it would defer the discovery
  of that fact to a failed session start") while the management section renders the
  full roster from its own store, so a broken preset is still visible and diagnosable.
  Why it transfers: the same split applies to any option list in August — offering a
  broken model or a broken tool is a deferred failure, and hiding it everywhere is a
  different failure.

- **A user-facing control only where it can still work** —
  `packages/client/ui-agent-preset/src/client/AgentPresetLabel.tsx:1-9` versus
  `packages/client/ui-agent-preset/src/client/AgentPresetSeat.tsx:1-13` — the
  mechanism: the *choice* is on the new-session screen and the header carries a
  *read-only label*, because the host refuses to swap a session's composition after
  its first turn; the file header says a header control "would promise a switch the
  host refuses." Why it transfers: the same rule decides where August's mode
  toggles, plan toggles and preset pickers belong, and it is a much better argument
  than "we put it there for discoverability".

- **The `pending` vs `confirmed` distinction for a background run, and the
  interrupted inference that follows from it** — see the two workflow-run ideas
  above; together they are the closest thing in the shard to August's
  `turn_end { reason }` design, and the phrase "the session log carries no fact that

## Uncertainties

#### Lens-by-lens: what this shard does and does not hold

The shard's nine packages are **surface** plugins — everything they own is a browser
surface. I checked each research lens against the shard's own source (not just its
READMEs), and here is what the evidence supports:

- **Agent loop and tool-calling flow — NOT in this shard.** No loop, no tool executor,
  no round accounting. What the shard *does* hold is the loop's two human-facing
  surfaces: the approval takeover (`packages/client/ui-approval/src/client/contract/slots.ts`)
  and the question takeover (`packages/client/ui-user-questions/src/client/contract/slots.ts`),
  which is where a tool call becomes a thing a person answers.
- **Reasoning / thinking content — NOT in this shard.** I grepped all of
  `packages/client` for `reasoning_effort|reasoning_content|thinking_delta|<think>`:
  the only two hits in the whole tree are the EN and ZH locale strings in
  `ui-settings-models` (a different shard) that *describe* a `reasoning_effort` request
  field to the user. Nothing here streams, buffers or renders a thinking block.
- **Prompt construction and caching — PARTIAL, and only as a stated contract.** No
  prompt is assembled here; nine READMEs each carry a mandatory
  `## Model Experience` + `#### KV Cache effect` block, and exactly one package
  (`ui-plan`) changes the request prefix (the `plan:policy` section), one is
  append-only (`ui-subagent`), one is conditional (`ui-goal`), and the rest say "None".
  That contract is the shard's real contribution to the caching lens, and it is
  documentation, not code.
- **Context window management and compaction — NOT in this shard.** The only mention is
  *guide copy* describing what the Minimal preset does ("Older history is compacted
  automatically under context pressure; use /compact while the agent is idle"),
  `packages/client/ui-agent-preset/src/client/guide-locales.ts:45`.
- **Model-specific adaptations — NOT in this shard.** The per-model surface
  (`toolSurface`, `maxTools`, `maxToolResultChars`) lives in the Host's model settings,
  outside these nine packages.
- **Memory / learning — NOT in this shard.** No brain, no facts, no skills, no
  distillation. The only related words are in preset *descriptions*.
- **Subagent / parallel execution — PARTIAL, and it is the interesting one.** `ui-subagent`
  is the browser half of the subagent tree: the lineage breadcrumb and lazily expanded
  catalog (`packages/client/ui-subagent/src/client/SubagentHeaderLineage.tsx`, 823 lines),
  the addressed child session (`src/client/sidebar-chat/index.tsx`), the read-only
  composer that replaces input when a child cannot take it
  (`src/client/SubagentReadOnlyComposer.tsx`), and the `@` reference *source* — whose
  implementation is **not** in this shard (see below). It renders parallel work; it
  does not schedule it.
- **Tool-call reliability — PARTIAL.** No retry policy, no malformed-output handling,
  no timeout. But the shard holds the client-side halves of the two failure modes
  August keeps rediscovering: a *sent* answer that was never confirmed
  (`packages/client/ui-user-questions/src/client/QuestionComposer.tsx:203-214`) and a
  request whose countdown must outlive the component that shows it
  (`packages/client/ui-user-questions/src/client/contract/slots.ts:360-373`).
- **UI / UX patterns — THIS IS THE SHARD.** Progress feedback, disclosure ownership,
  empty/loading/error states, one-query-N-rows, deferred auto-collapse, focus

  reconcile path that re-checks its predicate after awaiting a pending save

- **Evals / testing — THIS IS THE SHARD, heavily.** 55 of the 259 files are test
