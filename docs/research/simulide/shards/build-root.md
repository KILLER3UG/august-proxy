# simulide / build-root

## Shard shape

This shard is the repository's **root and entry layer**: the legal/identity files, the qmake build system, the Qt resource manifest, the process entry point, the top-level window, and the one shared utility header. It holds no simulation logic and no component implementations — it is everything you touch before the simulator exists. The shape is: `build_XX/SimulIDE_Build.pro` (a 6-line stub) sets `BUILD_DIR` and includes `SimulIDE.pri`, which is the *entire* build system — one recursive glob for every source file, a hand-maintained flat `INCLUDEPATH`, per-OS blocks, a build-date stamp, and a `lrelease` step that generates the translation binaries the resource manifest depends on. `src/application.qrc` is the manifest that compiles the fonts, translations, syntax-highlighter definitions and all 224 icons into the binary, so the app is a single portable executable. `src/main.cpp` is the process entry point and the place where the app's *automation surface* actually lives: a custom Qt message handler, a Windows parent-console attach, a `-nogui` headless mode and a `-test <folder>` batch-regression mode. `src/mainwindow.{h,cpp}` is the app shell — settings, fonts, theme, the three-way splitter layout, crash recovery, the help system and the layered file-path resolution that every other subsystem calls through. `src/utils.{h,cpp}` is the shared leaf: SI-prefix macros, number formatting, path helpers, four file readers that all name their caller in the error, and the canvas grid arithmetic.

The two things that make this shard interesting beyond "it is the app skeleton" are: **(a) the headless/automation surface**, which is what would let a harness drive SimulIDE without a human, and **(b) the path-resolution and help systems**, which are the closest thing in the repo to a content/resource architecture that an agent-facing skill could copy.

## Per-file notes

### .github/FUNDING.yml
- Purpose: GitHub Sponsors / funding-platform metadata. Read by GitHub, never by the app.
- Key abstractions: none — a flat YAML mapping of platform keys.
- Data flow: none. Not referenced by any source file in the repo (checked by grep).
- Non-obvious: every platform except `open_collective` (line 5) is present only as a **commented-out placeholder** with the template text still in it; the `github:` key is present but empty. The file is still valid YAML and GitHub accepts the commented form.
- Edge cases / failure handling: n/a.
- Surprising: **this repository has no CI at all.** `.github/` contains exactly this one file — no `workflows/` directory, and no `.gitlab-ci.yml` / `.travis.yml` / `appveyor.yml` anywhere in the clone (verified by directory listing and by the manifest, whose only `.github/` row is this file). The manifest's `build-CI` type label on this file, on `build_XX/SimulIDE_Build.pro` and on `SimulIDE.pri` is therefore misleading: nothing here is automated, and `README.md` documents no CI either.

### .gitignore
- One line, and it is the repository's **only** ignore rule: `resources/qm/*.*`.
- Purpose: keep the compiled Qt translation binaries (`.qm`) out of the tree — they are regenerated by `lrelease` at build time.
- Non-obvious: the pattern is `*.*`, not `*`, so the committed `resources/qm/readme` (a filename with no dot) survives the rule while every generated `.qm` is ignored. The directory is kept alive by that one committed placeholder.
- Surprising: a 1359-file repository with a single ignore rule means "what is generated" is decided entirely by this one line plus the build — there is no `build/`, no `*.user` (qmake's IDE files) and no editor-config ignore, so a developer running `qmake` inside the source tree would litter the repo.

### build_XX/SimulIDE_Build.pro
- Six lines: `BUILD_DIR = $$PWD` (line 3) then `include(../SimulIDE.pri)` (line 6). This is the whole build entry point.
- Purpose: the out-of-source qmake project. The directory name `build_XX` is a literal placeholder that ships in git, and it holds only this `.pro` file.
- Key abstractions: `BUILD_DIR` is the single variable the shared `.pri` reads to place its outputs (`TARGET_PREFIX = $$BUILD_DIR/executables/$$TARGET_NAME`, `OBJECTS_DIR *= $$OUT_PWD/build/objects`, `MOC_DIR *= $$OUT_PWD/build/moc`).
- Data flow: qmake reads this file → `BUILD_DIR` is set **before** the include so `SimulIDE.pri` can use it → the `.pri` computes the source list, include path, flags and destination.
- Non-obvious: because `BUILD_DIR` is set before the include, the `.pri`'s `$$PWD` refers to the **repo root** while `$$OUT_PWD`/`$$BUILD_DIR` refer to the **build** directory. That is what lets `$$files($$PWD/src/*.cpp, true)` scan the source tree and the objects land elsewhere.
- Edge cases: the include is a *relative* path (`../SimulIDE.pri`), so this file must stay exactly one level under the repo root; moving or copying it alone breaks the build with no diagnostic of its own.
- Surprising: there is **no `install` target**. `DESTDIR = $$TARGET_PREFIX` just drops the binary into `build/executables/SimulIDE_2.0.0-/`, and the README's claim that this folder contains "the executable and all files needed to run SimulIDE" is not true of the build output alone — see the `application.qrc` note for the runtime-data files the build never stages.

### README.md
- 61 lines: the project pitch plus build/run instructions. Nothing else — no architecture, no contributing guide, no test instructions, no packaging instructions.
- Purpose: the only documentation of how to build the thing.
- Key claims: "Simplicity, speed and ease of use are the key features"; "Simulation speed is one of the most relevant characteristics of this simulator. It has been deeply optimized to achieve excellent speeds and low cpu usage"; a code Editor and Debugger for Arduino, GcBasic, PIC asm, AVR asm with breakpoints, watch registers and global variables.
- Data flow: build deps → Qt5 dev packages (Core, Gui, Xml, Widgets, Concurrent, svg, Multimedia, Serialport, qmake) → `cd build_XX && qmake && make` → the executable appears in `build_XX/executables/SimulIDE_x.x.x`. Runtime deps list the same Qt5 modules plus Multimedia Plugins and Serialport.
- Non-obvious: "No need for installation, place SimulIDE folder wherever you want and run the executable" — portability is the packaging strategy, which is why the qrc compiles so much into the binary.
- Edge cases / failure handling: none documented.
- Surprising: **the two automation flags are documented nowhere.** `main.cpp` implements `-nogui` and `-test <folder>`, which are the only ways to drive the simulator without a human, and neither appears in the README. Anyone building a harness on top of SimulIDE would have to read `main.cpp` to discover them.

### SimulIDE.pri
- 176 lines. This file **is** the build system — there is no CMake, no CI, no script.
- Purpose: the shared qmake include that defines the version, the source list, the include path, the compiler flags, the platform branches, the build stamp, the output layout and the translation step.
- Key abstractions: `VERSION = "2.0.0"` / `RELEASE = ""` (lines 2-3) → `APP_VERSION` define and the output folder name; `TARGET = simulide` vs `TARGET_NAME = SimulIDE_$$VERSION-$$RELEASE` (line 148) — the *binary* is `simulide`, the *folder* is versioned; one recursive glob for all sources (lines 15-18: `$$files( $$PWD/src/*.cpp, true )`, `true` = recursive), which is why the whole vendored AngelScript engine under `src/angel/` and the 224-icon tree compile with no per-file registration.
- Data flow: qmake → generated Makefile → `runLrelease` (a `QMAKE_EXTRA_TARGETS`, hooked in as `PRE_TARGETDEPS`, lines 157-164) compiles `resources/translations/*.ts` into `resources/qm/*.qm` → rcc compiles `src/application.qrc` → the binary links into `build/executables/SimulIDE_2.0.0-/`.
- Non-obvious: the 61-line `INCLUDEPATH` block (lines 21-81) flattens **every** subdirectory of `src/` onto the include path, which is why `src/gui/circuitwidget/circuit.cpp` can `#include "circuit.h"` and `#include "component.h"` with no relative prefix. The four `-Wno-*` flags (lines 86-89) are each annotated `#AngelScript` — the vendored engine dictates project-wide compiler flags. `-Ofast` (line 90) applies to everything, and the DEBUG block (lines 91-96) *strips* `-O`/`-O1`/`-O2`/`-O3` back out and re-adds `-O0` plus `-D_GLIBCXX_ASSERTIONS`, so a debug build is unoptimised no matter what the global flag says. `LIBS += -lz` (line 98) exists for the component-library installer, which reads `.zip` archives.
- Edge cases / failure handling: the macOS block (lines 108-120) hard-codes a **Homebrew Cellar absolute path** — `QMAKE_CC = /usr/local/Cellar/gcc@7/7.5.0_4/bin/gcc-7` — so the macOS build only works on the machine that path was written on. The `contains( QMAKE_HOST.arch, arm64|aarch64 )` block (lines 122-128) picks the AngelScript ARM64 call thunk (`as_callfunc_arm64_xcode.S` on macOS, `as_callfunc_arm64_gcc.S` elsewhere) but there is no matching x64/arm64 selection for the rest of the tree, so a Windows-ARM build would compile the x64 thunk path. The POSIX date stamp uses `$(which date)` nested inside `$$system(...)` (line 135), whose qmake expansion semantics I could not verify without running qmake.
- Surprising: `REV_NO` and `BUILD_DATE` are computed by **shelling out at qmake time** (lines 130-137) and baked in as string defines (lines 144-146). Windows gets `yy-MM-dd` (e.g. `24-10-22`) and POSIX gets `%y%m%d` (e.g. `241022`). That difference is consumed at `src/mainwindow.cpp:43`, where `QString( REVNO ).remove("R").toInt()` parses it — see the note there and the Uncertainties section.

### src/application.qrc
- 283 lines. The Qt resource manifest, one `<qresource prefix="/">` block, every entry an `<file alias="…">`.
- Purpose: compile the fonts, translations, code-editor syntax definitions and **all 224 icons** into the binary, so the app runs from a single portable file.
- Key abstractions: the **alias is the runtime key**, not the path. The aliasing is deliberately flat: `../src/icons/mainwindow/new.svg` → `new.svg`, `../src/icons/components/led.png` → `led.png`, `../src/icons/font/font2.png` → `font2.png`. Everything except the `codeeditor/syntax/` subtree lands directly at `:/`.
- Data flow: rcc → `qrc_application.cpp` → the resources are inside the binary → `QFile::exists(":/simulide_en.qm")` (`src/main.cpp:44`), `QIcon(":/simulide.png")` (`src/mainwindow.cpp:37`), `QIcon(":/remove.svg")` (`src/mainwindow.cpp:287`) read them at runtime.
- Non-obvious: the qrc lists **14 `.qm` translation files** (lines 11-25, seven app + seven Qt) that live under `../resources/qm/` and are **git-ignored** — they exist only after `lrelease` has run. So a resource step depends on a generated artifact, and the ordering is expressed only through `PRE_TARGETDEPS += runLrelease` in the `.pri`, not through rcc's own dependency on the `.qm` files. The aliasing also **collapses two directories into one namespace**: a component icon and a main-window icon with the same base name would collide silently at rcc time.
- Edge cases / failure handling: in a fresh clone `resources/qm/` contains only the committed `readme`; without `lrelease` on `PATH` the rcc step has nothing to embed.
- Surprising: **the qrc embeds no runtime data.** The repo ships `resources/data/` with 154 help `.txt` files, 6 images, `diodes.model` and the `codeeditor/` tree, and only `codeeditor/syntax/` (11 files) and two compiler XMLs (`angelscript.xml`, `arduino.xml`, lines 27-28) made it in. So `MainWindow::getHelp`'s `":/help"` lookup (`src/mainwindow.cpp:361,364`) can never succeed in a stock build, and `getDataFilePath("diodes.model")` / `getDataFilePath("images/…")` resolve only if the user has a `data/` folder in their user or config directory. The build never stages `resources/data` into the output folder either. The split is: **code = compiled in, data = runtime files the user or packager must supply.**

### src/main.cpp
- 134 lines. The process entry point, and the app's whole automation surface.
- Purpose: install a message handler, attach to the parent console on Windows, build the `QApplication`, resolve the locale and install the translator, construct `MainWindow`, parse the command line, and enter the event loop.
- Key abstractions: `myMessageOutput` (lines 16-39), a `qInstallMessageHandler` that funnels `qDebug` into **both** the app's own debug pane (`CircuitWidget::self()->simDebugMessage(msg)`, line 23) **and** stderr, while Info/Warning/Critical/Fatal go only to stderr decorated with `file:line:function`.
- Data flow: `argv` → three branches → a deferred action: `-nogui` → `window.hideGui()` (lines 92-96); `-test <folder>` → `BatchTest::doBatchTest(arg)` (line 105); a file path → `CircuitWidget::loadCirc(arg)` for `.sim1`/`.sim2` else `EditorWindow::loadFile(arg)` (lines 118-127). Every deferred action goes through `QTimer::singleShot( 500, … )`.
- Non-obvious: the 500 ms deferral (lines 105, 120, 125) is a **startup-latency hack, not a synchronization primitive** — a circuit cannot be loaded until the event loop is running and `CircuitWidget::self()` exists. The locale is read from a `QSettings` opened at line 63, *before* `MainWindow` exists, because the translator must be installed before any UI is built; the fallback chain is system locale → base language → `:/simulide_en.qm` (lines 65-74).
- Edge cases / failure handling: the argument loop `break`s after the first non-flag argument (line 128), so only one file can ever be opened per launch. A `file://` prefix is stripped and `%20` decoded (line 110) so a URL from a `.desktop` launcher works; on Windows a leading `/` is removed (lines 111-113) because `file:///C:/…` leaves one behind. A missing file logs `"ERROR: unrecognized argument"` and stops.
- Surprising: `QSettings` is opened **twice** for the same file — once as a local in `main()` (line 63) for the language, once as a member built by `MainWindow`'s constructor (`src/mainwindow.cpp:50`) — and `MainWindow` reads the user-data directory from `"120userPath"` with a fallback to the older `"userPath"` key (`src/mainwindow.cpp:53-55`), a hand-rolled settings migration.

### src/mainwindow.h
- 145 lines: the root window's declaration and the app's most-used API surface.
- Purpose: expose settings, theme, font, help, the four path resolvers, and the singleton accessor the rest of the app uses.
- Key abstractions: the `Langs` enum (lines 23-38) with seven live languages and six kept as **commented-out entries** (Dutch, French, Italian, Russian, Portuguese, Slovak, Turkish); `static MainWindow* self()` (line 93) backed by `static MainWindow* m_pSelf` — the whole application addresses the main window through this one accessor.
- Data flow: the header is the contract; `mainwindow.cpp` implements it. The rest of the tree calls `MainWindow::self()->getDataFilePath(...)`, `->getHelp(...)`, `->revision()`, `->getCircFilePath(...)`.
- Non-obvious: the header *documents the resolution order in a comment* rather than in the implementation — `getDataFilePath` is annotated "Get file path in data folder, first user folder, if not SimulIDE folder" (line 83), which is the whole fallback contract in five words.
- Edge cases / failure handling: n/a at this level.
- Surprising: the dead-language list is **duplicated in two places** — the enum's comments in the header and the matching commented branches in `setLoc`/`loc` (`src/mainwindow.cpp:184-198` and `203-216`) — so adding a language means editing two parallel lists, and forgetting one leaves the enum and the mapping disagreeing.

### src/mainwindow.cpp
- 459 lines. The app shell: settings, fonts, theme, widget layout, crash recovery, the help system, and the layered path resolution every other subsystem depends on.
- Purpose: build the three-pane window, persist and restore user state, recover from a crash, resolve help text and data files, and expose the app's file-location policy.
- Key abstractions: the layout is a horizontal `QSplitter` with three panes — a tabbed side panel (Components / Libraries / Files, lines 303-309), the circuit widget, and the code editor (lines 311-314), sized `{150, 350, 500}` (line 318) and then overridden from saved state by `readSettings()` (line 150). Two `QSettings` objects: `simulide.ini` for the app and `compList.ini` for the component list (lines 50-51).
- Data flow: `QSettings` → `readSettings()` (lines 146-163) restores geometry, window state, both splitter states, the autosave interval, the auto-update flag and the theme; `writeSettings()` (lines 165-180) writes them back on close and also delegates to the installer, component list and file tree.
- Non-obvious: **F5 is the run key** — `keyPressEvent` maps `Qt::Key_F5` to `powerCircOn` (lines 127-133), a play-button convention. The font scale is hand-derived from the screen's logical DPI when unset (`dpiX/96.0`, lines 68-77) rather than using Qt's own HiDPI scaling, and six Ubuntu fonts are registered from the qrc (lines 61-66). The crash-recovery prompt (lines 101-115) is explicit: "Looks like SimulIDE crashed…", Open or Discard, and **Discard deletes the autosave**.
- Edge cases / failure handling: the autosave file has a **fixed name** — `getConfigPath("backup.sim2")` — so only one crashed run is ever recoverable, and the recovery dialog is modal at startup. `closeEvent` (lines 135-144) refuses to close if the editor has unsaved work or the circuit cannot be reset, and it **returns early in headless mode** (line 137), so `-nogui` skips the whole save dance.
- Surprising: `hideGui()` (lines 119-125) is the headless switch, and it does more than hide widgets — it calls `Circuit::self()->setAutoBck( -1 )` (line 124), so the headless mode deliberately **stops writing files next to the user's data**. `getHelp` (lines 343-384) is a content system in its own right: the name is lowercased and stripped of spaces, then six lookups are tried (`<name>_<locale>` then `<name>`, in the user dir, the config dir, then `":/help"`), the result is assembled by recursively expanding `#include` lines (lines 370-380), and the composed text is cached per name in `m_help`. `getFilePath` (lines 386-396) implements the lookup by walking a directory with `QDirIterator` and matching on **base name**.

### src/utils.h
- 101 lines: the shared utility header — units, number formatting, path helpers, file readers, grid arithmetic, list difference.
- Purpose: the leaf API every other file includes, so that string/number/path conventions are defined once.
- Key abstractions: the two unit macros, `unitToVal` (lines 18-22) which scales a value *into* the internal base unit from an SI suffix, and `valToUnit` (lines 24-43) which scales it *out* and picks the prefix; `substract<T>(l0, l1)` (lines 95-100), an ordered set difference that preserves `l0`'s order.
- Data flow: suffix string → macro → scaled value; the four file readers (lines 73-76) take a filename plus a **caller name** and return a parsed value or an empty one.
- Non-obvious: `valToUnit` couples prefix choice to **precision** in one place — the decimals are 3 below 10, 2 below 100, 1 below 1000, and 0 above (lines 41-43) — so the displayed precision of a number is a function of its magnitude, decided together with the prefix rather than by a separate formatter.
- Edge cases / failure handling: `unitToVal` has branches only for `" n"`, `" u"`, `" m"` and the unitless suffix, while `valToUnit` can *emit* `" p"`, `" n"`, `" u"`, `" m"`, `" "`, `" k"`, `" M"`, `" G"`. The two are therefore **not exact inverses**: there is no `unitToVal` branch for k/M/G, so a value carrying one of those suffixes is silently left unscaled.
- Surprising: there are **two different unit systems in one codebase**. `unitToVal`/`valToUnit` are relative to the oscilloscope's picosecond base (`src/gui/dataplotwidget/oscwidget.cpp:114` initialises the unit to `" p"` and lets `valToUnit` re-derive it), while `getMultiplier` (`src/utils.cpp:24`) is an **absolute** SI table (`p = 1e-12` … `T = 1e12`) used by the numeric property editors (`src/gui/properties/numprop.cpp:34`). Same suffix vocabulary, two different bases, no shared definition.

### src/utils.cpp
- 276 lines: the implementation of the above plus number formatting, quote helpers, path helpers, the four file readers and the canvas grid arithmetic.
- Purpose: the shared leaf implementation; also the place where the file-I/O error convention lives.
- Key abstractions: the `multipliers` table (line 22) mapping SI prefixes to absolute factors, with a special case for `"µ"` at line 29 that spells `1e-6` as `10e-7`; the four readers `fileToDomDoc` / `fileToString` / `fileToStringList` / `fileToByteArray` (lines 158-216), each taking a `caller` string and logging **the caller's name** with the failure.
- Data flow: a filename → `QDomDocument` / `QString` / `QStringList` / `QByteArray`, with the calling site named in every error message (`qDebug() << caller << "Error: Cannot read file:\n" + fileName + …`).
- Non-obvious: `fileToDomDoc` returns an **empty** `QDomDocument` on a parse error (lines 175-176) and reports the line and column — the caller must detect the failure itself; `fileToString` forces UTF-8 with `in.setCodec("UTF-8")` (line 190, a Qt5-era API).
- Edge cases / failure handling: `remQuotes` (lines 97-102) removes the first and last character **unconditionally** — on a string shorter than two characters the second `remove` is called with a negative position. `getMultiplier` maps an **unknown prefix to 1** (line 30), i.e. a silent "no scaling" fallback rather than an error. `findFile` (lines 138-154) recurses into subdirectories but skips names ending in `.` — the recursion guard is a filename heuristic, not a depth limit.
- Surprising: there are **two canvas grid resolutions** — 4 px for free placement (`toGrid`, `snapToGrid4`) and 8 px for components (`toCompGrid`, `snapToGrid8`) — and `roundDown` (lines 220-224) needs a separate negative-`x` branch because C++ integer division truncates toward zero rather than toward −∞. `unitToVal` and `getMultiplier` are unrelated helpers that happen to share a vocabulary (see `utils.h`).

## Ideas worth stealing

- **A headless mode that also stops writing next to the user's files** — `src/mainwindow.cpp:119-125` — `hideGui()` hides the side panel, the editor and the canvas, and then calls `Circuit::self()->setAutoBck( -1 )`. *Why it matters for August:* an agent-driven "simulate this and report" run must be indistinguishable from a human run to the engine but must not leave artefacts in the user's project directory. SimulIDE encodes that as a property of the headless switch itself, not as a separate code path that someone can forget to disable. Pair it with `src/mainwindow.cpp:135-137`, where `closeEvent` returns early in headless mode and therefore skips the save-and-prompt dance entirely.

- **A golden-file batch regression mode driven entirely from argv** — `src/main.cpp:97-107` (with `src/gui/testing/batchtest.cpp:36-52, 54-77`, which I read for context) — `-test <folder>` walks a directory tree for `*.sim1`/`*.sim2`, loads each circuit, powers it on, and prints `"All tests passed"` or `"N Tests failed:"` plus the failing filenames. *Why it matters for August:* this is the mechanism by which a *circuit simulation skill* could be graded — a folder of circuits each containing a self-checking test unit, run headless, exit-code-shaped, with no human present. The whole contract is four lines of argv parsing plus a folder scan. Note the honest limitation: the runner reports failures but does not set a process exit code, so a CI/harness wrapper has to read stdout, not `$?`.

- **The circuit file records the simulation parameters it was authored under** — `src/gui/circuitwidget/circuit.cpp:445-458` (read for context) — the `<circuit>` header carries `version`, `rev`, `stepSize`, `stepsPS`, `NLsteps`, `reaStep`, `animate`, `anicurr`, `ansi`, `width`, `height`. *Why it matters for August:* a saved artifact that fingerprints the *engine settings* it ran under is what makes a later run reproducible and a diff meaningful. An August circuit tool should write the same fields, so "the output changed" can be attributed to the circuit or to the settings — and `src/mainwindow.cpp:43` shows how the app's own revision number becomes one of those fields.

- **Three-tier resource resolution — user file, install file, compiled-in resource** — `src/mainwindow.cpp:423-436` — `getDataFilePath` tries the user data folder, then `<config>/data/<file>`, then the Qt resource `:/<file>`, and returns `""` only if all three miss. The header states the contract in one comment at `src/mainwindow.h:83`. *Why it matters for August:* a skill's reference corpus, its component library and its model data should resolve the same way — a user can patch one file in their data directory without reinstalling anything, and the built-in copy remains the floor. `src/mainwindow.cpp:438-453` adds the fourth case a coursework bundle needs: files relative to the *circuit's own* directory, then the circuit's `data/` subfolder, so a circuit ships as a self-contained folder.

- **A help system with locale fallback, includes and a cache** — `src/mainwindow.cpp:343-384` — six-step lookup (`<name>_<locale>` then `<name>`, across user dir → config dir → `:/help`), the name normalised by lowercasing and stripping spaces, the result composed by recursively expanding `#include "other.txt"` lines, and the composed text cached in `m_help`. *Why it matters for August:* this is the minimum viable shape of a *reference corpus* for a course skill — a base name, a per-locale variant, an include mechanism for composing a page out of parts, and a cache so repeated lookups are free. The include expansion is the part worth stealing: it lets a page be assembled from shared fragments without a full templating engine.

- **Every file-reading helper names its caller in the error** — `src/utils.cpp:158-216` — `fileToDomDoc(fileName, caller)`, `fileToString(fileName, caller)`, `fileToStringList`, `fileToByteArray` all take the calling site's name and emit `caller << "Error: Cannot read file:" << fileName`. The XML variant also reports the parse line and column. *Why it matters for August:* in a harness where an agent is told "the step failed", the difference between `Error: Cannot read file` and `Error: Cannot read file [circuit.cpp:412]` is the difference between a retryable step and a mystery. The Python analogue is one helper — `read_text(path, *, caller=...)` — with the caller's name baked into the exception message.

- **Prefix choice and display precision decided together** — `src/utils.h:24-43` — `valToUnit` picks the largest SI prefix that keeps the number under 1000 **and** sets the decimal count from the scaled magnitude (3 below 10, 2 below 100, 1 below 1000, 0 above), in one function. *Why it matters for August:* any tool that shows a physical quantity to a learner needs this; a separate formatter for "the number" and another for "the decimals" drifts, and the drift shows up as `0.000000001 F` in a UI that a student has to read. The same file shows the anti-pattern to avoid: `unitToVal` and `getMultiplier` are two unit systems with different bases and no shared definition.

- **A crash-recovery artefact with one fixed name and an explicit user decision** — `src/mainwindow.cpp:101-115` — the autosave is a single known file (`backup.sim2` in the config dir); on startup, if it exists, the app says "Looks like SimulIDE crashed…", offers Open or Discard, and **deletes it** on Discard. *Why it matters for August:* a long agent turn that dies should leave exactly one identifiable, recoverable artefact and the next boot should surface it as a decision rather than a silent overwrite. The "one fixed name" limitation is worth noting rather than copying: only the most recent crash is ever recoverable.

- **The GUI app's stdout must reach the parent terminal on Windows** — `src/main.cpp:54-58` — `AttachConsole(ATTACH_PARENT_PROCESS)` followed by `freopen("CONOUT$", "w", stdout)` and the same for stderr. *Why it matters for August:* a Tauri desktop app launched by a harness on Windows will not see the harness's stdout unless it attaches to the parent console explicitly. This is three lines and it is the difference between "the app's output is visible to the orchestrator" and "it is not". Pair it with `src/main.cpp:16-39`, which routes `qDebug` into the app's own debug pane *and* stderr — one log, two sinks.

- **Generated artefacts are produced by the build, not committed, and the ordering is declared** — `SimulIDE.pri:157-164` with `.gitignore:1` and `src/application.qrc:11-25` — `runLrelease` is a `QMAKE_EXTRA_TARGETS` that compiles the `.ts` sources into `resources/qm/*.qm` and moves them into place, hooked in as `PRE_TARGETDEPS`; the outputs are git-ignored by the repository's single rule `resources/qm/*.*`; and the qrc lists those very files as resources. *Why it matters for August:* the same three-part contract (generate at build time, ignore the output, declare the dependency) is what an August skill-pack build needs — and this repo shows the failure mode too: because the dependency is expressed as a *pre-target* hook rather than as rcc's own dependency on the `.qm` files, a build without `lrelease` on `PATH` fails at the resource step with a missing-file error that points at the qrc, not at the missing tool.

- **A build that discovers its own sources** — `SimulIDE.pri:15-18` — `SOURCES = $$files( $$PWD/src/*.cpp, true )`, `HEADERS`, `FORMS` and `TRANSLATIONS` are all globs, with `true` meaning recursive. *Why it matters for August:* a plugin/component registry that is directory-driven means adding a component is one file rather than one file plus an entry in a list — the same property the `components-analog` and `components-digital` shards' `Component::construct` / `libraryItem()` pairs rely on. The paired cost is visible at `SimulIDE.pri:21-81`: a 61-line hand-maintained `INCLUDEPATH` that must be edited whenever a directory is added, which is exactly the maintenance a real registry would remove.

- **The build tells the developer what it is doing** — `SimulIDE.pri:166-176` — a `message()` banner printed at qmake time: target name, target OS, host OS, build date, Qt version and the destination folder. *Why it matters for August:* a skill that a user runs on their own machine should announce, in one block, which build of the skill is running, on what host, against which dependency versions, and where it will write. It is six lines and it is the difference between a reproducible run and a mystery.

## Uncertainties

- **The `REVNO` → revision divergence.** `SimulIDE.pri:131` gives Windows `yy-MM-dd` (e.g. `24-10-22`) and `SimulIDE.pri:135` gives POSIX `%y%m%d` (e.g. `241022`). `src/mainwindow.cpp:43` does `QString( REVNO ).remove("R").toInt()`. `QString::toInt()` returns 0 when the string is not a valid integer, so I *expect* `m_revision == 0` on Windows and `241022`-style on POSIX — and `m_revision` is written into every saved circuit as `rev="…"` (`src/gui/circuitwidget/circuit.cpp:448`). **I could not verify this at runtime** (building and running the clone is forbidden by my instructions), so it stays a derived expectation. What I did check: the two format strings in the `.pri`, the parse site, the two consumers of `revision()`, and that `remove("R")` is a no-op for both formats since neither contains the letter "R".
- **The POSIX date command's qmake expansion.** `SimulIDE.pri:135` reads `$$system($(which date) +\"\\\"%y%m%d\\\"\")` — a `$(which date)` nested inside `$$system(...)`. I could not establish, without running qmake, how qmake expands `$(which …)` here, and therefore cannot say whether the POSIX `REV_NO` is even the date. This does not affect the Windows path, which uses an explicit `powershell` call.
- **The build ordering of `runLrelease` versus rcc.** `SimulIDE.pri:164` attaches `runLrelease` as a `PRE_TARGETDEPS`, and `src/application.qrc:11-25` lists the `.qm` files as resources. I cannot run `qmake`/`make` to confirm that the `.qm` files exist by the time rcc runs, so "the build works from a clean clone only if `lrelease` is on `PATH`" is an inference from the file contents, not an observed failure.
- **Whether the help corpus and the `resources/data/` tree are reachable in a real installation.** I established that `src/application.qrc` does not embed them and that the `.pri` has no rule copying them to `DESTDIR`, and that `MainWindow::getHelp`'s `":/help"` branch therefore cannot match in a stock build (`src/mainwindow.cpp:361,364`). Whether some out-of-tree packaging step (an installer, a distro package, a user's manual `data/` folder) supplies them is outside this repo — I found no such step in the build files, and I did not find an installer spec anywhere in the clone.
- **The macOS toolchain path.** `SimulIDE.pri:117-119` hard-codes a Homebrew Cellar path for gcc-7. I am confident the path is machine-specific, but I could not check whether a current macOS build still needs it or whether the `QMAKE_CC` assignment is dead code on modern setups.
- **`remQuotes` on a short string.** `src/utils.cpp:97-102` calls `string.remove( string.size()-1, 1 )` without a length check; for an empty string that is a negative position. I know Qt's `QString::remove(qsizetype, qsizetype)` is documented for `position >= 0`, but I did not run it, so I describe the call rather than assert the resulting behaviour.
