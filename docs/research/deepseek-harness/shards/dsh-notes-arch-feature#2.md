# deepseek-harness / dsh-notes-arch-feature#2

## Shard shape

This shard is 260 files, all under `.agents/notes/archived/feature/` in the `deepseek-harness` clone: the **archived feature-decision notes** of the DSH (DeepSeek Harness) project, written as ADR-style "Agent Notes" (Problem → Decision → Alternatives considered → Consequences → Testing/Verification). The corpus is 86 English notes (607 KB), 87 Chinese mirrors (`.zh.md`), and 87 translation-pairing records (`.i18n.yaml`). The English notes are the substance: they document the harness's *agent loop* machinery (PTC-mode parallel dispatch, subagent seams and out-of-process product providers, SDK/JSON-RPC subagent backends), its *context* layer (skill catalog hot-refresh, tmux location context, manual compaction, queue/steer), its *tool-surface* discipline (even tool rosters, per-model tool presentation, fs-tool error remedy, pwsh/bash parity), and its *web/TUI presentation* decisions (trajectory inspection ledger, subagent conversation catalog, tool cards, search, cards for read/search/diff/result). The `.i18n.yaml` files are not translation catalogs but **bilingual-pair consistency records**: each stores the git blob hash of both language sides of one note, so a translation that drifts from its English source is detectable by a hash comparison. Each trio is `note.md` + `note.zh.md` + `note.i18n.yaml`; one note (`2026-07-26-ptc-dispatch-ui-foundation.zh.md`) has only its Chinese side in this shard, and one `.i18n.yaml` (`2026-08-05-per-agent-tool-presentation.i18n.yaml`) has its English note in another shard.

## Per-file notes

### .agents/notes/archived/feature/2026-07-26-ptc-live-parallel-dispatch.md
- Purpose: defines the live dispatch lifecycle for "PTC mode" (a program-then-call tool mode) so the UI can show per-sub-call running state and so PTC programs get native-grade concurrency.
- Key abstractions: `tool/ptc-dispatch-start` / `tool/ptc-dispatch` event pair keyed by `subCallId`; `registry.executionMode` classification reusing the native `isConcurrencySafe` fail-closed contract; `maxParallelSubCalls` (default 10, validated by the Loader schema *and* re-validated at direct construction).
- Data flow: submitted calls are classified at start time, one single-lane driver owns every ORDERED stage (start append, `prepare`, head-of-line `finalize`/`finish`), while only the around-dispatch/body stage runs concurrently; `RunningToolCall` children in the runtime's `ToolCallTree` project the running ring, and a settle replaces the private-index entry in place, preserving start order under out-of-order completion.
- Non-obvious design decisions: the start event is appended **when the scheduler actually starts a call, not at submission**, because a queued call abandoned by run settlement would otherwise need a third "abandoned" terminal event — start-at-entry keeps the invariant *started ⇔ settles exactly once* (line 27). The bridge shares only the native scheduler's **contract** (classification, pool, barriers), not its machinery, because the loop schedules a fully-parsed batch while the bridge schedules an open-ended submission stream whose results return to the program (line 29).
- Edge cases / failure handling: an exclusive call drains the pool, runs alone and holds its barrier until its COMMIT completes; run settlement aborts in-flight dispatches, abandons queued-unstarted ones silently, and drains to quiescence — including a commit already mid-flight — before the outer result closes the turn (line 19).
- Surprising: a settle with no observed start (window cut mid-pair, or a pre-start-event log) appends directly instead of failing, so old logs keep rendering (line 20).

### .agents/notes/archived/feature/2026-07-26-todo-parallel-in-progress.md
- Purpose: lifts the "at most one `in_progress` todo" cap so a todo list can mirror genuinely parallel work (concurrent subagents, background commands, workflow fan-out).
- Key abstractions: required `Config.allowParallelInProgress` boolean on `packages/todo/tool-todo`; the durable-log invariant in `packages/todo/tool-todo/src/invariant.ts`; `planSummary` in `toolviews/plan-summary.ts`; the `summarySuffix` slot on the shared `ToolRow`.
- Data flow: the flag moves the model-facing description *and* the accepted input together — only the active-status clause of the description varies, so the model is never taught a rule the tool does not hold (line 29).
- Non-obvious design decisions: the durable-log invariant deliberately does **not** follow the flag, because a log written while parallel work was allowed must still replay after a deployment tightens the policy (line 31). The policy is a *required* config field rather than a default, since "may several tasks be active" is a property of the deployment, while "at most N" invents a threshold nothing can justify (line 36).
- Edge cases / failure handling: two web sites derived a one-line summary with `todos.find(t => t.status === 'in_progress')` — a *total* function under the old cap — so with several active they silently dropped every active item but the first; the expanded list was always correct, so neither change's tests caught it (line 41).
- Surprising: `planSummary` returns name and count as **separate fields** because the row ellipsizes the summary: a count appended to the task name sits at the far end of the truncatable text, so exactly the narrow-viewport/long-name cases that make the count informative are the ones that clip it away; the count therefore rides a non-shrinking `summarySuffix` slot (line 45).

### .agents/notes/archived/feature/2026-07-27-native-workspace-directory-picker.md
- Purpose: replaces the typed absolute-path field for adding a workspace with a native OS folder picker over the local Web carrier.
- Key abstractions: a single `host.pickDirectory` host RPC exposed through `WorkspaceRuntime`; `workspace.create({ path })` reuse; platform adapters (macOS `osascript`, Windows koffi `IFileOpenDialog` child process, Linux `zenity` with `kdialog` fallback).
- Data flow: the picker returns a path; the workspace manager **upserts the returned workspace before the selection callback runs**, so a newly adopted directory renders its basename immediately; selection then starts a blank session.
- Non-obvious design decisions: the RPC is accepted only from a loopback socket with same-origin browser metadata, and it does **not** use the default 30-second request timeout because a system dialog may stay open indefinitely — while caller and connection aborts still propagate to the platform process (line 29). Adding authentication infrastructure for one local native dialog was rejected as out of the threat model's scope (line 41).
- Edge cases / failure handling: cancel is silent and returns `null`; a duplicate path selects the existing workspace; a different canonical path adopts a separate Workspace even with an identical derived title; other failures show a compact retryable error; the Windows tier has **no fallback** — failures surface as-is.
- Surprising: `session.cwd`-style privileged calls here are guarded by "loopback + same-origin browser metadata", an out-of-band trust proof rather than a token (line 29, line 42).

### .agents/notes/archived/feature/2026-07-27-skill-catalog-hot-refresh.md
- Purpose: makes the model-visible skill catalog refresh while a session is running, without coupling progressive body loading to catalog churn.
- Key abstractions: `ctx.skills.snapshot()` returning summaries **plus a completeness bit**; `ctx.skills.registerProvider(factory)` handing the factory a registration-scoped `{ signal, invalidate }` control; `@deepseek-ai/dsh-skill-filesystem` (Chokidar); `@deepseek-ai/dsh-tool-skill` publishing a catalog as a sourced `UserMessage`; the `skills/change` TUI event.
- Data flow: the tool plugin applies exact `skill` visibility, hashes the exact rendered text between `<available_skills>` tags, and scans the read-only session events **backwards** for the newest recognizable visible catalog; a changed digest contributes a complete replacement to an enter decision, including an explicit empty catalog when all skills disappear.
- Non-obvious design decisions: catalog membership is separated from instruction-body loading — there is no body cache, hash, revision, or proactive notification, because every `skill(name)` call re-reads and re-parses the current file (line 26). A transient read failure is **not** evidence of deletion, so incomplete observations never become the authoritative model-facing catalog (line 38). The registry refuses to keep `invalidateProvider(provider)` public, because the factory-issued closure binds invalidation to one registration and becomes inert on disposal (line 39).
- Edge cases / failure handling: a missing root is followed from its nearest existing ancestor one absent segment at a time with `fs.watchFile`, then handed to Chokidar once it exists; each discovery re-probes the retained root/ancestor mode so ancestor observation survives a deletion that already published an authoritative empty catalog; first-party `write`/`edit` tool observations synchronously invalidate a relevant provider so the next model step sees its own mutation (line 20).
- Surprising: when compaction hides every catalog, the tool pays an **O(session-events) backward scan** to recover the fact and re-establishes the current catalog, including an empty tombstone (line 22); the TUI's own refresh never scans history because it only keeps the last complete result.

### .agents/notes/archived/feature/2026-07-27-tmux-location-context.md
- Purpose: lets the model know which tmux session/window/pane it occupies, so instructions like "the pane below" resolve.
- Key abstractions: opt-in function plugin `@deepseek-ai/dsh-tmux-context` in `packages/context/tmux-context/`; an `agent/pre-step` listener acting only at `step === 1`; `ctx.shell` as the only execution seam; `agent.inject()` for one `user/message` with source `{ kind: 'plugin', plugin: 'tmux-context' }`.
- Data flow: the plugin reads `$TMUX_PANE`, queries `tmux display-message -t "$TMUX_PANE" -p '<format>'` through `ctx.shell`, and injects a three-line block whose **second and third lines** are the compared unit; change suppression compares that block against the latest injection of this source found by scanning raw durable session events, so the schedule survives compaction and process resume without a process-local cache.
- Non-obvious design decisions: a real pane is detected by **tty match** (`ps -o tty= -p <pid>` vs the pane's `#{pane_tty}`), because `$TMUX_PANE`/`$TMUX` are *inherited* by terminals launched from a tmux shell (a VS Code integrated terminal) and would otherwise inject a stale, wrong location; a denylist of emulators is rejected as a partial, ever-growing list (line 22, line 61). The plugin contributes nothing to system-prompt assembly — replacing a value erases earlier readings behind prior reasoning and is not reconstructable, so each reading is a durable attributed message (line 59).
- Edge cases / failure handling: absent `ctx.shell`, absent tmux env, a wrong field count, an empty pane id, and a contained executor rejection all make the attempt a no-op that warns rather than failing the turn; sibling-pane contents are never captured (`capture-pane`) for size and privacy; pixel sizes are excluded because they churn on every resize.
- Surprising: a shipped runtime invariant was **removed** because it re-derived the producer's own scheduling and asserted a regex over text the same package had just rendered — it restated `apply()` rather than checking an independent relation (line 62).

### .agents/notes/archived/feature/2026-07-27-trajectory-inspection-ledger.md
- Purpose: replaces stacked Turn/Step cards with a compact, turn-aware event ledger plus a local record inspector, so prose, machine payloads, token usage, timing and nested tool activity are readable in one viewport.
- Key abstractions: `ConversationNodeAssembler` shared by Chat and Trajectory; `Session.views` target snapshot; Request numbering as one chronological space across ordinary and compaction requests; a fixed Overview projecting records onto three semantic timing lanes; a local inspector with entity-specific tabs.
- Data flow: Session owns one contiguous Event window, paging state, live gap repair and reconnect rebuild; Trajectory reads its target snapshot from `Session.views` and requests one older page when the user reaches the loaded range's top; each Definition extracts a stable ID and the shared Assembler replays only Contexts affected by matching, Location, or Reader changes.
- Non-obvious design decisions: call schemas come from the **active recorded Request header**, and keyless snapshot fixtures deliberately replace that catalog with the non-array `{{tools}}` token, which the durable inspection boundary treats as unavailable rather than fabricating schemas (line 22). Role hues are deliberately low-emphasis and carry no success/failure meaning, so decoration cannot be mistaken for runtime state (line 19). The Overview keeps the full time domain while focused so a selection can be resized or cleared without losing orientation (line 26).
- Edge cases / failure handling: request-only separators join the next measurable virtual item and a terminal separator keeps its own fixed clearance, so the virtualizer never owns a zero-height item; an explicit loading row covers records until initial positioning finishes; while an older prefix is unloaded an interactive first row requests one older page; finalised assistant spans divide at the first non-empty token delta so TTFT and decoding keep their real ratio, with a one-colour fallback for incomplete timing.
- Surprising: the separate Waterfall tab was **removed** and folded into the fixed Overview, and streaming updates are coalesced to at most once per animation frame while only the matching Trajectory Assistant Context is updated — completed Assistant State retains assembled blocks, timing and usage rather than every raw chunk payload (line 26, line 28).

### .agents/notes/archived/feature/2026-07-27-tui-running-glyph-smooth-fade.md
- Purpose: replaces the coloured, always-pulsing prompt glyph with a quiet dim-gray breath that fades in/out around a running turn.
- Key abstractions: `STATUS_FADE_MS = 300` envelope, `STATUS_PULSE_FLOOR = 0` / `STATUS_PULSE_PERIOD_MS = 1400` cosine throb, `STATUS_FADE_MIN_OPACITY = 0.12`, `STATUS_FADE_GRAY.trough/.settled`, `STATUS_ANIMATION_INTERVAL_MS = 50` (~20 fps), `FadingStatus` for the fade-out tail.
- Data flow: brightness = envelope × pulse; the truecolor opacity handed to `fadeGlyph` is `envelope × pulse`, and the glyph interpolates a 24-bit gray emitting `\x1b[38;2;r;g;bm`.
- Non-obvious design decisions: a zero floor plus an explicit visibility threshold hides the glyph entirely at the bottom of each breath, so the trough is genuinely absent; successive non-zero floors (0.45 → 0.15 → 0.02) each read too visible, and a low-but-nonzero gray toggle would give a hard blink rather than the soft fade a smooth cosine produces (line 32).
- Edge cases / failure handling: without truecolor there is no per-frame gray, so a separate `visible` flag driven by the envelope alone shows a steady muted glyph — the throb never blinks the fallback; with colour off entirely the glyph is bare, preserving the caret column. Teardown paths call `clearStatus` directly, stopping running and fading timers together.
- Surprising: the fade-out hands over the **last live phase glyph** (`runningStatus.lastGlyph`), not the ttft fallback the phase derivation returns once the closing turn's step has ended (line 22).

### .agents/notes/archived/feature/2026-07-27-tui-tool-card-header.md
- Purpose: gives TUI tool-call cards a fixed `{ring} Tool / <name>` header so tool identity is separable from the target it operates on.
- Key abstractions: `ToolCardComponent` in `packages/ui/tui/src/components/transcript.ts`; the ring marker `○` (pending) / `●` (settled); the header status colour (warning/ok/error); the diff footer `└ +A -R · N file(s)`.
- Data flow: the header is derived TUI-side from the call's tool name; the presenter title is relocated to the body's first line unless it merely repeats the tool name; a bash card's model-authored description is the only header detail (` / <desc>`).
- Non-obvious design decisions: no bold and no underline, because on terminals that render SGR-1 as the bright colour variant a bold green name reads as a different colour from the rest of the green header — the name stands out by position, not weight (line 24). The change is deliberately TUI-only: `presentation.ts` and every `presentCall`/`presentResult` are unchanged, so the `Tool / <name>` shape is not a cross-package contract (line 20).
- Edge cases / failure handling: a diff card drops its title entirely because per-file path headers and the change footer carry the meaning; the earlier redundancy-suppression that omitted a diff's per-file path is lost, so every diff prints its path once (line 32).
- Surprising: a uniform `└ …` summary footer for every card type was considered and **deferred**; only the diff footer shipped, and the other cards' treatments were kept deliberately rather than by omission (line 28).

### .agents/notes/archived/feature/2026-07-27-typescript-sdk-and-sdk-subagent-backend.md
- Purpose: extracts the stdio JSON-RPC harness protocol into shared nominal TypeScript types, adds a TypeScript SDK client, and adds a second out-of-process subagent backend whose child is a complete harness runtime.
- Key abstractions: `@deepseek-ai/dsh-sdk-protocol` (wire types + `JsonRpcLineTransport`), `@deepseek-ai/dsh-sdk-client` (`HarnessClient`, `DeepSeekHarness`/`HarnessSession`), `@deepseek-ai/dsh-subagent-dsh-sdk` (advertising `agentOptions: true`), and the shared seam file `out-of-process.ts` in the subagent seam.
- Data flow: `dsh-sdk-jsonrpc-server` validates the provider/model/effort route during `initialize` and creates every SDK root Agent from that fixed process-wide route; because JSON-RPC requests can dispatch concurrently it **rejects `session/prompt` until one initialization has completed successfully**, preventing pending or invalid routes from falling back to constructor defaults (line 21).
- Non-obvious design decisions: the protocol package is a separate package precisely so the SDK backend (which must not serve JSON-RPC) does not depend on the server plugin's peer set; the three packages are "layered exactly like the existing Python stack" (line 34). The launch interface resolves the same-version `@deepseek-ai/dsh` dependency rather than only `PATH`, because a Node consumer does not reliably inherit a project-local `.bin` directory (line 40). `env` **replaces** rather than merges, and is read at `start()`, so callers own credential policy.
- Edge cases / failure handling: a failed handshake installs a fresh client after successful cleanup so a later call retries with a new process; if initialization and SDK-owned cleanup both fail, `start()` rejects with an ordered `AggregateError` and **retains** the failed client rather than spawning beside a process whose exit was not proved. Teardown walks a private stdin-EOF → SIGTERM → SIGKILL ladder to actual exit, because the client runs outside any harness context.
- Surprising: the child answer is read from streamed `session.event`s — the last complete `assistant/message`, else accumulated `text-delta` chunks — so **partial answers survive cancellation**; stop reasons map `blocked` → `refusal` and other non-completed values → `error` (line 18). The wire still has **no cancel method**, so both the SDK's `RequestTimeoutError` and the backend's dispose settle locally while the server-side turn keeps running until process teardown (line 49).

### .agents/notes/archived/feature/2026-07-27-web-file-and-session-references.md
- Purpose: gives the Web composer a combined `@file` / `@session` reference menu with Host-backed discovery and structured cross-session snapshots.
- Key abstractions: `@deepseek-ai/dsh-client-ui-reference`; `@deepseek-ai/dsh-file-reference` (owns `ctx.fileReferences`, the shared `@path` grammar and model guidance); `@deepseek-ai/dsh-file-reference-local` (bounded per-agent Host-filesystem indexes, invalidation, scoped prompt installation); the canonical Host-produced `@[label](dsh-session:…)` mention.

### .agents/notes/archived/feature/2026-07-27-web-session-fork-actions.md
- Purpose: unifies "branch this conversation" across the session-row menu and message icon actions onto one client runtime action.
- Key abstractions: `sessions.fork` with `{ sessionId, atSeq?, increaseTitle: true }`; the client-side title increment; `WorkspaceView.sessionIds` as the flat manual order.
- Data flow: a session row forks at the source's last completed turn; an eligible message passes `atSeq: node.seq` to fork at the turn ending at that message; the Host request contains only `sessionId` and the optional `atSeq` — `increaseTitle` is client-only.
- Non-obvious design decisions: the client increments a trailing `(N)` / `（N）` in the **source session's persisted title** and only opens the child after the rename succeeds, so a failed rename never leaves the UI on a child that is not yet named (line 16). Session lineage is deliberately **not** projected into a list hierarchy: `parentId` remains for lineage and queries but does not control session-list visibility, because nesting requires automatic ancestor expansion and prevents children from participating in the workspace's peer manual order (line 20, line 28).
- Edge cases / failure handling: a fork or rename failure leaves the source session and current selection unchanged, while a child created before a rename failure remains in the list; failures stay silent, so the UI exposes no failure reason or retry entry point (line 36).
- Surprising: branching is allowed from assistant messages too, because settled assistant content also has a stable event `seq` — making only one of two visually identical branch buttons work would create an invisible behavioural difference (line 26).

### .agents/notes/archived/feature/2026-07-27-web-session-search.md
- Purpose: adds past-session content search to the Web sidebar without loading every session in the browser.
- Key abstractions: `@deepseek-ai/dsh-session-query-sqlite` mounted with `openAt: first-search` and an in-memory database; `session.search` over the typed RPC stack; `SESSION_SEARCH_RESULT_LIMIT` living with the request/result types in `@deepseek-ai/dsh-api-session-controller/types`; `ctx.sessionQuery.searchSessions`.
- Data flow: the Host derives the authorization set from the same visible summaries as `session.list`, asks the query service for globally ranked `user/message` and `assistant/message` matches, and consumes provider pages until it has 20 authorized sessions plus one lookahead; the client merges immediate local title/workspace matches with backend-ranked content matches, deduplicates by session id and renders a flat list.
- Non-obvious design decisions: the potentially large authorization set is kept **out of** the SQLite bindings, avoiding the portable variable ceiling while preserving global ranking (line 16). The result bound is one protocol constant, not per-connection state: a per-connection field would imply a transport-varying or server-negotiated bound and leave the same fact with two owners (line 20). The service is ACTIVE at boot while its `node:sqlite` module opens only on the first content query, keeping Node 22's experimental warning out of startup output (line 14).
- Edge cases / failure handling: a first-page `SESSION_QUERY_INVALID_LIMIT` halves the page size through 10/5/2/1 and the learned size survives continuations and stale restarts; limit probes and stale retries share a budget of 100 provider calls (≤2,000 inspected hits), and a page larger than requested, a repeated cursor, or an unexhausted stream at that budget fails closed as an `internal` business error; a stale continuation discards partial results and restarts against the original visibility snapshot; the carrier signal cancels superseded work and wins over a concurrent limit or stale rejection (line 16).
- Surprising: the shared semantic projection **excludes reasoning blocks**, so UI search never returns a model's private reasoning as a hit or snippet — and the derived-index schema version advances so existing persistent indexes rebuild without the former documents (line 22). The `unicode61` tokenizer may treat an uninterrupted Chinese sequence as one token, so `搜索` is not guaranteed to match inside `会话搜索功能` — a documented limit, not a bug.

### .agents/notes/archived/feature/2026-07-27-web-subagent-conversations.md
- Purpose: lets the browser browse session-backed subagents and let a human continue a continuable child, without breaking the continuable-subagent contract (at most one Activation, later work only through the exact live direct parent, Agent inbox as sole FIFO).
- Key abstractions: the durable parent-owned `subagentCatalog` projection; mode-bearing addresses `{ parentSessionId, childSessionId, mode }`; `dsh-resource://subagentchat/session/<childSessionId>?parent=…&mode=…`; `session.projections`, `session.page`, `session.follow`, `subagent.prompt` and `subagent.interrupt` routes; `SessionHeader.origin: 'subagent'`.
- Data flow: the address — not lineage or the coarse origin marker — selects the dedicated history and prompt transports; history reads the persisted session **without activation**, while a continuable prompt carries Queue or Steer delivery through `subagent.prompt` and succeeds at inbox acceptance with `{ messageId }`, exposing no Activation, no wait for completion, and no outcome (line 22).
- Non-obvious design decisions: generic Agent-bound session/command/goal routes return `agent-busy` for session-backed subagents, and the denial classifier accepts the coarse `origin` marker, a `subagent/descriptor` suffix, or exact live runtime ownership — these signals only prevent generic ownership and never replace catalog mode or direct-parent authorisation (line 24). Auto-resuming an absent parent is rejected: continuation requires the exact live direct parent and child navigation must not mutate the parent lifecycle (line 93).
- Edge cases / failure handling: a one-shot child is permanently read-only, while a continuable child accepts human follow-ups only while its exact direct-parent Agent is live; a running parent-offline child keeps the ordinary composer with input and Send disabled so independent Stop and live QueueDock controls stay reachable, and the read-only takeover returns once it stops. A list/prompt race is normal: the prompt result, not the earlier availability snapshot, is authoritative; a child may publish between history fetch and mux subscription, so the existing sequence reconciliation covers the cold-to-live path (line 63, line 118).
- Surprising: `subagentTiming` resets at every descriptor so an **inherited fork seed cannot enter the child's total**; the figure sums the four disjoint `tokenUsage` buckets across the durable log; an inactive row bounds an interrupted open turn with `active.through` so a stale projection never borrows newer session metadata (line 47).

### .agents/notes/archived/feature/2026-07-27-workspace-registration-deletion.md
- Purpose: defines what "Delete" on a workspace registration actually deletes — and proves it does not touch the user's folder or session logs.
- Key abstractions: `ctx.workspaceRegistry.delete(id)`; durable `workspaceIds` order; the `workspaces` table row; a `pendingMutation` marker written before create/delete; the `host/workspace-removed` stream frame.
- Data flow: deletion first writes the workspace order without the id, then removes the entity from the cache, then deletes the table row — the table deletion is the **notification commit point**, and the Host emits `host/workspace-removed` only from that committed deletion (line 22).
- Non-obvious design decisions: the delete confirmation states all three consequences up front (leaves the list, folder and session logs remain, sessions appear under Ungrouped); the registry never calls filesystem removal or `SessionPersistence`, because a registration does not own the directory, so a future destructive filesystem action must be separately named, separately confirmed and separately bounded (line 44).
- Edge cases / failure handling: a table-write failure restores the cache and prior durable order and publishes no removal frame; unknown ids return `false` at the domain contract and map to `workspace-not-found`; a deletion whose table write committed but whose marker cleanup failed still reports success, and startup clears the marker idempotently; unmarked order/table divergence keeps the fail-loud corruption behaviour rather than silently discarding rows (line 26).
- Surprising: on the client, a process-local tombstone rejects late changed frames and stale baseline rows for a never-reused workspace id, and the delete confirmation stays pending until the React projection has committed the removal so the next gesture cannot observe one stale list frame (line 30, line 32).

### .agents/notes/archived/feature/2026-08-05-durable-web-schedule.md
- Purpose: gives durable scheduled reminders two timing rules that survive the Host-owned schedule storage: absolute-time semantics and bounded fixed-rate arithmetic.
- Key abstractions: the Host-owned scheduled-messages decision (storage, activation, dispatch, delivery records, catalogue); the schedule package's timing selectors; RFC 3339 values with explicit offsets or `time_zone`.
- Data flow: a one-time `at`/`after` record stores only the canonical UTC `scheduledAt`; a `daily`/`weekly`/`cron` record stores its normalised local rule with an explicit `timeZone`; time-context tells the model to assume the Host-validated IANA zone for unqualified dates and times, but Schedule neither imports that plugin nor stores a session zone (line 18, line 20).
- Non-obvious design decisions: natural-language interpretation and Schedule parsing are deliberately **separate** — the model must turn its interpretation into an offset-bearing RFC 3339 value, so no interpretive default is spread through session core, Host create/fork, persistence formats, clients and mismatch recovery (line 18, line 36). The fixed-rate rule is bounded fixed-duration arithmetic, not a calendar rule: integer division selects the latest sequence point at or before the sampled wall clock, the occurrence is presented **once**, and the record advances directly to the future target, so a cold session never accumulates a replay backlog and delayed model work never shifts the sequence (line 24).
- Edge cases / failure handling: a structured local time inside a daylight-saving **gap** is rejected and an **overlap** chooses its first, earlier instant; the next sequence point beyond the four-digit-year storage range terminates the record; a five-minute minimum bounds wake and model-request frequency; there is no cross-record cooldown, gate, quota or retained batch timestamp (lines 20, 26).
- Surprising: dispatch records **queue admission, not model completion or user receipt** — a crash after follow-up admission but before the durable receipt can repeat the reminder, and the design makes no exactly-once promise; claim-first fencing was rejected because it can silently lose a reminder when enqueue fails (lines 30, line 38).

### .agents/notes/archived/feature/2026-08-05-feedback-gated-session-telemetry.md
- Purpose: adds two stricter telemetry policies — hold a session's telemetry until its user records feedback, or disable reporting while still explaining what happens to feedback.
- Key abstractions: the `SessionTelemetryMode` enum (`FULL` / `FEEDBACK_ONLY` / `DISABLED`); the generic coordinator's live and on-demand capture; `captureSession(session, throughSeq)`; the handoff cursor.
- Data flow: `FEEDBACK_ONLY` reads the canonical session log when a `feedback/record` is appended and hands over the unreleased prefix through that exact event; on-demand capture registers no continuous listeners and reads the canonical log after the same-object handoff cursor through an inclusive boundary, then deep-copies, redacts and hands over every event in that prefix (line 20).
- Non-obvious design decisions: on-demand capture reads the **canonical log** rather than retaining capture-time redacted records, because the canonical log already owns the events and retaining them would duplicate an unbounded session prefix (line 28). The redaction-before-backend boundary is preserved in both paths, and a new Session object begins immediately before `firstLiveSeq`, so a fresh object starts at seq 0 while a forked, resumed or migrated object skips its constructor seed (line 20). Only `FULL` exposes the public service's `emit()` path; `FEEDBACK_ONLY` gets a **private** backend capability so authorisation is structural and the public service stays closed throughout replay (line 22, line 30).
- Edge cases / failure handling: mode resolution is a closed, fail-before-setup check — an unknown direct-construction value fails before transport configuration is read; `DISABLED` constructs no exporter, processor or logger provider and does not inspect exporter configuration; the listener passes an event to `captureSession()` only when `session.eventAt(event.seq)` returns that exact `feedback/record` object, and `Session.append` commits that object before publishing `session/event`, so replay includes the feedback but cannot extend past its boundary (line 22).
- Surprising: feedback-only streams carry **neither `agent-error` nor `shutdown` records** (those do not exist in the canonical log), so shutdown absence is not a crash signal; and same-object replay after lost cursor state plus backend retries can duplicate lifecycle-local ledger rows, so receivers deduplicate on `(session.id, session.format_version, event.seq)` (line 36).

August has exactly this bug class (policy/permission state changing mid-session); the measured cost of the wrong design is in the same note at line 26 — a first-time permission switch dropped cache reads to **256 tokens** against ~14.7k uncached input, because the change was in the FIRST wire message. The rule that transfers: only facts that change go in the tail, and the tail is a *replacement* snapshot, not a delta.
- **Say only what the resolver can actually establish** — `.agents/notes/archived/feature/2026-07-30-current-sandbox-policy-context.md:18` — the model-facing policy statement lists only facts shared by every enforcement dialect, and explicitly omits backend-selected temp paths, `/dev/null`, runner readiness and exact tool availability "because `resolve()` cannot establish them at request assembly". A policy block that overclaims is a liability; a policy block that underclaims is a prompt the model will contradict.
- **Pre-register the experiment AND the positive control, and refuse to conclude when the control fails** — `.agents/notes/archived/feature/2026-07-30-current-sandbox-policy-context.md:30` — the note pre-registered "preemptive refusal" as the primary endpoint and required the OLD wording to produce at least one refusal in twelve fresh sessions before any replacement could be judged; the control produced zero refusals both times, so the candidate arms were never run and the note explicitly declines to select wording on that basis. This is the pattern August needs for any "the model now behaves better" claim: a control that must fail before the treatment is allowed to be evaluated.
- **Make the durable event itself the lock — no process-local mutex** — `.agents/notes/archived/feature/2026-07-30-queued-manual-compaction.md:51` — `compaction/start` is the ONLY compaction lock: no `WeakSet`, no wrapper mutex, no locked/unlocked method split, because two authorities can disagree after replay. The same note's `Agent.runMaintenance` claims the idle phase *before* invoking the task (line 30) so a wake-up send and a maintenance task have exactly one owner of the boundary, and the end-seed scan distinguishes a LIVE unmatched start from a STALE one (line 69) so a crash-recovered session is not wedged. August's context-relief paths are exactly this shape of problem.
- **Markers are time points, not event containers** — `.agents/notes/archived/feature/2026-07-30-queued-manual-compaction.md:61` — `compaction/start`/`compaction/end` mean lock acquisition and release; they do NOT claim exclusive ownership of the events between their seqs, so a non-waking `inject()` may legitimately land inside the interval, and stability is checked only over the selected span. A design that treats a marker as a container has to forbid valid concurrent context writes.
- **Two event kinds, one invariant: *started ⇔ settles exactly once*** — `.agents/notes/archived/feature/2026-07-26-ptc-live-parallel-dispatch.md:18` — the start event is appended when the scheduler ACTUALLY starts a call, not at submission, precisely so a queued call abandoned at run settlement logs nothing and no third "abandoned" terminal event is needed (line 27). The timing pair is then the single source for duration. This is the cheapest possible pattern for August's parallel tool calls and background jobs: a start/settle pair with a stated pairing invariant and no reconciliation state.
- **Split a tool's "strict" and "best-effort" paths explicitly, and let the UI treat a refusal as a convergent success** — `.agents/notes/archived/feature/2026-07-30-web-queue-steer-action.md:28` and `:58` — the queue-row steer is STRICT (it proves `acceptsNextStep` and refuses with `steer-unavailable` rather than falling back to the best-effort alias, because a closed window would create a NEW queued occurrence at a different position and identity), while newly typed composer input uses the best-effort path because it has no existing occurrence to preserve. Both negative outcomes are then treated by the UI as "converged through Queue" with no failure notice, because that is what actually happened.
- **Give every accepted item its own identity, and keep the wire a full snapshot** — `.agents/notes/archived/feature/2026-07-29-addressable-queue-operations.md:14` and `:44` — a `MessageId` is insufficient because one immutable message may be enqueued twice, so each FIFO acceptance gets its own `InboxItemId`; the wire then carries complete queue snapshots on every change because queues are expected to be short and deterministic recovery beats delta semantics. Full snapshots also let the client apply **no optimistic edit**, which is what makes a race reportable as a real race.
- **Project structured results onto a persisted channel with its OWN byte budget, and be honest about truncation** — `.agents/notes/archived/feature/2026-07-30-search-render-card.md:26` and `:28` — the card and the model-facing text consume the SAME retention outcome (the inline cap runs once), `total` is the pre-cap count and `truncated` says the page is capped, and the meta is bounded by a separate byte cap because the item-count cap does not bound the payload. The transfer: August's structured tool outputs need (a) one retention pass shared by every renderer, (b) an explicit `truncated`/`total` pair so no UI claims completeness the model never had, and (c) a byte budget on the structured copy that persists in the log.
- **One derivation per render intent, consumed by every render site** — `.agents/notes/archived/feature/2026-07-28-web-terminal-card.md:16` — a single `*-card-model.ts` turns the snapshot's `callView`/`resultView` pair into props so the chat row and the details panel cannot disagree about a command, its cwd or its exit status, and it returns the generic path (`null`) for every shape it does not recognise — including a `card` value this client version does not know, which arrives over the wire and cannot be trusted to be a compiled variant.
- **Type-check the table-pair invariant instead of documenting it** — `.agents/notes/archived/feature/2026-07-31-ptc-language-dispatch.md:41` — two parallel lookup tables are both `satisfies`-checked against ONE union, so a language added to one and not the other fails `typecheck`; the runtime `Object.hasOwn` guards (line 21) would only catch the drift once a second backend actually ships, i.e. at the consumer's integration point rather than where the drift was introduced. August's per-model and per-provider capability tables need the same mechanical pin.
- **Bound the candidate set outside the database, and fail closed at a call budget** — `.agents/notes/archived/feature/2026-07-27-web-session-search.md:16` — the large authorization set is kept OUT of the SQLite bindings (avoiding the portable variable ceiling) while global ranking is preserved; the provider's page size is learned downward on `SESSION_QUERY_INVALID_LIMIT` (20 → 10 → 5 → 2 → 1) and retained across continuations and stale restarts; limit probes and stale retries share one budget of 100 provider calls, and a page larger than requested, a repeated cursor or an unexhausted stream at that budget fails closed as a business error.
- **Model-facing wording at the model boundary, machine wording at the seam** — `.agents/notes/archived/feature/2026-08-03-fs-tool-error-remedy.md:14` — the recovery instruction ("— re-read the file, then retry") is appended by the TOOL package, after the sandbox mapping, while the structured `FsError` code and the `cause` chain are preserved for the retry/permission/UI layers. The rejected alternative is the instructive one: putting the remedy in the provider message leaks model-facing wording into every consumer of the seam vocabulary, and putting it in the prompt is unreliable because the failure arrives mid-task.
- **Enumerate the evidence tiers a third-party integration must satisfy, and refuse the cheap tiers** — `.agents/notes/archived/feature/2026-08-04-claude-code-and-codex-subagent-backends.md:12` — a keyless real-product test proves the official integration and teardown, a Loader composition test proves the package and documented configuration load without starting the product, and a credentialed e2e proves the production path end to end; "direct model HTTP or a product double cannot replace either product-running tier". This is the tiering August should apply to any external model/agent backend it wants to support.
- **Prove the model was actually sent the catalog, by reading the persisted request header** — `.agents/notes/archived/feature/2026-07-31-even-out-shipped-tool-rosters.md:38` — the shipped-composition smoke boots the real tree in a pseudo-terminal and reads the tool names out of the `request/header` the session log persisted, so the assertion is the catalog the model received, not the config that was supposed to produce it. The same note pins `glob`/`grep` as FIXED members because the search package registers both unconditionally (line 46) — a host-dependent pair would be an untestable surface.
- **Let a deployment choose a policy that the tool cannot observe, and put the choice in the tool's description** — `.agents/notes/archived/feature/2026-07-26-todo-parallel-in-progress.md:27` — whether several tasks may be `in_progress` depends on runtime concurrency the tool cannot see, so it becomes a REQUIRED `Config` field rather than a constant; the flag moves the model-facing description and the accepted input TOGETHER (splitting them teaches the model a rule the tool does not hold), and the durable-log invariant deliberately does NOT follow the flag so history written under one policy still replays under another.
- **Resolve the producer's name from the LOG, never from a client-side table** — `.agents/notes/archived/feature/2026-08-04-web-context-source-and-steer-marks.md:20` — the transcript names each injected context row by reading the durable `user/message.source`, so a resumed, forked or foreign log projects exactly like a live session and a renamed producer is identifiable without a client release; a dictionary keyed by plugin id drifts silently and cannot name a producer from a foreign log at all.
- **Hash-stamp both sides of a translated pair so translation drift is detectable** — `.agents/notes/archived/feature/2026-07-26-ptc-live-parallel-dispatch.i18n.yaml:5` — the `.i18n.yaml` sibling records the git blob hash of the English and the Chinese side of a note "as of the last confirmed-consistent state", re-recorded by `pnpm run verify-translation-pairing --write <file>`. A drift check for any doc set maintained in two languages, with a command that makes the re-record trivial.
- **Ship privacy and telemetry decisions as a RULING TABLE, one row per decision** — `.agents/notes/archived/feature/2026-07-31-telemetry-anonymous-user-id.md:16` — the table pairs each ruling (id source, storage form, IO form, concurrency, loss semantics, write failure, report position, semconv dependency, home, separate switch) with its value and a one-line rationale, and a second table gives every rejected alternative a one-line reason. This format makes a privacy posture auditable at a glance and is directly reusable for August's own credential/telemetry decisions.
- **Assert the EFFECTIVE roster, not the configuration** — `.agents/notes/archived/feature/2026-08-01-windows-pwsh-default.md:42` — the unit test composes the REAL shipped bundle layers through the boot's patch algorithm and pins the effective per-platform roster (win32 pwsh, POSIX bash, base-only), rather than asserting on a config file; the effective roster is the contract. The same note refuses a second override channel (an env escape hatch) so there is one source of truth for roster decisions (line 31).

I did not translate-compare the bodies sentence by sentence — that would have doubled the shard's 1.24 MB for no additional mechanism. Consequence: I can state that each mirror has the same section skeleton and the same content, but I cannot certify that no individual sentence was mistranslated. The repo's own defence against exactly that is the blob-hash pairing record, which I did read.
