## 5. The concrete signal that triggers a probation restore

Worth stating precisely, because "it regressed" is not an implementation:

1. An auto-apply books an outcome row (`harness_outcome.record`, `source='proposal'`,
   `key='proposal:<id>'`) and the apply's snapshot id goes on the ledger row.
2. The scheduled `outcome` job runs `measure_pending()`, which only considers rows whose
   **after-window has fully elapsed** (`applied_at <= now − outcomeWindowDays`, default 14) and
   that have never been measured (`measured_at IS NULL`).
3. `_classify(before, after)` fires the restore on `verdict == 'regressed'`, which means exactly one
   of two things — and both are RATES over a sample, since the review round fixed a rule that
   could revert a change on three episodes:
   - **targeted** (the proposal carried a `fingerprint`): recurrence as a proportion of the window
     (`fingerprintRecurrence / episodes`) rose by at least `_IMPROVE_EPS` (**0.15**).
   - **untargeted**: the after window's resolved rate is at least 0.15 below the before window's.
   - **Both sides need `_MIN_EPISODES` (8) episodes**, or the verdict is `insufficient`.
4. `_file_revert_proposal` then asks `harness_rails.probation_revert(...)`, which returns a receipt
   only if the outcome's proposal has an `auto_apply` ledger row, autonomy is still on, a
   `version_ts` is recorded, **and that snapshot is still the newest version for the skill**. Any
   one missing → `None` → the human gets the revert proposal instead, unchanged from before.
5. The restore goes through `skill_service.restoreVersion`, so it lands in the same history a
   human's undo writes to.

The honest limit: `flat`, `improved` and `insufficient` all leave the change in place, and a skill
that is simply never loaded measures `insufficient`, not a verdict. The trigger is recurrence or a
measured resolved-rate drop — never silence.
