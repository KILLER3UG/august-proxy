# deepseek-harness / dsh-client-rest#1

## Shard shape

This shard is the **browser half of the DeepSeek Harness web GUI** (`packages/client/*`), not the agent loop. It holds eleven client packages that together implement everything a browser page needs to talk to the Host process and to render itself: `connection` (the authenticated browser↔Host RPC/HTTP carrier, the Host/Origin trust fence, the browser-session cookie, and the *connection generation* reconnect controller), `file-upload` (Session-addressed staged uploads with a Worker-carried progress channel), `hmr` (live plugin-graph sync and rebuild-driven reload over SSE), `locale` (the zh/en preference, typed namespace dictionaries and the framework `t` seat), `modules` (the dual-face plugin loader: the Node half composes the `__DSH_BOOT__` graph and serves plugin bundles; the browser half is a lazy-CJS module table the vendored Cordis Loader consumes), `product-analytics` (Desktop-only event collection), `resources` (a URL-addressed live-value model behind a `useResource` hook), `shortcuts` (physical-key command registry and preference persistence), `store` (a React-free Immer/zustand snapshot engine), `ui-attachment` and `ui-deepseek-model-label-1017` (two focused UI plugins). Every package is a *dual-face* Cordis plugin: a Node half under the package root and a browser half under `./client`, wired together by `packages/client/tsdown.client.ts`, the shared tsdown preset that emits a closure-factory bundle (`window.__ModuleLoader__.load({id, factory})`) and enforces a **bundle purity gate** forbidding cross-plugin value imports. The `connection` package is the spine: `modules` registers the plugin graph the browser loads, `hmr` pushes graph changes to open pages, `resources` and `locale` supply live values to slot components, and `ui-attachment` fills the conversation's attachment slots. None of this shard touches the model loop directly — every package README states "Model Experience: None" — but several of its mechanisms (reconnect/generation lifecycle, retry/backoff, revision-identity and stale-download rejection, fixed-failure-reason reporting, per-key fallback chains) are exactly the plumbing an agent loop needs.

### packages/client/AGENTS.md
- Purpose: The authoring rules for `packages/client/*` — slot/props discipline, dependency declaration, build and localisation requirements.
- Key abstractions: two declaration forms (`ctx.slots.register` / `registerFactory`); the five derived prop shares (`PropsRuntime`, `PropsRenderSlots`, `PropsRenderFactories`, `PropsStore`, inject face); framework-made hooks only; stores as `createXXXStore()` factories with module-level handles forbidden as disguised singletons.

### packages/client/tsdown.client.ts
- Purpose: The shared build preset for every client package: how a package becomes a browser bundle, and what may cross a package boundary.
- Key abstractions: `clientBundle(packageDir, libEntry, options)` and `staticLinked(...)`; `INLINE_SAFE` (pure contract layers), `VENDORED_LIBRARY`, `GENERATED_REMOTE`; the three CSS virtual-loader prefixes; `BundleInputIsolation` for source-map rebasing.
- Data flow: `clientBundle` returns a `BuildFaceConfig` that reads `DSH_BUILD_FACE` to decide host/client phases; the client config emits CJS whose banner is `window.__ModuleLoader__.load({id, factory: (require) => {` and whose footer is `return module.exports; } });`.
- Non-obvious design decisions: **`dsh-client-bundle-purity` makes a cross-plugin value import a build error** — a plugin may only import another package's module if it is a requested module-table row, a vendored library, an inline-safe wire layer, or a generated `/remote` contribution. The stated reason: such an import either inlines a duplicate runtime instance or names a specifier the module table cannot answer.
- Edge cases / failure handling: `import.meta.env` is defined as an object *and* as `.MODE` because zustand probes `import.meta.env ? import.meta.env.MODE : ...` and the truthiness probe would otherwise survive as an empty `import.meta`; CSS-module ids carry a `.mjs` suffix so tsdown's own `.css` guard does not match them; `sourceMapExcludeSources: false` keeps browser profiling usable.
- Surprising: `asyncChunkRequirePlugin` rewrites the generated `Promise.resolve().then(() => require("./client.x.js"))` into `require.async("./client.x.js")` — the browser module table's own async op — and throws if a dynamic chunk has no generated import expression.

### packages/client/connection/src/api-path.ts
One constant `API_PATH = '/api'`, the single source both halves of the web transport use.

### packages/client/connection/src/api-request-trust.ts
- Purpose: The browser-trust fence every `/api` request must pass before authentication.
- Key abstractions: `assertTrustedAuthority`, `isRemoteAuthority`, `isTrustedApiRequest(request, trustedHosts, bindHost?)`.
- Data flow: the Host header is parsed with WHATWG URL under the listener's scheme, compared against loopback, the bind IP literal, or a configured `trustedHosts` entry; an attached `Origin` must name the same authority under that Origin's scheme; `sec-fetch-site: cross-site` is refused.
- Non-obvious design decisions: **the Host fence binds every request, browser-looking or not** — over plain HTTP a browser attaches neither `Origin` nor `Fetch-Metadata` to reads (images, navigations), so a rebound-origin GET is markerless and its response readable; `Host` is the one header rebinding cannot forge, so no marker shortcut may exist. `canonicalAuthority` judges the port from parses under *both* special schemes, because their default ports differ, so `:80` and `:443` still count as explicit.
- Edge cases / failure handling: configured authorities that WHATWG parsing would rewrite (a path, `user@host`, trailing whitespace, a dangling colon, a zero-padded port, `0x7f.0.0.1`, unbracketed IPv6) are refused at plugin load rather than silently ignored; the IPv6 zone id selects an interface, not an address, so `fe80::1%lo` matches only that exact spelling.
- Surprising: the fence "never establishes identity" — it is a rebinding/cross-site defence only, and is stated to be useless as an authentication mechanism.

### packages/client/connection/src/browser-auth.ts
- Purpose: Browser-session authentication for the Host Connection carrier (launch token → signed cookie → API peers).
- Key abstractions: `BrowserAuth.create(owner, credentials, maxAgeDays)`; the `client-connection/browser-session` credential grant record; cookie payload versions 1 (browser) and 2 (API, carrying a `PeerId`).
- Data flow: the process mints a random 32-byte launch token; `GET /?token=…` exchanges it for an authority-bound HMAC-signed cookie (host-only, `Path=/`, `HttpOnly`, `SameSite=Strict`, `Secure` only when *that* listener serves TLS); `/connect?token=…` returns a 302 with the Mux destination and a signed API cookie.
- Non-obvious design decisions: the cookie audience embeds the scheme, so an HTTP cookie cannot authenticate to a TLS listener on the same host and port; the signing secret lives in the credential store, so request authentication is synchronous and deleting the record revokes every session on the next activation.
- Edge cases / failure handling: a missing, expired, malformed, or wrong-authority cookie is a 401 *before* RPC dispatch; a non-owner `principal` in the stored record, a non-32-byte secret, or a non-string secret all fail loudly.
- Surprising: there is no logout operation — clearing the browser cookie ends one session; deleting the owner credential record and restarting revokes all of them.

### packages/client/connection/src/http-bridge.ts
- Purpose: The `node:http` ↔ WHATWG `fetch` bridge for the `/api` transport.
- Key abstractions: `bridge(req, res, apiHandler, peer, maxRequestBodyBytes)`; `DEFAULT_MAX_REQUEST_BODY_BYTES = 300 MiB`; two request body modes, `buffered` and `streaming`.
- Data flow: the request becomes a WHATWG `Request` (buffered → `Buffer.concat`, streaming → `Readable.toWeb` with `duplex: 'half'`), the handler answers, and the response body is written back chunk by chunk.
- Non-obvious design decisions: **client-disconnect detection MUST hang off the response, not the request** — since Node 16 `IncomingMessage`'s `close` fires as soon as the request body is consumed (immediately for a bodyless GET), which would abort a streaming response right after it opens; `ServerResponse`'s `close` plus `writableEnded` distinguishes a normal `end()` from the client going away. The 300 MiB default is derived from the 200 MiB aggregate image limit after base64 expansion plus envelope headroom, and the bridge buffers in memory, so it is also the per-request resident bound.
- Edge cases / failure handling: a declared `content-length` over the cap is a 413 with `connection: close` and `req.destroy()` — the body is not drained, because a client can trickle at will; a `false` return from `res.write` waits for `drain` (and `close`, so a disconnect cannot park the loop); after a disconnect the bridge drains the remaining response chunks without writing, because cancelling Node multipart bodies can race their producer.
- Surprising: `requestUnread` (a streaming route whose body was never read) forces `connection: close` on the response and destroys the request afterwards.

### packages/client/connection/src/rpc-host.ts
- Purpose: The Host-side registry and HTTP adapter for generic Connection RPC channels.
- Key abstractions: `HostConnectionService` (a Cordis `Service` providing `ctx.connection` on the Host), `connection.rpc.handle/intercept`, `connection.fetch.register` (exact `GET`/`HEAD`/`POST` routes), `connection.createPeer`.
- Data flow: an admitted request is dispatched to the matching channel interceptor, the handler's result is turned into a JSON or multipart response, and the `Peer` for the call travels with it.
- Non-obvious design decisions: the exact `fetch` registry **declares buffered vs streaming request bodies before the bridge reads a single byte**; a second registration of the same path/method is refused, and an unregistered path is a 404 rather than a fall-through.
- Edge cases / failure handling: exact routes answer **403 to a non-owner Peer** (the RPC interceptor still sees the call, so a guest can be handled at the channel level); `/api` itself is a reserved channel name and cannot be registered as a generic channel; a duplicate method in one route declaration is refused.
- Surprising: the `browserPeer` is a single shared `PeerScope` with an `owner` principal, so every authenticated browser call is the same principal — the security boundary is the admission fence, not the peer.

### packages/client/connection/src/rpc.ts
- Purpose: Carrier-neutral contracts shared by the Host and Client Connection halves.
- Key abstractions: branded `RpcId`; `ConnectionRpcResult<T> = {ok:true,value} | {ok:false,error}`; `ConnectionRpcAttachment` (a result-relative `path` plus `bytes`); `ConnectionTrustRequest`; `ClientConnectionRpc`.
- Data flow: a `ClientRequest` envelope (`type`/`rpcId`/`method`/`payload`) goes out, a `ServerResponse` envelope comes back, and binary results travel as multipart with the JSON part holding `null` placeholders.
- Non-obvious design decisions: `transportError` folds a rejected transport into an `internal` failure rather than throwing, so a transport error and a domain failure reach the caller through one shape.
- Edge cases / failure handling: the `details` field is a plain object, never an array.
- Surprising: `ConnectionRpcAttachment.path` uses string keys and numeric array indices and reserves *no* business field name — the handler that owns a result protocol does the projection.

### packages/client/connection/src/index.ts
- Purpose: The Host plugin entry: configuration, the `/api` and `/connect` routes, and the `connection/request` waterfall.
- Key abstractions: `Config` (recovery, `trustedHosts`, `cookieMaxAgeDays`, `maxRequestBodyBytes`); the `connection/request` waterfall event.
- Data flow: `apply` validates every configured `trustedHosts` entry (failing the plugin load loudly), creates `BrowserAuth`, then — once `webServer` exists — registers the `/api` prefix route and the `/connect` exact route and injects `__DSH_CONNECTION_RECOVERY__` into each served page.
- Non-obvious design decisions: `assertImageBodyCapacity` refuses a `maxRequestBodyBytes` below what the configured aggregate image limit needs, so a misconfiguration fails at load instead of 413-ing every image.
- Edge cases / failure handling: the waterfall lets a listener refuse *new* requests while admitted ones continue — the Desktop installer uses it to lock new API work during an update without cancelling work already accepted.
- Surprising: the Host half is inert in the browser build; the browser half (`./client`) is a separate export with its own `dualClient` Node bundle.

### packages/client/connection/src/client/connection.ts
- Purpose: Connection-generation readiness, cancellation, and continuous recovery.
- Key abstractions: `ConnectionController`; `ConnectionGenerationSource` (a source that attaches its listeners, calls `ready(host)`, then stays pending); `ConnectionSinks` (`onConnected`, `onStateChange`, `onReconnectRequested`); `ConnectionState` (`connected`/`disconnected`/`connecting`).
- Data flow: the controller opens the registered source, publishes the generation only after `ready`, and on loss applies the retry policy — a fresh physical carrier attempt before each logical retry.
- Non-obvious design decisions: **two separate timers for readiness** — a slow-Host *warning* (default 3 s) that does not cancel, and a hard *deadline* (default 15 s) that does; the backoff is `min(backoffMaxMs, backoffBaseMs * factor^(attempt-1))` with the delay taken at **50–100 % of that cap** (jitter), and retries continue at the final cap until recovery. Generation/attempt counters are instance-private, never in the store.
- Edge cases / failure handling: a sink that throws cannot kill the generation loop; `start()` is idempotent; a cancelled source's late `ready` cannot publish a generation; browser `offline` publishes `disconnected` and suspends attempts, and the next `online` resets the sequence to the base tier.
- Surprising: `ctx.connection.reconnect()` interrupts active work and starts retry 1 immediately, while the *Gateway mux owns no independent retry schedule* — there is exactly one backoff in the system.

### packages/client/connection/src/client/rpc.ts
- Purpose: The browser caller for generic Connection unary RPC channels.
- Key abstractions: `createWebConnectionRpc(doFetch?, openStream?)`; `RpcFetch`; `RpcStreamOpen` (a worker-local carrier with an uplink).
- Data flow: build a `ClientRequest`, POST it to the document-relative route, parse the response, and check that the echoed `rpcId` matches the one sent.
- Non-obvious design decisions: **binary results travel as multipart with `null` placeholders** — the JSON `metadata` part holds the RPC envelope with `null` where the bytes were, plus an attachment table of path/codec/part; the client validates the envelope, the `rpcId`, the table and the parts, then restores each byte value as an `ArrayBuffer`-backed view. Results without attachments (including base64 strings) and all failures stay plain JSON.
- Edge cases / failure handling: a duplicate multipart field name is an invalid binary response; a placeholder that is not `null` is rejected; a caller cancellation after the response is in flight rejects with the caller's reason; `assertTarget` refuses any channel or endpoint whose shape is not `^\/[A-Za-z0-9._~-]+$` + `^[A-Za-z0-9_$.-]+$` segments — no empty, `.` or `..` segments and no query characters.
- Surprising: `openStream` only accepts the `/api` channel, and the whole `open` method is omitted when no worker-local carrier is supplied.

### packages/client/connection/src/client/index.ts
- Purpose: The browser plugin entry: `ctx.connection` and the connection-generation lifecycle.
- Key abstractions: `installConnection(ctx, options)`; `ClientTransportHooks` (`rpc`, `fetch`, `openStream`, `createWebSocket`); `ConnectionHandle` (`generation`, `state`, `rpc`, `start`, `stop`, `reconnect`, `registerGenerationSource`).
- Data flow: the plugin reads `globalThis.__DSH_TRANSPORT__`, `__DSH_CONNECTION_RECOVERY__` and `location`, then installs the service; each call site owns one generation source and one carrier.
- Non-obvious design decisions: the plugin is `immediately: true` — it must exist before anything else mounts; a shell that owns a different transport provides both carrier halves rather than forking the plugin; each `installConnection` invocation creates one Context-owned service so several client trees can use different carriers in one realm.
- Edge cases / failure handling: malformed bootstrap recovery **fails before the service is published** (so `ctx.connection` is undefined rather than half-configured); the `connection/reset` event tells wire-derived caches to repull.
- Surprising: a single-consumer guard means the connection loop has exactly one owner — a second `start()` on the same handle is refused.

### packages/client/file-upload/src/index.ts
- Purpose: The Host upload service: streamed intake and Session-owned staged receipts.
- Key abstractions: `FileUploads` (a `TypertRemoteService`); `StagedFileUpload`; `AgentResolver`; **`PromptFileBinding`** and its `PromptFileBindingGuard`.
- Data flow: the service registers the streaming fetch route and a command file-receipt resolver; receipts live in a `WeakMap<Session, Map<receiptId, upload>>` keyed by the *exact* Session object; a `user/message` event with an `rpcId` retires the receipts bound to that request.
- Non-obvious design decisions: **prompt delivery holds each receipt binding in a disposable transaction** — disposal restores the previous binding until successful delivery commits it, and only then does queue/history observation retire the receipt. A model cannot, by naming a session, bind a receipt to a different agent: the resolver returns the exact live Agent or throws.
- Edge cases / failure handling: an unregistered or double-registered agent resolver throws; `session/disposed` drops the session's receipts; a receipt that was never staged is a `session/attachment-invalid` `RemoteError` with `reason: 'FILE_NOT_STAGED'`.
- Surprising: the receipt table is a `WeakMap` keyed by Session object identity, so a session that goes away takes its receipts with it.

### packages/client/file-upload/src/client/runtime.ts
- Purpose: The background browser upload implementation for `Blob` and byte-stream bodies.
- Key abstractions: `fileUploadWorker(scope, createXhr, doFetch)` — a self-contained Worker body emitted from a function string; `FileUploadRuntime`; the pre-Cordis `__DSH_FILE_UPLOAD__` page hook.
- Data flow: a `Blob` is sent by XMLHttpRequest **inside a dedicated Worker** so the service can report browser upload progress (including the total when the browser provides it); a `ReadableStream` is transferred to that Worker and fed to `fetch` incrementally, reporting consumed bytes without a total; exact bytes use the generated Remote.
- Non-obvious design decisions: the page thread never aggregates the bytes — a `Blob` is handed to the Worker whole and a stream is *transferred* (which locks the caller's object, so a retry needs a new stream).
- Edge cases / failure handling: a worker that fails to load, an unsupported stream carrier, and an abort all fail before or during the send; the returned receipt is validated field by field (`receiptId`, `attachmentId`, `name`, a safe non-negative integer `bytes`) and a malformed receipt is a `TypeError`.
- Surprising: the Worker is emitted from a function *string*, so adding a runtime import would require moving it to a standalone Worker entry — a stated limit of the design.

### packages/client/hmr/src/index.ts
- Purpose: The Host transport for Web client graph changes and rebuilt bundles.
- Key abstractions: `PluginsEventFrame`; the `/plugins/events` SSE channel; one `statSync` poll over every graph row's bundle.
- Data flow: the poll compares each bundle's `mtimeMs`/`ctimeMs`/`size` with the recorded baseline; a change calls `clientModules.rebuilt(id)`, which recomposes the graph and broadcasts a `rebuilt` frame; a graph change broadcasts the whole `graph`.
- Non-obvious design decisions: **polling by design** — network mounts deliver no inotify events; and the revision is derived from *metadata*, not content hashing, so an unchanged artifact needs no content read and a Host restart over unchanged artifacts keeps the same revisions (a reconnecting graph stream therefore does not replace browser plugins).
- Edge cases / failure handling: an `ENOENT` from `rebuilt` marks the watch dirty and retries on the next poll rather than logging; other errors are logged as warnings; the route refuses non-`GET`/`HEAD` methods with 405.
- Surprising: the SSE channel sends the *full* graph to every new connection, so a reconnecting page resynchronises without asking.

### packages/client/hmr/src/events.ts
- Purpose: The wire protocol of the `/plugins/events` channel, shared by both halves.
- Key abstractions: `PluginsEventFrame` (`graph` | `rebuilt`); `PluginsEventParseResult`; `parsePluginsEventFrame`.
- Data flow: the browser parses each SSE payload and hands the frame to the module system.
- Non-obvious design decisions: the parser distinguishes **forward-compatible unknown types from malformed known frames** — an unknown `type` string is `{kind:'unknown'}` (ignored), while a known type with a bad payload is `{kind:'invalid'}` (warned). Sharing the *type* keeps the two ends from drifting; the browser still validates at its parse point.
- Edge cases / failure handling: a non-object payload, a `rebuilt` frame without a string `id`/`rev`, and a `graph` frame with a null graph are all invalid.
- Surprising: the comment is explicit that sharing a type prevents drift, not mis-parsing.

### packages/client/hmr/src/client/index.ts
- Purpose: The Web SSE transport for page-owned entry reconciliation and code replacement.
- Key abstractions: `apply(ctx)` requiring the `modules` service; the page transport hook `__DSH_TRANSPORT__.fetch`.
- Data flow: a `graph` frame calls `entries.sync(graph)`, a `rebuilt` frame calls `entries.reload(id, rev)`, and both are serialised by the module system.
- Non-obvious design decisions: the event stream is read through the shell's `fetch` carrier when the page owns one (the worker preview's tunnel) and through `EventSource` otherwise — one implementation, two carriers; a stream that *ends* while the plugin is active is an error, not a quiet stop.
- Edge cases / failure handling: an unparseable payload and an invalid known frame are both warned and dropped; a stream that ends unexpectedly throws "client graph changes stop until the page reloads"; an abort during disposal is silent.
- Surprising: the `EventSource` path uses the document-relative route `plugins/events`, so the page resolves it under whatever mount served it.

### packages/client/modules/src/client/manifest.ts
- Purpose: The browser-safe contract face of the client module system: the `__DSH_BOOT__` wire types, the boot-manifest parser, and the boundaries around `ClientModuleSystem`.
- Key abstractions: `WebBootEntry`, `WebBootBatch`, `WebBootGraph`, `WebBootRelease`; `BootManifest`/`BootModuleRow`; `ClientModuleLoader`; `ClientModuleLoaderTarget` (the `window.__ModuleLoader__` facade); `DshWindow`.
- Data flow: the Host composes the graph and injects it; the browser parses it and resolves each row's URL lazily.
- Non-obvious design decisions: **the lazy CJS model** — executing a plugin bundle only *registers* its factory (`window.__ModuleLoader__.load({id, factory})`); every module side effect, including CSS injection, lives inside the factory closure and runs at materialisation, memoised in `loadCache`, so a factory that requires another registered-but-unmaterialised module materialises it recursively and load order needs no external sequencing. The resolution branch order is fixed: seed word → shell instance; memoised record → exports; graph row → register dependency factories and own factory; registered factory → materialise; **anything else → throw** — the runtime mirror of the build-time bundle purity gate.
- Edge cases / failure handling: a duplicate graph entry, a module-arrival cycle, a malformed `external` array, a missing batch table, a bad batch phase and a duplicate batch URL are all refused with a specific message; a release object carrying extra members has them dropped so equality compares only version and commit.
- Surprising: the `external` field carries *exact* non-inject module requests, and a request for a specifier no row and no static seed can answer is a loud failure, not a silent `undefined`.

### packages/client/modules/src/client/system.ts
- Purpose: The implementation behind the `ClientModuleLoader` contract — the state tables and the load/materialise/invalidate machinery.
- Key abstractions: `ClientModuleSystem`; the `loadCache`; `graphRows`; `reloadTargets`; `generations`; `factories`.
- Data flow: `import(id)` resolves the branch order, fetches the bundle, registers its factory, materialises it on first require, and memoises the exports; `invalidate(id, rev)` bumps the generation, drops the factory and the memoised record (and any sibling `client.*` chunk), and records the replacement URL.
- Non-obvious design decisions: **style claiming** — a factory's `<style>` tags are inventoried by diffing the untagged styles present *before* materialisation against those present after, and the new ones are tagged `data-plugin` so a reload can remove exactly the styles it owns. Chunk URLs are derived from the owning row's one-resource URL, and a chunk arriving after its owner was invalidated is discarded.
- Edge cases / failure handling: a bundle URL with no `rev` query is an error; a chunk that cannot be resolved from the row's URL is an error; the browser `WebSocket`/`<script>` load failure rejects with the script's URL.
- Surprising: `invalidate` also clears the `importErrors` entry, so a retried row starts from a clean slate.

### packages/client/modules/src/client/entries.ts
- Purpose: Page-owned Loader entries: transport-independent reconciliation, retries and code replacement.
- Key abstractions: `ClientEntries`; `ClientEntryState` (`syncing`, `failures`); the serialised `queue`; the `generation` counter; `ReleaseChangeGate`.
- Data flow: `sync(graph)` and `reload(id, rev)` are enqueued on one promise chain; the reconcile pass adds, removes and re-enables entries on the Loader, then awaits the Loader and reports per-entry failures.
- Non-obvious design decisions: **a local generation counter prevents a stale download from mounting** after the desired entry set or code has changed — every await point in the reconcile and replace paths re-checks `this.current(generation)`. Snapshots with the same target share one pending load, and new arrivals use single-resource URLs so a startup batch is never re-executed (which would stop at the first duplicate factory registration).
- Edge cases / failure handling: removing the bootstrap module is refused with "removing bootstrap module"; an import failure is reported per entry and the *same* Loader entry is retained for retry rather than replaced by an orphan sibling; a failed replacement leaves unrelated page failures visible.
- Surprising: a graph from a release other than the boot release never enters the queue at all — retries keep reconciling the last applied graph.

### packages/client/modules/src/client/release-change.ts
- Purpose: The gate deciding which Host graphs a page may apply.
- Key abstractions: `ReleaseChangeGate`; `ClientReleaseChange` (`page`, `previous`, `host`).
- Data flow: `observe(release)` records the Host's release and returns whether the graph belongs to the page's boot release; the page applies graphs and rebuilt frames only while that is true.
- Non-obvious design decisions: the page's release identity is `{version, commit}` — both must match; the mismatch is *announced* (a `console.warn` plus a published change snapshot) rather than silently ignored, and the user can `dismissRelease()` to stop the announcement for that Host release while the page still refuses the other release.
- Edge cases / failure handling: a dismissed release is remembered as a value, so an unpublished release is still a thing that can be dismissed; returning to the boot release clears the announcement.
- Surprising: the reason for the gate is that **every module the page runs must belong to the release the page booted from** — a half-old, half-new plugin tree is the thing being prevented.

### packages/client/modules/src/index.ts
- Purpose: The Node half: scan the Host Loader's entries for packages declaring `dsh.client`, compose the boot graph, serve the plugin bundles, and provide the `clientModules` service.
- Key abstractions: `ClientModuleRegistry`; `ClientArtifactBaseline`; `WebBootGraph`; `ComboArtifact`; `bootInjections`.
- Data flow: the scan marks dirty entry names and a microtask flush reconciles them against the live Loader entries; the composed graph is injected into the served index alongside the registration facade, the preloads, the parser-blocking bootstrap combo, and the graph itself.
- Non-obvious design decisions: **the scan is incremental per package and there is no full-rescan code path** — every `internal/plugin` emission marks the fiber's entry name dirty, and the activation pass seeds the same dirty set so first scan and steady state share one implementation. Package metadata (including the *negative* "not a client package" verdict) is cached per Loader specifier and owning-tree base URL until restart. A package's manifest name identifies its browser module, so **distinct active Loader sources for one package are a composition error**. A response body is built lazily on the first `GET`, so an artifact that is never requested is never read; `HEAD` materialises nothing.
- Edge cases / failure handling: a bundle whose source map is malformed falls back to an identity section so the bundle stays debuggable; the combo URL is partitioned before it exceeds 3 KiB (3 072 bytes) so a long plugin list cannot produce an unservable URL; an unknown resource or revision is a 404.
- Surprising: the per-plugin revision is derived from `mtimeMs`, `ctimeMs` and `size` — **ctime** distinguishes a rewrite that preserves mtime and size, so a rebuild is still seen, without hashing any content.

### packages/client/resources/src/client/resources.ts
- Purpose: The provider registry and the per-address states behind `useResource`.
- Key abstractions: `ResourceRegistry`; `ResourceRecord` (address, protocol, store, source, holder count, `AbortController`); `RESOURCE_SCHEME`; `protocolOf(address)`.
- Data flow: the first holder (a `source` subscriber or a `pin`) opens the provider's stream; frames update the snapshot store; the last holder's release aborts the stream and resets the snapshot to idle.
- Non-obvious design decisions: **a record is kept for every address ever sourced and is never dropped — only its state is.** The reason is given: keeping the record keeps `source()` reference-stable across React's render-then-subscribe window and a StrictMode remount, where a recreated record would make every render resubscribe and restart the stream.
- Edge cases / failure handling: a frame the provider yields *after* the release that aborted it belongs to nobody and is dropped (and the loop returns the iterator); a failure frame marks the resource `failed` while keeping the last value, and the next ok frame clears it; a stream that ends on its own keeps its last state.
- Surprising: `protocolOf` lower-cases the host of a `dsh-resource://` URL but treats every other scheme as "no resource" — `sidebar://guide` is a navigation address, not a resource.

### packages/client/resources/src/client/contract.ts

### packages/client/shortcuts/src/client/registry.ts
- Purpose: Command registration, normalized default bindings, and synchronous dispatch.
- Key abstractions: `ShortcutRegistry`; `commands` / `fixedCommands` / `conflicts` / `bindings` maps; the `catalog` and `config` observables.
- Data flow: a command registers its defaults per profile; `configure(snapshot)` recomputes the effective bindings and the derived catalog; `dispatch(gesture, context, consume)` arbitrates and runs.
- Non-obvious design decisions: **a conflicting row keeps its requested binding visible but cannot execute it** — the dispatch returns `{status:'blocked', reason:'conflict'}` and *consumes* the event rather than silently unbinding the command. The arbitration order is fixed: region ownership, then a priority path, then a conflict check, then a modal check, then the owner's own `resolve(context)`.
- Edge cases / failure handling: a repeated key event is consumed but does not re-run the action; a command whose owner returns `pass` leaves the event to the next candidate; a command whose owner returns `blocked` is consumed and not run; a command outside the current modal is blocked with reason `modal`.
- Surprising: terminal `Ctrl+W`/`Ctrl+R` are explicitly passed through on Linux, because those are the terminal's own line-edit keys.

### packages/client/shortcuts/src/persistence.ts
- Purpose: Serialised preference transactions; storage owners publish only accepted writes or read diagnostics.
- Key abstractions: `ShortcutPersistence`; `ShortcutConfigSnapshot` (`revision`, `sequence`, `document`, `status`, `error`, `usingDefaults`); `ShortcutSaveResult` (`saved`/`stale`/`unreadable`/`write-failed`/`not-ready`/`conflict`); `ShortcutStorage`.
- Data flow: every operation runs on one promise queue (a single writer); `edit` re-reads (for the browser adapter), compares the draft revision, validates the whole candidate document, writes, and only then publishes a new accepted snapshot with a fresh revision.
- Non-obvious design decisions: **the revision is an opaque identity, not a counter** — it is replaced on every accepted change, so a draft made against an older state is rejected as `stale` rather than silently applied. A write failure keeps the previous complete document *and* the draft, so the same draft can be retried. The `sequence` is monotone within one storage-owner lifetime so clients can discard out-of-order IPC replies.
- Edge cases / failure handling: an unreadable or future-version document blocks edits entirely (`unreadable`) and never replaces the stored bytes; an explicit edit that would silently disable *another* command's default binding is refused as a `conflict`; a subscriber that throws is contained and the save still succeeds.
- Surprising: `setDefinitions(null)` (the product is not ready) makes every edit `not-ready` — the model of "the catalog is not installed yet" is explicit.

### packages/client/shortcuts/src/binding.ts
- Purpose: The physical-key protocol shared by the browser commands and the desktop adapters.
- Key abstractions: `ShortcutBinding` / `NormalizedBinding`; `normalizeBinding`; `bindingKey`; `presentBinding`; `isWebBindingAllowed`.
- Data flow: a binding declares one or two physical `code`s plus a modifier set; normalisation expands `primary` to `meta` on macOS and `control` elsewhere, sorts the codes, and rejects unsupported codes and duplicate keys.
- Non-obvious design decisions: **the normalised modifier order is also the keycap order** (`control`, `alt`, `shift`, `meta`), and the two codes are sorted so `A+B` and `B+A` are the same binding. `presentBinding` emits `+` separators on Windows and adjacent keycaps on macOS, and **a two-key chord omits the ARIA accelerator** because ARIA `accesskey`/`aria-keyshortcuts` only supports one non-modifier key.

### packages/client/store/src/index.ts
- Purpose: The React-free snapshot store engine (zustand vanilla + immer + `subscribeWithSelector` + a rAF flush middleware + opt-in persist + dev freeze) and the declarative `defineStore` shell.
- Key abstractions: `SnapshotStore`; `defineStore(spec)` → `StoreHandle`; `shallowEqual`; `notifySubscribers`.
- Data flow: `defineStore` bakes an `init`/`persist`/`actions` literal into a handle; `handle.create(scopeKey?)` makes a live instance whose `actions` are the immer-draft mutators with the draft parameter baked away.
- Non-obvious design decisions: **the flush mode is a deliberate choice, not a default** — `sync` is the default "because controlled inputs need same-tick echo", while `raf` coalesces a frame's worth of updates into one notification, with the stated trade-off that a component mounting mid-frame reads fresh state while existing subscribers hear it next flush. `init` is a *lambda* so every instance gets a fresh state, and the persist key is **suffixed with the scope key**, so per-session instances persist independently and a scope's cleanup removes exactly its own key.
- Edge cases / failure handling: a rehydration failure is reported but does not prevent store creation; a persistence write failure does not reject the write; `clearPersisted` is a no-op without a persist declaration or storage and swallows storage failures; `set()` freezes the owned envelope outside production *without* traversing opaque object handles (a class instance the store holds is left unfrozen).
- Surprising: the engine deliberately ships **no React hook** — hook synthesis belongs to ui-renderer, so a component never sees the instance itself, only a selector hook and the declared actions.

- Key abstractions: `ObservableSnapshot`; `SnapshotSelectorHook` / `MaybeSnapshotSelectorHook`; `ActionsDecl` / `BakedActions`; `StoreSpec`; `StoreHandle` / `StoreFactory`; `PropsStore` / `BoundActions` / `HandleOf`.
- Data flow: a registrant declares a `StoreSpec`; the framework (or a test) calls `create(scopeKey)`; the component receives `useStore` and `actions`.
- Non-obvious design decisions: **the declared actions are the complete mutation API** — the audit face; components can only write through them. `ActionsDecl` uses `any[]` rather than `unknown[]` because `unknown[]` would reject every concrete signature under strict parameter contravariance. `MaybeSnapshotSelectorHook` exists so a session-scoped hook call site stays stable across no-session/session transitions without pretending a session snapshot exists.

## Ideas worth stealing

- **Bind the Host header on every request, not just the ones that carry browser markers** — `packages/client/connection/src/api-request-trust.ts:1` (and `isTrustedApiRequest` at `:121`) — the docstring states the reason precisely: over plain HTTP a browser attaches neither `Origin` nor `Fetch-Metadata` to reads (images, navigations — those headers go only to trustworthy destinations), so a rebound-origin GET is markerless and its response readable. `Host` is the one header DNS rebinding cannot forge. *Why it transfers to August*: any local HTTP API August serves to a browser (the local backend, the MCP door, the settings API) has the same confused-deputy exposure, and the fix is a single unconditional check plus a **loud failure on a malformed config** (`assertTrustedAuthority` at `:53`) rather than a silently ignored entry. The same file also shows the discipline of refusing `0x7f.0.0.1`, a zero-padded port and a trailing-dot spelling, because WHATWG parsing would silently rewrite them and broaden the grant.
- **Two timers for one handshake: a warning that does not cancel, and a deadline that does** — `packages/client/connection/src/client/connection.ts:295` (warning) and `:298` (deadline) — a slow Host produces a log line at 3 s and a cancellation at 15 s, and the warning is *cancelled* if readiness, failure, cancellation or the deadline happens first (`:309`). *Why it transfers*: August's turn/connection paths need the same "something is slow, but not yet wrong" distinction; one timer cannot express it, and a single generous timeout hides a hung peer.
- **Jittered backoff whose cap is a *fraction* of a computed tier, not the tier itself** — `packages/client/connection/src/client/connection.ts:139` (`backoffCap`) and `:144` (`backoffDelay`, 50–100 % of the cap) — the tiers are 500 ms, 1 s, 2 s, 4 s, 8 s, 10 s and retries continue at the final cap until recovery, with `onReconnectRequested` asking the Gateway to replace the physical carrier *once* before each logical retry. *Why it transfers*: August's provider-retry path should not have every client reconnect in lockstep; the "replace the physical carrier before the logical retry" split is also exactly the shape of "open a new provider connection, then retry the turn".
- **Hang the client-disconnect detection off the *response*, never the request** — `packages/client/connection/src/http-bridge.ts:45` — since Node 16, `IncomingMessage`'s `close` fires as soon as the request body is consumed (immediately for a bodyless GET), which would abort a streaming response right after it opened; `ServerResponse`'s `close` plus `writableEnded` is the only reliable signal. *Why it transfers*: August's local backend serves streaming responses to a browser that can vanish at any moment; getting this wrong aborts a live stream for no reason, and the mistake is invisible until a user closes a tab.
- **Reject an oversized body by *destroying* the request, not draining it** — `packages/client/connection/src/http-bridge.ts:62` — a declared `content-length` over the cap is a 413 with `connection: close` and `req.destroy()`; the same discipline applies to the chunked overrun. The comment gives the reason: "the socket must not stay parked draining a body the client can trickle at will after the rejection". *Why it transfers*: the same shape is a slow-loris defence on any local HTTP door August opens, and the paired rule — **a cap is a per-request resident bound because the bridge buffers in memory** (`DEFAULT_MAX_REQUEST_BODY_BYTES` sized from the aggregate image limit, `:11`) — is the reasoning August's own 20 MB file-read ceiling already uses.
- **Binary results travel as multipart with `null` placeholders plus an attachment table** — `packages/client/connection/src/client/rpc.ts:62` (media-type branch), `:90` (the `metadata` part) and `:129` (the placeholder check) — the JSON part holds the response envelope with `null` where the bytes were, plus a table of path/codec/part; the client validates the envelope, the `rpcId`, the table and the parts, then restores each byte value as an `ArrayBuffer`-backed view. *Why it transfers*: August's own binary-attachments RPC (workspace file reads, image uploads) is exactly this shape, and the two rules that make it safe — **no business field name is reserved**, and the *handler that owns the result protocol* does the projection rather than the transport discovering binary fields — are the transferable part.
- **Make a cross-package value import a build error, with a named escape hatch** — `packages/client/tsdown.client.ts:560` (the `dsh-client-bundle-purity` plugin) — an `@deepseek-ai/*` import that is neither a requested module-table row, a vendored library, an inline-safe wire layer, nor a generated `/remote` contribution fails the build, and the error message tells the author to declare a module request or collaborate through services instead. *Why it transfers*: this is the plugin-isolation rule August needs for a client-plugin system; the escape-hatch list is the important half — a ban with no named exceptions pushes teams to inline duplicate runtime instances.
- **The lazy-CJS model: executing a bundle only *registers a factory*** — `packages/client/modules/src/client/manifest.ts:9` — every module side effect, including CSS injection, lives inside the factory closure and runs at materialisation, memoised in `loadCache`; a factory that requires another registered-but-unmaterialised module materialises it recursively, so load order needs no external sequencing, and **anything else throws** (`:21`) rather than returning `undefined`. *Why it transfers*: an August plugin/subagent package loaded at runtime gets the same property — nothing runs until the feature is first used, and an unresolvable import is a loud failure instead of a silent hole.
- **Incremental composition with no full-rescan path, and a cached *negative* verdict** — `packages/client/modules/src/index.ts:12` — every `internal/plugin` emission marks the fiber's entry name dirty, a microtask flush reconciles the dirty names against the live entries, and the activation pass seeds the same dirty set so first scan and steady state share one implementation; package metadata (including the "not a client package" verdict) is cached per Loader specifier until restart. *Why it transfers*: a registry that rescans everything on every change is fine at 20 packages and fatal at 200; the cached *negative* verdict is the detail most registries forget.
- **Derive a revision from `mtime` + `ctime` + `size`, not from a content hash** — `packages/client/modules/src/index.ts` (the `ClientArtifactBaseline` shape) and `packages/client/hmr/src/index.ts:51` (`bundleStat`) — ctime distinguishes a rewrite that preserves mtime and size, so a rebuild is still seen, and an unchanged artifact needs no content read at all; a Host restart over unchanged artifacts therefore keeps the same revisions, so a reconnecting stream does not replace the browser plugins. *Why it transfers*: August's plugin/HMR and asset-cache paths can use the same identity, and the stated trade-off is honest in the README — metadata-only changes can cause a spurious reload, and a content change invisible in all three fields cannot be detected.
- **Gate the whole page on the release it booted from** — `packages/client/modules/src/client/release-change.ts:31` — the page applies graphs and rebuilt frames only while the connected Host serves the same `{version, commit}` release; a mismatch is *announced* (a published change snapshot plus a warning) rather than silently ignored, and can be dismissed for that Host release. *Why it transfers*: the generalisation is "a client must not silently mix two server versions" — August's desktop app talking to a mismatched backend has exactly this hazard, and the announcement-plus-dismiss shape is a usable UX.
- **A local generation counter as a stale-download guard** — `packages/client/modules/src/client/entries.ts:112` and `:175` (`current(generation)`) — the desired-state generation is bumped whenever the target set or a code revision changes, and every await point in the reconcile path re-checks it, so a download that lands after the target moved is dropped rather than mounted. *Why it transfers*: this is the same guard August needs for a tool result, a stream chunk or a subagent reply that arrives after the user has moved on; the shape (a counter, not a timestamp) is cheap and exact.
- **Keep the record, drop the state** — `packages/client/resources/src/client/resources.ts:1` — a record is kept for every address ever sourced and is never dropped; only its state is discarded when the last holder leaves. The reason is given and is the transferable part: keeping the record keeps `source()` reference-stable across React's render-then-subscribe window and a StrictMode remount, where a recreated record would make every render resubscribe and restart the stream. *Why it transfers*: any August UI with a live-value subscription needs this to avoid a resubscribe storm; the memory cost is bounded by "distinct addresses ever read", which the README states.
- **Failures are frames, not throws** — `packages/client/resources/src/client/contract.ts:74` — a provider yields `{ok:false, error}` and the resource turns `failed` with that error *beside the last value*; the next ok frame clears it; a throw inside a provider's stream is a programming error and is not caught. *Why it transfers*: a partial-failure channel that keeps the last good value is exactly what August's tool-call and attachment surfaces need; the "a throw is a programming error, do not catch it" clause prevents the error channel from becoming a catch-all.
- **One dictionary registry, one fallback chain, one stable bind identity** — `packages/client/locale/src/client/index.ts:466` (the per-key chain: requested namespace → declared fallbacks → the `common` namespace → the key itself) and `:448` (`bind` returns the *same* function per namespace) — a registration bumps the snapshot revision but **does not emit `locale/change`**; only an active-locale switch emits it, because a registration-heavy boot would storm event listeners that may re-register slots in response. *Why it transfers*: the same shape fits any registry of pluggable text or capabilities — a revision for render invalidation, a separate event for semantic change — and the stable function identity is what lets it ride an inject surface without breaking memoisation.
- **A conflict blocks, it does not silently unbind** — `packages/client/shortcuts/src/client/registry.ts:165` — a conflicting row keeps its requested binding visible but cannot execute it; the dispatch consumes the event and returns `{status:'blocked', reason:'conflict'}`. *Why it transfers*: August's tool-name registry, hook registry and provider aliases have the same collision case; the "visible but not executable" state is what a user can actually understand, and consuming the event stops a second command from firing the same keystroke.
- **Revision-checked preference writes with a classified outcome** — `packages/client/shortcuts/src/persistence.ts:92` — the draft carries a revision; a mismatch is `stale` rather than silently applied; a write failure keeps the previous document *and* the draft so the same draft retries; an unreadable or future-version document blocks edits entirely and never replaces the stored bytes. *Why it transfers*: August's Settings writes go to a shared `cordis.patch.yml`; the same five outcomes (saved / stale / unreadable / write-failed / conflict) cover every failure August can hit there, and "the write failure keeps the draft" is the difference between a lost setting and a retry.
- **Fixed reasons instead of raw failure text** — `packages/client/product-analytics/src/environment-query.ts:27` — a failed OS metadata query returns `unavailable | invalid-value | query-failed | timeout | output-limit | unsupported` and never the command output or the error text; the same file waits for the child's `close` event because `execFile` can report an abort before stdio closes. *Why it transfers*: any August diagnostic that reports *why* something failed to the user or to a log should carry a reason from a closed set, not a raw exception; and the "await the child close" rule is the difference between a clean teardown and a leaked child.
- **Cache the expensive, re-read the cheap, and re-check the policy on both sides of the await** — `packages/client/product-analytics/src/index.ts:103` (the environment snapshot is collected once and shared) and `:101`/`:111` (the `enabled()` check before and after the awaits) — identity is re-read per event so a later event reflects a login change, while the OS probe is not repeated. *Why it transfers*: the same split is right for August's session metadata or a device probe; and the double policy check is a general rule — **a policy that can change while an async operation is in flight must be checked after the await too**, or a revoked permission leaks one event.
- **A staged receipt held in a disposable transaction** — `packages/client/file-upload/src/index.ts:39` (`PromptFileBindingGuard`) — prompt delivery holds each receipt binding in a disposable transaction: disposal restores the previous binding until successful delivery commits it, and only then does queue/history observation retire the receipt. *Why it transfers*: this is the exact shape for any August capability that is granted for one turn — it must be committed by the success path and rolled back by the failure path, with the rollback living in the transaction rather than in the caller's error path.
- **A background Worker for progress, a transferable stream for bytes** — `packages/client/file-upload/src/client/runtime.ts:79` — a `Blob` is sent by XHR *inside a dedicated Worker* so the browser's own upload progress (including the total) is available; a `ReadableStream` is transferred to that Worker and fed to fetch incrementally, reporting consumed bytes without a total; the page thread never aggregates the bytes. *Why it transfers*: August's desktop app moves large files over a local transport; the "progress with a total vs progress without a total" distinction is one users notice, and the Worker keeps the UI thread free.
- **The image sizing rule, stated once** — `packages/client/ui-attachment/src/MessageImage.tsx:36` (`singleFit`) — long edge 240 px, aspect clamped to `[0.25, 4]`, never upscaled past the natural size, and the crop anchor kept toward the informative edge (top for tall images, left for wide ones). *Why it transfers*: a small, self-contained, reviewable rule that removes a whole class of "the image looks wrong" complaints, and the comment explains *why* each half of it exists.
- **The page's own failure vocabulary, in one table** — `packages/client/shortcuts/src/binding.ts:96` (`isWebBindingAllowed`) and `packages/client/shortcuts/src/client/dom.ts:64` — the browser's delivery limits are a *named predicate* (no chords in a browser, only a small admitted set on Linux), and the DOM adapter's protection list (composition, `keyCode 229`, `AltGraph`, dead keys) is an explicit enumeration rather than an emergent behaviour. *Why it transfers*: the August agent loop has the same class of "the platform will not deliver this" knowledge (a headless browser will not deliver a three-modifier chord; a model will not deliver a second key); naming it as a predicate makes it testable and lets a refusal be *reported* rather than silently swallowed.
