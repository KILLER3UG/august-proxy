## 5. The concrete signal that triggers a probation restore

Worth stating precisely, because "it regressed" is not an implementation:

1. An auto-apply books an outcome row (`harness_outcome.record`, `source='proposal'`,
   `key='proposal:<id>'`) and the apply's snapshot id goes on the ledger row.
2. The scheduled `outcome` job runs `measure_pending()`, which only considers rows whose
   **after-window has fully elapsed** (`applied_at <= now − outcomeWindowDays`, default 14) and
   that have never been measured (`measured_at IS NULL`).
3. `_classify(before, after)` fires the restore on `verdict == 'regressed'`, which means exactly one
   of two things — and both are RATES over a sample, since the review round fixed a rule that
   could revert a change on three episodes:
   - **targeted** (the proposal carried a `fingerprint`): recurrence as a proportion of the window
     (`fingerprintRecurrence / episodes`) rose by at least `_IMPROVE_EPS` (**0.15**).
   - **untargeted**: the after window's resolved rate is at least 0.15 below the before window's.
   - **Both sides need `_MIN_EPISODES` (8) episodes**, or the verdict is `insufficient`.
4. `_file_revert_proposal` then asks `harness_rails.probation_revert(...)`, which returns a receipt
   only if the outcome's proposal has an `auto_apply` ledger row, autonomy is still on, a
   `version_ts` is recorded, **and that snapshot is still the newest version for the skill**. Any
   one missing → `None` → the human gets the revert proposal instead, unchanged from before.
5. The restore goes through `skill_service.restoreVersion`, so it lands in the same history a
   human's undo writes to.

The honest limit: `flat`, `improved` and `insufficient` all leave the change in place, and a skill
that is simply never loaded measures `insufficient`, not a verdict. The trigger is recurrence or a
measured resolved-rate drop — never silence.

- **Verifying UI in a real browser**: serve `web-dist` from the backend itself (same origin, no
  proxy, no CORS puzzle) and drive it with headless chromium via playwright — import it by absolute
  path from a script outside the repo (`file:///C:/Dev/august-harness-wt/node_modules/playwright/index.mjs`)
  so Node can resolve it. The in-app Qoder browser reports `NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`.
  Four things cost an hour each, learned on the 2026-10-06 pass:
  * the backend needs `AUGUST_CORS_ORIGINS=http://127.0.0.1:<port>` or a browser `POST` is a
    **403** while the same `POST` from `urllib` succeeds — the seed looks fine and the page is empty;
  * the sidebar roster is **localStorage** (`august-sessions-list-v1`, `august_last_session`), not
    `/api/sessions`. A server-side session never appears until you write a roster entry shaped like
    one the app wrote itself; and a new browser context drops localStorage, so seed + reload +
    measure must run in one script;
  * settled receipts are **folded** behind `.activity-summary-header[aria-expanded]` — click it
    before counting rows or a working feature reads as missing;
  * edit-class receipts render in `EditRailRow`, **not** `ToolStepRow`. A check aimed only at
    `[data-slot="tool-step-row"]` cannot see them, and that is where the last real bug was hiding.
- `AUGUST_CORS_ORIGINS` is **comma**-separated, and a browser POST from an origin the guard does not
  trust is a 403 `untrusted origin` — including same-origin, for a backend started without it. GETs
  work, so it reads like a broken button rather than a blocked request.
- The **first-run setup modal covers the composer**, so the chip is not clickable until it is
  dismissed (`Skip for now`).
- `saveBrainConfig` takes a **flat camelCase patch**; the nested `auxiliary.cognitive.orchestrator`
  shape is what it WRITES, not what it reads. A nested patch "succeeds" and changes nothing.
- A react-query `findByTestId` on a container resolves while its child query is still loading —
  await the control, not the wrapper. Three test-harness bugs this session were exactly this.
