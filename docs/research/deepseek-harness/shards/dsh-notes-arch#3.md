# deepseek-harness / dsh-notes-arch#3

## Shard shape

This shard is 35 files drawn from one frozen subtree of the `deepseek-harness` repo: `.agents/notes/archived/architecture/`. It is 12 English **Agent Notes** (all `Status: implemented`, sealed `Archived: 2026-09-30`, except the Schedule note at `2026-09-25`), their 12 Chinese mirrors, and 11 bilingual-pair sidecars (the twelfth sidecar, `2026-09-17-session-row-menu-actions-slot.i18n.yaml`, is owned by shard `dsh-notes-arch#2`). The notes are the repo's decision record — each one is "what we decided, what we gave up, and what we rejected" — and the set is coherent: they are the *extension and composition* half of DSH's architecture. Slot lists make the client UI extensible (session row menu, plugin detail), package layout is used as an extension boundary (settings companion packages, one bundle per feature), the plugin host is treated as a single-instance trust domain (profile plugins vs. host runtimes), and three notes are about keeping the agent's context and the browser's mount honest (creator skills under the pruner threshold, document-relative routes under a static gate, live Config schemas instead of a CLI dump). Together they read as the "host is a runtime, not a monolith" thesis: every extension point is a named, ordered, hash-checked, mount-independent seam rather than an import.

### .agents/notes/archived/architecture/2026-09-17-session-row-menu-actions-slot.md

- Purpose: Replace the closed Session-row "..." menu and hover-button strip inside `ui-workspace` with two root-scoped `list` slots, so a client plugin can add, reorder or shadow a row action without editing the owning package.
- Key abstractions: `sidebar.workspaces.session.menu.item` and `sidebar.workspaces.session.row.action` slot lists; ascending `order` plus the registry's ordinary cell rules (reusing a shipped id at another `priority` shadows that action); `inject.hooks` faces (`usePinned` / `useArchived` Sets derived once per Workspace snapshot, and `useMenuOpenState`); `shell.overlay` entries for the rename dialog and the row-action notice; `MenuItemButton` from `ui-primitives`.
- Data flow: `ui-workspace`'s `apply` registers its own actions (`pin` menu 100 / button 200, `rename` 200, `fork` 300, `archive` menu 400 / button 100) exactly as a plugin would → entries render in `order` → an entry's own `inject` face carries one callback → `pinSession` delegates to `uiWorkspace.pinSession`, which performs the Host pin and then fronts the session in its accounts' saved orders via `pinSessionOrder`, reading the memberships current at completion from the object-layer snapshots (`pin-order.ts`) → the view order is written through the viewing-store instance the `apply` creates and hands the browser's registration as its handle.
- Non-obvious design decisions: There is no separate "extension group" — the owner draws no separator, and a group start is the entry's own `separatorBefore` (line 14), because a dedicated appended slot would make the shipped rows a privileged group a plugin can only follow. An entry receives only the row identity `{ sessionId, displayTitle }` and reads the Host state it needs itself, so "each action's behavior is that action's own" and the browser stays out of it (line 16); owner-supplied `pinned`/`archived` props and callbacks were rejected for exactly that reason (line 26). Entries that computed their own view-order writes were rejected because subscribing to the whole Session list re-renders every visible row on every list change (line 30).
- Edge cases / failure handling: pin renders nothing on an archived row because the Host keeps the pinned and archived sets exclusive, and archive never consults pin (line 16). Closing is the owner's state for both row kinds: data rows through the owner's `onSelect`, component rows through the slot-level `useMenuOpenState` hook, with `SessionNodeItem` passing its `[open, setOpen]` pair as the occurrence's `hookContext` (line 20). A `cordis-client-runner` closure that cannot import the primitive renders a `role="menuitem"` button directly and still joins the menu's keyboard walk, submenu exclusivity and post-selection focus return, because `Menu` decides all three from the DOM (line 20).
- Surprising: the archived-row notice's second action now switches the archived filter to "show" through the same store instance, because the browser's view-options menu is no longer in the loop (line 18) — a user affordance outlives the menu it used to open.

### .agents/notes/archived/architecture/2026-09-17-settings-pages-as-companion-packages.md

- Purpose: Split the four official settings pages out of `ui-settings-plugins` so each lives in a client-only companion package, and so a community plugin has a worked example of a settings page living with the plugin that owns the namespace.
- Key abstractions: registration targets `plugins.bundle.config` / `plugins.row.config` (community) and `plugins.item` (built-in); `ctx.settingsScope`; the registration rule `settingsScope.whileServed(namespaces, register)`; the `ui-primitives` form kit (`SettingsFormModel`, `settingsNumberField`, `settingsTextField`, `SettingsValueField`, `SettingsSecretField`, `SettingsForm`).
- Data flow: the Host begins serving a namespace → the shared describe mirror changes → `whileServed` runs the companion's registration → the page appears in the Plugins page's Official group → the page reads and writes through `ctx.settingsScope` → when no namespace is served the registration is disposed and the page disappears. Four packages therefore share one rule instead of four copies.
- Non-obvious design decisions: moving each page into the Host package that registers its namespace was rejected — the shell namespace is registered by the executor families under the sandbox row, the loop package would gain a browser build for one number field, and the Subagent namespaces come from a subpath row that carries no browser half (line 10). Host packages stay free of browser code, and the namespace a page edits is spelled as a literal and never imported from the owner (line 16). The form frame takes its copy as `labels` and the model a structural scope, so the baseline package depends on neither a plugin nor its dictionary (line 18).
- Edge cases / failure handling: a schema-driven generic form was rejected because it "covers scalar fields and stops at the first dynamic control" — the Subagent page's live model catalogue, its cross-field rule, its one-mutation save — so every exception would become a role the schema was never for (line 26). A single shared dictionary for the frame's copy was rejected because it would couple every page to another plugin's dictionary keys; each page's dictionary carries the few frame strings (line 30).
- Surprising: `subject.id` on an official page became a discriminator that `plugins.detail.*` contributions key on, so the shell page's id changed from `bash` to `shell` — the id now names the capability the page edits rather than one executor family (line 37).

### .agents/notes/archived/architecture/2026-09-17-shared-office-runtime.md

- Purpose: Let SDK and container deployments use the same Office authoring libraries as Desktop without depending on Desktop's application packaging and signing code.
- Key abstractions: `tool-workspace-dependencies` (manifest validation, interpreter paths, installation, the model query); the shared build entry `scripts/primary-runtime/prepare.ts` (download lock, extraction, native smoke checks); the `runtime.json` manifest (Python / Node.js / pnpm versions at the top level, all Python distribution versions in `pythonPackages`); `payloadDigest`.
- Data flow: the shared build entry downloads and extracts the locked payload for Desktop targets and GNU/Linux x64/ARM64 → `runtime.json` records the versions → the wheel carries target-native CPython, Office libraries and external skills in a sibling `<platform>-<arch>/` resource directory → `tool-workspace-dependencies` installs or reads it in place and answers the model query → the packaged SDK profile enables the query and the Office skills from its carrier default, with `DSH_PRIMARY_RUNTIME` overriding the path and an empty string opting out.
- Non-obvious design decisions: the package stays in the skill group beside its Office workflow consumer and exposes no workspace entity service — the payload supplies the workflows, the package exposes only the query (line 14). The shared parser accepts legacy `components` files without rewriting them, retains their consistency checks and returns only the canonical flat fields, and rejects mixed formats (line 20). Short platform directory names leave room for Python extension and dependency DLL paths after Windows installation (line 22).
- Edge cases / failure handling: successful tool preparation is shared by concurrent calls for one plugin lifetime; failed preparation is retryable; disposal removes registration and waits for outstanding filesystem work; copy mode verifies a staged replacement and restores the preceding installation after a failed publication, while in-place mode performs no payload writes (line 36). Missing Office resources produce a startup warning and leave the optional skill provider inactive, and runtime metadata and interpreter availability are validated on the first tool call (line 38). SDK configuration changes require a restart; musl builds remain outside the lock (line 38).
- Surprising: real filesystem resources rather than startup extraction let Python load native extensions and let skills invoke their shared checker, and the wheel simply grows by the compressed payload size (line 22) — an explicit trade of install size for zero extraction cost.

### .agents/notes/archived/architecture/2026-09-17-web-feature-routes-and-route-gate.md

- Purpose: Make feature-owned browser routes work under any mount prefix, and stop new code from re-binding the bundle to one mount.
- Key abstractions: the `*_PATH` (absolute registration key) / `*_ROUTE` (document-relative browser form) duality for `OPEN_IN_APP_*`, `PRESENT_*`, `CHANGED_FILES_PATH`, `CHANGES_*`, `SESSION_LOG_EXPORT_PATH` and `FILE_UPLOAD_PATH`; `document.baseURI` resolution; Fetch-shaped carriers (`FileUploadFetch`, `RpcFetch`) that resolve a relative route against their own base; the static gate `verify-client-route-resolution`.
- Data flow: a feature producer keeps its absolute registration key and derives the browser form beside it → browser code addresses only the `*_ROUTE` form → the page-installed carrier receives that relative route and resolves it against its own base → the two consumers that genuinely need an absolute URL (the upload worker, whose own base is a `blob:` URL, and the markdown image vocabulary) resolve against `document.baseURI` instead.
- Non-obvious design decisions: banning every `location` read in browser code was rejected because identity comparisons, the preview's own query read and the worker tunnel's host-relative mapping are all legitimate — the gate governs request targets, which is where a mount-bound route actually appears (line 22). Rewriting feature responses in the proxy was rejected because it duplicates the mount in deployment configuration for every route the proxy does not know about (line 24). The same pass also checks the Host producers of browser references: a `url`, `src` or `href` field stamped with a root-absolute app route is rejected, while route keys and response-table keys stay absolute and out of scope (line 18).
- Edge cases / failure handling: the gate reads inline literal fragments only, so a composed reference (`comboReference(...)`, `artifact.url.slice(1)`) is not traced, and that regression signal is owned by `packages/client/modules/tests/node-half.client.spec.ts` (line 28). The gate's own spec pins a negative control per rule — interpolated targets (`${origin}/api/file`), protocol-relative and absolute forms, an unstripped shared `*_PATH` key, a relative route resolved against a `location` read, root-absolute producer fields (line 32).
- Surprising: preview pages do not expose their worker's file API at the document URL, so markdown local-file image URLs cannot reach that Host — a consequence that forced the image vocabulary to be absolute-only (line 28).

### .agents/notes/archived/architecture/2026-09-18-chat-navigation-performance.md

- Purpose: Bound the three independent costs of a long session — one DOM mark per known turn, rediscovery of an already-known landing, and one publication per fetched page — without virtualizing the transcript itself.
- Key abstractions: `TurnNavigator` (TanStack React Virtual, fixed 10px pitch); `ChatViewport` (DOM reads, clamped writes, native events, turn anchors); `ChatReading` (follow-tail policy, semantic restoration, sampled reader movement); `ChatNavigation` (loaded/unloaded jumps, paging anchors, replacement tasks, fallback); `useChatScroll` (committed inputs and coordination); `Session.loadThrough` (accepted-page buffer plus a private paging cursor).
- Data flow: a jump request → `ChatNavigation` retains accepted pages in a private buffer until the shared target is covered or loading ends → the page list is reversed once and flattened once → one ordered prepend is published, while live events continue through their normal publication path → `ChatViewport` returns the actual landing together with available turn and semantic-position facts → the reading policy consumes those facts with no second hit test.
- Non-obvious design decisions: the rail's offset calculation clamps against cached geometry and invokes the supported `scrollBy`, deliberately avoiding the library's DOM-based maximum-offset calculation used by `scrollToIndex` (line 18). Timer and animation-frame completion invoke the owners directly instead of incrementing React tick state (line 24). A later page failure publishes the successful prefix once, and stream or window replacement discards obsolete buffered pages; single-page `loadOlder` stays immediate and repeated jump requests keep the existing lowest-target policy (line 30).
- Edge cases / failure handling: the note states exactly what was **not** eliminated — main-transcript geometry reads, semantic-anchor queries, ordinary native-scroll metrics, final layout, center-width reflow during Sidebar animation, possible repaints on transform/color change, and the native scroll event that assigning `scrollTop` may still deliver (line 60). The viewport ignores its own unchanged scroll echoes and events from the nested rail (line 22). Only the visible range, overscan and the focused mark with its neighbours stay mounted; the full turn metadata remains resident, so this is rail virtualization, not transcript virtualization (line 16).
- Surprising: the work model is stated as work-count estimates and not as timings — 10,000 turns with about 50 mounted marks imply roughly 99.5% fewer rail marks, "not a 200× end-to-end speedup", and 20 equal pages go from `210B` aggregate entry visits to `20B` while the page requests stay 20 (line 46). The heading is "Theoretical work model" for exactly that reason (line 32).

### .agents/notes/archived/architecture/2026-09-18-localized-package-metadata.md

- Purpose: Give installed, subpath and disabled plugins readable titles and descriptions without activating them and without keeping built-in copy inside Plugin Manager.
- Key abstractions: optional `meta.title` / `meta.description` in `locale/<language>.json`; Node module resolution through the applicable profile and package exports (`my-plugins/locale/en.json`, `my-plugins/search/locale/en.json`); the English resource as the discovery anchor with sibling language filenames discovered from the same directory; a per-field fallback chain; `<plugin specifier>/icon` under the same address rule.
- Data flow: the Host reads installed bundles and their declared plugin rows **without importing or activating them** → Node module resolution selects the locale file through package exports, evaluating no plugin code → the Host resolves `en.json`, discovers the sibling language filenames, and resolves each with the same plugin specifier and parent URL → the Remote carries multilingual values or literal fallback text for the two display fields → the Client reuses its existing language selection and fallback chain at render time, with no new language registration or second fallback policy.
- Non-obvious design decisions: locale addresses are **not** derived from a resolved JavaScript filename or an owning package directory, because build tools can put several plugin entries in one directory and resource exports preserve each plugin's identity independently of the compiled layout (line 33, and the rejected alternative at line 70). A subpath plugin is not a package: it never reads a `package.json`, even one exported at its address, and does not inherit its owning package's introduction (line 46, alternative at line 68). File paths and file URLs, including Windows drive and UNC paths, skip resource resolution and return no metadata — "a file address alone is not a metadata error" (line 33).
- Edge cases / failure handling: present locale display fields must be non-empty strings; language identifiers are case-insensitive and duplicates are rejected; any language may omit either display field (line 35). Missing resources or missing fields fall back independently per field, while invalid locale fields or malformed files report a diagnostic instead of silently falling back, retaining the management operations (line 46). Metadata errors stay per-plugin diagnostics and never remove the manager's repair controls (line 92).
- Surprising: display metadata is read **per request with no metadata cache**, because the lookup has to retain the complete module specifier and its resolution parent — package-name-only caching cannot distinguish exported plugins or different installations (line 92). The Install view still uses registry information from `pnpm view` and never substitutes locale metadata, and pre-install registry/Git/tarball inspection does not read remote package contents for translation (line 54).

### .agents/notes/archived/architecture/2026-09-18-profile-plugin-host-runtime-instances.md

- Purpose: Stop out-of-tree profile plugins from loading a second copy of a host runtime whose identity is compared by module-local state, which had put Agent #1's MCP tools into the process-global layer and rejected Agent #2's creation (issue #4573).
- Key abstractions: the peer-vs-dependency declaration rule; profile pnpm settings `nodeLinker: hoisted` with `autoInstallPeers: false`; the runtime-resolution interception layer at `$DSH_HOME/profiles/node_modules`; `dsh-scope` (`createScope` as the writer; `scopeOf`, `carrierKeyOf`, `scopeTarget` as the readers); `dsh-mcp-client`'s module-local `serverName` reservation table; `verify-package-dependencies` and its `peerRequiredHostExports` table.
- Data flow: a profile installs a plugin out of tree → the plugin resolves bare specifiers along the ancestor `node_modules` chain → the profile's own layer sits **above** the interception layer → a `dependencies` edge hands the plugin its own copy of every package it reaches → that copy's `createScope` writes a module-local `Symbol('dsh.scope')` tag the installation's `scopeOf` cannot read → the registration meant for one Agent lands in the process-global layer → the second Agent's tool synchronization collides → `failOnStartupError: true` turns the collision into a rejected Agent creation.
- Non-obvious design decisions: a host runtime whose cross-instance identity matters is declared in `peerDependencies` and `devDependencies`, **never** in `dependencies`, so the peer is not installed into the profile and the import reaches the installation's single instance (line 16). The rule covers the **writer** as well as the readers — `createScope` is included because "the writer mints the tag its readers compare" (line 18). Making the tag a `Symbol.for` was rejected: it fixes the tag lookup alone, while scope parents and event-carrier keys stay per copy, giving "a smaller visible failure with a more confusing cause" and keeping the duplicate the profile never needed (line 28).
- Edge cases / failure handling: matching the profile's package versions to the Host's does not help, because equal versions still load two module instances from two directories (line 30). The rule makes the plugin depend on the installation shipping the peer; a plugin outside the installation's closure fails to load rather than starting with a second copy (line 35). An already-installed profile keeps its copies until the plugin dependency is upgraded and reinstalled, and no Host-side change can repair it (line 34).
- Surprising: three sibling experimental providers still declare `dsh-mcp-client` as a *dependency*, so hoisting places a copy above the interception layer and this package's peer resolves to it — the scope split does not return (none of them declares `dsh-scope`), but the `serverName` reservations split; tracked as issue #4628, and the note names the gate's package selection as the open coverage gap (lines 37-38).

### .agents/notes/archived/architecture/2026-09-19-lossless-projection-checkpoint-json.md

- Purpose: Make reopening a projection checkpoint yield the same state as replaying the session log, when the checkpoint contains opaque extension data.
- Key abstractions: the existing `isJsonValue` predicate from `dsh-util-values`; the checkpoint writer's `snapshotJsonValue`; `StorageDomain` table values as immutable borrowed records; the projection's `stateSchema` as the owner of its hydration value.
- Data flow: the writer snapshots a JSON value that may legitimately contain a key named `__proto__` → the reader validates with `isJsonValue`, which enforces the same lossless rules without rebuilding valid objects → the domain returns the stored value with every own key intact, including nested `__proto__` and `constructor` → the projection hydrates through its own `stateSchema`.
- Non-obvious design decisions: `z.json()` was rejected because "its object reconstruction removes valid own keys, so a successful validation can still change the checkpoint value" (line 18) — a validator that mutates the thing it validates. Validating and cloning with `snapshotJsonValue` was rejected too: it preserves the keys but copies already-immutable stored values, and the read-only predicate matches the storage-domain borrowed-value contract (line 19).
- Edge cases / failure handling: validation still rejects non-JSON and lossy values; the borrowed-value validator supplies no defensive-copy guarantee, and opaque fields must use validation that preserves their keys (line 23). The domain version is unchanged because the stored JSON representation is unchanged — this corrects the reader, not the format (line 25).
- Surprising: the whole fix is a reader swap with no format change, and the regression coverage opens a synthetic fixture produced by the **real writer**, then writes, closes and reopens it through `StorageDomain` (line 25) — the round trip is the test.

### .agents/notes/archived/architecture/2026-09-21-creator-skills-progressive-disclosure.md

- Purpose: Keep the creator skills inside the tool-result pruner budget and stop the skill text from being the only knowledge source.
- Key abstractions: `SKILL.md` holding only the procedure, the knowledge-source order and an index table; `references/` for recipes; `templates/` for copyable bundles; the skill base directory the `skill` tool already reports; `cordis_inspect_query`; `Config.listConfigs`'s resolved `packageDir`; `DSH_PROFILE` and `DSH_PROFILE_DIR` as reserved shell built-ins; the `doc-sync` freshness gate for a generated composition reference.

## Ideas worth stealing

- **An extension point is a slot list the owner also uses** — `.agents/notes/archived/architecture/2026-09-17-session-row-menu-actions-slot.md:14` — `ui-workspace` declares `sidebar.workspaces.session.menu.item` and `sidebar.workspaces.session.row.action` and registers its *own* `pin`/`rename`/`fork`/`archive` actions into them at orders 100/200/300/400, so a plugin lands "wherever its order says" and reusing a shipped id at another `priority` shadows it through ordinary registry cell rules; there is no privileged owner group (a group start is the entry's own `separatorBefore`). Transfers to August: any UI list a user might want to extend should be one ordered slot list with the shipped items *in* it, not a shipped list plus an append-only extension area — that removes the second rendering path and the "extension group" special case.

- **The owner hands over state, not verbs** — `.agents/notes/archived/architecture/2026-09-17-session-row-menu-actions-slot.md:16` — an entry receives only `{ sessionId, displayTitle }` and reads the Host state it needs through hooks its *own* registration injects (`usePinned`/`useArchived`, Sets derived once per Workspace snapshot); the behaviour lives in the registration's `inject` face, so the component calls exactly one callback, and `pinSession` reads the object-layer snapshots once at completion instead of subscribing to the whole Session list. Transfers to August: an extension should own its own behaviour and read shared state through injected selectors, otherwise every extension re-renders every row (the rejected alternative is spelled out at line 30).

- **Progressive disclosure with the pruner threshold as a gate** — `.agents/notes/archived/architecture/2026-09-21-creator-skills-progressive-disclosure.md:14` — the skill had exceeded the 8192-char threshold at which the preset's tool-result pruner keeps only head and tail, so `SKILL.md` keeps procedure + index, recipes move to `references/`, bundles to `templates/`, and **a test keeps the leading file under the pruner head and checks every referenced file exists and every template parses**. Transfers to August: August already truncates tool results (`maxToolResultChars` per model); the missing piece is the mirror-image gate — a check that a shipped skill/prompt file stays inside the truncation budget and that every referenced artefact resolves, so the head/tail truncation never silently eats the middle of a skill.

- **Ordered knowledge sources instead of forbidden ones** — `.agents/notes/archived/architecture/2026-09-21-creator-skills-progressive-disclosure.md:16` — the skills no longer ban reading package sources; the order is inspect (`cordis_inspect_query`) → the package README under the `packageDir` `Config.listConfigs` resolves → built `lib/` declarations or checkout sources, with bundled packages resolving from the installation and profile-installed ones from the profile, plus `DSH_PROFILE`/`DSH_PROFILE_DIR` as reserved shell built-ins. Transfers to August: "read the source instead of restating it in the prompt" is a context-budget win, and it needs the *path* to be derivable at runtime (a registry lookup), not guessed from a directory name.

- **Peer-dependency rule for cross-instance identity** — `.agents/notes/archived/architecture/2026-09-18-profile-plugin-host-runtime-instances.md:16` — a host runtime whose identity is compared across copies goes in `peerDependencies`/`devDependencies`, never `dependencies`; with `nodeLinker: hoisted` + `autoInstallPeers: false` the peer is not installed into the profile and the import reaches the installation's single instance through the interception layer. Line 18 extends the rule to the **writer** ("the writer mints the tag its readers compare"), and line 28 records why `Symbol.for` is not a fix — it repairs the tag lookup while scope parents and carrier keys stay per copy. Transfers to August: any mechanism that loads third-party code into the same process (plugins, MCP servers, skill runtimes) must guarantee single-instance for modules holding identity state; the failure mode (a per-Agent registration silently landing in a global layer, then an Agent rejected at startup) is invisible until two agents exist.

- **Publish once, buffer the rest** — `.agents/notes/archived/architecture/2026-09-18-chat-navigation-performance.md:30` — `Session.loadThrough` retains accepted pages and a private paging cursor until the shared target is covered or loading ends, reverses the page list and flattens it **once**, and publishes one ordered prepend; a later page failure publishes the successful prefix once, and stream or window replacement discards obsolete buffered pages. Transfers to August: the same shape applies to any batched append into the transcript (history paging, compaction output, a tool that returns many records) — incremental publication multiplies the rebuild cost, because each intermediate publication re-derives growing indexes.

- **State the work model, and refuse to over-claim it** — `.agents/notes/archived/architecture/2026-09-18-chat-navigation-performance.md:34` — the note tabulates previous vs current work with named variables (`T`, `V`, `P`, `B`, `W0`), explicitly labels the table "work-count estimates, not timing measurements" (line 34), and states that 10,000 turns with ~50 mounted marks imply ~99.5% fewer rail marks, "not a 200× end-to-end speedup" (line 46); line 60 lists what was *not* eliminated. Transfers to August: when a performance note claims a win, the same table plus the residual-cost list is the format that survives review — and it is exactly the discipline August's own docs already apply to its file-size ceilings.

- **A validator that mutates the value it validates** — `.agents/notes/archived/architecture/2026-09-19-lossless-projection-checkpoint-json.md:14` — `z.json()` rebuilds objects and drops a valid own `__proto__` key, so a *successful* validation could change the checkpoint and reopening it would differ from replaying the log; the fix is the existing read-only `isJsonValue` predicate, and the alternative of validating-and-cloning was rejected because it copies already-immutable borrowed values. Transfers to August: any schema gate standing between a persisted artifact and a re-read must be checked for round-trip fidelity — validate without rebuilding, and prove it by writing/closing/reopening a fixture the real writer produced.

- **Mount-independent addressing, enforced by a static gate** — `.agents/notes/archived/architecture/2026-09-17-web-feature-routes-and-route-gate.md:18` — every route keeps an absolute `*_PATH` registration key and derives a document-relative `*_ROUTE` for the browser; `verify-client-route-resolution` runs in `hygiene` and CI over every browser source and rejects root-absolute, protocol-relative and absolute app routes in request targets (request constructor, fetch-shaped call, dynamic import; assigned resource properties; JSX `src`/`href`), plus relative app routes resolved against a `location` read, and separately checks Host producers stamping a root-absolute `url`/`src`/`href`. Line 28 states the limit — inline literal fragments only, so composed references are untraced and owned by another spec. Transfers to August: the pattern is "one mount-relative rule + a gate that fails the build", and the stated blind spot with a named second owner is the part worth copying.

- **Read the live registry, not a dump** — `.agents/notes/archived/architecture/2026-09-21-live-config-inspect-provider.md:14` — `Config.listConfigs` walks `ctx.loader.entries()` and each fiber's runtime Config and projects the mounted plugin's native Config into one self-contained JSON Schema, with inactive entries reporting `inactive` and no schema; the boot-free collector is deliberately not re-run because a running profile already holds the module-resolution interception that the collector installs and forbids overlapping (line 16), and teaching the skill to shell out to the CLI dump was rejected because the session guarantees neither the profile name nor `dsh` on PATH (line 22). Transfers to August: this is the same shape as August's `check:brain-config` (ask the backend which keys it accepts) generalised — the schema an agent writes against should be the running system's, read through an inspect tool, not a static document that can drift.

- **Give the model a sampled now, as a durable message** — `.agents/notes/archived/architecture/2026-09-24-web-default-schedule-composition.md:18` — `time-context` appends one durable user message per eligible step carrying the sampled instant, the browser zone attached to the open request, and the elapsed time since the preceding model-visible message; the sampled instant is precisely what lets the model turn "tomorrow at nine" into an offset-bearing `at` value, and the reading replays, compacts and appears in exported session logs like any other user message. Transfers to August: an agent that must reason about time should be handed a clock reading inside the transcript rather than be expected to guess or to be handed a fixed string in the system prompt; the cost is stated honestly (line 36 — every session pays four extra tool schemas and one message per step).

- **Enforce the context budget where the truncation happens** — `.agents/notes/archived/architecture/2026-09-24-web-default-schedule-composition.md:39` — once the preset table grew past the base composition's 12,500-token inline budget, the spill policy was changed to keep the answer's head and tail plus a spill path instead of the complete JSON. Transfers to August: August already truncates tool results per model profile; the transferable piece is the *spill path* — a truncated answer that tells the model where the rest lives beats a truncated answer that looks complete.

- **Read metadata without executing the plugin** — `.agents/notes/archived/architecture/2026-09-18-localized-package-metadata.md:25` — the Host resolves `locale/en.json` through Node package exports *without evaluating plugin code*, so disabled, client-less and failed plugins still have readable titles; file paths and file URLs (including Windows drive and UNC) skip resolution and return no metadata, and "a file address alone is not a metadata error" (line 33). Transfers to August: metadata for an extension must be obtainable without loading the extension — that is what makes a disabled or broken plugin still listable, and it is the difference between a manager that can repair itself and one that cannot.

- **A bilingual pair as a hash-pinned, frozen artifact** — `.agents/notes/archived/architecture/2026-09-17-settings-pages-as-companion-packages.i18n.yaml:1` — every document is a triplet (`.md`, `.zh.md`, `.i18n.yaml`) whose sidecar records the git blob hash of each side "as of the last confirmed-consistent state", re-recorded with `pnpm run verify-translation-pairing --write <pair>`, and archived triplets are frozen and sealed by their own verifier. Transfers to August: the mechanism (not necessarily the Chinese) is a *reviewable act of confirmation* — a hash diff proves two artifacts are in sync, and the archive rule ("do not treat it as authority for current behavior") stops a frozen decision record from being read as live behaviour.
