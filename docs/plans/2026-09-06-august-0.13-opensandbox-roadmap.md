> **The title said "August 0.13" and the tree is 0.18.18** (`package.json` at

Date: 2026-09-06 · Status: DRAFT (the three candidate workstreams are still unbuilt; their *problem statements* are corrected below) · Continues the OpenSandbox study from the 0.12.21 batch

The 0.12.21 batch landed two real wins from the OpenSandbox study: a Docker-backed `run_command` execution tier (`app/services/sandbox/backends/container.py`, opt-in via `AUGUST_CONTAINER_SANDBOX=1`) and an enforced egress filter that turns `network: false` into a real policy (`app/services/sandbox/egress.py`, loopback CONNECT/absolute-HTTP proxy with a 403 deny). This doc tracks the next three architectural candidates — each is its own multi-session feature, not a rider.

## §1 Credential broker (priority 1 — security, especially Bot Mode)

**The problem.** ~~Provider keys, model-API keys, and the user's third-party tokens (GitHub PAT, Slack bot token, Google OAuth refresh) all live in `data/providers.json` and other JSON files that the model can read via `read_file` and exfiltrate via `run_command`.~~ **That is FALSE as of the current tree: the model can no longer read them.** The credential-read path is closed outright — `backend-py/app/services/sandbox/hardline.py:17-19` states it in the module docstring: *"READS of credential files (private keys, `.aws/credentials`, `providers.json`, any `.pem`/`.key`) are blocked outright"*, and credential STORES are blocked by directory, read and write alike (`:20-26`). On top of that, the data directory's own `config.json` — which carries `serviceConnections.github.token` and a Google `accessToken` — is refused by absolute path (`hardline.py:253-264`, `_august_secret_files`). And the outbound body is scrubbed at the **transport**, not in a serializer: `BaseProviderClient.wireBody(body)` (`backend-py/app/providers/clients/base.py:399-427`) calls `scrubOutboundBody` on every body that goes to a provider, so a key that rode into the transcript once is replaced before it is re-sent.

**What is actually left of this problem.** The hardline rules are a *path* policy: they refuse named stores and directories. What a credential broker would still add is a *capability* door — the model never holds a secret at all, it asks the broker to make the call — which is a stronger guarantee than "the model may not read this particular file", because it survives a path the rules do not know about, and it gives the user a place to see "secure_call to api.github.com was made from agent X". The exfiltration path is also not fully closed: a secret the *user* pastes into the conversation is not a file the hardline can refuse, and the outbound scrub is what removes it again. So the broker's value is real but narrower than this paragraph claimed: **the model cannot read the credential stores; what it cannot do is hold a credential at all.** Two premises need re-checking against current sandbox policy before starting §1 — the tier set is container/seatbelt/bwrap/AppContainer only, and a tier was deliberately removed from this tree once already.

The credential broker flips the contract: the model never holds secrets, it only asks the broker to make calls.

**The shape.** A local policy proxy listening on loopback, exactly like the egress filter, but for *outbound* credentialed calls. The model invokes something like `secure_call(target="api.github.com", method="GET", path="/repos/foo/bar")`; the broker attaches the matching token from the user's vault, forwards the request, returns the response. The tool layer (or a thin Python SDK in `code` mode) holds the broker URL, and the broker is the only thing that ever touches `data/providers.json`'s secret fields.

**What it replaces.** `connect_github` / `connect_slack` / `connect_google` / `install_mcp_server` become the bridge-side that hands the broker the user's token; the model never sees it. Bot Mode especially benefits — bots run unattended with tools, so the blast radius of a key exfil is much larger than for the main session.

**Why this is the next big one.** The 0.12.21 batch made isolation real (container + egress). This makes *the model itself* unable to leak the thing that isolation is supposed to protect. Without it, every other security improvement is one clever prompt away from being bypassed.

**Composition note.** Same proxy pattern as the egress filter, same env-injection seam in `agent_subprocess_kwargs`. Reuses the credential-scrubbing regex in `noninteractive_env`. The container tier's `--network none` already denies the model any direct path to the network for sandboxed commands, so the broker is the *only* authorized egress — that gives it the natural choke point.

**Scope estimate.** A dedicated plan doc per workstream (broker protocol, vault schema, per-tool integration, observability for the user to see "secure_call to api.github.com was made from agent X"). Each is its own session or two. Out of scope for one batch.

## §2 Stateful code interpreter for `code` mode (priority 2 — productivity)

**The problem.** ~~`code` mode spawns a fresh interpreter per fenced block. No persistent state across cells,~~ **the "no persistent state" half is FALSE: persistent state SHIPPED.** Each cell restores the previous cell's variables before it runs and snapshots them back afterwards — `backend-py/app/services/workbench/code_runner.py:331-344` (`_RESTORE_HEAD`, "August kernel: restore persistent variables from the previous code run") and `:350-383` (`_SNAPSHOT_TAIL`, which pickles every user variable independently, per-variable and total caps, skipping anything unpicklable or oversized and pruning deleted variables).

**What is still missing** is the other half of the original sentence: there is no rich output capture (no dataframe/image/matplotlib rendering out of a cell — a grep for `matplotlib`, `dataframe` and friends in `code_runner.py` returns nothing) and no multi-language kernels (Python only; no Node/Bash kernel). The venv path that used to back it was deleted during the dead-code sweep. EDA and data work in particular have to either inline everything in one block or stuff state into files — the *state* half of that is fixed, the *output* half is not.

**The shape.** Back `code` mode onto OpenSandbox's code-interpreter image (Python + Node + Bash kernels, persistent state, rich output capture). Three surface options: (a) ship a small local executor that talks to a uvx-managed interpreter, (b) reuse the container backend with a developer image that has the kernels installed, (c) integrate with the user's existing Jupyter server. Each is its own plan doc.

**What it enables.** Real exploratory data analysis (pandas output tables, matplotlib charts), persistent variables across cells, file-creation side effects captured in the workspace, and a path for the circuit/EDA toolchain to share one execution environment. The `kernel.bridge_call` path in `workbench/kernel.py` is the right integration point.

**Scope estimate.** A self-contained interpreter service, a transport layer (the existing async tool path), a `code` mode UX update that surfaces cell output, and tests around persistence + multi-language. Multi-session.

## §3 Isolated browser + VNC takeover (priority 3 — quality-of-life)

**The problem.** ~~August's browser automation drives the user's *real* browser.~~ **That is FALSE: the browser is a HEADLESS Chromium with a fresh context, so the user's profile is never involved.** `backend-py/app/services/browser/session_manager.py:177-196` launches with `headless=True` and then `browser.new_context(...)` — a new, empty context per session; there is no `user_data_dir` and no `launch_persistent_context` anywhere in `backend-py/app/services/browser/`. The user's cookies and saved passwords are therefore never in scope, and there is nothing to "drop the user back into".

The login-wall flow (`_detectLoginWall` in `browser/handlers.py:180` → ActionNeededCard → "Take over") exists, but **"Take over" does not hand the user their own browser either** — it only focuses the agent's own panel: `frontend/desktop/src/components/chat/ActionNeededCard.tsx:54-58` calls `addRightDrawerSection('browser')`. There is no VNC, no second browser, and no profile mixing anywhere in the product.

**The real gap is the one the takeover was papering over: logins do not survive.** Because the context is fresh every session, a site that needs a login needs one every time, and the user cannot fix that by logging in once in their own browser. That gap is **Part 23's B-2** (persistent browser profile) — `docs/plans/2026-09-04-part23-control-plane.md` — which is where it is tracked, not here. What is left for THIS section is the isolation/takeover mechanism: a per-session browser the user can drive, so "take over" means something, and so two sessions cannot contaminate each other.

**The shape.** A separate Chromium instance per session, run in a container with VNC + DevTools. The agent's automation is fully isolated (no shared cookies with the user's actual profile). "Take over" opens a VNC view of the isolated browser — the user sees and drives the agent's session, not their own. Handoff back is a click, the agent resumes with cookies intact.

**What it enables.** Multi-tenant browser safety (two sessions, two isolated browsers, no cross-contamination), live takeover without profile mixing, and a credible path to a "sandboxed browsing" security model that competes with OpenSandbox's chrome/desktop pattern.

**Scope estimate.** VNC + a container image with Chromium + DevTools, a frontend takeover panel (probably a new tab in the existing right-rail), and a session-bind layer that maps one workbench session to one isolated browser. Multi-session, with at least one interim checkpoint for the VNC UX.

## §4 Daemon TTLs (already shipped 2026-09-06)

`app/services/daemon_manager.py` now stamps every spawned daemon with `expires_at = now + AUGUST_DAEMON_TTL_S` (default 3600s) and runs a 60-second reaper that kills any expired daemon. The `list_daemons` tool reports `expires_in_s`. The model's own "daemons outlive my turn" complaint is structurally addressed — the leak now self-clears in at most TTL+60s.
