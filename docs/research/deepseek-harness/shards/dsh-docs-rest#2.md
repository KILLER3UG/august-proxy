# deepseek-harness / dsh-docs-rest#2

## Shard shape

This shard is the **documentation floor** of the DeepSeek Harness: 164 files, every one of them under `docs/`. It holds no executable code — it holds the *contracts* the code is supposed to keep, in four families.

- **12 top-level pages + their 12 Chinese mirrors** (`docs/*.md`, `docs/*.zh.md`): the tool-catalog, the tool-execution-pipeline graph, the persistence catalog, the session-format status, the testing policy, the vendor rescope map, and the two UI style standards (`ui-radius`, `web-styling`). Three of these are *generated* (`tool-catalog`, `persistence-catalog`, `persistence-schema.json`) and one is a *Mermaid graph* generated by `scripts/gen-doc-graphs.ts`.
- **4 postmortems + index** (`docs/postmortem/0001…0004`), the highest-value prose in the shard: four real production defects, each written up as "what broke, what mechanism, why every safety net missed it, what guardrail was added".
- **42 upgrade guides × 3 files** (`docs/upgrade-guide/<version>/<slug>/guide.md` + `.zh.md` + `.i18n.yaml`), covering releases v0.1.7-rc.2 through v0.2.1-alpha.4. Each guide is a *behavioural-change contract* with a `## Change` section and a numbered `## Migration`.
- **54 `.i18n.yaml` bilingual-pair records**, the per-heading EN/ZH content hashes that keep the English and Chinese halves of every doc in lockstep.

How they fit together: the **generated catalogs** (tool + persistence) are the machine-checkable statement of *what the model is offered* and *what the session log is allowed to contain*; the **postmortems** are the retrospective statement of *how the process failed*; the **upgrade guides** are the forward statement of *what changes for the user*; and the **testing policy** is the meta-rule that ties them together ("line coverage is necessary, never sufficient" — `docs/testing.md:10`). The `.i18n.yaml` layer is the glue: it is a content hash per heading section, so a translation that drifts from its source is a *gate failure*, not a review comment.

## Per-file notes

### docs/tool-execution-pipeline.md
- **Purpose:** the single authoritative picture of where policy, hooks, sandboxing, filesystem guards, result rewriting and UI rendering run in a tool call — "without changing the loop".
- **Key abstractions:** three *waterfalls* (`tools/pre-execute`, `tools/execute`, `tools/post-execute`), a set of **registered monotonic guards** (deny or abstain; identity protected), `ctx.approval` (one-shot prompt), `ToolDefinition.projectContent` / `ToolDefinition.finalizeContent`, and the `tools/result` notification.
- **Data flow:** assistant tool-call block → `tool/call` session event (logged *before* execution) → UI pending card → pre-execute waterfall → monotonic guards → (ask → `ctx.approval`) → execute waterfall (timeout, retry, metrics *around* dispatch) → registered tool `execute()` body → `fs/write-intent`/`fs/edit-intent` gate (tool-fs mutations only) → tool-owned events (`todo/write`, `fs/observed`, `hook/invoked`, `hook/result`, `tool/ptc-dispatch`) → `projectContent` → post-execute waterfall (accept/block/replace/add context) → registry outer normalization → `finalizeContent` → `tools/result` (frozen authoritative outcome) → `tool/result` session event → batch settles → additionalContexts FIFO injected as `user/message` *after* the recorded tool results.
- **Non-obvious design decisions:** the registry takes a **lossless snapshot of the candidate result** and normalizes a snapshot failure into `isError` *before* the visible definition's snapshotted `finalizeContent` runs (`docs/tool-execution-pipeline.md:63`) — so a "content-only invariant" can never see a half-built result. `ctx.approval` resolves *asks* *before* the monotonic guards, while policy that must not be reordered stays a registered guard — two different mechanisms for "may be refused" (`docs/tool-execution-pipeline.md:63`).
- **Edge cases / failure handling:** every stage may `throw`, and all four throw paths (pre, guard, around-wrapper, post) funnel into the same normalization node, so a throwing waterfall still yields an `isError` result rather than an unhandled rejection. `approval` is denied when the approver is "absent or unanswerable" — fail-closed.
- **Surprising:** PTC mode sends *both* the reserved `run_code` transport and its serialized sub-calls through the same pipeline; sub-calls carry the parent token, log `tool/ptc-dispatch`, return denials as binding rejections, and **omit `additionalContexts` to preserve call/result adjacency** (`docs/tool-execution-pipeline.md:63`). A tool that injects extra context during a nested PTC call would break the adjacency a reader relies on.

### docs/tool-catalog.md
- **Purpose:** every model-facing tool a shipped plugin contributes to `ctx.tools` — the `name`, `description` and exact JSON-Schema `parameters` the model receives through system-prompt assembly.
- **Key abstractions:** the **Tool Package Map** (tool package → model-visible names → required services → events written → shipped aliases → deployment note) and one section per package with each tool's schema.
- **Data flow:** a *generator* boots each tool plugin on a real Cordis context and reads `ctx.tools.schemas()`; the result is a markdown catalog verified fresh by `pnpm run verify-tool-catalog` (part of `doc-sync`).
- **Non-obvious design decisions:** a tool schema is **not statically knowable** — runtime-spread enums, concatenated descriptions, config-driven names, raw-JSON-Schema MCP tools — so the generator BOOTS the plugin rather than parsing the AST as the Cordis catalog does (`docs/tool-catalog.md:8`). A **completeness guard globs `packages/*/tool-*` and fails if any package is missing from the boot manifest**, so a new tool cannot be silently undocumented (`docs/tool-catalog.md:8`).
- **Edge cases / failure handling:** a `Config` field that is *required with no default* forces the generator to choose a branch, and the per-package note records which branch the page shows (`allowParallelInProgress: true` for `todo_write` is the explicit case, `docs/tool-catalog.md:2609`). The registered tool **name can itself be load-time config** (`tool-subagent`'s `toolName`), so a deployment may expose a package under a different name — the catalog records the shipped aliases (`subagent`, `subagent_fork`, `docs/tool-catalog.md:41`).
- **Surprising:** the schemas carry *operational* instructions inside property descriptions — `bash` says "Provide `description` before `command` in the arguments" (`docs/tool-catalog.md:654`), `write` says "Provide `file_path` before `content`" (`docs/tool-catalog.md:1096`), `edit` says "Provide `file_path` before `old_string` and `new_string`" (`docs/tool-catalog.md:1011`). That is a *prompt-prefix-stability* instruction smuggled into the schema, so the serialized tool call keeps a stable leading byte order.

### docs/persistence-catalog.zh.md
- **Purpose:** the Chinese half of the generated catalog of every persisted Session event, its source declaration and its resolved type — the machine-checkable statement of what a session log may contain.
- **Key abstractions:** the **fingerprint table** (65 root types → category → SHA-256 → resolved-type anchor), the **event envelope** fence (`SessionEventType`, `SurfaceEventType`, `SurfaceOp`, `SessionEvent<T>`), per-namespace event fences, and one **resolved-type** section per digest.
- **Data flow:** the generator resolves each declared TypeScript type into a normalized node graph, hashes it, and writes both the prose (declared fences with source JSDoc) and the machine schema (`persistence-schema.json`). The digest covers referenced types; comments, source locations, aliases, erased brand marks and readonly markers do **not** affect it, while tuple order, property names, value types and optionality do (`docs/persistence-catalog.zh.md:18`).
- **Non-obvious design decisions:** the catalog is split into **surface** events (produce model history) and **log-only** events (durable, replayable, never in the model transcript) (`docs/persistence-catalog.zh.md:14`). `SessionEvent` is a proper discriminated union over `type`, and `surfaceOp`/`sourceEventSeqs` are *conditional* — the type system forbids a non-surface event from carrying them (`docs/persistence-catalog.zh.md:158-161`).
- **Edge cases / failure handling:** the `ignorable?: true` marker defaults to **required**: a reader that meets an unrecognized type *without* the marker MUST refuse to reconstruct the session rather than silently dropping the event, because a forgotten marker over-refuses (an inconvenience) rather than resuming a gutted session (`docs/persistence-catalog.zh.md:149-156`).
- **Surprising:** the **shadow-price protocol**. A surface `replace` event is priced by the metering event immediately before it (`compaction/summary` for a summarizing compaction, `compaction/prune` for a prune), which states the heuristic token price of the exact replaced range so a pure consumer can subtract it *without retaining per-node prices*; the replacement MUST be appended synchronously right after (`docs/persistence-catalog.zh.md:391-399`). The adjacency between `compaction/summary` and the `user/message` that shadows the compacted range is contractual, not incidental (`docs/persistence-catalog.zh.md:432-440`).

### docs/persistence-schema.json
- **Purpose:** the machine-readable companion to the persistence catalog — the normalized schema graph the SHA-256 digests are computed over.
- **Key abstractions:** `formatVersion: 2`; `roots[]` (65 entries: 2 `header`, 1 `envelope`, 62 `event`) each with `key`, `kind`, `digest` and a `schema` node graph; `types[]` (614 entries) each with `digest`, `names[]` and `sources[]`.
- **Data flow:** the generator emits a node graph per root — nodes of `kind: object` (with `properties[]` of name/type/optional and an `indices[]` for tuples), `kind: primitive` (string/number/boolean) and `kind: literal` — and a flat table of every reachable type keyed by digest, with the source file and line that declared it.
- **Non-obvious design decisions:** the graph is *normalised* rather than a literal JSON Schema, so the digest is over a canonical form; a root's digest covers the types it references, which is why a change in a leaf type moves the root's fingerprint (`docs/persistence-catalog.zh.md:18`).
- **Edge cases / failure handling:** many `types[]` entries carry an empty `names[]` and `sources[]` — anonymous or transitively-reached types that are structurally significant (their digest still changes) but have no declaration site to point at.
- **Surprising:** the file is 636 KB / 26,177 lines but contains only three top-level keys; almost all of it is the node-graph expansion of the 65 roots plus the 614-entry digest table.

### docs/session-format-status.md
- **Purpose:** to distinguish the *checkout writer*, the *accepted compatibility baseline* and the *latest published* Session format — three different numbers that are easy to conflate.
- **Key abstractions:** `SESSION_FORMAT_VERSION` (the only hand-maintained writer number in code), the `session-format-finalization` record (`latestFinalizedVersion: 4`), and the `session-format-release` record (`latestReleasedVersion: 4`, `evidenceTag: dsh-v0.2.0-rc.2`).
- **Data flow:** the catalog generator derives codec ordering and checks that adjacent migrations reach the writer version; a doc-standard test checks record structure, bilingual equality, evidence-tag/writer-path consistency, and that the documented release does not exceed the checkout writer.
- **Non-obvious design decisions:** "A package version, codec export name, fixture filename, or projection-cache version is not the writer authority" (`docs/session-format-status.md:20`). Finalization does **not** freeze every future V4 addition and does not assert publication; a schema change may stay V4 when the reader-compatibility rules are satisfied and a review is recorded (`docs/session-format-status.md:35`).
- **Edge cases / failure handling:** an alpha, beta or release-candidate publication still establishes released Session-format obligations — "GitHub's prerelease flag does not make persisted user data disposable", and a missing release record is not evidence of non-publication (`docs/session-format-status.md:24`).
- **Surprising:** the release record is **never lowered on the development trunk**, and the release *status* is a *comparison* rather than a boolean: equal means shipped, greater means not yet recorded, lower means an older writer (`docs/session-format-status.md:22`, `:54`).

### docs/testing.md
- **Purpose:** the repository's test policy, tier by tier, and the rules that keep a green suite meaningful.
- **Key abstractions:** eight tiers — unit, coverage gate, real-API e2e, owner-local expected output, performance benchmarks, snapshot, Web browser snapshot — plus the rules "prefer the real implementation over a mock", "verify the world, not the self-report", and "test the real entry path".
- **Data flow:** unit (`pnpm run test`) runs package/example specs plus `scripts/**/*.spec.ts`; coverage is per-file 100% on `packages/*/*/src`; snapshots replay a *recorded* session's highest generation as both input and expected output; the Web lane compares `snapshots/web/` and `apps/web/tests/expected/` in Chromium and the model/reasoning picker in WebKit.
- **Non-obvious design decisions:** the coverage gate's per-file 100% is stated as necessary but never sufficient — "it proves lines *ran*, not that the feature works as shipped" — and an uncovered line is treated as *dead code to delete*, not a test to bolt on (`docs/testing.md:10`). The with-key policy is an explicit budget statement: "We are DeepSeek — do not ration real-API tests. A no-key test proves plumbing; only a with-key run proves the agent works against a real model", and self-skip "is not a cost signal" (`docs/testing.md:25`).
- **Edge cases / failure handling:** `packages/shell/pwsh-local/src` needs a real `pwsh`, so its suites self-skip and `vitest.config.ts` exempts the file on pwsh-less hosts while CI ships pwsh and enforces the full bar (`docs/testing.md:10`). Forked workers share one host and one volume — only the *process* is isolated, so ports, predictable paths and inherited children are not, and a spec that passes only alone has a test defect, not an unstable runner (`docs/testing.md:21`).
- **Surprising:** two rules that read like platitudes are actually gates. "A guard only guards if the regression fails it" — for a plugin without `inject`, a Loader smoke stays green when a default export replaces the required named exports, so the test must add `expect('default' in mod).toBe(false)` plus an `unwrapExports` round-trip *and prove it* by introducing the regression, watching red, and reverting (`docs/testing.md:40`). And test resolution is **source-plane only**: bare workspace imports resolve to `src`, never through package `exports` to a built `lib/`, because a stale artifact there loads a second copy of module singletons (`docs/testing.md:45`).

### docs/postmortem/README.md
- **Purpose:** defines what a post-mortem is and is not, and the bar for writing one.
- **Key abstractions:** the *post-mortem* (a backward-looking failure record) versus the *Agent Note* (a deliberate design decision or a proposal); the three admission criteria; the mandatory Executive summary.
- **Data flow:** every post-mortem opens with a thirty-second Executive summary, then Summary / Timeline / Root cause / Guardrails; the guardrails (tests, AGENTS.md rules, ADRs) must be *linked* so the write-up is auditable.
- **Non-obvious design decisions:** the admission criteria are explicit — **subtle** (the mechanism is non-obvious and a careful engineer would re-derive it the hard way), **systemic** (the escape was a gap in tests/tooling/conventions, not a one-off typo), and **costly to rediscover** (`docs/postmortem/README.md:9`).
- **Edge cases / failure handling:** a post-mortem is written when a bug reaches a place it shouldn't have — a real user, a merged PR, a release. The interesting part is "why our process let it through", not the one-line fix.
- **Surprising:** the rule is written as a *cost* test, not a severity test: a bug that was easy to find and cheap to fix does not warrant one, so the corpus stays small and every entry is worth reading.

### docs/postmortem/0001-acp-default-export-drops-inject.md
- **Purpose:** explain why the ACP server (`dsh --profile acp`) crashed on connect with `cannot get property "agents" without inject` despite 178 green unit tests and 100% line coverage.
- **Key abstractions:** the Cordis **namespace plugin** form (`name`/`inject`/`Config`/`apply`), `Loader.unwrapExports`, the **fiber tree** and its ancestor-only service walk, and the **traceable shadow** created by `createShadowMethod`.
- **Data flow:** `Loader.unwrapExports` does `exports = exports.default ?? exports` — with a stray `export default apply` the module namespace is thrown away, the fiber is built with an **empty inject**, `apply` runs with no services, and the first line `const agents = ctx.agents` walks ROOT → Include → Loader → ROOT, finds nothing, and throws at *load* time. After that fix, `session/load` still threw on `sessionPersistence`: `AgentLoop.resume` read `this.ctx.sessionPersistence` through a shadow whose fiber walk is ancestor-only, and the service lives on a *sibling* branch.
- **Non-obvious design decisions:** the two bugs share one error string but are genuinely different mechanisms — the first is a one-line export mistake, the second is the shadow walk. The fix for the second is to read the optional service with `ctx.get('sessionPersistence')`, the **topology-independent** lookup that still preserves active-state checks (`docs/postmortem/0001-acp-default-export-drops-inject.md:111`). The investigation falsified its own elegant theory by instrumenting the fiber walk in vendored `reflect.ts` and running the real subprocess: the throw was at `apply()` line 179, on the ROOT fiber, with no shadow (`docs/postmortem/0001-acp-default-export-drops-inject.md:23`).
- **Edge cases / failure handling:** the in-memory harness missed bug #2 because a top-level test takes the `!ctx.fiber.runtime` early bypass (`ctx.reflect.get(prop, false)`), which is a direct global-store lookup ignoring fiber topology entirely. The key-gated e2e that *did* drive `session/new` only "passed" locally because a **stale built `lib/`** happened to satisfy module resolution (`docs/postmortem/0001-acp-default-export-drops-inject.md:96`).
- **Surprising:** "100% line coverage was satisfied the whole time. Coverage proves lines *ran*; it says nothing about whether the feature works *the way it ships*" (`docs/postmortem/0001-acp-default-export-drops-inject.md:98`). The durable guardrail is a **keyless** e2e over real stdio that boots the profile through the real Loader and asserts `session/new` resolves — verified to fail when `export default apply` is restored — plus `TSX_TSCONFIG_PATH` in the spawn so tsx resolves the repo tsconfig regardless of cwd and the test runs *source*, not a possibly-stale build.

### docs/postmortem/0002-js-expression-disabled-filesystem-tools.md
- **Purpose:** explain why the filesystem snapshot tools were permanently disabled while every check stayed green.
- **Key abstractions:** the Cordis **Include `!!js` expression tag**, `Entry._resolveConfig()` (which interpolates `entry.options.config`) versus `Entry.disabled` (which tests `entry.options.disabled` *without* interpolation), and the snapshot **header pin** mechanism.
- **Data flow:** the ACP composition put the filesystem plugins in the default `cordis.yml` with `disabled: !!js ...`; Include parsed each `!!js` scalar into an **expression object**, which is *truthy*; the Loader consumed the entry metadata directly, so every filesystem fiber stayed absent. Seven filesystem scenarios and the mixed workspace-edit scenario then called tools that were not in the registry, producing `ToolNotFoundError` with code `UNKNOWN_TOOL` and generic failed tool cards on stdout.
- **Non-obvious design decisions:** the fix is NOT to interpolate `disabled` — "permission presets update bash sandbox and approval state at runtime, but cannot mount, unmount, or confine the filesystem stack", so a naive interpolation fix would have granted the confined default unintended filesystem access (`docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:21`). Instead the filesystem scenarios boot a **separate explicit full-access overlay** (`fs.cordis.yml`) with its own replay config and request-header class.
- **Edge cases / failure handling:** the YAML tag was syntactically valid, so loading produced **no diagnostic at all** — the failure mode was silence, not an error. The snapshot suite passed because the framework treats any deterministic transcript as valid behaviour, and the refresh rewrote the expected stdout and session logs *before* any semantic assertion rejected the missing tools; the filesystem scenarios also shared a header pin from the default composition, so the pin never proved their own tools were registered.
- **Surprising:** "A snapshot refresh is fixture production, not correctness review. Semantic impossibilities such as a missing registered tool need assertions independent of the expected output" (`docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:46`). The shipped guards are therefore *semantic*, not textual: `verify-cordis-config` rejects expression nodes in Loader entry metadata, and `dsh-session-snapshot` rejects structured `UNKNOWN_TOOL` results in fresh runs and in committed fixtures.

### docs/postmortem/0003-web-agent-gui-feedback-loop.md
- **Purpose:** explain how a Web agent validated a *replacement* server instead of the GUI that was hosting its session.
- **Key abstractions:** the **canonical GUI URL** and **runtime mode** (production refresh vs development HMR) as model-visible facts; `window.__DSH_BOOT__` (injected only by the full host); managed background-process lifecycles.
- **Data flow:** the session ran in the GUI on port 3081 with an empty `test/` workspace. The agent edited the theme, delegated acceptance to the user, launched bare Vite on 5173 and saw HTTP 200, declared success — while the browser threw `client-modules: window.__DSH_BOOT__ is missing or not an object` and rendered a white page. It then rebuilt the shell, launched an unmanaged `dsh web` on 3334 via shell `&`, verified *that* returned 200 with a boot manifest, and never probed 3081.
- **Non-obvious design decisions:** the guardrail is to make the runtime's identity a *fact the model can read* — the Web launcher publishes the canonical loopback URL in the logged `app:web-surface` prompt section and in the managed `$DSH_WEB_URL` environment variable (`docs/postmortem/0003-web-agent-gui-feedback-loop.md:42`). `apps/web`'s standalone Vite serve mode is **rejected during configuration**, and its subprocess test instruments `Server.listen()` so a transient bind cannot pass unnoticed.
- **Edge cases / failure handling:** the first regression test repeated the mistake in another form — a *timeout* killed Vite and satisfied a nonzero-exit assertion; live reproduction exposed the false positive. Background semantics were bypassed with shell `&`, so job identity, completion notices, collection and cleanup did not apply and the redundant server outlived the turn.
- **Surprising:** the evidence discipline is the transferable part — the write-up cites **exact session-log sequence numbers** (30939, 31865, 34309, 34441, 34681) and follows the persisted events "rather than reconstructing intent from the later report" (`docs/postmortem/0003-web-agent-gui-feedback-loop.md:17`). And the lesson is a distinction, not a slogan: "HTTP readiness, build success, and a boot manifest are different facts. Acceptance names the exact origin and externally observes the requested change there" (`docs/postmortem/0003-web-agent-gui-feedback-loop.md:51`).

### docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md
- **Purpose:** explain why a benign Landlock notice made ordinary ripgrep no-match results surface as `SANDBOX_UNAVAILABLE`.
- **Key abstractions:** the **native launcher contract** (exit 125 + a fatal `landlock-run:` line for launcher failure; the *exact* informational line `landlock-run: partial enforcement (older Landlock ABI)` for a partially-enforcing kernel), and `RunnerFailureRule`.
- **Data flow:** the sandbox provider reduced the contract to a bag of substrings (`runnerFailureSignatures: ['landlock-run: ']`); the bash consumer joined that prefix with *any* nonzero exit and reported stderr's first line. The child's status was therefore attached to the launcher's informational line — `false`, ripgrep's no-match exit 1, invalid-pattern exit 2, even a child-selected exit 125.
- **Non-obvious design decisions:** the *type* was the defect. The public sandbox result could express only substrings; it could not say "Landlock failure requires exit 125", "the evidence must be within one fatal line", or "one exact line under the same prefix is informational". `RunnerFailureRule` now carries optional allowed exit codes, case-insensitive **per-line** fatal signatures, and case-insensitive **exact** informational-line exclusions (`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:43`).
- **Edge cases / failure handling:** filesystem search added a *second* attribution error — the then-bash-backed `runRipgrep()` caught every rejected bash run and replaced it with a generic `SEARCH_FAILED`, destroying the structured `SandboxUnavailableError`. The fix moves ripgrep to packaged binary through `ctx.subprocess`, outside the sandboxed bash seam entirely.
- **Surprising:** two lessons generalize past sandboxes. "Process attribution requires a conjunction of independent evidence; a shared prefix is not a protocol" (`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:52`) — and the write-up is honest that stderr remains an *in-band* attribution channel, so a confined child can still deliberately reproduce a gated fatal line: the tighter conjunction prevents the accidental collision but does not authenticate the writer, and an out-of-band status protocol is named as separate hardening rather than a fix. Second: "An adapter must preserve structured failures owned by the seam below it instead of replacing them with its own nearest generic category" (`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:54`).

### docs/rescope.md
- **Purpose:** the name mapping for the vendored Cordis stack — upstream name → published name → upstream version → role.
- **Key abstractions:** the nine-row mapping table (`vendor/cordis/` → `@deepseek-ai/cordis`, and the cosmokit / schemastery / plugin-loader / plugin-include / plugin-group / plugin-timer / plugin-hmr / plugin-logger-console siblings), and the *explicit non-touch list*.
- **Data flow:** `scripts/rescope-vendor.ts` owns the mapping and performs the rename; `pnpm run rescope-vendor` reports, `--apply` rewrites every reference, `:check` asserts the post-state in the hygiene gate, and `--apply --reverse` reverts (`docs/rescope.md:44-51`).
- **Non-obvious design decisions:** the rename exists because every harness package declares the framework as a *peer dependency* — publishing the harness publishes this layer with it, and under the upstream names that publication would squat them on the registry. Subpath exports keep their path (`@cordisjs/plugin-loader/repository` → `@deepseek-ai/cordis-plugin-loader/repository`).
- **Edge cases / failure handling:** the *non-touch* list is the interesting half — directory names, upstream source versions, dependency ranges, the Loader's `cordis:` builtin prefix, the `cordis.yml` family, harness packages whose own names contain the word, and upstream runtime identifiers such as `Symbol.for('schemastery')` are all preserved. Prose *outside* `docs/` keeps the names it was written with.
- **Surprising:** the vendored `package.json`'s own `version` field is the *harness's released manifest version* (bumped by `pnpm run release:vendor`), while the table records the *upstream* version of the pinned snapshot — two different versions in two different places, deliberately.

### docs/ui-radius.md
- **Purpose:** a single radius scale for DSH Web and Desktop, selected by component *role* then *size*, with rules for nested geometry, hover fills and settings-card materials.
- **Key abstractions:** the six-band scale — R4 (`--dsw-radius-xs`, below H20) / R8 (sm, H20–28) / R12 (md, H32–40) / R16 (lg) / R20 (xl, independent content cards) / R28 (panel, enclosing surfaces) (`docs/ui-radius.md:30-37`); the three *nested-geometry arrangements*; the circle/capsule exception.
- **Data flow:** a component picks a role, picks a size variant, and consumes the named token. `H` is the designed outer height including borders; `R` is the CSS `border-radius` before the browser clamps overlapping corners.
- **Non-obvious design decisions:** the radius is chosen by *role*, not by size alone — "A taller card remains a card: do not promote it to R28 merely because it exceeds a button's height" (`docs/ui-radius.md:39`). Nested radii use a *nominal* subtraction, and the document says so: "Equal exponents do not make them exact offset curves, so their diagonal gap may differ from the side inset" (`docs/ui-radius.md:73`).
- **Edge cases / failure handling:** `corner-shape` is **not inherited** — the theme applies it to elements *and* their `::before`/`::after`, so an avatar's `img` needs an explicit `corner-shape: round` or must inherit from a circular container (`docs/ui-radius.md:52-56`). Every full-round declaration (`50%`, `100%`, pill) must be paired with `corner-shape: round` in the same rule.
- **Surprising:** the *split guide card* pattern — put the shared radius and `overflow: hidden` on the **outer** card and `border-radius: 0` on the flush inner buttons, so both hover fills clip to one contour and no crescent appears between fill and border; the dropdown menu must stay *outside* the clipped subtree via the existing portal, and an external focus ring must not be clipped away (`docs/ui-radius.md:79-91`). The verification section is unusually honest about what a guard cannot do: "The radius guard rejects off-scale literals and unknown tokens; it cannot determine whether a valid token is appropriate for a component or whether two rendered contours align. Confirm those visually." (`docs/ui-radius.md:116`).

### docs/web-styling.md
- **Purpose:** styling *ownership* and component rules for the browser client packages.
- **Key abstractions:** `ui-theme` (owns `--dsw-*` static scale, semantic aliases, typography, motion, gradients, shadows, scrollbars, light/dark), `ui-layout` (applies the resolved theme snapshot), `ui-primitives` (the only cross-feature control channel), the **elevation** material, and the **menu surface** material.

- **Surprising:** `orderId` relaxing from UUID to arbitrary string is a *widening* of an identifier's contract; the guide keeps the same advice for acknowledging — "Keep `orderId` unchanged when acknowledging a notification" — so the value is an opaque handle, not a parsed one.

## Ideas worth stealing

- **A guard that cannot fail the regression is not a guard — prove it fails.** `docs/testing.md:40` — the rule is "A guard only guards if the regression fails it", and the prescription is concrete: for a plugin without `inject`, add `expect('default' in mod).toBe(false)` plus an `unwrapExports` round-trip, then *introduce the regression, watch red, revert*. This is the single most transferable practice in the shard for August: every static gate should have a documented, executed "red" proof, otherwise it is decoration.

- **An "empty catalog" is a distinct, quiet answer — reserve it for "not configured yet", never for "misconfigured".** `docs/upgrade-guide/v0.2.1-alpha.1/deepseek-model-discovery/guide.md:12` and `docs/upgrade-guide/v0.2.1-alpha.2/pi-ai-model-discovery/guide.md:12` — a route whose credential is missing returns an empty model list (hiding the group) while a *malformed* credential still fails discovery loudly, and a saved selection absent from the catalog shows "Select model" **without rewriting the stored value**. August's provider/model picker should adopt the same three-way split: absent → empty + quiet, wrong → error, temporarily unavailable → keep the stored selection.

- **The "shadow price" protocol: price a replacement in the event immediately before it, so a consumer can subtract cost without retaining per-node prices.** `docs/persistence-catalog.zh.md:391-399` — a surface `replace` event is priced by the metering event directly before it (`compaction/summary` for a summarizing compaction, `compaction/prune` for a prune), and the replacement MUST be appended synchronously right after. August's compaction path could use the same trick: emit the shadowed range's token count once, adjacent to the replacement, and every consumer can compute "tokens freed" without keeping a per-message ledger.

- **An unrecognized event type defaults to REQUIRED, not ignorable — over-refuse rather than resume a gutted session.** `docs/persistence-catalog.zh.md:149-156` — the `ignorable?: true` marker is opt-in; a reader meeting an unknown type without it MUST refuse to reconstruct the session. The stated reason is asymmetric cost: "defaulting to required means a forgotten marker over-refuses (an inconvenience) rather than silently resuming a gutted session." This is the right default for any append-only log August persists.

- **Tool schemas that teach a stable argument order are doing prompt-prefix stabilisation.** `docs/tool-catalog.md:654` (bash: "Provide `description` before `command`"), `docs/tool-catalog.md:1096` (write: "Provide `file_path` before `content`"), `docs/tool-catalog.md:1011` (edit: "Provide `file_path` before `old_string` and `new_string`") — the argument order is pinned so the serialized tool-call prefix stays byte-stable, which is exactly what a provider's prefix cache needs. Cheap, and invisible until you notice it.

- **A structured failure owned by a lower seam must survive the adapter above it.** `docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:54` — the bash-backed search caught every rejected run and replaced a structured `SandboxUnavailableError` with a generic `SEARCH_FAILED`; the fix moved ripgrep to a packaged binary through `ctx.subprocess`, outside the sandboxed bash seam. August should mark its error classes as *owned by the layer that raises them* and make the layer above re-raise rather than translate.

- **Attribution needs a CONJUNCTION of evidence; a shared prefix is not a protocol.** `docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md:52` — the fix was a rule type carrying allowed exit codes, per-line fatal signatures and *exact* informational-line exclusions, not a longer string match. The same shape applies to August's marker tables: the pattern in your own AGENTS.md about a "400 marker" and the receipt vocabulary is the identical failure class.

- **Acceptance must name the exact origin and observe the world externally — HTTP 200, a successful build and a boot manifest are three different facts.** `docs/postmortem/0003-web-agent-gui-feedback-loop.md:51` — the Web agent declared success on a bare-Vite HTTP 200 while the browser showed a white screen, then validated a *replacement* server while the original page had already picked up the rebuilt artifacts. August's own rule ("verify production refresh and development HMR against external state") is the same idea; the postmortem shows the failure mode concretely and, valuably, cites exact session-log sequence numbers as the evidence trail.

- **A snapshot refresh is fixture production, not correctness review.** `docs/postmortem/0002-js-expression-disabled-filesystem-tools.md:46` — the filesystem scenarios passed because the refresh rewrote the expected stdout and session logs before any semantic assertion rejected the missing tools, and the shared header pin never proved *their* tools were registered. The shipped guards are semantic, not textual: reject `UNKNOWN_TOOL` results in fresh runs and committed fixtures. August's snapshot/eval pipeline needs the same "semantic assertion independent of the expected output" rule, or a refresh will happily certify a regression.

- **Do not ration real-API tests; a keyless test proves plumbing only.** `docs/testing.md:25` — "We are DeepSeek — do not ration real-API tests… Highest-value are smoke tests that boot a shipped `dsh` profile, send one prompt, and check the world — they catch the 'green unit tests, broken product' class that mocks cannot." And self-skip is explicitly "not a cost signal", so a missing key is not a licence to let the suite go quiet.

- **Prefer the real implementation; mock only the expensive or nondeterministic boundary.** `docs/testing.md:29` — "A hand-rolled stand-in proves the bridge moves bytes, not that the shipping tool behaves as asserted", and the concrete pattern is `makeBridgeHarness()`: the real loop, session store, tool registry and JSONL persistence behind a scripted `MockAdapter` as the *only* mock. August's bridge and tool tests should adopt exactly this seam.

- **Verify the world, not the self-report.** `docs/testing.md:33-35` — "an e2e assertion re-runs the command or re-reads the file externally; a keyword probe on the agent's own output lets a cheating agent pass", plus "Assert untouched files are byte-identical" and resource ownership in `afterEach` even on failure/retry/timeout.

- **A delegation id must be unique across the whole runtime, not per parent.** `docs/upgrade-guide/v0.2.1-alpha.1/subagent-activations/guide.md:55` — "each returned `SubagentRun.id` must be unique across parents, providers, and local Sessions in the runtime. Generate a fresh id for each execution instead of using a parent-local counter." A per-parent counter is unique only within the parent and collides in any runtime-wide `list_agents` view; a uuid suffix (as the job registry now uses, `docs/upgrade-guide/v0.2.1-alpha.1/job-id-identity/guide.md:12`) is the cheap fix.

- **Cancellation ownership transfers from the signal to the receipt.** `docs/upgrade-guide/v0.2.1-alpha.1/subagent-activations/guide.md:51` — "The startup signal stops owning cancellation after publication: retain the receipt and call `dispose()` to cancel that exact activation." Cleanup failures are reported by `dispose()` *separately* from the captured result, so a failed cleanup never rewrites the answer, and `stopReason` must be inspected before treating a result as success.

- **A send is not a delivery and not a completion — say what the acknowledgement does not mean.** `docs/upgrade-guide/v0.2.1-alpha.1/team-direct-inbox/guide.md:12` — `send_message` returns `{ "sent": true }` and the guide spells out the three things it does *not* mean: model processing, a synchronous storage flush, and resend de-duplication. August's inter-agent messaging should return an equally minimal receipt *and* document its limits.

- **Refuse a wildcard bind at load, and assert trust per authority rather than per address.** `docs/upgrade-guide/v0.2.1-alpha.1/web-listener-trust-config/guide.md:14` — `0.0.0.0` and `::` are rejected because "binding every interface exposes the port to the network"; the bind IP itself is accepted with no `--trusted-host` entry, while a proxy or DNS authority still needs one.

- **One policy, one enforcement point — do not add a per-runtime sandbox setting.** `docs/upgrade-guide/v0.2.1-alpha.1/python-ptc-sandbox/guide.md:19` — "Do not add a separate Python-only sandbox setting", and `sandbox-unavailable` must be inspected *separately* from a denied file operation because they need different repairs. August's code-mode / tool-execution paths should share the one resolved policy.

- **Context providers are re-evaluated at request admission, and the refresh must not re-open the prompt.** `docs/upgrade-guide/v0.2.1-alpha.1/working-directory/guide.md:25` — dynamic context providers are evaluated again at request admission, after pre-step listeners and route preparation; the admission refresh replaces a provider's cached text while *preserving* assembly-only context and the accepted system prompt, tool schemas and variables. This is the mechanism that keeps a live context (working directory, memory tail, clock) correct without a per-step full rebuild.

- **Make the hidden runtime facts model-visible, not tribal knowledge.** `docs/postmortem/0003-web-agent-gui-feedback-loop.md:42` — the Web launcher publishes the canonical loopback URL in the logged `app:web-surface` prompt section and in the managed `$DSH_WEB_URL` environment variable. August's equivalent (the current URL, the runtime mode, whether the watcher is actually running) is exactly the same class of hidden prerequisite, and the postmortem shows the cost of leaving it hidden.

- **A generated catalog that boots the real thing, plus a completeness guard, is worth more than a hand-written one.** `docs/tool-catalog.md:8` — the generator boots each tool plugin on a real context and reads `ctx.tools.schemas()` (because a schema is not statically knowable), and a guard globs `packages/*/tool-*` and fails if any package is missing from the boot manifest, "so a new tool cannot be silently undocumented". The same shape applies to August's tool registry and its own prompt assembly.

- **Fingerprint the persisted types so a schema change is visible without reading the diff.** `docs/persistence-catalog.zh.md:18` — a normalized graph is hashed per type; comments, source locations, aliases, erased brand marks and readonly markers do not move the digest, while tuple order, property names, value types and optionality do. August can use the same canonicalization to make "did this change the wire format?" a one-line answer.

- **A tool-presentation mode is per preset, and the mixed mode is rejected rather than deprecated.** `docs/upgrade-guide/v0.2.1-alpha.1/tool-presentation-mode/guide.md:14` — `native` (direct function calls) or `ptc` (a `run_code` program calling a generated SDK), and different agent presets in the same application may use different modes. The parallel execution contract is spelled out at `docs/tool-catalog.md:23`: submission-ordered starts and policy, concurrency-safe bodies overlapping up to `maxParallelSubCalls`, each nested execution re-entering the complete guarded pipeline and linked to its outer result.

- **A parallel workflow must degrade per item, but fail loudly on misuse.** `docs/tool-catalog.md:2672-2677` — `pipeline` runs each item through the stages independently with no barrier (a stage throw drops that item to `null` and skips its remaining stages), `parallel` awaits all thunks (a throwing thunk resolves to `null`), and *misused hooks* (bad arguments, unknown options, unsupported schemas, tripped caps) end the whole script instead of producing `null`. The split between "an item failed" and "you used the API wrong" is the part worth copying.

- **Do not poll; the runtime tells you when a child finishes.** `docs/tool-catalog.md:2150` ("You will be notified when a subagent finishes; there is no need to keep checking its status") and `docs/tool-catalog.md:2543` ("Re-list after wakeup or timeout instead of polling") — August's delegation surface already says this in its own tool descriptions, and the catalog shows the convention is applied consistently across both the subagent and the team-leader tool families.

- **A stored credential must beat an exported variable, and the check must not print the value.** `docs/upgrade-guide/v0.2.1-alpha.2/stored-credentials-precedence/guide.md:12-14` — the stored `refs` entry now wins, the Models page can save a key while the name is exported, and the verification step is "Check names and presence without printing credential values".

- **Compatibility has one authority, and a malformed manifest fails closed.** `docs/upgrade-guide/v0.2.1-alpha.3/plugin-engines-dsh/guide.md:12` — a package's own `engines.dsh` range decides alone; the peer rule is only the fallback; a non-object `engines` makes the manifest unreadable and the package is **refused**; the refusal record's key is renamed `peers` → `requirements` because the constraint's *name* and its *source* are now decoupled. The "fail closed on an unreadable manifest" half is the part August's own plugin/marketplace loader should copy.
