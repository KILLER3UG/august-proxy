## Correction: the packaging wheel guard does not reach the threat it names

`2284ca81` added `.whl` / `venv` / `site-packages` to the payload guard, with a commit message saying
`wheels` is a staged payload root "so a wheel dropped there WOULD ship in the installer" and that the
guard now stops it. **Measured: it does not.**

`assertPayloadHasNoUserState` (`scripts/desktop-backend-payload.mjs:91-95`) walks exactly three roots —
`backend-py/app`, `backend-py/sidecar`, `skills`. `resources/wheels/` is not among them, and the comment
at `:86-88` says that is deliberate. Planting `probe_gpl_test-1.0-py3-none-any.whl` in
`resources/wheels/` and calling the assertion: **the build passes.**

Worse, making it reachable would break every build: `resources/wheels/` legitimately contains **60
wheels** — that tree *is* the offline-install mechanism. A blanket `.whl` refusal there is not a
license check, it is a build failure.

So:
- The rule still has real value in the three roots it does scan (a wheel or venv vendored into
  `skills/` or `backend-py/app` is caught, and `test:packaging` proves that by planting one).
- What actually keeps manimgx out of the installer is **architectural, not the guard**: provisioning
  writes to `<workspace>/.aug/kernel/venv`, and `resources/wheels/` is populated by `buildWheels()`
  from the backend's own dependency set. A per-user `pip install` never enters it.
- A guard that could check this would read `*.dist-info/METADATA` out of each wheel — a wheel is a zip —
  and compare licenses, not filenames. A name denylist would be a label check, which is the pattern
  this repo has already been burned by twice.

**My own earlier statement was wrong too**: on 2026-10-13 I said the guardrail was "real, not
theoretical, because `desktop-backend-payload.mjs:195` stages and hashes `wheels`". Line 195 is the
*hashing* walk, a different walk from the user-state scan. I conflated the two.

Left unfixed deliberately: a METADATA-reading license check is a new capability, not a bug fix, and the
threat needs a developer to add manimgx to the backend dependency set — which surfaces in
`pyproject.toml`/`uv.lock` in review. **Needs review:** add the METADATA check, or correct the commit
message and the plan's Stage 4 to say the control is architectural?

## The new spec failed on the second full run, and it was the app

`tool-rows.spec.ts:107` asserted the voice-command row names its command
(`“/compact” has no result card in this build.`). It passed when I ran the two affected
specs alone, and **failed under the full 6-worker suite** with the row reading
"This message refers to a voice command that is no longer installed." Not a flake — a real
readiness race that my own previous commit (`79b5362a`) had made user-visible by writing a
sentence that asserts removal.

The mechanism: `main.tsx:81` defers `import('./api/voice/builtins')` with
`requestIdleCallback(…, { timeout: 2000 })`, and `voiceCommandRegistry` is a plain array with
no subscribers. A transcript restored inside that idle window calls `getById()`, gets `null`,
renders the unknown branch — **and is never re-rendered by the later registration**. So a
legitimate `/compact` message can sit saying the command was uninstalled, permanently, on a
loaded machine. That is the exact defect class this plan is about, and I shipped a instance of
it twelve minutes before the test caught it.

Two changes, both needed:

- `MessageBubble.tsx` — the unknown branch no longer claims anything about installation; it
  states what is true whether or not the registry has loaded ("voice commands have no result
  card in this build"), and the comment records the deferral so nobody re-sharpens that
  sentence into a claim again.
- `DesignRoute.tsx` — the lab that renders the row now imports the built-ins itself, so the
  spec's precondition is explicit instead of racing boot order. A dev-only file; production
  keeps its idle deferral.

Full suite after: **18/18 twice in a row**, tsc clean, frontend 227/227 (`FE_EXIT=0`).

## Settings selects migrated to the app's own listbox — and the panel accepts no clicks offline

`GeneralSection.tsx` had four native `<select>` boxes (`:152, :179, :195, :205`) beside the app's
own `components/settings/SettingsSelect.tsx`, already used by `AuditTimeline`,
`ComputerAccessSettings` and `CustomIntegrationForm` — the primitive exists precisely because
Windows/WebView2 renders native `<option>` white-on-white. All four migrated; `inputClass` and the
now-unused `cn` import went with them, and the `data-testid="settings-live-html-preview"` was
dropped because **nothing consumes it** (grep: the only occurrence was the attribute itself).

Two sites needed more than a swap: they were wrapped in `<label>`, and a `<button>` is not a
labelable element, so keeping the label would have silently broken "click the text to open the
field". They are `<div>` + `aria-label` on the control now.

**Verified render, not interaction — and the reason is its own finding.** In Chromium on
`/settings` with `/api` mocked to 404: `native selects on page: 0`, and all four render as
`button[aria-haspopup="listbox"]` with the right accessible names. But no click lands — and the
control that proves it is not my change: a **pre-existing** rail button is blocked identically,
with `document.elementFromPoint` returning the panel's own `div.fixed.inset-0.z-50` wrapper in
both cases. So offline web mode can verify structure and computed style, never a click — which is
the real reason every behavioural check in this plan runs through a `/_design?lab=` mount. The
dropdown's open/select behaviour in the desktop app (where the backend is up) is **not
re-verified here**; it is the same primitive the other sections have been using.
